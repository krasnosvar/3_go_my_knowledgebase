# Protocol Buffers (Protobuf)

Protobuf — язык описания схемы данных и бинарный формат сериализации от Google. Это IDL (Interface Definition Language): вы описываете структуру сообщений в `.proto`, а компилятор `protoc` генерирует типизированный код для нужного языка. Protobuf — формат данных по умолчанию для gRPC, но применим и сам по себе.

## Схема сообщения

Листинги ниже — НЕ runnable, они иллюстрируют синтаксис `.proto` (proto3):

```proto
syntax = "proto3";

message User {
  int64  id     = 1;   // = 1 — это НОМЕР ПОЛЯ (field tag), а не значение
  string name   = 2;
  string email  = 3;
  repeated string roles = 4;   // repeated = список/массив
}
```

Ключевое: у каждого поля есть **номер (field number)** — именно он, а не имя поля, едет в бинарном представлении. Имена нужны только людям и коду; на проводе поле идентифицируется числом.

Базовые типы: `int32/int64`, `uint32/uint64`, `sint*` (для отрицательных, zig-zag), `bool`, `string`, `bytes`, `double`, `float`, вложенные `message`, `enum`, `map<K,V>`, `repeated` (списки).

## Кодирование (wire format)

Protobuf кодирует сообщение как последовательность пар «ключ-значение» в формате TLV (tag-length-value):

```
Каждое поле:  [ключ][значение]
ключ = (field_number << 3) | wire_type
```

- **wire_type** говорит, как читать значение: varint (0), 64-бит (1), length-delimited для строк/bytes/вложенных сообщений (2), 32-бит (5).
- **varint** — переменная длина: маленькие числа занимают 1 байт, большие — больше. Поэтому важно давать часто используемым полям номера 1–15 (их ключ помещается в 1 байт).

Что это даёт по сравнению с JSON:

- Компактность: нет имён полей и кавычек в данных, числа — varint.
- Скорость парсинга: бинарь читается быстрее текста.
- Цена: данные **не самоописательны** — без `.proto`-схемы байты не расшифровать (в отличие от читаемого глазами JSON).

```
JSON:      {"id":42,"name":"Alice"}          ~24 байта, читается глазами
Protobuf:  08 2A 12 05 41 6C 69 63 65         ~9 байт, нужна схема
```

## Эволюция сообщений и обратная совместимость

Главная сила Protobuf — можно менять схему, не ломая старых клиентов, потому что поля идентифицируются номерами, а неизвестные поля просто **игнорируются** при чтении.

Правила совместимости:

- **Никогда не меняй номер существующего поля** — это ломает всех.
- **Добавляй новые поля только с новыми номерами.** Старый код их не знает и пропустит; новый прочитает.
- В proto3 у скалярных полей нет «отсутствия»: незаполненное поле читается как значение по умолчанию (0, "", false). Это делает добавление поля безопасным.
- **Не переиспользуй удалённые номера.** Если поле удалили — зарезервируй его номер и имя, чтобы никто не занял их случайно:

```proto
message User {
  reserved 3, 5 to 7;          // номера больше нельзя использовать
  reserved "email", "phone";   // имена больше нельзя использовать
  int64  id   = 1;
  string name = 2;
}
```

- Переименование поля безопасно на проводе (номер тот же), но ломает код, который читал старое имя.
- Совместимые смены типа ограничены (например, `int32`/`int64`/`bool` совместимы между собой как varint), но менять `int` на `string` нельзя.

Итого — совместимость держится на дисциплине: **номера полей неприкосновенны, добавляем только новое, удалённое резервируем.**

> ⚠️ Частый вопрос на собеседовании: почему в Protobuf важны номера полей, а не имена? Потому что на проводе поле кодируется номером; имена в бинарь не попадают. Смена номера ломает совместимость, а переименование — нет.

> ⚠️ Частый вопрос на собеседовании: как безопасно удалить поле? Удалить его использование и объявить `reserved` для его номера (и имени), чтобы номер никогда не занял другое поле.

> ⚠️ Частый вопрос на собеседовании: Protobuf vs JSON? Protobuf компактнее и быстрее, но требует схему и не читается глазами; JSON самоописателен и удобен для отладки/браузера, но многословнее.
