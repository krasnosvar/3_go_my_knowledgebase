# Как выбирать: REST vs gRPC vs GraphQL

Единственно правильного стиля нет — выбор диктуют потребитель API, требования к латентности и гибкости, и то, кто пишет клиента. Ниже — сравнение и решающие критерии.

## Сводная таблица

| Критерий              | REST                  | gRPC                        | GraphQL                       |
|-----------------------|-----------------------|-----------------------------|-------------------------------|
| Транспорт             | HTTP/1.1, HTTP/2      | HTTP/2                       | обычно HTTP/1.1 (`POST`)      |
| Формат данных         | JSON (текст)          | Protobuf (бинарь)           | JSON (текст)                  |
| Контракт/схема        | опционально (OpenAPI) | строгий (`.proto`)          | строгий (SDL)                 |
| Кто задаёт форму ответа | сервер (эндпоинт)   | сервер (метод)              | клиент (запрос)               |
| Стриминг              | ограниченно (SSE/WS)  | да (4 типа)                 | Subscription (поверх WS)      |
| Браузер нативно       | да                    | нет (нужен gRPC-Web)        | да                            |
| Читаемость/отладка    | высокая (`curl`)      | низкая (бинарь)             | средняя                       |
| Кэширование по HTTP   | простое (GET+ETag)    | нет из коробки              | сложно (один `POST`)          |

## Критерии выбора

**Внешние / публичные API, браузерные клиенты -> REST.**
Работает везде, читается человеком, легко кэшируется и документируется (OpenAPI), низкий порог входа для сторонних разработчиков. Дефолтный выбор, если сомневаетесь.

**Межсервисное взаимодействие внутри системы -> gRPC.**
Строгий контракт из `.proto`, компактный бинарный Protobuf, HTTP/2-мультиплексирование и низкая латентность, генерация стабов под любой язык, встроенный стриминг. Отладка сложнее и в браузере нативно не работает — но для внутренних сервисов это неважно.

**Гибкие клиенты с разными потребностями в данных -> GraphQL.**
Когда много разных фронтендов (веб, iOS, Android) хотят разные срезы одних данных, и REST начинает плодить эндпоинты либо страдать от over/under-fetching. Клиент сам берёт нужные поля одним запросом. Цена — сложность на сервере (N+1, ограничение сложности запросов, слабое HTTP-кэширование).

## Дерево решений

```
Клиент — браузер / сторонние разработчики?
  └─ да  -> нужен ли клиенту гибкий выбор полей из многих сущностей?
  │         ├─ да  -> GraphQL
  │         └─ нет -> REST
  └─ нет (внутренний сервис) -> нужны низкая латентность / стриминг / строгий контракт?
            ├─ да  -> gRPC
            └─ нет -> REST (проще отлаживать и хостить)
```

## Гибридные архитектуры

На практике стили сочетают:

- **REST/GraphQL наружу, gRPC внутрь.** API-gateway принимает REST или GraphQL от клиентов, а с бэкенд-сервисами общается по gRPC. Частый паттерн.
- **GraphQL как агрегатор** поверх нескольких REST/gRPC-сервисов (BFF — Backend For Frontend).
- **REST + вебхуки/SSE** там, где нужны серверные события, но не хочется тащить gRPC-стриминг.

Не выбирайте стиль «по моде» — начните с потребителя API и требований, а таблица выше подскажет остальное.

> ⚠️ Частый вопрос на собеседовании: что выбрать для публичного API — REST, gRPC или GraphQL? По умолчанию REST: универсален, кэшируется, читается человеком, работает в браузере. gRPC — для внутренних сервисов, GraphQL — для гибких клиентов с разными запросами.

> ⚠️ Частый вопрос на собеседовании: можно ли смешивать стили? Да, это норма: наружу REST/GraphQL через gateway, внутри между сервисами — gRPC.
