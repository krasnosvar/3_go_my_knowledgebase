# REST

REST (Representational State Transfer) — не протокол, а архитектурный стиль поверх HTTP. Сервис моделируется как набор **ресурсов**, к которым обращаются по URL, а действия над ними задаются **HTTP-методами**. Ответы обычно в JSON.

## Ресурсы и URL

Ресурс — это сущность (пользователь, заказ, товар). URL адресует ресурс, а не действие.

```
GET    /users            <- коллекция пользователей
GET    /users/42         <- конкретный пользователь
GET    /users/42/orders  <- вложенная коллекция (заказы пользователя 42)
```

Правила именования:

- Существительные, а не глаголы: `/users`, а не `/getUsers`.
- Коллекции во множественном числе: `/users`, `/orders`.
- Действие выражается методом (`GET`/`POST`/...), а не путём.
- Иерархия через вложенность: `/users/42/orders/7`.

## HTTP-методы и идемпотентность

| Метод   | Назначение                     | Безопасный (safe) | Идемпотентный |
|---------|--------------------------------|:-----------------:|:-------------:|
| GET     | получить ресурс                | да                | да            |
| POST    | создать / выполнить действие   | нет               | нет           |
| PUT     | заменить ресурс целиком        | нет               | да            |
| PATCH   | частично изменить ресурс       | нет               | нет*          |
| DELETE  | удалить ресурс                 | нет               | да            |
| HEAD    | как GET, но без тела ответа    | да                | да            |
| OPTIONS | узнать поддерживаемые методы   | да                | да            |

- **Безопасный (safe)** — не меняет состояние на сервере (только чтение).
- **Идемпотентный** — повторный одинаковый вызов приводит систему в то же состояние, что и один вызов. Это критично для **retry**: если ответ на PUT/DELETE потерялся в сети, клиент может безопасно повторить запрос.
- *PATCH в общем случае не идемпотентен (например, `увеличить на 1`), но может быть идемпотентным при определённом теле.

Почему POST не идемпотентен: два `POST /users` создадут двух пользователей. Именно поэтому «создание» через повтор опасно (см. `06_use_cases.md` и пример `03_idempotency`).

## Коды статусов

Клиент должен реагировать на **категорию** статуса (первая цифра), а не только на конкретный код.

| Диапазон | Категория     | Типичные коды                                             |
|----------|---------------|----------------------------------------------------------|
| 2xx      | Success       | 200 OK, 201 Created, 202 Accepted, 204 No Content        |
| 3xx      | Redirection   | 301 Moved Permanently, 304 Not Modified                  |
| 4xx      | Client Error  | 400, 401, 403, 404, 409 Conflict, 422, 429 Too Many Requests |
| 5xx      | Server Error  | 500, 502, 503, 504                                       |

Правильные коды для типичных операций:

- `GET /users/42` найден -> **200**; не найден -> **404**.
- `POST /users` создан -> **201** + заголовок `Location: /users/43`.
- `PUT /users/42` заменён -> **200** (или **204**, если тело не возвращаем).
- `DELETE /users/42` удалён -> **204** (тела нет).
- Невалидное тело -> **400**; конфликт (например, дубликат) -> **409**.

## Версионирование

API эволюционирует; ломающие изменения нельзя навязывать старым клиентам. Способы указать версию:

1. **В пути** (самый распространённый): `GET /v1/users`, `GET /v2/users`. Явно, легко кэшировать и роутить.
2. **В заголовке**: `Accept: application/vnd.example.v2+json`. Чище URL, но сложнее отлаживать.
3. **В query-параметре**: `GET /users?version=2`. Просто, но легко потерять при копировании ссылок.

Практика: пути версионируют мажорно (`/v1`, `/v2`), а неломающие изменения (новые опциональные поля) выкатывают без смены версии.

## Пагинация

Отдавать всю коллекцию одним ответом нельзя — это убивает и сервер, и клиента. Два основных подхода:

**Offset/limit** (offset-based):

```
GET /users?limit=20&offset=40   <- 20 записей начиная с 41-й
```

Просто и позволяет прыгать на произвольную страницу, но на больших offset БД тормозит (`OFFSET 100000`), а вставки/удаления сдвигают окно и дают дубли/пропуски.

**Cursor/keyset** (cursor-based):

```
GET /users?limit=20&after=eyJpZCI6NDB9   <- 20 записей после курсора
```

Курсор кодирует позицию последнего элемента (например, `id` или `created_at`). Стабильно при изменениях данных и быстро на любой глубине, но нельзя прыгнуть на произвольную страницу.

Ответ обычно несёт метаданные:

```json
{
  "items": [ /* ... */ ],
  "limit": 20,
  "offset": 40,
  "total": 137,
  "next": "/users?limit=20&offset=60"
}
```

Runnable-демо offset/limit — в примере `02_pagination`.

> ⚠️ Частый вопрос на собеседовании: чем PUT отличается от PATCH? PUT заменяет ресурс **целиком** (то, что не прислали, будет затёрто/сброшено) и идемпотентен. PATCH меняет **часть** полей и в общем случае не идемпотентен.

> ⚠️ Частый вопрос на собеседовании: почему POST не идемпотентен и как с этим жить при retry? Повтор POST создаёт дубликат. Решения: делать создание через PUT по известному ID либо использовать **Idempotency-Key** (см. пример `03_idempotency`).

> ⚠️ Частый вопрос на собеседовании: 401 vs 403? 401 — не аутентифицирован (неизвестно, кто ты). 403 — аутентифицирован, но нет прав.
