# GraphQL

GraphQL — язык запросов к API и среда его исполнения (Facebook). Ключевая идея: у сервиса **одна точка входа** (обычно `POST /graphql`), а клиент сам описывает, **какие именно поля** ему нужны. Сервер возвращает ровно эту форму данных. Это противоположность REST, где форму ответа диктует сервер, а под разные нужды заводят разные эндпоинты.

## Схема (SDL)

Контракт описывается типизированной схемой (Schema Definition Language). Листинги ниже — НЕ runnable, они иллюстрируют синтаксис:

```graphql
type User {
  id: ID!
  name: String!
  orders: [Order!]!
}

type Order {
  id: ID!
  total: Float!
}

type Query {
  user(id: ID!): User
  users: [User!]!
}

type Mutation {
  createUser(name: String!): User!
}
```

- `!` — обязательное (non-null) поле.
- `[Order!]!` — непустой список ненулевых `Order`.
- `Query` — корень для чтения, `Mutation` — для изменений.

## Query и Mutation

**Query** — чтение. Клиент указывает нужные поля, и только их:

```graphql
query {
  user(id: "42") {
    name
    orders { total }
  }
}
```

Ответ повторяет форму запроса:

```json
{ "data": { "user": { "name": "Alice", "orders": [ { "total": 19.9 } ] } } }
```

**Mutation** — изменение (создать/обновить/удалить). Даже мутация возвращает выбранные поля результата:

```graphql
mutation {
  createUser(name: "Bob") { id name }
}
```

Есть ещё `Subscription` для потоковых обновлений (обычно поверх WebSocket) — упоминаем для полноты.

## Over-fetching и under-fetching

Именно эти две проблемы REST решает GraphQL:

- **Over-fetching** — эндпоинт возвращает больше, чем нужно. `GET /users/42` отдаёт весь объект, а экрану нужно только имя. Лишние байты и работа сервера.
- **Under-fetching** — одного запроса мало, приходится делать несколько. Чтобы показать пользователя и его заказы, в REST это `GET /users/42` + `GET /users/42/orders` (проблема "N+1 запросов на клиенте").

GraphQL закрывает оба случая: клиент одним запросом берёт ровно нужные поля из нескольких связанных сущностей.

```
REST (under-fetching):        GraphQL (один запрос):
  GET /users/42                 query { user(id:42){
  GET /users/42/orders            name
  GET /orders/7/items             orders { items { name } }
  ...                           } }
```

## Проблема N+1 на сервере

GraphQL смещает сложность на сервер. Запрос списка пользователей с их заказами наивно превращается в **1 запрос за пользователями + N запросов за заказами каждого** — классическая проблема N+1 к БД.

```
users            -> 1 запрос
orders(user 1)   -> +1
orders(user 2)   -> +1
...
orders(user N)   -> +1     Итого: 1 + N запросов
```

Стандартное решение — **DataLoader**: батчинг и кэширование внутри одного GraphQL-запроса. Резолверы не ходят в БД по одному, а собирают ключи и делают один пакетный запрос (`WHERE user_id IN (...)`), сводя N+1 к 2 запросам.

Другие особенности, за которыми надо следить на сервере: сложно кэшировать на уровне HTTP (всё идёт через один `POST`), нужен контроль глубины/сложности запроса (иначе клиент может запросить дорогой глубоко вложенный граф).

> ⚠️ Частый вопрос на собеседовании: какие проблемы REST решает GraphQL? Over-fetching (лишние поля) и under-fetching (много запросов для связанных данных) — клиент запрашивает ровно нужное одним запросом.

> ⚠️ Частый вопрос на собеседовании: что такое проблема N+1 в GraphQL и как её решают? Наивные резолверы делают отдельный запрос к БД на каждый элемент списка (1 + N). Решение — DataLoader: батчинг запросов и кэш в пределах одного запроса.
