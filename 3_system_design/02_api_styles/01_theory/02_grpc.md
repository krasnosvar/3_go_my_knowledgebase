# gRPC

gRPC — фреймворк удалённого вызова процедур (RPC) от Google. Вместо «дёргать ресурсы по URL» (как REST) клиент **вызывает методы сервиса как обычные функции**, а фреймворк берёт на себя сериализацию, транспорт и генерацию кода. По умолчанию данные кодируются в Protobuf (см. `03_protobuf.md`), а транспорт — HTTP/2.

## RPC поверх HTTP/2

Контракт описывается в `.proto`-файле: сервис, его методы и типы сообщений (листинг ниже — НЕ runnable, приведён для иллюстрации схемы).

```proto
// user.proto
syntax = "proto3";

service UserService {
  rpc GetUser (GetUserRequest) returns (User);
  rpc ListUsers (ListUsersRequest) returns (stream User);
}

message GetUserRequest {
  int64 id = 1;
}

message User {
  int64 id = 1;
  string name = 2;
}
```

Почему именно HTTP/2 — он даёт то, что нужно RPC:

- **Мультиплексирование** — много параллельных вызовов по одному TCP-соединению без блокировки друг друга.
- **Бинарные фреймы** — компактно и быстро парсится.
- **Двунаправленные потоки (streams)** — основа для стриминга gRPC.
- **Сжатие заголовков (HPACK)** и переиспользование соединения.

Каждый RPC-вызов — это HTTP/2-поток; метаданные едут в заголовках, а Protobuf-payload — во фреймах DATA.

## Четыре типа вызовов

```
1) Unary (обычный запрос-ответ)
   client --- request ---> server
   client <-- response --- server

2) Server streaming (один запрос, поток ответов)
   client --- request ---> server
   client <-- resp #1 ----- server
   client <-- resp #2 ----- server
   client <-- resp #N ----- server

3) Client streaming (поток запросов, один ответ)
   client --- req #1 ----> server
   client --- req #2 ----> server
   client --- req #N ----> server
   client <-- response --- server

4) Bidirectional streaming (потоки в обе стороны)
   client <==== req/resp вперемешку ====> server
```

- **Unary** — 95% случаев: `GetUser(id) -> User`.
- **Server streaming** — сервер отдаёт много сообщений: лента событий, выгрузка большого списка порциями.
- **Client streaming** — клиент шлёт поток: загрузка файла чанками, батч телеметрии.
- **Bidirectional** — чат, live-обновления, интерактивные протоколы.

Стриминг возможен именно благодаря HTTP/2-потокам; в «голом» HTTP/1.1 такого из коробки нет.

## Генерация кода

Ключевая идея: **код клиента и сервера генерируется из `.proto`**, а не пишется руками.

```
user.proto ---> protoc (+ плагин protoc-gen-go, protoc-gen-go-grpc) --->
    user.pb.go       (типы сообщений: struct User, GetUserRequest, ...)
    user_grpc.pb.go  (интерфейс сервера + типизированный клиент-стаб)
```

Разработчик на сервере реализует сгенерированный интерфейс, а клиент просто зовёт `client.GetUser(ctx, &GetUserRequest{Id: 42})` — сериализация, отправка по HTTP/2 и десериализация ответа скрыты. Тот же `.proto` компилируется в стабы для Go, Java, Python и т.д. — контракт единый на все языки.

> Runnable-примера gRPC в этом разделе нет намеренно: нужны внешний компилятор `protoc` и пакеты `google.golang.org/grpc`, что выходит за рамки stdlib-only. Здесь — только теория и `.proto`-листинги.

## Где gRPC выигрывает

- **Межсервисное взаимодействие (microservices)** — строгий контракт, компактный бинарный формат, низкая задержка.
- **Высокие нагрузки / низкая латентность** — Protobuf компактнее и быстрее JSON, HTTP/2 мультиплексирует.
- **Стриминг** — потоковые сценарии из коробки (server/client/bidi).
- **Полиглот-окружение** — стабы генерируются под любой язык из одного контракта.
- **Строгая типизация и версионирование через схему** — контракт нельзя «случайно» нарушить.

Слабые стороны: не работает нативно в браузере без прослойки (gRPC-Web), человеку сложнее отлаживать бинарный трафик (в отличие от `curl` по REST), сложнее промежуточное кэширование.

> ⚠️ Частый вопрос на собеседовании: почему gRPC требует HTTP/2? Из-за мультиплексирования и двунаправленных потоков — без них не было бы клиент/серверного и bidi-стриминга и дешёвой параллельности вызовов по одному соединению.

> ⚠️ Частый вопрос на собеседовании: gRPC vs REST — где грань? Внешние публичные API и браузерные клиенты -> обычно REST/JSON; внутреннее межсервисное взаимодействие с жёстким контрактом и высокой нагрузкой -> gRPC.
