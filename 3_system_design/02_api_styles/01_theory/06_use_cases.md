# Практические применения и паттерны

Подтемы `01`–`05` разобрали стили API по отдельности. Здесь — как это выглядит на практике: типичные сценарии, correctness-паттерны и подводные камни, которые всплывают в проде и на собеседованиях.

## Типичные сценарии выбора

- **Мобильное приложение + разнородные экраны.** Много клиентов хотят разные срезы данных -> GraphQL (или REST c продуманными эндпоинтами и полем `fields=`).
- **Платёжный сервис зовёт сервис счетов.** Внутреннее взаимодействие, важна латентность и строгий контракт -> gRPC + Protobuf.
- **Открытый API для интеграторов.** Сторонние разработчики, нужен `curl`, документация, версии -> REST + OpenAPI.
- **Лента событий / чат / телеметрия потоком.** Стриминг -> gRPC (server/bidi streaming) либо SSE/WebSocket поверх REST.

## Паттерны корректности (независимо от стиля)

**Идемпотентность и retry.** Сеть теряет ответы; клиент повторяет запрос. Повторять безопасно только идемпотентные операции (GET/PUT/DELETE). Для не-идемпотентного создания (POST) применяют **Idempotency-Key**: клиент шлёт уникальный ключ, сервер запоминает результат и на повтор с тем же ключом возвращает тот же ответ, не создавая дубликат. Демонстрация — пример `03_idempotency`.

**Пагинация всех коллекций.** Никогда не отдавайте список без ограничения размера. offset/limit — для админок и произвольных страниц; cursor/keyset — для лент и больших наборов (см. `01_rest.md`, пример `02_pagination`).

**Таймауты и дедлайны.** Каждый вызов должен иметь таймаут, иначе один зависший upstream подвешивает всю цепочку. В gRPC/Go это `context` с дедлайном; в HTTP-клиенте — `http.Client{Timeout: ...}`.

**Правильные коды статусов.** Клиент строит логику retry/алертов на категориях: 4xx повторять бессмысленно (запрос кривой), 5xx и 429 — можно с backoff. Отдавать 200 с `{"error": ...}` внутри — антипаттерн для REST.

**Версионирование и эволюция контракта.** Добавляйте только опциональные/новые поля; ломающие изменения — через новую версию (`/v2`) в REST или новые номера полей в Protobuf. Никогда не переиспользуйте удалённые номера полей.

## Сравнение форматов на одном примере

Один и тот же ресурс `User{id:42, name:"Alice"}`:

```
REST/JSON:   GET /v1/users/42  ->  200 {"id":42,"name":"Alice"}
gRPC:        UserService.GetUser(GetUserRequest{id:42}) -> User (Protobuf-байты)
GraphQL:     POST /graphql  { user(id:42){ name } } -> {"data":{"user":{"name":"Alice"}}}
```

Одна сущность, три способа: URL+метод (REST), вызов метода (gRPC), запрос полей (GraphQL).

## Частые ошибки

- Глаголы в REST-URL (`/getUser`) вместо ресурсов + методов.
- Возврат 200 на ошибку — ломает retry/мониторинг у клиента.
- POST без защиты от повторов -> дубликаты при retry.
- Отсутствие пагинации -> тяжёлые ответы и OOM.
- Смена номера поля в Protobuf -> тихо сломанная совместимость.
- GraphQL без DataLoader и без лимита сложности -> N+1 и дорогие запросы кладут БД.
- gRPC наружу в браузер без gRPC-Web -> не работает.

> ⚠️ Частый вопрос на собеседовании: как сделать создание ресурса безопасным при повторах? Idempotency-Key (сервер дедуплицирует по ключу) либо создание через PUT по заранее известному ID (идемпотентно).

> ⚠️ Частый вопрос на собеседовании: почему нельзя возвращать ошибку с кодом 200? Клиенты и промежуточные узлы (LB, кэши, ретраеры) ориентируются на HTTP-статус; 200 c ошибкой в теле ломает retry-логику, кэширование и мониторинг.
