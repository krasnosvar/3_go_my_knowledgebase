# The Twelve-Factor App

**12-factor** — методология построения приложений «как сервис» (SaaS), готовых к облаку, горизонтальному масштабированию и непрерывному деплою (сформулирована в Heroku). Go-сервисы естественно ложатся на эти правила. Ниже — все двенадцать факторов кратко.

| # | Фактор | Суть |
|---|--------|------|
| 1 | **Codebase** | Одна кодовая база в системе контроля версий → много деплоев (dev/stage/prod из одного репозитория). |
| 2 | **Dependencies** | Зависимости объявлены явно и изолированы. В Go — `go.mod`/`go.sum`; не полагаться на системные библиотеки. |
| 3 | **Config** | Конфигурация — в переменных окружения, а не в коде/файлах в репозитории. Разное окружение = разные env, тот же билд. |
| 4 | **Backing services** | Внешние сервисы (БД, кэш, очередь) — присоединяемые ресурсы, адресуемые по URL/конфигу; заменяемы без правки кода. |
| 5 | **Build, release, run** | Строго разделять стадии: build (компиляция), release (build + config), run (запуск). Релиз неизменяем и версионирован. |
| 6 | **Processes** | Приложение — один или несколько **stateless**-процессов; состояние выносится в backing services. Ничего не хранить в памяти между запросами. |
| 7 | **Port binding** | Сервис сам экспортирует HTTP/порт (в Go — `http.ListenAndServe`), не полагаясь на внешний сервер приложений. |
| 8 | **Concurrency** | Масштабирование — запуском большего числа процессов (горизонтально), а не только потоками внутри одного. Процессы — единица масштаба. |
| 9 | **Disposability** | Процессы быстро стартуют и корректно завершаются (graceful shutdown по SIGTERM). Устойчивость к внезапной смерти. |
| 10 | **Dev/prod parity** | Держать dev, staging и prod максимально похожими (те же backing services, версии, инструменты). Сокращать разрыв во времени/людях/инструментах. |
| 11 | **Logs** | Логи — поток событий в `stdout`; агрегацией/хранением занимается окружение, а не само приложение. |
| 12 | **Admin processes** | Разовые задачи (миграции, скрипты) запускать как одноразовые процессы в том же окружении и релизе. |

## Отражение в Go

- **Config (3)** — читать из env (`os.Getenv`), а не хардкодить; секреты не коммитить.
- **Port binding (7)** — `http.ListenAndServe(":"+port, mux)`, порт из env.
- **Disposability (9)** — `signal.NotifyContext` + `http.Server.Shutdown(ctx)` для graceful shutdown.
- **Logs (11)** — писать в `stdout`/`stderr` (`log`, `slog`), без ротации файлов внутри приложения.
- **Stateless (6)** — единственный статически слинкованный бинарник, состояние — в БД/кэше; удобно паковать в scratch/distroless-контейнер.

```go
// Config из env + port binding + graceful shutdown (эскиз).
port := os.Getenv("PORT")
if port == "" {
	port = "8080"
}
srv := &http.Server{Addr: ":" + port, Handler: mux}

ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()

go srv.ListenAndServe()
<-ctx.Done()                 // дождались сигнала
srv.Shutdown(context.Background()) // корректно завершились
```

> ⚠️ Частый вопрос на собеседовании: почему 12-factor требует хранить конфиг в переменных окружения, а не в файлах? Чтобы один и тот же неизменяемый билд/образ разворачивался в любом окружении, меняя только env; конфиг с секретами не попадает в репозиторий и не «зашивается» в артефакт.

> ⚠️ Частый вопрос на собеседовании: что значит stateless-процесс (фактор 6) и зачем? Процесс не хранит состояние между запросами (сессии, кэши — в backing services). Это позволяет свободно масштабировать и перезапускать процессы (факторы 8 и 9) без потери данных и без липких сессий.
