# SOLID

SOLID — пять принципов объектно-ориентированного дизайна (Роберт Мартин). В Go нет классов и наследования, но принципы полностью применимы: их реализуют через **интерфейсы, композицию и маленькие типы**. Ниже — каждая буква с коротким примером на Go.

## S — Single Responsibility Principle (единственная ответственность)

У типа (пакета, функции) должна быть одна причина для изменения. Смешивать бизнес-логику, форматирование и запись в БД в одном типе — нарушение.

```go
// Плохо: один тип и считает зарплату, и печатает, и сохраняет.
// Хорошо: разделяем ответственности.

type Payroll struct{}
func (Payroll) Calculate(hours, rate int) int { return hours * rate }

type Report struct{}
func (Report) Format(amount int) string { return fmt.Sprintf("итого: %d", amount) }

type Store struct{}
func (Store) Save(amount int) error { /* запись в БД */ return nil }
```

Каждый тип меняется по своей причине: изменилась формула — правим `Payroll`, изменился формат — `Report`.

## O — Open/Closed Principle (открыт для расширения, закрыт для изменения)

Поведение расширяется без правки существующего кода. В Go это чаще всего интерфейс + новые реализации (а не `switch` по типу, который приходится дополнять).

```go
type Discount interface {
	Apply(price float64) float64
}

type NoDiscount struct{}
func (NoDiscount) Apply(p float64) float64 { return p }

type Percent struct{ Off float64 }
func (d Percent) Apply(p float64) float64 { return p * (1 - d.Off) }

// Новую скидку добавляем новым типом, PriceOf менять не нужно.
func PriceOf(base float64, d Discount) float64 { return d.Apply(base) }
```

## L — Liskov Substitution Principle (подстановка Барбары Лисков)

Любая реализация интерфейса должна вести себя согласно его контракту — код, работающий с интерфейсом, не должен ломаться от подмены реализации. В Go нет наследования, но контракт интерфейса нарушить легко.

```go
type Storage interface {
	Get(key string) (string, error) // при отсутствии ключа — вернуть ошибку, а не panic
}
```

Если одна реализация возвращает ошибку при отсутствии ключа, а другая паникует — LSP нарушен: вызывающий код нельзя писать единообразно. Контракт (включая поведение при ошибках и nil) — часть интерфейса.

## I — Interface Segregation Principle (разделение интерфейсов)

Клиент не должен зависеть от методов, которые не использует. Много маленьких интерфейсов лучше одного «толстого». Go поощряет это напрямую: интерфейсы объявляют там, где потребляют.

```go
// stdlib — образец ISP:
type Reader interface { Read(p []byte) (int, error) }
type Writer interface { Write(p []byte) (int, error) }
type ReadWriter interface { Reader; Writer } // композиция при необходимости
```

Функции просят ровно то, что им нужно (`io.Reader`), а не гигантский `File`.

## D — Dependency Inversion Principle (инверсия зависимостей)

Высокоуровневые модули не должны зависеть от низкоуровневых — оба зависят от абстракций. На практике: зависимость передаётся как интерфейс (обычно через конструктор), а не создаётся внутри.

```go
type Notifier interface {
	Send(msg string) error
}

// Report зависит от абстракции Notifier, а не от конкретного EmailSender.
type Report struct{ n Notifier }

func NewReport(n Notifier) *Report { return &Report{n: n} }
func (r *Report) Publish() error   { return r.n.Send("отчёт готов") }
```

Теперь `Report` не знает про email/slack/заглушку — их подставляют снаружи. Это же делает код тестируемым (в тест подставляем фейковый `Notifier`).

> ⚠️ Частый вопрос на собеседовании: как SOLID ложится на Go без классов и наследования? Через маленькие интерфейсы (S, I), их реализации вместо `switch` по типу (O), соблюдение контракта интерфейса (L) и передачу зависимостей интерфейсами извне (D). Ключевые механизмы — интерфейсы и композиция, а не иерархии наследования.

> ⚠️ Частый вопрос на собеседовании: где в Go объявлять интерфейс — рядом с реализацией или с потребителем? Идиоматично — на стороне потребителя («accept interfaces, return structs»). Это естественно даёт узкие интерфейсы (ISP) и инверсию зависимостей (DIP).
