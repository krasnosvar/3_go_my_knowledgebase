# Design Principles: практические применения

Как принципы и паттерны из раздела всплывают в реальной инженерной практике и на System Design / code review.

## Тестируемость через DIP

Самая частая практическая выгода SOLID — тесты. Если высокоуровневый код зависит от интерфейса (DIP), а не от конкретной БД/HTTP-клиента, в тесте подставляется фейк — без сети и без реальной базы.

```go
type UserRepo interface{ FindName(id int) (string, error) }

type Greeter struct{ repo UserRepo }

func (g Greeter) Greet(id int) (string, error) {
	name, err := g.repo.FindName(id)
	if err != nil {
		return "", err
	}
	return "привет, " + name, nil
}
// В тесте подставляем fakeRepo, в проде — sqlRepo. Greeter не меняется.
```

## Middleware как цепочка декораторов

HTTP-middleware (логирование, аутентификация, метрики, recover) — это Decorator + Chain of Responsibility поверх `http.Handler`. Добавление сквозной функциональности не трогает бизнес-хэндлеры (OCP).

```go
func WithLogging(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		log.Printf("%s %s", r.Method, r.URL.Path)
		next.ServeHTTP(w, r)
	})
}
// mux := WithLogging(WithAuth(businessHandler)) — стек обёрток.
```

## Strategy для сменных алгоритмов

Разные тарифы/скидки, способы сортировки, форматы экспорта, политики ретраев — всё это стратегии. В Go подставляют func-значение или маленький интерфейс; `sort.Slice(s, less)` в stdlib — ровно это.

## Functional options вместо разрастающихся конструкторов

Когда у конструктора появляется 5+ параметров с умолчаниями (KISS/YAGNI под давлением), functional options дают расширяемое API без ломки сигнатуры и без «телескопических» конструкторов.

## 12-factor на деплое

- Конфиг из env → один образ на все окружения (dev/stage/prod).
- Логи в stdout → сбор берёт на себя платформа (k8s + Loki/CloudWatch).
- Graceful shutdown по SIGTERM → безопасные rolling-обновления в Kubernetes (под завершает in-flight запросы).
- Stateless-процессы → свободное горизонтальное масштабирование (HPA).

## Запахи кода на review (что искать)

- `switch` по типу, который дополняется при каждой новой сущности → просится интерфейс (OCP).
- Один тип делает всё (валидация + БД + HTTP) → нарушение SRP.
- «Толстый» интерфейс с 15 методами, из которых потребитель зовёт два → нарушение ISP.
- Конкретная зависимость (`*sql.DB`) прямо в бизнес-логике вместо интерфейса → мешает тестам (DIP).
- Абстракции/плагины «на будущее» без текущего требования → нарушение YAGNI.

> ⚠️ Частый вопрос на собеседовании: как принципы связаны между собой? SRP даёт маленькие типы → из них естественно вырастают узкие интерфейсы (ISP) → потребитель зависит от абстракции (DIP) → новое поведение добавляется реализациями и декораторами без правок (OCP). А KISS/YAGNI не дают увлечься и наплодить абстракций сверх нужного.

> ⚠️ Частый вопрос на собеседовании: назовите практическую пользу DIP кроме «красоты». Тестируемость (подмена фейком), заменяемость реализации (сменить БД/провайдера без правки логики) и разрыв компиляционных зависимостей между слоями.
