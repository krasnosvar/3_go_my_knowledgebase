# Строительные блоки и когда их доставать

System design — это сборка из типовых компонентов. Ниже — «ящик с инструментами»: что делает каждый блок, какой сигнал говорит «пора его добавить», и ссылка на подробный раздел этой базы. На интервью не тащите все сразу — добавляйте по мере обоснования.

## Обзорная таблица

|------|--------|------------------------|--------|
| Load Balancer | распределение нагрузки, отказоустойчивость | > 1 инстанса приложения | [08_reliability_scalability](../../08_reliability_scalability/) |
| Stateless app-серверы | горизонтальное масштабирование | нужно масштабировать API | [06_architecture](../../06_architecture/) |
| Кэш (Redis/Valkey) | снять нагрузку на БД, latency | read-heavy, повторяющиеся чтения | [03_caching](../../03_caching/) |
| Реплики БД (read replicas) | масштабирование чтения | read ≫ write | [04_data_scaling](../../04_data_scaling/) |
| Шардинг | масштабирование записи и объёма | одна нода не тянет объём/write | [04_data_scaling](../../04_data_scaling/) |
| Очередь сообщений | развязка, сглаживание пиков, async | медленная/побочная работа | [05_messaging](../../05_messaging/) |

## Load Balancer (балансировщик нагрузки)

Распределяет запросы между инстансами, убирает упавшие из ротации (health checks), даёт единую точку входа. Бывает **L4** (по TCP/IP, быстрее) и **L7** (по HTTP, умнее: маршрутизация по пути/заголовкам).

**Когда:** как только приложение работает больше чем на одном сервере. Алгоритмы: round-robin, least-connections, consistent hashing (для sticky-распределения по кэш-узлам). Подробнее — [08_reliability_scalability](../../08_reliability_scalability/).

## Stateless app-серверы

Серверы без локального состояния: любое состояние (сессии) — во внешнем хранилище (Redis, БД). Тогда любой инстанс обрабатывает любой запрос, и масштабирование — это просто «добавить инстансов за LB».

**Когда:** почти всегда для веб-API. Первое, что масштабируем горизонтально. См. [06_architecture](../../06_architecture/) и [07_design_principles](../../07_design_principles/).

## Кэш

Хранилище в памяти (Redis/Valkey) перед БД. Даёт latency в доли миллисекунды и снимает нагрузку с базы. RAM в ~100 раз быстрее диска (см. [02_estimations.md](./02_estimations.md)).

**Когда:** read-heavy нагрузка, одни и те же данные читаются многократно (профили, горячие ссылки, лента).

**Что обсудить:** стратегия (cache-aside чаще всего), политика вытеснения (LRU), TTL, инвалидация, проблема «cache stampede», консистентность кэша и БД. Всё это — в [03_caching](../../03_caching/).

## Реплики БД для чтения (read replicas)

Мастер принимает записи, реплики отдают чтения. Масштабирует именно чтение.

**Когда:** чтений на порядок больше записей (сокращатель, лента). Цена — **репликационный лаг**: реплика немного отстаёт, отсюда read-after-write проблемы. Подробнее — [04_data_scaling](../../04_data_scaling/).

## Шардинг (партиционирование)

Разбиение данных по нескольким узлам по ключу (например, `hash(user_id) % N`). Масштабирует запись и объём, когда одна нода уже не тянет.

**Когда:** объём данных или поток записей не помещаются в одну ноду (десятки TB, высокий write QPS).

**Что обсудить:** выбор ключа шардирования (чтобы избежать hotspots), рехэшинг при добавлении шардов (consistent hashing), сложность кросс-шардовых запросов и транзакций. См. [04_data_scaling](../../04_data_scaling/).

## Очередь сообщений (Kafka / RabbitMQ / SQS)

Развязывает продюсеров и консьюмеров, сглаживает пики (буфер), позволяет делать тяжёлую/побочную работу асинхронно (отправка email, обработка видео, fanout ленты).

**Когда:** есть работа, которую не нужно делать синхронно в запросе; нужно пережить всплеск нагрузки; нужна надёжная доставка событий между сервисами.

**Что обсудить:** at-least-once vs exactly-once, идемпотентность консьюмеров, порядок, backpressure. Подробнее — [05_messaging](../../05_messaging/).

## CDN (Content Delivery Network)

Кэширует статику (картинки, видео, JS/CSS) на узлах близко к пользователю. Снимает трафик с origin и режет latency за счёт географии.

**Когда:** раздаёте статические/медиа-файлы, аудитория глобальная. Если прикидка bandwidth даёт гигабайты в секунду на медиа — это работа для CDN, не для origin (см. [02_estimations.md](./02_estimations.md)).

## Blob storage (объектное хранилище, S3)

Дёшево и надёжно хранит большие бинарные объекты (файлы, картинки, видео, бэкапы). В БД кладут **метаданные и ссылку** на объект, сам объект — в blob storage (часто раздаётся через CDN).

**Когда:** нужно хранить файлы/медиа. Не держите бинарники в реляционной БД.

## Как выбирать на интервью

1. Начните с минимума: клиент → LB → stateless app-серверы → одна БД.
2. Прикиньте нагрузку ([02_estimations.md](./02_estimations.md)) — это подскажет, какой блок нужен.
3. Read-heavy → добавьте **кэш**, затем **read replicas**.
4. Не помещается объём/write → **шардинг**.
5. Есть async-работа или пики → **очередь**.
6. Медиа и глобальная аудитория → **blob storage + CDN**.
7. На каждом шаге проговаривайте компромисс (сложность, консистентность, стоимость).

> ⚠️ Частый вопрос на собеседовании: когда добавлять кэш? Когда нагрузка read-heavy и есть повторяющиеся чтения одних и тех же данных. Кэш не бесплатен: появляется проблема инвалидации и консистентности кэша с БД. Не добавляйте кэш «на всякий случай» — сначала обоснуйте прикидкой.
