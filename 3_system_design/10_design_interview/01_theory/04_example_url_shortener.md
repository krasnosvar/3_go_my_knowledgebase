# Разбор: сокращатель ссылок (URL shortener)

Классическая задача (аналог bit.ly / tinyurl). Разбираем строго по методологии из [01_approach.md](./01_approach.md). Это эталон того, как проходить любую задачу на интервью.

## 1. Требования

### Функциональные
- Создать короткую ссылку по длинному URL.
- Редирект: по короткой ссылке отправить пользователя на исходный URL.
- (Опционально) кастомный alias.
- (Опционально) срок жизни ссылки (expiration).

### Нефункциональные
- **Read-heavy**: редиректов (чтений) на 1–2 порядка больше, чем создания (записей). Возьмём 100:1.
- **Низкая latency** редиректа (это критичный путь пользователя, целимся в p99 < 50–100 мс).
- **Высокая доступность**: если сервис лежит — не работают все уже созданные ссылки.
- Короткий код — компактный и не угадываемый последовательно (желательно).

### Вне scope (проговорить)
Авторизация, биллинг, детальная аналитика — упомянуть, но не проектировать.

## 2. Оценка нагрузки

Предположим (проговариваем вслух):
- 100 млн новых ссылок в сутки.
- Соотношение чтение/запись 100:1 → 10 млрд редиректов в сутки.

```
write QPS = 10^8 / 10^5 ≈ 1000 QPS  (пик ~2000)
read  QPS = 10^10 / 10^5 = 100 000 QPS  (пик ~200 000)
```

Хранилище (запись ~500 байт, храним 5 лет):

```
100 млн/сутки × 500 байт = 50 GB/сутки
× 365 × 5 ≈ 91 TB
```

Число ключей за 5 лет: `100 млн × 365 × 5 ≈ 1.8 × 10^11` (~180 млрд) — определяет длину короткого кода.

**Выводы:** чтений 100–200 тыс QPS → обязателен кэш и реплики. Объём ~90 TB → нужен шардинг/распределённое хранилище. 180 млрд ключей → длина кода ~7 символов (см. ниже).

## 3. API

```
POST /api/v1/urls
  body:  { "longUrl": "https://...", "alias": "optional", "ttl": "optional" }
  resp:  { "shortUrl": "https://sho.rt/aB3xY7z" }

GET /{shortCode}
  resp:  301/302 Location: https://<оригинальный URL>
```

**301 vs 302:** `301 Moved Permanently` кэшируется браузером — быстрее для пользователя, но клики не долетают до сервиса (плохо для аналитики). `302 Found` не кэшируется — каждый клик идёт через сервис (нужно для аналитики, но выше нагрузка). Выбор — компромисс; для аналитики берём 302.

## 4. Модель данных

Доступ — простой key-value: по `short_code` достать `long_url`. Join'ов и транзакций нет → подходит NoSQL key-value / широко-колоночное хранилище с шардированием по `short_code`. Реляционка тоже сгодится с шардингом.

```
Таблица urls:
  short_code   VARCHAR(7)   PRIMARY KEY   // ключ шардирования
  long_url     TEXT
  created_at   TIMESTAMP
  expires_at   TIMESTAMP NULL
```

## 5. Генерация короткого кода

Ключевое проектное решение. Нужен уникальный код длиной ~7 символов.

### Сколько символов?
Алфавит **base62** = `[a-zA-Z0-9]` = 62 символа.

```
62^6 ≈ 5.7 × 10^10  (~57 млрд)  — мало для 180 млрд
62^7 ≈ 3.5 × 10^12  (~3.5 трлн) — хватает с запасом
```

Берём **7 символов**.

### Подходы к генерации

**A. Хэш от URL (например, MD5/SHA) → взять первые байты → base62.**
- Плюс: одинаковый URL даёт один код (дедупликация).
- Минус: коллизии хэша → нужна проверка и повтор; усложняет.

**B. Инкрементный ID → base62-кодирование (выбираем этот).**
- Централизованный счётчик выдаёт уникальный `id` (1, 2, 3, …).
- Кодируем `id` в base62 → получаем короткий код. Уникальность гарантирована без коллизий.
- Реализация base62-кодирования — в примере [02_examples/01_base62_shortener](../02_examples/01_base62_shortener/).

**Проблема подхода B — единый счётчик как SPOF и узкое место.** Решения:
- Диапазоны (ranges): каждый app-сервер берёт у координатора блок ID (например, 1000 штук) и раздаёт локально; за новым блоком ходит редко. Снимает нагрузку с центрального счётчика.
- Отдельный распределённый генератор ID (по типу Snowflake): 64-битный ID из времени + machine id + счётчика, генерируется локально без общего состояния.

Последовательные ID предсказуемы (можно перебирать чужие ссылки). Если это важно — «перемешивают» ID перед кодированием или добавляют случайную компоненту.

## 6. High-level дизайн

```
             ┌──────────────┐
Клиент ─────▶│ Load Balancer│
             └──────┬───────┘
                    │
          ┌─────────▼─────────┐
          │  App-серверы      │  (stateless, за LB)
          │  - POST создать   │
          │  - GET  редирект  │
          └───┬───────────┬───┘
              │           │
      чтение  │           │  запись
        ┌─────▼───┐   ┌───▼──────────┐
        │  Кэш    │   │ Генератор ID │
        │(Valkey) │   └───┬──────────┘
        └─────┬───┘       │
   miss ──────┤           │
        ┌─────▼───────────▼──┐
        │  БД (шардирована   │
        │  по short_code,    │
        │  + read replicas)  │
        └────────────────────┘
```

**Поток чтения (редирект, критичный путь):**
1. `GET /{code}` → app-сервер.
2. Смотрим в кэш (cache-aside). Hit → сразу отдаём `302 Location`.
3. Miss → читаем из БД (read replica), кладём в кэш с TTL, отдаём редирект.

**Поток записи (создание):**
1. `POST /urls` → app-сервер.
2. Берём следующий ID (из локального блока диапазона).
3. Кодируем в base62 → `short_code`.
4. Пишем в БД (мастер соответствующего шарда).
5. Возвращаем short URL.

## 7. Масштабирование и кэш

- **App-серверы** stateless → масштабируем горизонтально за LB.
- **Кэш**: 100–200 тыс read QPS обслуживает Valkey. По правилу 80/20 горячие ссылки помещаются в память (см. прикидку в [02_estimations.md](./02_estimations.md)). TTL, LRU-вытеснение. См. [03_caching](../../03_caching/).
- **БД**: read replicas под 200 тыс QPS чтения; шардинг по `short_code` под ~90 TB и write-нагрузку. См. [04_data_scaling](../../04_data_scaling/).
- **CDN / edge-редиректы**: очень горячие ссылки можно резолвить на edge, снижая нагрузку на origin.

## 8. Узкие места и trade-offs

| Узкое место | Риск | Решение |
|-------------|------|---------|
| Генератор ID | SPOF, contention | Диапазоны ID / Snowflake-подобный |
| Кэш | cache stampede на горячей ссылке | request coalescing, TTL с jitter |
| БД мастер | предел записи/объёма | шардинг по short_code |
| Репликационный лаг | свежесозданная ссылка не видна на реплике | читать создателя с мастера, либо писать в кэш сразу |
| Hot shard | неравномерность по коду | равномерный ключ (base62 от ID распределяется хорошо) |

**Итоговые компромиссы, которые проговариваем:**
- Инкрементный ID + base62 вместо хэша — нет коллизий ценой централизованного счётчика (смягчаем диапазонами).
- 302 вместо 301 — есть аналитика ценой большей нагрузки.
- Eventual consistency между кэшом/репликами и мастером допустима: ссылка неизменяема, устаревание опасно только сразу после создания.

> ⚠️ Частый вопрос на собеседовании: почему base62, а не base64? base64 включает символы `+` и `/`, требующие URL-кодирования, что уродует ссылку. base62 (`a-zA-Z0-9`) безопасен для URL и даёт компактный код.

> ⚠️ Частый вопрос на собеседовании: как гарантировать уникальность коротких кодов? Проще всего — брать глобально уникальный инкрементный ID и кодировать его в base62: биекция между числом и строкой исключает коллизии в принципе, в отличие от хэширования, где коллизии надо ловить и перегенерировать.
