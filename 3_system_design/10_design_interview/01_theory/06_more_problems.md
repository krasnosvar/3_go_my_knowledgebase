# Наброски по остальным типовым задачам

Краткие «скелеты» распространённых задач: ключевые требования, центральное проектное решение и на что смотрит интервьюер. Каждую проходите по методологии из [01_approach.md](./01_approach.md) — здесь только опорные точки, а не полные разборы.

## Чат / мессенджер (WhatsApp / Telegram)

**Ключевые требования:** 1:1 и групповые чаты, доставка в реальном времени, статусы (доставлено/прочитано), онлайн-присутствие, история сообщений, доставка при офлайне.

**Центральное решение — как доставлять в реальном времени:**
- Постоянное соединение вместо polling: **WebSocket** (или long-polling как fallback). Клиент держит соединение с gateway-сервером.
- Нужен **сервис присутствия/маршрутизации**: какой пользователь на каком gateway-узле сейчас висит (карта `user_id → connection` в Redis). Сообщение маршрутизируется на нужный узел.
- Офлайн-получатель: сообщение кладётся в его «инбокс»/очередь и доставляется при следующем подключении.

**На что смотреть:**
- Модель хранения сообщений: шард по `chat_id`, сортировка по времени; огромный write-объём → NoSQL/широко-колоночное ([04_data_scaling](../../04_data_scaling/)).
- Гарантии доставки и порядок: at-least-once + дедупликация по message_id; порядок внутри чата. См. [05_messaging](../../05_messaging/).
- Групповой fanout: разослать сообщение всем участникам (аналог fanout из [05_example_news_feed.md](./05_example_news_feed.md)); для больших групп — ограничения.
- Масштабирование stateful WebSocket-узлов: как балансировать постоянные соединения ([08_reliability_scalability](../../08_reliability_scalability/)).

> ⚠️ Частый вопрос на собеседовании: polling или push? Постоянный WebSocket, потому что polling либо ест ресурсы (частый), либо даёт задержку (редкий). Сложность WebSocket — stateful-соединения: нужен реестр «пользователь → узел» для маршрутизации.

## Rate limiter (как сервис)

**Ключевые требования:** ограничить число запросов на клиента/ключ за окно времени (например, 100 req/min); распределённо (много инстансов API); низкий overhead; понятное поведение на границе окна.

**Центральное решение — алгоритм:**
- **Token bucket** — пополняемое ведро токенов; допускает всплески до размера ведра. Популярный выбор.
- **Leaky bucket** — сглаживает поток до постоянной скорости.
- **Fixed window counter** — счётчик на окно; просто, но всплеск на стыке двух окон даёт до 2× лимита.
- **Sliding window log / counter** — точнее на границе окна, чуть дороже.

**На что смотреть:**
- **Распределённость**: счётчики в общем сторе (Redis/Valkey), атомарные инкременты; иначе каждый инстанс лимитирует отдельно. См. [03_caching](../../03_caching/).
- Ключ лимита: по user_id / API-key / IP.
- Поведение при превышении: `429 Too Many Requests` + заголовки `Retry-After`, `X-RateLimit-Remaining`.
- Компромисс точность vs стоимость: точный sliding log дороже по памяти, чем fixed window.
- Fail-open vs fail-closed при недоступности стора счётчиков.

> ⚠️ Частый вопрос на собеседовании: как сделать rate limiter распределённым? Счётчики должны быть в общем хранилище (Redis) с атомарными операциями, иначе N инстансов пропустят N × limit. Компромисс — latency обращения к общему стору на каждый запрос; часто смягчают локальным кэшем с периодической синхронизацией.

## Платёжная система

**Ключевые требования:** провести платёж, не потеряв и не задвоив деньги; **строгая консистентность**; аудит и идемпотентность; интеграция с внешними платёжными провайдерами; согласованность между сервисами.

**Центральные решения:**
- **Идемпотентность.** Клиент присылает `Idempotency-Key`; сервер хранит результат по ключу и при повторе (retry, двойной клик) возвращает тот же результат, не проводя платёж дважды. Обязательно, т.к. сеть ненадёжна и клиенты ретраят.
- **Консистентность.** В отличие от лент/лайков здесь нельзя eventual «потерять» деньги. Транзакции БД (ACID) для операций над балансом; между сервисами — **saga** с компенсирующими транзакциями либо двухфазные подходы. См. [04_data_scaling](../../04_data_scaling/): [CAP](../../04_data_scaling/01_theory/03_cap_theorem.md), [распределённые транзакции и saga](../../04_data_scaling/01_theory/05_distributed_tx.md).
- **Двойная запись (double-entry bookkeeping)**: каждая операция — дебет одного счёта и кредит другого; сумма всегда сходится, есть аудит.
- **Надёжные события**: списание и уведомление внешнего провайдера через outbox-паттерн, чтобы событие не потерялось и не задвоилось. См. [05_messaging](../../05_messaging/).

**На что смотреть:** обработка частичных сбоев (списали, но не подтвердили у провайдера), reconciliation (сверка с провайдером), точные типы для денег (никаких float — целые копейки/минорные единицы), аудит-лог.

> ⚠️ Частый вопрос на собеседовании: как не провести платёж дважды при повторной отправке? Идемпотентность через ключ идемпотентности: сервер сохраняет исход операции по ключу, повторный запрос с тем же ключом возвращает сохранённый результат вместо нового списания. Это защищает от ретраев и сетевых дублей.

## Файловое хранилище (Dropbox / Google Drive)

**Ключевые требования:** загрузка/скачивание файлов, синхронизация между устройствами, шаринг, версии, работа с большими файлами.

**Центральные решения:**
- **Метаданные отдельно от содержимого.** Метаданные (имя, путь, версии, права, ссылка на объект) — в БД; сами байты — в **blob storage (S3)**. См. [04_data_scaling](../../04_data_scaling/).
- **Chunking (разбиение на блоки).** Файл режется на блоки фиксированного размера (например, 4 MB). Даёт: докачку/дозагрузку только изменённых блоков, дедупликацию (одинаковые блоки хранятся один раз, адресуются по хэшу содержимого), параллельную загрузку.
- **Синхронизация**: клиент отслеживает изменения и заливает только изменённые блоки; сервер уведомляет другие устройства (long-poll/WebSocket) о новых версиях.
- **Раздача** — через CDN для скачивания популярных файлов.

**На что смотреть:** разрешение конфликтов при одновременном редактировании (версии, «last write wins» vs ветвление), консистентность метаданных, права доступа/шаринг, экономия трафика через дельта-синхронизацию.

> ⚠️ Частый вопрос на собеседовании: как эффективно синхронизировать большие файлы? Chunking: файл делится на блоки, каждый адресуется по хэшу содержимого. При изменении заливаются только изменённые блоки, одинаковые блоки дедуплицируются. Это экономит трафик и хранилище и позволяет докачку.

## Общий подход к любой новой задаче

1. Определите **функциональные** и **нефункциональные** требования (масштаб, read/write, latency, консистентность).
2. Прикиньте нагрузку ([02_estimations.md](./02_estimations.md)).
3. Найдите **центральное проектное решение** задачи (для каждой оно своё — из таблицы ниже) и обсудите его компромиссы.
4. Соберите дизайн из блоков ([03_building_blocks.md](./03_building_blocks.md)), найдите узкие места.

| Задача | Центральное решение |
|--------|---------------------|
| Сокращатель ссылок | генерация уникального короткого кода (base62 от ID) |
| Лента новостей | fanout on write vs on read (гибрид) |
| Чат / мессенджер | доставка в реальном времени (WebSocket + реестр соединений) |
| Rate limiter | алгоритм лимитирования + распределённые счётчики |
| Платёжная система | идемпотентность + строгая консистентность |
| Файловое хранилище | разделение метаданных и байтов + chunking |
