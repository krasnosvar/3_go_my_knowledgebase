# Разбор: лента новостей (news feed)

Задача уровня Twitter/Instagram-ленты: пользователь видит агрегированный, отсортированный поток постов от тех, на кого подписан. Разбираем по методологии из [01_approach.md](./01_approach.md). Центральное решение здесь — **fanout on write vs fanout on read**.

## 1. Требования

### Функциональные
- Опубликовать пост (текст/медиа).
- Подписаться / отписаться.
- Получить свою ленту: посты подписок, обычно по времени (или ранжированные), с пагинацией.

### Нефункциональные
- **Read-heavy**: ленту смотрят гораздо чаще, чем публикуют. Возьмём чтение/запись ~100:1.
- Низкая latency загрузки ленты (p99 < 200 мс) — это первый экран приложения.
- Высокая доступность; eventual consistency допустима (пост может появиться у подписчиков с задержкой в секунды).
- Проблема «звёзд» (celebrities): у аккаунта могут быть десятки миллионов подписчиков.

### Вне scope
Алгоритмическое ранжирование, реклама, модерация — упомянуть, но не проектировать (базово считаем ленту хронологической).

## 2. Оценка нагрузки

Предположим: DAU = 100 млн, каждый смотрит ленту 5 раз в сутки, публикует 0.1 поста в сутки.

```
чтений ленты в сутки = 10^8 × 5 = 5 × 10^8  → read QPS ≈ 5 × 10^8 / 10^5 = 5000
постов в сутки       = 10^8 × 0.1 = 10^7    → write QPS ≈ 100
```

Хранилище постов (пост ~1 KB метаданных, медиа — отдельно в blob storage): `10^7 × 1 KB = 10 GB/сутки`. За год ~3.6 TB метаданных — нужен шардинг.

**Вывод:** read ≫ write (5000 vs 100 QPS) → выгодно заранее готовить ленту (fanout on write). Но есть звёзды — для них это дорого.

## 3. API

```
POST /api/v1/posts              { text, mediaIds }        -> { postId }
GET  /api/v1/feed?cursor=...     -> { posts: [...], nextCursor }
POST /api/v1/follow             { targetUserId }
```

Пагинация — **курсорная** (cursor/keyset), а не offset: лента постоянно растёт, offset «съезжает» и медленный.

## 4. Модель данных

```
posts:      post_id (PK), author_id, text, media_ids, created_at   // шард по author_id
follows:    follower_id, followee_id, created_at                    // кто на кого подписан
feed_cache: user_id, [post_id, post_id, ...]                        // предрассчитанная лента (при fanout on write)
```

Медиа кладём в blob storage (S3) + CDN, в `posts` — только `media_ids`. См. [04_data_scaling](../../04_data_scaling/).

## 5. Ключевое решение: fanout on write vs fanout on read

### Fanout on write (push-модель)
При публикации поста сразу «разносим» его во **ленты всех подписчиков** (пишем `post_id` в их `feed_cache`, обычно в Redis/Valkey).

- **Чтение ленты — очень быстрое**: лента уже готова, просто читаем список.
- **Запись — дорогая**: 1 пост → N вставок (N = число подписчиков). Для звезды с 50 млн подписчиков один пост = 50 млн операций → всплеск нагрузки и лаг («celebrity problem»).
- Хорошо для read-heavy при умеренном числе подписчиков.

### Fanout on read (pull-модель)
Ленту собираем **в момент запроса**: берём подписки пользователя, тянем их свежие посты, мержим и сортируем.

- **Запись — дешёвая**: просто сохранить пост.
- **Чтение — дорогое**: на каждый запрос ленты — сбор и merge из многих источников → выше latency.
- Хорошо для звёзд (не надо разносить пост миллионам) и для неактивных пользователей (не готовим ленту тем, кто не заходит).

### Гибридный подход (то, что отвечают на интервью)
- Для **обычных** авторов — **fanout on write**: посты заранее лежат в лентах подписчиков.
- Для **звёзд** (порог, скажем, > 100 тыс подписчиков) — **fanout on read**: их посты не разносим, а подмешиваем в ленту при чтении.
- Итоговая лента пользователя = предрассчитанная часть (push) + свежие посты звёзд, на которых он подписан (pull), слитые и отсортированные.

Это и есть главный trade-off задачи: балансируем стоимость записи и чтения в зависимости от «веса» автора.

## 6. High-level дизайн

```
                       ┌──────────────┐
Клиент ───────────────▶│ Load Balancer│
                       └──────┬───────┘
                              │
                   ┌──────────▼──────────┐
          publish  │   App-серверы       │  read feed
        ┌──────────┤ (Post / Feed API)   ├──────────┐
        │          └──────────┬──────────┘          │
        │                     │                      │
 ┌──────▼──────┐       ┌──────▼──────┐       ┌───────▼────────┐
 │ Fanout      │       │  Posts DB   │       │  Feed cache    │
 │ (очередь +  │──────▶│ (шард по    │       │  (Redis/Valkey │
 │  воркеры)   │ push  │  author)    │       │  списки лент)  │
 └─────────────┘       └─────────────┘       └────────────────┘
```

**Поток публикации:**
1. `POST /posts` → сохраняем пост в Posts DB.
2. Кладём событие в очередь ([05_messaging](../../05_messaging/)).
3. Fanout-воркеры: если автор не звезда — разносят `post_id` в `feed_cache` подписчиков (push). Если звезда — не разносят.

**Поток чтения ленты:**
1. `GET /feed` → читаем предрассчитанную ленту из `feed_cache` (push-часть).
2. Отдельно тянем свежие посты звёзд из подписок (pull-часть).
3. Мержим, сортируем по времени, применяем пагинацию, возвращаем.
4. Метаданные постов дочитываем из кэша/БД; медиа отдаём через CDN.

## 7. Кэш и хранение

- **feed_cache** — списки `post_id` на пользователя в Redis/Valkey; храним первые N (например, 500–800) элементов, старое — из БД. См. [03_caching](../../03_caching/).
- **Posts DB** — шардинг по `author_id`; read replicas под чтение. См. [04_data_scaling](../../04_data_scaling/).
- **Очередь** для fanout — сглаживает всплески при вирусных постах и развязывает публикацию от разноса. См. [05_messaging](../../05_messaging/).
- **Blob storage + CDN** — медиа.

## 8. Узкие места и trade-offs

| Узкое место | Риск | Решение |
|-------------|------|---------|
| Fanout звезды | всплеск в миллионы записей | гибрид: звёзд читаем через pull |
| Fanout-лаг | пост появляется у подписчиков с задержкой | асинхронный fanout + eventual consistency (приемлемо) |
| Горячий шард автора-звезды | перегрузка одной ноды | кэш постов звёзд, реплики |
| Рост feed_cache | память | хранить только первые N, остальное из БД |
| Неактивные пользователи | зря готовим им ленту | для них — только pull, ленту собирать при заходе |

**Итоговые компромиссы:**
- Гибридный fanout: push для массовой аудитории (быстрое чтение), pull для звёзд и неактивных (дешёвая запись).
- Eventual consistency ленты: секундная задержка появления поста допустима, зато система масштабируется и остаётся доступной.

> ⚠️ Частый вопрос на собеседовании: fanout on write или on read? Оба — гибрид. Fanout on write делает чтение дешёвым, но убивается на аккаунтах-звёздах (миллионы записей на пост). Fanout on read спасает от «celebrity problem», но делает чтение дорогим. Промышленные ленты комбинируют: обычные авторы — push, звёзды — pull, и мержат обе части при отдаче ленты.
