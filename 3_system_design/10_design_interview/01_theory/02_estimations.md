# Оценки «на салфетке» (back-of-the-envelope)

Цель прикидок — не точная цифра, а **порядок величины**: тысячи QPS или миллионы? Гигабайты или петабайты? От этого зависит, нужны ли кэш, шардинг, CDN. Считайте вслух, округляйте агрессивно.

## Степени 10, которые надо знать наизусть

Округляем `1024 ≈ 1000`, поэтому степени двойки удобно переводить в степени десяти:

| Степень 2 | Приблизительно | Полное число | Байты |
|-----------|----------------|--------------|-------|
| 2^10 | 1 тысяча (K) | 1 024 | 1 KB |
| 2^20 | 1 миллион (M) | ~1 000 000 | 1 MB |
| 2^30 | 1 миллиард (G) | ~1 000 000 000 | 1 GB |
| 2^40 | 1 триллион (T) | ~10^12 | 1 TB |
| 2^50 | 1 квадриллион (P) | ~10^15 | 1 PB |

Полезные константы времени:

| Интервал | Секунд (округлённо) |
|----------|---------------------|
| 1 минута | 60 |
| 1 час | 3 600 |
| 1 день | 86 400 ≈ **10^5** |
| 1 месяц | ~2.6 × 10^6 |
| 1 год | ~3.15 × 10^7 |

Ключевой трюк: **в сутках ~100 000 секунд**. Значит `QPS ≈ (запросов в сутки) / 100 000`.

## Latency numbers every programmer should know

Ориентиры задержек (порядки величин, по мотивам таблицы Jeff Dean; современное железо быстрее, но соотношения сохраняются):

| Операция | Задержка | Относительно |
|----------|----------|--------------|
| L1 cache reference | ~1 нс | 1× |
| Branch mispredict | ~3 нс | |
| L2 cache reference | ~4 нс | |
| Mutex lock/unlock | ~17 нс | |
| Main memory (RAM) reference | ~100 нс | ~100× от L1 |
| Compress 1 KB (Zippy/Snappy) | ~2 мкс | |
| Send 1 KB по сети 1 Gbps | ~10 мкс | |
| Read 1 MB из RAM | ~100 мкс | |
| Round trip внутри дата-центра | ~500 мкс | |
| Read 1 MB с SSD | ~1 мс | |
| Disk seek (HDD) | ~10 мс | |
| Read 1 MB с HDD | ~20–30 мс | |
| Round trip CA ↔ Netherlands | ~150 мс | межконтинентальный |

Выводы, которые из этого следуют (и которые проговаривают на интервью):

- **RAM в ~100 раз быстрее диска** → отсюда смысл кэша в памяти (Redis/Valkey).
- **SSD на порядок быстрее HDD** по случайному доступу.
- **Сеть внутри ДЦ (0.5 мс) на 2 порядка дешевле межрегиональной (150 мс)** → размещайте связанные сервисы рядом, а пользователей обслуживайте из ближайшего региона/CDN.
- Всё, что можно, читаем из памяти; на диск ходим за холодными данными; между регионами — только когда обязаны.

## Единицы трафика

- Скорость сети измеряется в **битах** (Gbps), объём данных — в **байтах**. `1 байт = 8 бит`.
- 1 Gbps ≈ 125 MB/s.

## Как считать QPS

```
QPS (средний) = запросов в сутки / 86400  (≈ /10^5)
QPS (пик)     ≈ средний × 2..3
```

Часто дают DAU (daily active users) и число действий на пользователя:

```
запросов в сутки = DAU × действий_на_пользователя_в_сутки
```

**Пример.** Сервис с DAU = 10 млн, каждый пользователь делает 20 запросов в сутки:

```
запросов в сутки = 10^7 × 20 = 2 × 10^8
средний QPS      = 2 × 10^8 / 10^5 = 2000 QPS
пиковый QPS      ≈ 2000 × 2 = 4000 QPS
```

Вывод: 4000 QPS — это несколько stateless-инстансов за балансировщиком, не экзотика.

## Как считать хранилище

```
объём = размер_записи × число_записей_в_сутки × дней_хранения
```

**Пример.** Сокращатель ссылок: 100 млн новых ссылок в сутки, каждая запись ~500 байт (long URL + short code + метаданные), храним 5 лет:

```
в сутки = 10^8 × 500 байт = 5 × 10^10 байт = 50 GB/сутки
за 5 лет = 50 GB × 365 × 5 ≈ 91 TB
```

Вывод: десятки терабайт — одна нода не потянет комфортно, нужен шардинг или распределённое хранилище.

## Как считать пропускную способность (bandwidth)

```
throughput = QPS × размер_ответа
```

**Пример.** 5000 QPS на чтение, средний ответ 1 KB:

```
5000 × 1 KB = 5 MB/s (≈ 40 Mbps) — легко для одного сервера/сети.
```

А если раздаём картинки по 2 MB при тех же 5000 QPS: `5000 × 2 MB = 10 GB/s` — это уже задача для CDN, а не для origin-сервера.

## Как считать память под кэш

Правило **80/20**: 80% запросов приходится на 20% данных (горячие данные). Кэшируем именно их.

**Пример.** 20 млн уникальных ссылок читаются в сутки, кэшируем горячие 20%, запись в кэше ~200 байт:

```
0.2 × 2 × 10^7 × 200 байт = 8 × 10^8 байт ≈ 0.8 GB
```

Вывод: помещается в память одного узла Redis/Valkey — отдельный шардированный кэш не нужен.

## Порядок действий на интервью

1. Зафиксируйте вводные (DAU, действий на пользователя, размер записи, срок хранения) — если не дали, предположите разумные и проговорите.
2. Посчитайте QPS средний и пиковый.
3. Посчитайте объём хранилища за горизонт хранения.
4. Посчитайте пропускную способность на чтение/запись.
5. Прикиньте память под кэш.
6. Сделайте вывод: где узкое место и какие компоненты нужны.

> ⚠️ Частый вопрос на собеседовании: «сколько это будет QPS?». Не пытайтесь считать точно. Округлите DAU и действия до степеней 10, поделите суточные запросы на 10^5 (секунд в сутках) — получите средний QPS, умножьте на 2–3 для пика. Интервьюер оценивает метод, а не арифметику до третьего знака.
