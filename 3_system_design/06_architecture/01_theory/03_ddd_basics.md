# DDD (основы)

Domain-Driven Design (Эрик Эванс) — подход к моделированию сложной предметной области: код и его структура выражают понятия бизнеса, а не технические детали. Здесь — минимум тактических и стратегических понятий, который нужен на практике и на собеседовании.

## Ubiquitous Language (единый язык)

Единый словарь терминов, общий для разработчиков и экспертов предметной области. Одно и то же понятие называется одинаково в разговоре, в требованиях и в коде.

- Если бизнес говорит «Заказ», «Позиция», «Отгрузка» — в коде так и должно быть: `Order`, `LineItem`, `Shipment`, а не `DataRow` или `Item2`.
- Язык живёт внутри конкретного контекста: один термин в разных контекстах может значить разное (см. ниже).

## Bounded Context (ограниченный контекст)

Явная граница, внутри которой конкретная модель и единый язык согласованы и однозначны. За границей — другая модель, возможно с теми же словами, но другим смыслом.

```
   Bounded Context: Sales          Bounded Context: Support
   +----------------------+        +-------------------------+
   | Customer             |        | Customer                |
   |  - лимит кредита     |        |  - история обращений    |
   |  - сегмент продаж    |        |  - приоритет тикетов    |
   +----------------------+        +-------------------------+
        «Customer» здесь и там — РАЗНЫЕ модели одного слова
```

- Границы контекстов обычно совпадают с границами команд и часто — с границами микросервисов.
- Между контекстами модели не «протекают»: их связывают явные контракты (Context Map: shared kernel, customer/supplier, anti-corruption layer и т.п.).

## Тактические строительные блоки

- **Entity (сущность)** — объект с идентичностью (identity), которая сохраняется во времени, даже когда атрибуты меняются. Два заказа с одинаковыми полями, но разными `ID` — это разные заказы. Равенство — по идентификатору.
- **Value Object (объект-значение)** — определяется своими значениями, идентичности нет; равенство — по значению. Обычно неизменяемый (immutable). Примеры: `Money{amount, currency}`, `Address`, `DateRange`. Заменяется целиком, а не мутируется.
- **Aggregate (агрегат)** — кластер связанных сущностей и value-объектов, который меняется как единое целое. У агрегата есть **aggregate root** — единственная точка входа, через которую идут все изменения; root следит за инвариантами всего кластера. Внешний код держит ссылку только на root, а не на внутренние сущности.

```
   Aggregate: Order (root)
   +-------------------------------+
   | Order (root, entity)          |   ← ссылки извне только на root
   |   OrderID (identity)          |
   |   Status                      |
   |   +-------------------------+ |
   |   | LineItem (entity)       | |   ← внутренние члены агрегата
   |   | Money (value object)    | |
   |   +-------------------------+ |
   |  инвариант: сумма позиций =   |
   |  итог заказа                  |
   +-------------------------------+
```

Правила агрегата: транзакция меняет один агрегат целиком; ссылки между агрегатами — по идентификатору (`CustomerID`), а не прямым указателем на чужой объект.

## Зачем это в System Design

- Bounded context — естественный кандидат на границу микросервиса и на границу владения данными.
- Aggregate — естественная граница транзакции и консистентности (внутри — сильная согласованность, между агрегатами/сервисами — eventual).
- Ubiquitous language снижает потери смысла между бизнесом и кодом.

> ⚠️ Частый вопрос на собеседовании: чем entity отличается от value object? Entity имеет идентичность и сравнивается по ней (жизненный цикл, меняющиеся атрибуты при том же ID). Value object не имеет идентичности, сравнивается по значению и обычно неизменяем — его заменяют целиком.

> ⚠️ Частый вопрос на собеседовании: как DDD помогает нарезать микросервисы? Через bounded contexts: граница контекста (со своей моделью, языком и данными) — хороший кандидат на границу сервиса. Это уменьшает связанность и не даёт разрезать систему по техническим слоям (что ведёт к распределённому монолиту).
