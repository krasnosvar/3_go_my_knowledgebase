# Dependency Injection в Go

Dependency Injection (DI) — зависимость не создаётся внутри объекта, а передаётся ему извне. Это практическая форма принципа инверсии зависимостей (DIP): код зависит от абстракции (интерфейса), а конкретную реализацию подставляют снаружи.

## Проблема без DI

Когда объект сам создаёт свои зависимости, он к ним жёстко привязан:

```go
type Service struct {
    db *PostgresDB // жёсткая привязка к конкретной БД
}

func NewService() *Service {
    return &Service{db: NewPostgresDB("...")} // сами создали, не подменить
}
```

Такой `Service` нельзя протестировать без настоящей PostgreSQL и нельзя заменить БД, не правя сам сервис.

## DI через интерфейсы и конструкторы

Идиома Go: зависимость описывается **интерфейсом**, а конкретная реализация приходит через **конструктор**.

```go
// Порт (интерфейс) — потребитель объявляет то, что ему нужно.
type UserRepo interface {
    Save(u User) error
    Get(id string) (User, bool)
}

// Сервис зависит от абстракции, а не от конкретной БД.
type Service struct {
    repo UserRepo
}

// Конструктор принимает зависимость извне (constructor injection).
func NewService(repo UserRepo) *Service {
    return &Service{repo: repo}
}
```

В `main` (composition root) собираем граф зависимостей и подставляем нужную реализацию:

```go
func main() {
    repo := NewPostgresRepo(...) // прод
    // repo := NewInMemoryRepo() // тесты/локально — подмена одной строкой
    svc := NewService(repo)
    _ = svc
}
```

Идиомы Go, которые делают это удобным:
- **«Accept interfaces, return structs»** — принимайте интерфейсы (гибкость на входе), возвращайте конкретные типы.
- **Маленькие интерфейсы** — объявляйте узкий интерфейс на стороне потребителя (только нужные методы), а не «толстый» на стороне реализации.
- **Composition root** — единственное место (обычно `main`), где создаются конкретные реализации и связывается весь граф зависимостей.

## Ручной DI vs генераторы (wire)

- **Ручной DI** — просто вызовы конструкторов в `main`, передающие зависимости по цепочке. Прозрачно, без магии, отлично для малых и средних графов. В большинстве Go-проектов этого достаточно.
- **google/wire** — генератор кода: описываете «провайдеры» (конструкторы), а wire на этапе компиляции генерирует код сборки графа. Плюс — компилтайм-проверка и отсутствие рантайм-рефлексии; минус — дополнительный инструмент и генерация. Полезно, когда граф зависимостей большой и вручную его собирать утомительно.
- **DI-контейнеры на рефлексии** (например, uber/dig) — собирают граф в рантайме. Меньше кода, но ошибки всплывают в рантайме, а не при компиляции; в Go применяют реже.

Практический выбор: начинайте с ручного DI; переходите на wire, только когда ручная сборка графа становится реальной болью.

## Что DI даёт

- Тестируемость — подставляем заглушки/фейки вместо реальной инфраструктуры.
- Заменяемость — меняем реализацию (БД, транспорт), не трогая потребителя.
- Явные зависимости — по сигнатуре конструктора видно, что нужно объекту.

> ⚠️ Частый вопрос на собеседовании: нужен ли в Go DI-фреймворк? Обычно нет. DI в Go — это просто передача интерфейсов через конструкторы и сборка графа в `main`. Фреймворк (wire) оправдан только при большом графе зависимостей; он не добавляет возможностей языку, а автоматизирует рутинную сборку.

> ⚠️ Частый вопрос на собеседовании: где объявлять интерфейс зависимости? На стороне потребителя (там, где вызывают), а не на стороне реализации. Тогда потребитель не зависит от конкретного пакета-реализации, а реализация неявно удовлетворяет узкому интерфейсу — это и есть инверсия зависимостей по-Go.
