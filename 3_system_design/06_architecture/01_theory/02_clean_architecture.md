# Clean Architecture

Clean Architecture (Роберт Мартин) — способ разложить код по концентрическим слоям так, чтобы бизнес-логика не зависела от деталей (БД, веб-фреймворка, внешних API). Родственные идеи: Hexagonal Architecture (ports & adapters, Алистер Кокберн) и Onion Architecture — все они про одно и то же **правило зависимостей**.

## Слои

Снаружи — детали (изменчивые), внутри — бизнес-суть (стабильная).

```
        +-------------------------------------------------+
        |  Frameworks & Drivers                           |   внешний слой
        |  (HTTP, gRPC, SQL-драйвер, CLI, kafka-клиент)   |   детали
        |   +-----------------------------------------+   |
        |   |  Interface Adapters                     |   |
        |   |  (handlers, presenters, repo-реализации)|   |
        |   |   +---------------------------------+   |   |
        |   |   |  Use Cases (Application)        |   |   |
        |   |   |  (сценарии, оркестрация)        |   |   |
        |   |   |   +-------------------------+   |   |   |
        |   |   |   |  Entities (Domain)      |   |   |   |
        |   |   |   |  (бизнес-правила)       |   |   |   |   внутреннее ядро
        |   |   |   +-------------------------+   |   |   |
        |   |   +---------------------------------+   |   |
        |   +-----------------------------------------+   |
        +-------------------------------------------------+
```

- **Entities (домен)** — самые общие и стабильные бизнес-правила и объекты предметной области. Ничего не знают о БД, HTTP, фреймворках.
- **Use Cases (приложение)** — сценарии приложения: оркестрируют сущности, описывают «что система делает» (создать заказ, зарегистрировать пользователя). Зависят только от домена и от интерфейсов (портов).
- **Interface Adapters** — переводчики между внутренним и внешним миром: HTTP-хэндлеры, presenters, конкретные реализации репозиториев (адаптеры к БД).
- **Frameworks & Drivers** — сам веб-фреймворк, драйвер СУБД, брокер сообщений. Самая изменчивая периферия.

## Правило зависимостей (Dependency Rule)

**Исходные зависимости направлены только внутрь.** Внутренний слой ничего не знает о внешнем: имена типов, функций, структур из внешних слоёв не должны упоминаться во внутренних.

```
Frameworks -> Adapters -> Use Cases -> Entities
   (зависимости кода указывают ВНУТРЬ, к ядру)
```

Следствие: бизнес-логику можно тестировать без БД и HTTP; заменить PostgreSQL на in-memory или веб на CLI — не трогая ядро.

## Инверсия зависимостей (порты и адаптеры)

Проблема: use case должен что-то сохранить в БД — казалось бы, это зависимость наружу (на слой адаптеров). Решение — **инверсия зависимостей (DIP)**: use case объявляет **порт** (интерфейс) в своём слое и зависит от него, а конкретный **адаптер** во внешнем слое этот интерфейс реализует.

```
   Use Case  ──определяет──▶  Repository (интерфейс, порт)   [внутренний слой]
                                      ▲
                                      │ реализует (implements)
                              PostgresRepo (адаптер)         [внешний слой]
```

Направление вызова во время выполнения — наружу (use case вызывает БД), но направление **зависимости кода** — внутрь: адаптер зависит от интерфейса ядра, а не наоборот. Интерфейс принадлежит тому, кто его использует (потребителю), а не тому, кто реализует.

В Go это ложится особенно естественно: интерфейсы удовлетворяются неявно (structural typing), поэтому порт объявляют в пакете use case, а адаптер в другом пакете просто соответствует ему — без директивы `implements` и без импорта интерфейса адаптером.

## Что это даёт

- Тестируемость: ядро тестируется на заглушках портов, без инфраструктуры.
- Заменяемость деталей: БД, транспорт, внешние сервисы меняются без правки бизнес-логики.
- Понятные границы: зависимости идут в одну сторону, нет циклов между модулями.

## Цена и границы применимости

Clean Architecture добавляет слои, интерфейсы и мэппинг данных между слоями — это оправдано для нетривиальной бизнес-логики с долгим сроком жизни. Для простого CRUD-сервиса строгое разделение на 4 слоя может быть избыточным; берите принцип (зависимости внутрь, изоляция домена от деталей), а число физических слоёв — по необходимости.

> ⚠️ Частый вопрос на собеседовании: как use case «пишет в БД», не завися от БД? Через инверсию зависимостей: use case зависит от интерфейса-порта (например, `Repository`), объявленного в своём слое; конкретный адаптер к БД реализует этот интерфейс во внешнем слое. Зависимость кода указывает внутрь, поток управления во время выполнения — наружу.

> ⚠️ Частый вопрос на собеседовании: кому «принадлежит» интерфейс — тому, кто реализует, или тому, кто использует? Потребителю. Интерфейс объявляется рядом с use case (тем, кто его вызывает), поэтому внешний адаптер зависит от ядра, а не ядро от адаптера. В Go это ещё и идиома: «accept interfaces» на стороне вызывающего.
