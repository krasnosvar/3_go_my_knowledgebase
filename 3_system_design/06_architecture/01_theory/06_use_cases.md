# Architecture: практические применения

Как архитектурные решения этого раздела всплывают в реальной инженерии и в задачах System Design. Сводка «когда что», без воды.

## Выбор стиля: монолит или микросервисы

- **Начинай с модульного монолита**, если границы домена не устоялись, команда небольшая, важна скорость. Держи чёткие внутренние модули — потом их проще выделить.
- **Переходи к сервисам** по конкретным причинам: часть системы требует независимого масштабирования, разные команды тормозят друг друга на общем деплое, нужна изоляция отказов.
- **Избегай распределённого монолита**: раздельный деплой и раздельные данные — обязательное условие, иначе получишь сложность распределёнки без её выгод.

## Границы сервисов через DDD

- Режь по **bounded contexts**, а не по техническим слоям. Один контекст = один язык, одна модель, свои данные — хороший кандидат на границу сервиса.
- Владение данными: у сервиса своя БД, чужие данные — по идентификатору и через API/события, не через общую таблицу.
- **Aggregate** задаёт границу транзакции: внутри — сильная согласованность, между сервисами — eventual (саги, идемпотентность, outbox).

## Структура кода внутри сервиса

- Применяй **правило зависимостей**: домен и use case не знают о HTTP/БД; детали (транспорт, хранилище) — снаружи и подключаются через порты.
- **Порты и адаптеры**: интерфейс объявляй на стороне потребителя (use case), реализацию — в адаптере. Это позволяет тестировать ядро на заглушках и менять инфраструктуру без правки бизнес-логики.
- Не переусердствуй: для простого CRUD хватит пары слоёв; строгое 4-слойное деление оправдано при нетривиальной логике и долгом сроке жизни.

## Сборка зависимостей (DI)

- **Constructor injection** + интерфейсы: зависимость передаётся снаружи, потребитель зависит от абстракции.
- **Composition root** в `main`: единственное место, где создаются конкретные реализации и связывается граф.
- **Ручной DI по умолчанию**; wire/кодогенерация — только когда граф реально большой.

## Инфраструктура связи сервисов

- **API Gateway** — периметр: маршрутизация, auth, rate limiting, TLS, наблюдаемость. Держи тонким, не клади туда бизнес-логику.
- **BFF** — отдельный шлюз под клиента (mobile/web) для агрегации и подгонки ответов.
- **Service discovery** — динамический поиск инстансов; в Kubernetes обычно server-side через Service + DNS и health-checks.

## Типичная сборка запроса в микросервисной системе

```
клиент ─▶ API Gateway ─(auth, routing)─▶ BFF ─(агрегация)─▶ сервисы
   сервисы находят друг друга через discovery (DNS/registry)
   внутри сервиса: handler(adapter) ─▶ use case ─▶ entity, port ─▶ adapter(БД)
```

## Частые ошибки

- Разрезали монолит по слоям (UI-сервис, «логика»-сервис, «БД»-сервис) → распределённый монолит.
- Общая БД у нескольких сервисов → скрытая жёсткая связанность.
- Синхронные цепочки A→B→C→D без таймаутов/предохранителей → каскадные отказы.
- Бизнес-логика в API Gateway → узкое место и единая точка отказа.
- Оверинжиниринг: Clean Architecture на 4 слоя ради простого CRUD.

> ⚠️ Частый вопрос на собеседовании: как бы вы разбили монолит на сервисы? Ожидаемый ход: определить bounded contexts (DDD), сделать границы сервисов по ним, дать каждому свои данные, связать через API/события, обеспечить раздельный деплой — и явно проговорить, что синхронные цепочки и общая БД ведут к распределённому монолиту.

> ⚠️ Частый вопрос на собеседовании: как эти темы связаны между собой? DDD даёт границы (bounded context → сервис, aggregate → транзакция); Clean Architecture/DI организуют код внутри сервиса (зависимости внутрь, порты/адаптеры); Gateway/discovery/BFF связывают сервисы снаружи. Это один сквозной путь от домена до инфраструктуры.
