# Монолит vs микросервисы

Два полярных стиля организации системы: единый развёртываемый артефакт против набора независимо развёртываемых сервисов. Выбор — это не вопрос «моды», а компромисс между простотой разработки и независимостью масштабирования/деплоя.

## Монолит

Всё приложение — один процесс и один артефакт деплоя. Модули общаются вызовами функций внутри процесса, данные обычно в одной БД.

- **Плюсы:**
  - Простой деплой — один бинарник/образ, одна CI/CD-цепочка.
  - Простая отладка и трассировка — весь путь запроса в одном процессе, обычный стек вызовов.
  - Нет сетевых задержек и частичных отказов между модулями — вызов функции надёжен и синхронен.
  - Транзакции — одна БД, легко держать консистентность через ACID-транзакцию.
  - Дёшево на старте — не нужна инфраструктура для service discovery, распределённого трейсинга, межсервисной аутентификации.
- **Минусы:**
  - Масштабируется целиком — нельзя масштабировать только «горячий» модуль, реплицируется весь процесс.
  - Один стек технологий на всех.
  - Деплой всего ради изменения в одном модуле; рискованные релизы.
  - При росте команды растёт связанность (coupling), границы модулей размываются, если не следить.

## Микросервисы

Система разбита на независимые сервисы, каждый со своей ответственностью, своим деплоем и (в идеале) своей БД. Общаются по сети — HTTP/gRPC или через брокер сообщений.

- **Плюсы:**
  - Независимый деплой и релизный цикл у каждой команды/сервиса.
  - Независимое масштабирование — реплицируем только нагруженный сервис.
  - Разные технологии под разные задачи (polyglot).
  - Изоляция отказов — падение одного сервиса не обязано ронять всю систему (при грамотных таймаутах/предохранителях).
- **Минусы:**
  - Сетевые вызовы: задержки, таймауты, ретраи, частичные отказы (fallacies of distributed computing).
  - Нет распределённых ACID-транзакций «из коробки» — согласованность через саги, идемпотентность, eventual consistency.
  - Операционная сложность: service discovery, распределённый трейсинг, централизованные логи, версионирование контрактов.
  - Тяжелее локальная отладка и сквозное тестирование.

## Направление сравнения

```
         Монолит                        Микросервисы
   +--------------------+        +------+  +------+  +------+
   |  Orders            |        |Orders|  |Users |  |Bills |
   |  Users             |        |  DB  |  |  DB  |  |  DB  |
   |  Billing           |        +--+---+  +--+---+  +--+---+
   |  (одна БД)         |           |         |         |
   +--------------------+           +----сеть-+----+----+
   1 деплой, 1 процесс           N деплоев, N процессов, N БД
```

## Когда что оправдано

- **Монолит (в т.ч. «модульный монолит»)** — новый продукт, небольшая команда, неустоявшиеся границы домена, нужна скорость итераций. Чёткие внутренние модули с явными границами дают 80% пользы микросервисов без сетевой цены.
- **Микросервисы** — большие организации с множеством автономных команд, разные требования к масштабированию/надёжности у частей системы, устоявшиеся доменные границы.

Здоровый путь чаще всего: начать с модульного монолита и выделять сервисы по мере роста боли, когда границы уже понятны.

## Распределённый монолит — антипаттерн

Худший из миров: сервисы физически разнесены по сети (платите сетевую цену), но остаются жёстко связанными, поэтому не получаете независимости.

Признаки распределённого монолита:
- Сервисы нельзя задеплоить по отдельности — релиз всегда «пачкой», их версии должны совпадать.
- Общая БД, в которую пишут несколько сервисов (нарушены границы данных).
- Синхронные цепочки вызовов A→B→C→D: любой отказ или задержка внизу рушит весь запрос.
- Изменение контракта одного сервиса ломает соседей, координация релизов через таблицы согласований.

Итог: сложность распределённой системы есть, а выгод (независимый деплой/масштаб/изоляция отказов) нет. Причина обычно — разрезали монолит по техническим слоям, а не по доменным границам, и оставили общую БД.

> ⚠️ Частый вопрос на собеседовании: с чего начинать — с монолита или микросервисов? Разумный ответ: с монолита (лучше модульного), потому что на старте границы домена неизвестны, а стоимость операционной сложности микросервисов реальна сразу. Выделять сервисы — по мере того как появляются конкретные причины: независимое масштабирование, автономия команд, изоляция отказов.

> ⚠️ Частый вопрос на собеседовании: чем распределённый монолит отличается от микросервисов? Формально это тоже несколько сервисов по сети, но они жёстко связаны (общая БД, синхронный деплой, ломкие контракты), поэтому платят сетевую цену без выгод независимости. Ключевые маркеры независимости — раздельный деплой и раздельные данные.
