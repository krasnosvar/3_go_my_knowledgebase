# API Gateway, Service Discovery, BFF

Инфраструктурные компоненты, которые появляются, когда монолит превращается в набор сервисов: единая точка входа, механизм «как сервисы находят друг друга» и специализированные шлюзы под конкретных клиентов.

## API Gateway

Единая точка входа для внешних клиентов перед набором внутренних сервисов. Клиент не знает о внутренней топологии — он общается со шлюзом.

```
                    +-------------+     +-----------------+
   клиенты  ───────▶|             |────▶| Orders Service  |
  (web/mobile)      | API Gateway |────▶| Users Service   |
                    |             |────▶| Billing Service |
                    +-------------+     +-----------------+
```

Что обычно берёт на себя шлюз (cross-cutting concerns):
- Маршрутизация запросов к нужному сервису.
- Аутентификация/авторизация на входе (проверка токена один раз на периметре).
- Rate limiting, квоты, защита от перегрузки.
- Терминация TLS, CORS.
- Агрегация ответов нескольких сервисов, преобразование протоколов (например, наружу REST, внутрь gRPC).
- Наблюдаемость: логи, метрики, трейсинг на границе.

Риск: шлюз легко превращается в «толстую» точку с бизнес-логикой и в узкое место/единую точку отказа — держите его тонким и масштабируемым.

## Service Discovery

Как сервис узнаёт сетевой адрес другого сервиса, когда инстансы динамически появляются/исчезают (автоскейл, рестарты, разные IP).

- **Client-side discovery** — клиент спрашивает реестр (service registry) список живых инстансов и сам выбирает один (балансировка на клиенте). Пример: Consul + клиентская логика.
- **Server-side discovery** — клиент идёт на фиксированный адрес балансировщика/прокси, а тот сам находит живой инстанс. Пример: Kubernetes Service + kube-proxy, DNS-имя `svc.namespace.svc.cluster.local`.
- **Реестр сервисов** — база «имя сервиса → адреса живых инстансов», наполняется через регистрацию и health-checks (Consul, etcd, встроенный реестр Kubernetes).

```
   Инстансы регистрируются:          Клиент резолвит имя:
   svc-a:10.0.0.1 ─┐                 "svc-a" ──▶ [registry/DNS] ──▶ 10.0.0.2
   svc-a:10.0.0.2 ─┼─▶ [ Registry ]  (отдаёт только здоровые инстансы)
   svc-a:10.0.0.3 ─┘   + healthcheck
```

В Kubernetes это чаще всего «бесплатно»: Service даёт стабильное DNS-имя и виртуальный IP, а платформа сама держит список здоровых подов.

## BFF (Backend for Frontend)

Отдельный бэкенд-шлюз под конкретный тип клиента: свой для web, свой для мобильного, свой для партнёрского API.

```
   Web  ───▶ [ BFF-web ] ──┐
                           ├──▶ внутренние сервисы (Orders, Users, ...)
   Mobile ─▶ [ BFF-mobile ]┘
```

Зачем: у разных клиентов разные потребности к данным и форме ответа. Мобильному нужны компактные агрегированные ответы (экономия трафика/раундтрипов), web — другие. BFF агрегирует и формирует ответ под своего клиента, не раздувая общие сервисы клиент-специфичной логикой.

Отличие от общего API Gateway: gateway — универсальная точка входа с cross-cutting concerns; BFF — клиент-ориентированный слой агрегации/подгонки данных (их часто совмещают: gateway на периметре + несколько BFF за ним).

> ⚠️ Частый вопрос на собеседовании: чем API Gateway отличается от BFF? Gateway — единая универсальная точка входа (маршрутизация, auth, rate limit, TLS) для всех клиентов; BFF — отдельный бэкенд под конкретный фронтенд, задача которого — агрегировать и подогнать данные под нужды именно этого клиента. Часто применяются вместе.

> ⚠️ Частый вопрос на собеседовании: client-side vs server-side discovery? При client-side клиент сам берёт список инстансов из реестра и балансирует; при server-side клиент обращается к стабильному прокси/балансировщику, который сам находит живой инстанс. В Kubernetes используется server-side через Service + DNS.
