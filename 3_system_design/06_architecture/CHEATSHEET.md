## Монолит vs микросервисы

Подробно: [01_monolith_vs_microservices.md](./01_theory/01_monolith_vs_microservices.md).

| Аспект | Монолит | Микросервисы |
| :--- | :--- | :--- |
| Деплой | один артефакт, одна CI/CD-цепочка | независимый у каждого сервиса |
| Масштабирование | целиком | только нагруженный сервис |
| Вызовы между модулями | функция в процессе: надёжно, синхронно | сеть: задержки, таймауты, частичные отказы |
| Транзакции | ACID в одной БД | саги, идемпотентность, eventual consistency |
| Стек | один на всех | polyglot |
| Отладка | обычный стек вызовов | распределённый трейсинг, централизованные логи |
| Изоляция отказов | нет | есть (при таймаутах и предохранителях) |
| Цена на старте | низкая | discovery, трейсинг, межсервисная auth, версии контрактов |

| Ситуация | Выбор |
| :--- | :--- |
| Новый продукт, маленькая команда, границы домена не устоялись | модульный монолит |
| Много автономных команд, разные требования к масштабу/надёжности частей, устоявшиеся границы | микросервисы |
| Путь по умолчанию | модульный монолит → выделять сервисы по мере конкретной боли |

| Признак распределённого монолита | Почему плохо |
| :--- | :--- |
| Релиз только «пачкой», версии должны совпадать | нет независимого деплоя |
| Общая БД, в которую пишут несколько сервисов | нарушены границы данных |
| Синхронные цепочки A→B→C→D | отказ внизу рушит весь запрос |
| Изменение контракта ломает соседей | связанность как у монолита + сетевая цена |

Маркеры настоящей независимости: **раздельный деплой и раздельные данные**.

## Clean Architecture

Подробно: [02_clean_architecture.md](./01_theory/02_clean_architecture.md).

| Слой (снаружи → внутрь) | Что лежит |
| :--- | :--- |
| Frameworks & Drivers | HTTP, gRPC, SQL-драйвер, CLI, kafka-клиент |
| Interface Adapters | handlers, presenters, реализации репозиториев |
| Use Cases | сценарии приложения, оркестрация сущностей; зависят от домена и портов |
| Entities | бизнес-правила; ничего не знают о БД/HTTP |

| Понятие | Суть |
| :--- | :--- |
| Dependency Rule | зависимости кода направлены только **внутрь**: `Frameworks -> Adapters -> Use Cases -> Entities` |
| Порт | интерфейс, объявленный в слое use case (у потребителя) |
| Адаптер | реализация порта во внешнем слое (`PostgresRepo`) |
| Инверсия | вызов в рантайме идёт наружу, зависимость кода — внутрь |
| Go-специфика | неявная реализация интерфейсов: адаптер не импортирует интерфейс и не пишет `implements` |
| Родственные | Hexagonal (ports & adapters), Onion — то же правило зависимостей |

## DDD

Подробно: [03_ddd_basics.md](./01_theory/03_ddd_basics.md).

| Понятие | Суть | Пример |
| :--- | :--- | :--- |
| Ubiquitous Language | один словарь у бизнеса и кода | `Order`, `LineItem`, `Shipment`, а не `DataRow` |
| Bounded Context | граница, внутри которой модель однозначна | `Customer` в Sales ≠ `Customer` в Support |
| Context Map | явные связи контекстов | shared kernel, customer/supplier, anti-corruption layer |
| Entity | идентичность, равенство по ID | два заказа с одинаковыми полями, но разными `ID` — разные |
| Value Object | без идентичности, равенство по значению, неизменяемый | `Money{amount, currency}`, `Address`, `DateRange` |
| Aggregate | кластер, меняется целиком; вход только через root | `Order` (root) + `LineItem` + `Money` |

| Правило | Следствие для System Design |
| :--- | :--- |
| Транзакция меняет один агрегат | aggregate = граница транзакции и сильной согласованности |
| Ссылки между агрегатами — по ID (`CustomerID`) | между агрегатами/сервисами — eventual |
| Bounded context ≈ команда ≈ сервис | границу сервиса режем по контексту, а не по техническому слою |

## Dependency Injection

Подробно: [04_dependency_injection.md](./01_theory/04_dependency_injection.md).

```go
type UserRepo interface { // порт объявляет потребитель
	Save(u User) error
	Get(id string) (User, bool)
}

type Service struct{ repo UserRepo }

func NewService(repo UserRepo) *Service { return &Service{repo: repo} } // constructor injection

// composition root — main:
// svc := NewService(NewPostgresRepo(dsn)) // прод
// svc := NewService(NewInMemoryRepo())    // тесты/локально
```

| Идиома / способ | Когда |
| :--- | :--- |
| «Accept interfaces, return structs» | всегда |
| Узкий интерфейс на стороне потребителя | всегда |
| Composition root в `main` | единственное место создания конкретных реализаций |
| Ручной DI (вызовы конструкторов) | по умолчанию, малые и средние графы |
| `google/wire` (кодогенерация) | большой граф; проверка при компиляции, без рефлексии |
| Контейнеры на рефлексии (`uber/dig`) | редко: ошибки всплывают в рантайме |

## API Gateway, discovery, BFF

Подробно: [05_gateway_discovery.md](./01_theory/05_gateway_discovery.md).

| Компонент | Задача | Риск / нюанс |
| :--- | :--- | :--- |
| API Gateway | единая точка входа: маршрутизация, auth, rate limit, TLS, CORS, агрегация, REST→gRPC, наблюдаемость | толстеет бизнес-логикой → узкое место и SPOF |
| BFF | отдельный шлюз под клиента (web / mobile / партнёры): агрегирует и подгоняет ответ | часто стоит за общим gateway |
| Service registry | «имя → живые инстансы», наполняется регистрацией и health-checks | Consul, etcd, реестр Kubernetes |

| Discovery | Кто выбирает инстанс | Пример |
| :--- | :--- | :--- |
| Client-side | клиент: берёт список из реестра и балансирует сам | Consul + клиентская логика |
| Server-side | балансировщик/прокси за стабильным адресом | Kubernetes Service + kube-proxy, `svc.namespace.svc.cluster.local` |

## Сквозной путь запроса

Подробно: [06_use_cases.md](./01_theory/06_use_cases.md).

```
клиент ─▶ API Gateway ─(auth, routing)─▶ BFF ─(агрегация)─▶ сервисы
сервисы находят друг друга через discovery (DNS/registry)
внутри сервиса: handler(adapter) ─▶ use case ─▶ entity, port ─▶ adapter(БД)
```

## Ловушки

- ⚠️ Резать монолит по техническим слоям (UI / «логика» / «БД») → распределённый монолит.
- ⚠️ Общая БД у нескольких сервисов → скрытая жёсткая связанность.
- ⚠️ Синхронные цепочки A→B→C→D без таймаутов и предохранителей → каскадные отказы.
- ⚠️ Бизнес-логика в API Gateway → узкое место и единая точка отказа.
- ⚠️ Clean Architecture на 4 слоя ради простого CRUD — оверинжиниринг; берите принцип, а не число слоёв.
- ⚠️ Интерфейс рядом с реализацией вместо потребителя → ядро зависит от пакета адаптера.
- ⚠️ Сервис сам создаёт зависимость (`NewPostgresDB` внутри `NewService`) → не подменить в тесте.
- ⚠️ Прямой указатель на внутреннюю сущность чужого агрегата вместо ссылки по ID.
