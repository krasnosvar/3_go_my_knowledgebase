# Уровни согласованности (Consistency models)

Модель согласованности — контракт: что чтение вправе увидеть после набора записей на реплицированных данных. От строгой (дорогой, интуитивной) до слабой (дешёвой, с аномалиями).

## Спектр моделей

### Strong consistency / линеаризуемость

Система ведёт себя как единственная копия данных: как только запись завершилась, любое последующее чтение (с любого узла) видит это значение или более новое. Есть единый согласованный порядок операций.

- Плюсы: просто рассуждать, нет аномалий.
- Минусы: дорого — требует синхронной координации между репликами (задержка), при разделении сети жертвует доступностью (CP, см. `03_cap_theorem.md`).

### Eventual consistency (согласованность в конечном счёте)

Если новых записей нет, реплики *со временем* сойдутся к одному значению. Но в моменте разные чтения могут вернуть разные (устаревшие) версии.

- Плюсы: высокая доступность и низкая задержка (AP).
- Минусы: аномалии чтения; конфликты приходится разрешать (LWW, векторные часы, CRDT).

### Промежуточные гарантии (клиентоцентричные)

Часто нужны не полная линеаризуемость, а точечные гарантии для одного клиента:

- **Read-your-writes (read-after-write).** Клиент всегда видит *свои* завершённые записи. Не гарантирует, что увидит чужие свежие. Лечит аномалию «обновил профиль — вижу старое».
- **Monotonic reads.** Последовательные чтения одного клиента не «едут назад» во времени: увидев значение версии N, дальше не увидишь версию < N. Лечит «данные прыгают» при чтении с разных реплик.
- **Monotonic writes.** Записи одного клиента применяются в порядке их отправки.
- **Consistent prefix reads.** Читатель видит записи в причинно-согласованном порядке (не «ответ раньше вопроса»). Важно при шардировании.

Эти гарантии слабее strong, но устраняют самые болезненные аномалии дешевле.

```
Спектр:  strong (линеаризуемость)
            │  read-your-writes / monotonic reads / causal
            ▼
         eventual
   ← строже, дороже, ниже доступность   слабее, дешевле, выше доступность →
```

## Кворумы (quorum)

В leaderless-репликации (Dynamo-стиль) согласованность настраивается кворумами на `N` репликах:

- `N` — число реплик, хранящих ключ.
- `W` — сколько реплик должны подтвердить **запись**, чтобы она считалась успешной.
- `R` — с скольких реплик читаем, выбирая самую свежую версию.

**Правило кворума: `W + R > N`.** Тогда множества узлов записи и чтения гарантированно **пересекаются** хотя бы в одном узле — значит, чтение увидит последнюю успешную запись.

```
N=3, W=2, R=2, W+R=4 > 3
запись в реплики {A,B}          пересечение = {B}
чтение из реплик {B,C}   ──▶  читатель видит запись через узел B
```

Настройка баланса:
- `W=N, R=1` — быстрые чтения, медленные/уязвимые записи.
- `W=1, R=N` — быстрые записи, дорогие чтения.
- `W=R=⌈(N+1)/2⌉` — сбалансированный кворум большинства.
- `W+R ≤ N` — кворум *не* гарантируется: можно прочитать устаревшее (eventual). Так сознательно делают ради доступности/скорости.

Оговорки: строгий кворум всё же допускает аномалии при сбоях/конкурентных записях (нужны read-repair, версионирование); «sloppy quorum» с hinted handoff повышает доступность, но ослабляет гарантию пересечения. Пример работы кворума — в `02_examples/03_quorum_rw`.

> ⚠️ Частый вопрос на собеседовании: почему кворум обеспечивает согласованное чтение и что означает `W + R > N`? При `W+R>N` множество узлов, подтвердивших запись, и множество узлов, опрошенных при чтении, обязаны пересекаться минимум в одном узле — на нём лежит последняя запись, и чтение (выбрав самую свежую версию) её увидит.

> ⚠️ Частый вопрос на собеседовании: чем read-your-writes отличается от strong consistency? Read-your-writes — гарантия только для одного клиента (он видит собственные записи), но он может не видеть свежие чужие. Strong consistency — глобальная: любое чтение любого клиента видит последнюю запись.
