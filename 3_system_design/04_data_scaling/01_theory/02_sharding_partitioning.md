# Шардирование и партиционирование

Когда данные не влезают на один узел (по объёму или по нагрузке на запись), их **разбивают на части**. Репликация копирует одни и те же данные, а разбиение раскладывает *разные* данные по разным местам.

## Партиционирование vs шардирование

Термины часто путают. Практическое разграничение:

- **Партиционирование (partitioning)** — разбиение таблицы/датасета на части (partitions). Может быть **в пределах одного узла** (например, партиции таблицы по месяцам в одной СУБД) — тогда это про управляемость и производительность запросов, а не про распределённость.
- **Шардирование (sharding)** — это партиционирование, при котором части (**шарды**) разложены **по разным узлам/серверам**. То есть шардирование = горизонтальное партиционирование, распределённое между машинами.

```
Партиционирование (один узел):        Шардирование (несколько узлов):
┌──────────── DB ────────────┐        ┌── node A ──┐ ┌── node B ──┐
│ part[2024] part[2025] ...  │        │  shard 0   │ │  shard 1   │
└─────────────────────────────┘        └────────────┘ └────────────┘
```

Итог: всякий шард — это партиция, но не всякая партиция — шард. Дальше речь о горизонтальном шардировании между узлами.

## Ключ шардирования (shard key)

**Ключ шардирования** — поле (или набор полей), по которому вычисляется, в какой шард попадёт строка (например, `user_id`, `tenant_id`). От него зависит всё:

- **Равномерность.** Плохой ключ создаёт «горячие» шарды (hot spots): например, шардирование по стране, где 80% пользователей в одной стране.
- **Локальность запросов.** Хорошо, когда частый запрос обслуживается одним шардом. Запрос, которому нужны все шарды (scatter-gather), дорогой.
- **Кросс-шардовые операции.** JOIN и транзакции между шардами сложны и медленны — их стараются избегать выбором ключа (например, все данные одного тенанта в одном шарде).

## Стратегии разбиения

### Hash-партиционирование

`shard = hash(key) % N`. Хеш «размазывает» ключи равномерно.

- Плюс: равномерное распределение, нет hot spots по значению ключа.
- Минус: теряется диапазонная локальность — запрос «все заказы за период» уходит во все шарды. При изменении `N` (ре-шардинг) переезжает почти всё (см. ниже про consistent hashing).

### Range-партиционирование

Ключи делятся на непрерывные диапазоны: `[a–f] → shard0`, `[g–m] → shard1`, ...

- Плюс: эффективные диапазонные запросы (range scan) — они попадают в один-два шарда.
- Минус: перекос и hot spots. Классика — ключ по времени: все свежие записи льются в последний шард (горячий), старые лежат мёртвым грузом.

### Directory-партиционирование (lookup table)

Отдельный сервис/таблица явно хранит соответствие «ключ (или диапазон) → шард».

- Плюс: максимальная гибкость — можно перемещать данные и менять раскладку, просто обновив справочник.
- Минус: справочник — лишний хоп и единая точка отказа/узкое место; его самого надо реплицировать и кэшировать.

| Стратегия | Диапазонные запросы | Равномерность | Гибкость ре-шардинга |
|---|---|---|---|
| Hash | плохо (scatter) | хорошо | плохо (без consistent hashing) |
| Range | хорошо | риск hot spots | средне (сплит/мердж диапазонов) |
| Directory | зависит | управляемая | отлично |

## Ре-шардинг (rebalancing)

Добавили/убрали узлы — данные надо перераспределить. Цель: **переместить как можно меньше ключей** и не останавливать сервис.

- **Наивный `hash % N`** — при смене `N` меняется остаток почти для всех ключей: перемещается ~(N−1)/N данных. Практически неприменимо на живом кластере.
- **Consistent hashing (кольцо)** — узлы и ключи хешируются на кольцо; ключ идёт к ближайшему по часовой стрелке узлу. При добавлении/удалении узла переезжает лишь доля ≈ 1/N ключей (соседний участок). **Виртуальные узлы** (несколько точек на кольце на один физический узел) выравнивают распределение. Пример — в `02_examples/01_consistent_hashing`.
- **Фиксированное число партиций.** Заранее создать много партиций (напр. 1024), больше числа узлов; при ре-шардинге целыми партициями двигаем их между узлами, не пересчитывая хеши. Так делает, например, Riak/Elasticsearch-подобный подход.

> ⚠️ Частый вопрос на собеседовании: чем плох `hash(key) % N` при изменении числа узлов и как решает consistent hashing? При смене `N` остаток от деления меняется почти у всех ключей — перемещается ~(N−1)/N данных. Consistent hashing раскладывает узлы и ключи на кольцо, поэтому при добавлении/удалении узла двигается только ~1/N ключей (участок соседа), а виртуальные узлы выравнивают нагрузку.

> ⚠️ Частый вопрос на собеседовании: как выбрать ключ шардирования? Так, чтобы данные распределялись равномерно (нет hot spots), частые запросы обслуживались одним шардом (локальность) и минимизировались кросс-шардовые JOIN/транзакции. Часто это естественная граница изоляции — `user_id`/`tenant_id`.
