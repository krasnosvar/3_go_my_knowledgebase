# SQL vs NoSQL: когда что

Выбор хранилища — про модель данных, паттерны доступа и требования к согласованности/масштабу, а не про моду. «NoSQL» — это зонтик над очень разными системами.

## SQL (реляционные СУБД)

PostgreSQL, MySQL, и т.п. Данные в таблицах со строгой схемой, связи через внешние ключи, язык — SQL.

- **Сильные стороны:** строгая схема и целостность (constraints, FK), мощные ad-hoc запросы и JOIN, **ACID-транзакции**, зрелость и экосистема.
- **Слабые стороны:** горизонтальное масштабирование записи сложнее (нужно шардирование, кросс-шардовые JOIN болезненны); жёсткая схема = миграции.
- **Когда:** сложные связи и запросы заранее не известны; критична целостность и транзакции (платежи, учёт, бронирования); данные хорошо ложатся в таблицы.

## NoSQL — семейства

### Key-Value (Redis, DynamoDB, Valkey)

Словарь `ключ → значение`. Простейшая модель, очень быстрая, легко шардируется.
- Когда: кэш, сессии, счётчики, лидерборды; доступ строго по ключу.

### Документные (MongoDB, Couchbase)

Хранят JSON/BSON-документы, схема гибкая, вложенность вместо JOIN.
- Когда: агрегат целиком читается/пишется по id (профиль, заказ со строками), схема эволюционирует, иерархичные данные.

### Колоночные / wide-column (Cassandra, ScyllaDB, HBase)

Строки с динамическими колонками, оптимизированы под огромные объёмы записи и запросы по ключу партиции. Часто AP, tunable consistency.
- Когда: write-heavy, временные ряды, огромный масштаб, известные заранее паттерны запросов (моделируешь таблицы под запросы).

### Графовые (Neo4j)

Узлы и рёбра; обход связей — операция первого класса.
- Когда: соцсети, рекомендации, графы зависимостей — много связей и обходов.

### Аналитические / колоночно-ориентированные (ClickHouse, BigQuery)

Хранение по колонкам для агрегаций по миллиардам строк (OLAP), а не для точечных OLTP-операций.
- Когда: аналитика, отчёты, агрегаты по большим объёмам.

## Сравнение (обобщённо)

| Критерий | SQL | NoSQL (в целом) |
|---|---|---|
| Схема | строгая, заранее | гибкая / schema-on-read |
| Связи, JOIN | сильная сторона | слабо / денормализация |
| Транзакции | ACID из коробки | ограниченные (часто на 1 ключ/документ) |
| Гориз. масштаб записи | сложнее (шардинг) | заложен в дизайн |
| Ad-hoc запросы | гибкие | под заранее известные паттерны |
| Согласованность | обычно strong | часто tunable/eventual |

## Как выбирать

1. **Модель данных.** Реляции и произвольные запросы → SQL. Один агрегат по ключу → KV/документ. Обходы связей → граф. Аналитика → колоночная OLAP.
2. **Паттерны доступа.** В NoSQL таблицы моделируют *под запросы*; если запросы заранее не ясны — SQL гибче.
3. **Согласованность/транзакции.** Нужны многострочные ACID → SQL (или NewSQL). Терпимо eventual ради масштаба/доступности → NoSQL.
4. **Масштаб записи.** Экстремальный write throughput → wide-column/KV.

Реальность: **polyglot persistence** — разные части системы используют разные хранилища (Postgres для заказов + Redis для кэша + ClickHouse для аналитики). Не «SQL против NoSQL», а «правильный инструмент под задачу». Плюс **NewSQL** (CockroachDB, Spanner, TiDB) даёт SQL/ACID с горизонтальным масштабом.

> ⚠️ Частый вопрос на собеседовании: когда выбрать NoSQL вместо реляционной БД? Когда модель — самодостаточные агрегаты по ключу или требуется экстремальный горизонтальный масштаб/доступность при терпимости к eventual consistency и известных заранее паттернах запросов. Если же нужны сложные ad-hoc запросы, связи и многострочные ACID-транзакции — берут SQL.

> ⚠️ Частый вопрос на собеседовании: означает ли NoSQL «нет транзакций»? Нет. Многие NoSQL дают атомарность на уровне одного ключа/документа, а некоторые — и многодокументные транзакции. Просто ACID-гарантии обычно уже, чем в реляционных СУБД, и часто настраиваемы.
