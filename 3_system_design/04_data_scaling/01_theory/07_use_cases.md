# Практические применения (Use cases)

Свод: как решения из этого раздела складываются в реальные системы. Через призму «данные не влезают/не тянут — что делать».

## Эволюция хранилища под ростом нагрузки

```
1) одна БД                     всё на одном узле, простые ACID
2) + реплики для чтения        read scaling, но лаг и eventual при чтении с реплик
3) + шардирование записи       write scaling, но кросс-шардовые JOIN/tx дорогие
4) + разные хранилища          polyglot: SQL + кэш + OLAP + очередь
```

Правило: не усложнять раньше времени. Одна БД с индексами и репликами закрывает очень многое; шардирование добавляют, когда упёрлись в запись/объём.

## Типовые связки

- **Read-heavy сервис (лента, каталог).** Лидер + реплики; чтения с реплик, где терпима лёгкая устарелость; критичное (свои изменения) — read-your-writes с лидера. Сверху кэш (KV).
- **Write-heavy / огромный объём (метрики, события, IoT).** Шардирование по ключу (consistent hashing или партиции), часто wide-column (Cassandra), tunable consistency (AP), запись без кросс-шардовых транзакций.
- **Платежи/учёт.** SQL с ACID, strong consistency; если данных много — шард по `account_id`, чтобы транзакция жила в одном шарде; между сервисами — Saga + outbox.
- **Мультитенантный SaaS.** Ключ шардирования `tenant_id` — данные тенанта локальны в одном шарде, запросы не разлетаются.
- **Глобально распределённый сервис.** Реплики по регионам; выбор CP/AP на разрыв; для строгой согласованности — NewSQL (Spanner/Cockroach) ценой задержки (PACELC: EC).

## Как рассуждать на собеседовании (чек-лист)

1. **Паттерны доступа и объёмы.** read/write ratio, размер данных, QPS, рост. Отсюда — нужна ли вообще распределённость.
2. **Модель данных.** Реляции/запросы → SQL; агрегаты по ключу → KV/документ; связи → граф; аналитика → OLAP.
3. **Масштаб чтений.** Реплики + кэш; помни про replication lag и нужные клиентские гарантии (read-your-writes, monotonic reads).
4. **Масштаб записей/объёма.** Шардирование; выбери ключ (равномерность + локальность + минимум кросс-шард); стратегию (hash/range/directory) и способ ре-шардинга (consistent hashing / фикс. партиции).
5. **Согласованность.** Что критично строго, что терпит eventual. Для leaderless — кворумы `W+R>N`. При разрыве сети — осознанный CP или AP.
6. **Транзакции между сервисами.** Один шард → локальная ACID; иначе Saga + идемпотентность + outbox для событий.
7. **Компромиссы вслух.** Каждое решение — это trade-off (задержка ↔ согласованность, доступность ↔ согласованность, простота ↔ масштаб). Проговаривай их.

## Частые ошибки

- Шардирование «на всякий случай», когда хватило бы реплик и индексов.
- Плохой ключ шардирования → hot spots и повальные scatter-gather запросы.
- Наивный `hash % N` на живом кластере (переезд почти всех данных при ре-шардинге).
- Чтение критичных данных с реплики без учёта лага (аномалии read-after-write).
- Попытка сделать распределённую ACID через 2PC там, где хватило бы саги/outbox.
- «Строгая согласованность везде» — платишь задержкой и доступностью там, где это не нужно.

> ⚠️ Частый вопрос на собеседовании: с чего начать проектирование хранилища данных для сервиса? С паттернов доступа и объёмов (read/write ratio, размер, QPS, рост) и модели данных — из них следует выбор хранилища, нужны ли реплики/шардинг и какие гарантии согласованности; каждое решение объясняется через его trade-off.
