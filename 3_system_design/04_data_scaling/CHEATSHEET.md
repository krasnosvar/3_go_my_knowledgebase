# Data Scaling — шпаргалка

Подробности и объяснения — в [01_theory/](./01_theory/). ⚠️ — частая ловушка.

## Репликация

Подробно: [01_replication.md](./01_theory/01_replication.md).

| Топология | Суть | Цена |
| :--- | :--- | :--- |
| Leader–follower | записи — на лидер, реплики применяют replication log | лидер — узкое место записи, нужен failover |
| Multi-leader | несколько лидеров | разрешение конфликтов |
| Leaderless | кворумы (Dynamo, Cassandra) | read-repair, версии |

| | Синхронная | Асинхронная | Semi-sync |
| :--- | :--- | :--- | :--- |
| Лидер ждёт реплик | да | нет | одну (или кворум) |
| Задержка записи | выше | ниже | средняя |
| Потеря при падении лидера | нет | возможна | нет для подтвердившей реплики |
| Доступность записи | зависит от реплики | не зависит | частично |

| Аномалия (из-за lag) | Решение |
| :--- | :--- |
| Read-after-write: не вижу свою запись | read-your-writes: читать с лидера / с догнавшей реплики, закрепить на лидере после записи |
| Monotonic reads: данные «прыгают назад» | закрепить пользователя за одной репликой (хеш id) |
| Записи не масштабируются репликами | шардирование |

С реплик — ленты, аналитика, счётчики; с лидера — баланс перед списанием, только что изменённое пользователем.

## Шардирование и партиционирование

Подробно: [02_sharding_partitioning.md](./01_theory/02_sharding_partitioning.md).

| Термин | Суть |
| :--- | :--- |
| Партиционирование | разбиение датасета на части, возможно в одном узле (партиции по месяцам) |
| Шардирование | партиции (шарды) на разных узлах; всякий шард — партиция, не наоборот |
| Shard key | равномерность (нет hot spots) + локальность запросов + минимум кросс-шард JOIN/tx; часто `user_id` / `tenant_id` |

| Стратегия | Как | Диапазоны | Равномерность | Ре-шардинг |
| :--- | :--- | :--- | :--- | :--- |
| Hash | `hash(key) % N` | плохо (scatter-gather) | хорошо | плохо без consistent hashing |
| Range | `[a–f] → shard0` | хорошо | hot spots (ключ по времени) | средне (split/merge) |
| Directory | справочник «ключ → шард» | зависит | управляемая | отлично; справочник — SPOF |

| Ре-шардинг | Переезжает |
| :--- | :--- |
| Наивный `hash % N` | ~(N−1)/N ключей |
| Consistent hashing (кольцо + виртуальные узлы) | ~1/N ключей |
| Фиксированное число партиций (напр. 1024) | двигаются целые партиции, хеши не пересчитываются |

```go
package main

import (
	"fmt"
	"hash/crc32"
	"slices"
	"strconv"
)

type Ring struct {
	hashes []uint32          // отсортированные точки на кольце
	owner  map[uint32]string // точка → физический узел
}

func NewRing(nodes []string, vnodes int) *Ring {
	r := &Ring{owner: map[uint32]string{}}
	for _, n := range nodes {
		for i := range vnodes { // виртуальные узлы (range over int — Go 1.22+)
			h := crc32.ChecksumIEEE([]byte(n + "#" + strconv.Itoa(i)))
			r.hashes = append(r.hashes, h)
			r.owner[h] = n
		}
	}
	slices.Sort(r.hashes)
	return r
}

// Get — ближайшая точка по часовой стрелке.
func (r *Ring) Get(key string) string {
	h := crc32.ChecksumIEEE([]byte(key))
	i, _ := slices.BinarySearch(r.hashes, h)
	if i == len(r.hashes) {
		i = 0 // по кругу
	}
	return r.owner[r.hashes[i]]
}

func main() {
	const keys = 100000
	before := NewRing([]string{"A", "B", "C", "D"}, 100)
	after := NewRing([]string{"A", "B", "C", "D", "E"}, 100)
	movedRing, movedMod := 0, 0
	for k := range keys {
		key := "user:" + strconv.Itoa(k)
		if before.Get(key) != after.Get(key) {
			movedRing++
		}
		if k%4 != k%5 { // наивный hash % N
			movedMod++
		}
	}
	fmt.Printf("ring: %.0f%%, mod N: %.0f%%\n",
		100*float64(movedRing)/keys, 100*float64(movedMod)/keys)
	// ring: 23%, mod N: 80%  (≈1/N против ≈(N−1)/N)
}
```

## CAP и PACELC

Подробно: [03_cap_theorem.md](./01_theory/03_cap_theorem.md).

| Буква | Значение |
| :--- | :--- |
| C | линеаризуемость: чтение видит последнюю запись (не «C» из ACID) |
| A | каждый работающий узел отвечает |
| P | работа при разрыве сети; в распределённой системе обязательна |

| Выбор при partition | Поведение | Примеры | Где уместно |
| :--- | :--- | :--- | :--- |
| CP | неуверенный узел отказывает | кворумы, ZooKeeper/etcd, Raft | балансы, блокировки, лидер-конфиг |
| AP | отвечает тем, что знает; конфликты потом (LWW, векторные часы, CRDT) | Cassandra, Riak, DNS | ленты, корзины, каталоги, кэши |

| PACELC | Смысл | Пример |
| :--- | :--- | :--- |
| if P → A или C; else → L или C | даже без сбоев строгость стоит задержки | — |
| PA/EL | доступность при разрыве, низкая задержка в норме | Dynamo, Cassandra |
| PC/EC | согласованность всегда | Spanner, CockroachDB |

## Модели согласованности и кворумы

Подробно: [04_consistency.md](./01_theory/04_consistency.md).

| Модель | Гарантия |
| :--- | :--- |
| Strong / линеаризуемость | любое чтение после завершённой записи видит её или новее |
| Read-your-writes | клиент видит свои записи (чужие — не обязательно) |
| Monotonic reads | чтения одного клиента не едут назад |
| Monotonic writes | записи клиента применяются по порядку |
| Consistent prefix | причинный порядок («не ответ раньше вопроса») |
| Eventual | без новых записей реплики сойдутся |

| Кворум (N реплик) | Свойство |
| :--- | :--- |
| `W + R > N` | множества записи и чтения пересекаются → чтение видит последнюю запись |
| `N=3, W=2, R=2` | 4 > 3, сбалансированно |
| `W=N, R=1` | быстрые чтения, хрупкие записи |
| `W=1, R=N` | быстрые записи, дорогие чтения |
| `W=R=⌈(N+1)/2⌉` | кворум большинства |
| `W + R ≤ N` | eventual, ради скорости/доступности |
| Sloppy quorum + hinted handoff | доступнее, но пересечение не гарантировано |

## Распределённые транзакции

Подробно: [05_distributed_tx.md](./01_theory/05_distributed_tx.md).

| Подход | Как | Минусы | Когда |
| :--- | :--- | :--- | :--- |
| Локальная ACID | одна БД / один шард | — | всегда, когда возможно |
| 2PC (XA) | prepare (блок, YES/NO) → commit/abort | блокирующий, in-doubt при падении координатора | редкие операции, все участники поддерживают XA |
| Saga | цепочка локальных tx + компенсации (`T1→T2→T3`, откат `C2→C1`) | нет изоляции, компенсации вручную, шаги идемпотентны | микросервисы, долгие процессы |
| Transactional outbox | `INSERT INTO outbox` в той же tx; relay/CDC публикует | at-least-once → идемпотентные консьюмеры | «изменить БД + опубликовать событие» |

Saga: choreography (реакция на события) или orchestration (центральный оркестратор).

## SQL vs NoSQL

Подробно: [06_sql_vs_nosql.md](./01_theory/06_sql_vs_nosql.md).

| Семейство | Примеры | Когда |
| :--- | :--- | :--- |
| Реляционные | PostgreSQL, MySQL | связи, ad-hoc запросы, ACID (платежи, учёт, брони) |
| Key-Value | Redis, DynamoDB, Valkey | кэш, сессии, счётчики, доступ по ключу |
| Документные | MongoDB, Couchbase | агрегат целиком по id, гибкая схема |
| Wide-column | Cassandra, ScyllaDB, HBase | write-heavy, временные ряды, запросы известны заранее |
| Графовые | Neo4j | обходы связей: соцсети, рекомендации |
| OLAP колоночные | ClickHouse, BigQuery | агрегаты по миллиардам строк |
| NewSQL | CockroachDB, Spanner, TiDB | SQL/ACID + горизонтальный масштаб |

| Критерий | SQL | NoSQL |
| :--- | :--- | :--- |
| Схема | строгая | гибкая / schema-on-read |
| JOIN | сильная сторона | денормализация |
| Транзакции | ACID | часто на 1 ключ/документ |
| Масштаб записи | шардинг, сложнее | заложен в дизайн |
| Запросы | ad-hoc | под известные паттерны |
| Согласованность | обычно strong | tunable / eventual |

## Эволюция и чек-лист

Подробно: [07_use_cases.md](./01_theory/07_use_cases.md).

| Шаг | Даёт | Цена |
| :--- | :--- | :--- |
| 1. Одна БД + индексы | ACID, просто | предел одного узла |
| 2. + реплики | масштаб чтений | lag, eventual |
| 3. + шардирование | масштаб записи/объёма | кросс-шард JOIN/tx |
| 4. + polyglot | SQL + кэш + OLAP + очередь | эксплуатация |

| Сценарий | Связка |
| :--- | :--- |
| Read-heavy (лента, каталог) | лидер + реплики + кэш; read-your-writes с лидера |
| Write-heavy (метрики, IoT) | шардинг, wide-column, AP |
| Платежи | SQL ACID, шард по `account_id`, Saga + outbox между сервисами |
| SaaS | шард по `tenant_id` |
| Глобальный | реплики по регионам; NewSQL ценой задержки (EC) |

## Ловушки

- ⚠️ Шардирование «на всякий случай» вместо реплик и индексов.
- ⚠️ Плохой shard key → hot spots и повальный scatter-gather.
- ⚠️ `hash % N` на живом кластере → переезд почти всех данных.
- ⚠️ Критичное чтение с реплики без учёта lag → «не вижу свою запись».
- ⚠️ 2PC там, где хватило бы саги/outbox.
- ⚠️ «CA-система» в распределённом мире — это один узел.
- ⚠️ Strong consistency везде — плата задержкой и доступностью без нужды.
