# Backpressure, буферы, flow control

**Backpressure** — механизм, которым медленный получатель заставляет быстрого отправителя **притормозить**, вместо того чтобы система копила необработанные данные до исчерпания памяти. Это про то, что происходит, когда продюсер быстрее консьюмера.

## Проблема: продюсер быстрее консьюмера

Если производить сообщения быстрее, чем их обрабатывают, разница где-то накапливается:

```
producer  ──►──►──►──►──►──►──►   (1000 msg/s)
                                   ┌──────────────┐
                                   │   буфер grows │  <- растёт неограниченно?
                                   └──────────────┘
consumer  ──►········──►········   (100 msg/s)
```

Без ограничения буфер растёт → OOM, рост задержки, обвал. Варианты реакции:

- **Ограничить буфер и блокировать продюсера** (backpressure) — самое безопасное: продюсер ждёт, пока освободится место.
- **Отбрасывать сообщения (drop / load shedding)** — при at-most-once допустимо (метрики), при важных данных нет.
- **Буферизировать на диск** (лог-брокеры типа Kafka) — сдвигает проблему, но не отменяет: retention всё равно конечен.

## Backpressure в Go: каналы

В Go backpressure выражается естественно через **буферизованные каналы**. Ёмкость канала = размер буфера; когда он полон, `send` **блокируется** — это и есть обратное давление.

```go
ch := make(chan int, 4) // буфер на 4 элемента

// продюсер
ch <- x   // если буфер полон -> блокируется, пока консьюмер не заберёт
```

- **Небуферизованный канал** (`make(chan int)`) → полный синхрон: `send` ждёт `receive`. Продюсер не обгонит консьюмера ни на одно сообщение (жёсткий backpressure).
- **Буфер N** → продюсер может уйти вперёд максимум на N сообщений, дальше блокируется.
- Так скорость продюсера **автоматически** подстраивается под консьюмера — без бесконечного роста памяти. Демонстрация — в примере `03_backpressure`.

```
небуферизованный:  producer --> [ ] --> consumer   (шаг в шаг)
буфер = 4:         producer --> [x][x][x][x] --> consumer  (обгон максимум на 4)
```

## Flow control на уровне брокеров

- **Kafka** — потребитель сам тянет данные (**pull**) в своём темпе через `poll()`; брокер не давит на консьюмера. «Отставание» видно как **consumer lag** (разница между последним оффсетом и закоммиченным). Растущий lag — сигнал, что консьюмеров/партиций мало.
- **RabbitMQ** — **prefetch (QoS)** ограничивает число неподтверждённых сообщений на консьюмера: не заберёт следующее, пока не ack’нул текущие. Плюс механизм TCP-flow-control при переполнении.
- **TCP** сам по себе имеет flow control (receive window) — тот же принцип на транспортном уровне.

## Push vs pull

- **Push** (брокер шлёт консьюмеру): низкая задержка, но легко перегрузить медленного получателя → нужен явный backpressure (prefetch/credits).
- **Pull** (консьюмер тянет сам): консьюмер регулирует темп сам → естественный backpressure, но чуть выше задержка (нужно опрашивать). Kafka — pull, поэтому «backpressure» там встроен в модель.

## Практические приёмы

- **Ограниченные буферы**, а не безграничные очереди в памяти.
- **Пул воркеров** фиксированного размера читает из канала → ограничивает параллелизм и потребление ресурсов.
- **Bounded queue + rejection/DLQ** при переполнении — деградировать предсказуемо, а не падать.
- **Мониторить lag / глубину очереди**; масштабировать консьюмеров (в пределах числа партиций).

> ⚠️ Частый вопрос на собеседовании: что делать, если продюсер быстрее консьюмера? Применить backpressure: ограничить буфер, чтобы продюсер блокировался при заполнении (в Go — буферизованный канал). Альтернативы — отбрасывать сообщения (load shedding, только для неважных данных) или масштабировать консьюмеров.

> ⚠️ Частый вопрос на собеседовании: почему Kafka устойчива к медленным консьюмерам? Модель pull: консьюмер сам тянет данные в своём темпе, брокер его не заваливает. Отставание видно как consumer lag, данные ждут на диске в пределах retention.
