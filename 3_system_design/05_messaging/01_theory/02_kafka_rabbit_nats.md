# Kafka vs RabbitMQ vs NATS

Три популярных решения, но с разной философией. Выбор зависит не от «что моднее», а от модели данных: нужен ли **лог с историей**, **гибкая маршрутизация задач** или **лёгкий быстрый транспорт**.

## Apache Kafka — распределённый лог

Kafka — это **лог commit-типа** (append-only), а не классическая очередь. Топики разбиты на партиции, консьюмеры хранят оффсеты и читают ленту.

- **Модель:** publish–subscribe поверх устойчивого лога; сообщения хранятся по retention (время/размер) и **не удаляются при чтении**.
- **Порядок:** гарантирован внутри партиции.
- **Масштаб:** очень высокая пропускная способность (сотни тыс.–млн сообщений/с), горизонтально масштабируется партициями.
- **Реплей:** можно перечитать историю, сдвинув оффсет.
- **Минусы:** тяжелее в эксплуатации; маршрутизация примитивна (по ключу в партицию), сложная логика — на стороне консьюмера; повышенная задержка по сравнению с NATS.

**Когда:** event streaming, event sourcing, аналитика/ETL, аудит, шина событий между многими сервисами, где важны история и высокий throughput.

## RabbitMQ — брокер очередей с маршрутизацией

Классический брокер по модели **AMQP**: продюсер шлёт в **exchange**, тот по правилам (**binding**) раскладывает сообщения по **очередям**, консьюмеры забирают из очередей.

```
producer -> [exchange] --binding--> [queue A] -> consumer
                       \--binding--> [queue B] -> consumer
```

- **Типы exchange:** `direct` (по точному routing key), `topic` (по шаблону `logs.*.error`), `fanout` (всем очередям), `headers`.
- **Модель:** competing consumers; после ack сообщение **удаляется**.
- **Плюсы:** богатая маршрутизация, приоритеты, TTL, dead-letter queues, per-message ack, гибко для сложных workflow.
- **Минусы:** нет «перемотки» (сообщение ушло после ack); при огромном throughput и накоплении очередей деградирует сильнее, чем лог.

**Когда:** очереди задач (task queues), RPC поверх сообщений, сложная маршрутизация, приоритеты, умеренный объём, где важна доставка каждой задачи одному воркеру.

## NATS — лёгкий быстрый брокер

Минималистичный высокоскоростной pub/sub. Базовый NATS (core) — **fire-and-forget** без персистентности: нет подписчика — сообщение потеряно. **JetStream** добавляет персистентность, стримы и at-least-once — приближая NATS к логу.

- **Плюсы:** очень низкая задержка, простота, малый вес, встроенный request-reply, кластеризация; хорош для микросервисной шины и edge/IoT.
- **Минусы:** core NATS не хранит сообщения; для гарантий и истории нужен JetStream (это уже другой профиль эксплуатации), экосистема меньше, чем у Kafka.

**Когда:** быстрый внутренний обмен между микросервисами, request-reply, метрики/сигналы, IoT; JetStream — когда нужны persistence и at-least-once без веса Kafka.

## Сравнение

| Свойство | Kafka | RabbitMQ | NATS (core / JetStream) |
|---|---|---|---|
| Базовая модель | лог (log) | очередь + маршрутизация | pub/sub / стрим |
| Персистентность | да (retention) | да (до ack) | нет / да (JetStream) |
| Реплей истории | да | нет | нет / да |
| Маршрутизация | по ключу в партицию | богатая (exchange/binding) | subject-иерархия |
| Порядок | внутри партиции | внутри очереди | внутри стрима (JetStream) |
| Throughput | очень высокий | средний–высокий | очень высокий |
| Задержка | средняя | средняя | очень низкая |
| Сложность эксплуатации | высокая | средняя | низкая–средняя |

## Как выбрать

- Нужны **история, реплей, высокий throughput, event sourcing** → **Kafka**.
- Нужны **гибкая маршрутизация, приоритеты, очереди задач, DLQ** → **RabbitMQ**.
- Нужен **лёгкий быстрый транспорт / request-reply**, персистентность вторична → **NATS** (с JetStream, если нужны гарантии).

> ⚠️ Частый вопрос на собеседовании: Kafka — это очередь? Строго говоря нет: это распределённый упорядоченный лог. Сообщения не удаляются при чтении, консьюмер хранит оффсет и может перечитать историю. «Очередное» поведение (одно сообщение — одному воркеру) даёт RabbitMQ/SQS.

> ⚠️ Частый вопрос на собеседовании: чем core NATS отличается от JetStream? Core NATS — fire-and-forget без хранения (нет живого подписчика — сообщение потеряно, at-most-once). JetStream добавляет персистентные стримы, оффсеты и at-least-once.
