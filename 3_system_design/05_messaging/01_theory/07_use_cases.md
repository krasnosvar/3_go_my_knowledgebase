# Практические применения и паттерны

Сводка того, как приёмы из этого раздела складываются в рабочие решения, и как рассуждать о них на собеседовании и в проектировании.

## Когда вообще брать брокер

Асинхронный обмен через брокер оправдан, когда:

- отправителю **не нужен немедленный ответ** (обработку можно отложить);
- нагрузка **неравномерна** и её надо сгладить (буферизация всплесков);
- одно событие интересно **многим** независимым потребителям (fan-out);
- нужна **устойчивость** к падению получателя (сообщения ждут в брокере);
- сервисы надо **развязать** по времени и деплою.

Не нужен, когда требуется синхронный ответ здесь и сейчас (запрос-ответ), а лишний брокер только добавит задержку и точку отказа — тогда HTTP/gRPC.

## Выбор брокера под задачу

| Задача | Что брать | Почему |
|---|---|---|
| Event streaming, аналитика, event sourcing, аудит | **Kafka** | лог с историей, реплей, высокий throughput |
| Очереди задач, RPC-over-MQ, сложная маршрутизация, приоритеты, DLQ | **RabbitMQ** | гибкие exchange/binding, per-message ack |
| Быстрый внутренний обмен, request-reply, IoT | **NATS** (+ JetStream для гарантий) | низкая задержка, простота |
| Управляемая очередь в облаке без своей инфры | SQS / Pub/Sub | меньше эксплуатации |

## Типовые паттерны

- **Work queue (competing consumers).** Пул воркеров разбирает задачи из одной очереди; масштабируется добавлением воркеров. (Kafka: параллелизм ≤ числа партиций.)
- **Publish/Subscribe (fan-out).** Одно событие → много подписчиков; в Kafka — разные consumer groups.
- **Event-driven / event sourcing.** Состояние как поток событий в логе; сервисы реагируют на события, историю можно перечитать.
- **Transactional outbox + inbox.** Надёжная публикация из БД и дедупликация на приёме → effectively-once (см. [05_outbox_inbox.md](./05_outbox_inbox.md)).
- **Saga.** Распределённая бизнес-транзакция как цепочка событий с компенсирующими шагами вместо 2PC.
- **CQRS.** Запись через команды/события, чтение — из отдельной проекции, обновляемой консьюмером событий.
- **Dead-letter queue.** «Ядовитые» сообщения после N ретраев уводятся в DLQ, чтобы не блокировать поток.

## Correctness-чеклист

- **Гарантия доставки осознанно выбрана** (обычно at-least-once) → консьюмер **идемпотентен** или дедуплицирует по message-id.
- **Порядок**: где нужен — сообщения одной сущности с одним ключом (одна партиция).
- **Ретраи с backoff + DLQ**; ack — только после успешной обработки.
- **Backpressure**: ограниченные буферы, мониторинг lag / глубины очереди; масштабировать консьюмеров в пределах числа партиций.
- **Двойная запись** устранена через outbox, а не через «сначала БД, потом publish».
- **Схема сообщений версионируется** (обратная совместимость), payload содержит id и, где нужно, ключ идемпотентности.

## Диагностика в эксплуатации

- **Растёт consumer lag / глубина очереди** → консьюмеры не успевают: добавить консьюмеров (≤ партиций), ускорить обработку, проверить частые ребалансы.
- **Дубли эффектов** → сломана идемпотентность/дедуп; проверить, когда коммитится оффсет/ack.
- **Потеря сообщений** → ack/commit до обработки (at-most-once там, где нужен at-least-once), или двойная запись без outbox.
- **Застой из-за одного сообщения** → poison message; нужен DLQ и лимит ретраев.

> ⚠️ Частый вопрос на собеседовании: как гарантировать порядок обработки событий одного пользователя при масштабировании? Отправлять их с ключом = user-id, чтобы они попадали в одну партицию (порядок в партиции сохранён), а параллелизм получать за счёт множества ключей по разным партициям.

> ⚠️ Частый вопрос на собеседовании: спроектируйте надёжную доставку событий из сервиса. Outbox (атомарно с БД) → relay/CDC в брокер (at-least-once) → консьюмер с дедупликацией по message-id (inbox/идемпотентность) → ретраи с backoff и DLQ. Итог — effectively-once с сохранением порядка по ключу.
