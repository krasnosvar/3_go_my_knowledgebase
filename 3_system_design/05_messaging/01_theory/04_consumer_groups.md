# Consumer groups, партиционирование, ребаланс, порядок

**Consumer group** — набор консьюмеров, которые совместно читают один топик и делят между собой работу. Это механизм горизонтального масштабирования обработки в лог-брокерах (Kafka; аналогично durable-подписки в NATS JetStream).

## Как распределяется работа

Ключевое правило Kafka: **одну партицию в пределах группы читает ровно один консьюмер**. Партиции — единица параллелизма.

```
topic "orders", partitions = 4        consumer group "billing"

  partition 0 ─┐
  partition 1 ─┼──> consumer A   (читает p0, p1)
  partition 2 ─┐
  partition 3 ─┼──> consumer B   (читает p2, p3)

добавили consumer C -> ребаланс:
  p0 -> A,  p1 -> B,  p2 -> C,  p3 -> ... (перераспределили)
```

- Консьюмеров **≤** партиций имеет смысл: если консьюмеров больше, чем партиций, лишние простаивают (партиций на всех не хватит).
- **Разные группы независимы.** Группа `billing` и группа `analytics` читают один топик каждая со своим оффсетом — это fan-out. Внутри группы — competing consumers.

```
                    ┌── group "billing"   (свой набор оффсетов)
topic "orders" ──── ┤
                    └── group "analytics" (свой набор оффсетов, читает те же данные)
```

## Партиционирование и параллелизм

- Число партиций задаёт **потолок параллелизма** группы: 4 партиции → максимум 4 активных консьюмера.
- Партицию выбирает продюсер по ключу: `partition = hash(key) % N`. Нет ключа → round-robin/случайно.
- Увеличить партиции можно, уменьшить — нет. И при изменении числа партиций `hash%N` меняет раскладку ключей → рвётся история порядка по ключу. Число партиций планируют заранее.

## Ребаланс (rebalance)

Когда состав группы или топика меняется, партиции **перераспределяются** между живыми консьюмерами. Триггеры:

- консьюмер присоединился/вышел/упал (истёк heartbeat, session timeout);
- добавили партиции в топик;
- консьюмер слишком долго обрабатывал батч и не слал heartbeat (превысил `max.poll.interval`) → его выкинули из группы.

**Проблема «stop-the-world» ребаланса:** на время перераспределения обработка в группе приостанавливается. Частые ребалансы = проседание throughput. Смягчают:
- **cooperative / incremental rebalancing** — переназначают только затронутые партиции, а не всё сразу;
- **static membership** — консьюмер сохраняет свою идентичность при кратком рестарте и не вызывает ребаланс.

## Порядок и оффсеты

- **Порядок гарантирован только внутри партиции.** Хотите строгий порядок событий сущности — отправляйте их с одним ключом (одна партиция).
- **Коммит оффсета** = «дочитал до сюда». Когда коммитить — определяет гарантию доставки:
  - коммит **до** обработки → at-most-once (упал после коммита = потеря);
  - коммит **после** обработки → at-least-once (упал до коммита = повтор).
- После ребаланса новый владелец партиции продолжает с **последнего закоммиченного оффсета** → незакоммиченные сообщения обработаются повторно (снова дубли → нужна идемпотентность).

> ⚠️ Частый вопрос на собеседовании: сколько консьюмеров одной группы могут читать одну партицию? Ровно один. Поэтому число партиций ограничивает максимальный параллелизм группы; лишние консьюмеры простаивают.

> ⚠️ Частый вопрос на собеседовании: как одно событие доставить нескольким сервисам-обработчикам? Каждому сервису — своя consumer group. Внутри группы работа делится (competing consumers), а разные группы читают один топик независимо, каждая со своим оффсетом (fan-out).

> ⚠️ Частый вопрос на собеседовании: чем плох частый ребаланс? Классический ребаланс «останавливает мир» — вся группа замирает на перераспределение партиций, throughput проседает. Лечится cooperative-rebalancing, static membership и достаточным ack-таймаутом.
