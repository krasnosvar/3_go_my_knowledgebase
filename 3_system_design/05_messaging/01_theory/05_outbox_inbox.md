# Transactional Outbox, Inbox и идемпотентные консьюмеры

Классическая проблема: сервис должен **записать в свою БД** и **опубликовать событие в брокер**. Это два разных хранилища — атомарно вместе они не коммитятся.

## Проблема двойной записи (dual write)

```
  BEGIN
    INSERT order ...          <- записали в БД
  COMMIT
  publish("order.created")    <- упали ЗДЕСЬ -> в БД заказ есть, события нет
```

Любой порядок плох:
- **сначала БД, потом брокер** — упали между ними → данные есть, события нет (потеря события);
- **сначала брокер, потом БД** — упали между ними → событие ушло, а данных нет (фантомное событие);
- распределённые транзакции (2PC) через БД и брокер — дорого, хрупко, часто недоступно.

## Transactional Outbox — надёжная публикация

Идея: писать событие **в ту же БД, в той же транзакции**, что и бизнес-данные — в таблицу `outbox`. Отдельный процесс потом читает `outbox` и публикует в брокер.

```
  BEGIN
    INSERT order ...
    INSERT outbox(id, payload, published=false)   <- атомарно вместе с заказом
  COMMIT                                            <- либо оба, либо ничего

  --- отдельный процесс (relay / poller) ---
  loop:
    выбрать из outbox необработанные строки
    опубликовать в брокер
    пометить published=true (или удалить)
```

- Бизнес-запись и запись события коммитятся **одной локальной транзакцией** → нет расхождения.
- **Relay** (публикатор) читает `outbox` и шлёт в брокер. Реализуют опросом (polling) или через **CDC** (change data capture, напр. Debezium читает WAL/binlog).
- Relay может **упасть после публикации, но до пометки `published=true`** → повторно опубликует то же событие. Значит publish тут **at-least-once**, и на стороне получателя нужна дедупликация. Пример «слива» outbox — в упражнении `04_outbox_drain`.

## Inbox — надёжный приём и дедупликация

Симметричный паттерн у **получателя**. Прежде чем обработать входящее сообщение, консьюмер записывает его id в таблицу `inbox` — **в той же транзакции**, что и бизнес-эффект.

```
  BEGIN
    INSERT inbox(message_id)   -- уникальный ключ; при дубле -> conflict/ошибка
    ... применить бизнес-эффект ...
  COMMIT
```

- Уникальный индекс по `message_id` → повторная вставка того же id падает (`ON CONFLICT`/duplicate key) → транзакция откатывается, эффект **не применяется дважды**.
- Так at-least-once превращается в **effectively-once**: приняли повтор, но эффект однократен.

```
producer --outbox--> брокер --at-least-once (возможны дубли)--> consumer --inbox/dedup--> БД
   \___ атомарно с данными ___/                                    \___ атомарно, дедуп по id ___/
```

## Идемпотентные консьюмеры

Inbox — частный случай **идемпотентности**: повторная обработка не меняет результат.

- **Дедуп по id.** Хранить обработанные `message_id` (таблица/множество), пропускать повторы. В памяти — `map[id]bool` (см. пример `02_at_least_once_idempotent`); в проде — таблица с TTL/окном.
- **Идемпотентная операция.** Проектировать эффект так, чтобы повтор был безопасен: `SET status='paid'` вместо `payments += 1`; `INSERT ... ON CONFLICT DO NOTHING`; upsert по натуральному ключу.
- **Ключ идемпотентности** передаётся в самом сообщении (message-id) и логически привязан к бизнес-операции, а не к попытке доставки.

## Итог

| Паттерн | Где | Решает |
|---|---|---|
| Transactional Outbox | у продюсера | атомарность «БД + публикация», отсутствие потери событий |
| Inbox / dedup | у консьюмера | отсечение дублей от at-least-once |
| Идемпотентная операция | у консьюмера | безопасность повторов без хранения состояния |

> ⚠️ Частый вопрос на собеседовании: как атомарно записать в БД и опубликовать событие? Через transactional outbox: событие пишется в таблицу outbox в той же транзакции, что и данные, а отдельный relay/CDC потом публикует его в брокер. Так исчезает проблема двойной записи.

> ⚠️ Частый вопрос на собеседовании: outbox гарантирует exactly-once публикацию? Нет, at-least-once — relay может опубликовать повторно после сбоя. Дубли отсекаются на стороне консьюмера (inbox / идемпотентность), получается effectively-once.
