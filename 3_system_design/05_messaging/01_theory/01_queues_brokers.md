# Очереди и брокеры сообщений

Обмен сообщениями (messaging) — способ связать сервисы **асинхронно**: отправитель кладёт сообщение в промежуточную систему (брокер), получатель забирает его позже. Это развязывает сервисы во времени, в пространстве и по скорости.

## Синхронное vs асинхронное взаимодействие

**Синхронно (например, HTTP-запрос):** сервис A вызывает B и **ждёт** ответа. A и B должны быть живы одновременно, A блокируется на время B, всплеск нагрузки на A мгновенно бьёт по B.

**Асинхронно (через брокер):** A публикует сообщение и идёт дальше. B обработает его, когда сможет.

```
Синхронно:
  A ---- запрос ----> B      A ждёт, пока B ответит; B должен быть жив

Асинхронно:
  A --> [ брокер / очередь ] --> B
        сообщения ждут,          A не ждёт B;
        пока B готов             B может быть временно недоступен
```

## Зачем нужны очереди и брокеры

- **Развязка (decoupling).** A знает только про брокер, не про то, кто и как читает сообщения. Консьюмеров можно добавлять/менять независимо.
- **Сглаживание нагрузки (load levelling, buffering).** Всплеск запросов накапливается в очереди, а консьюмеры разгребают его в своём темпе — вместо того чтобы уронить медленный сервис.
- **Устойчивость (resilience).** Если консьюмер упал, сообщения не теряются — они ждут в брокере до восстановления.
- **Масштабирование.** Несколько консьюмеров читают из одной очереди параллельно (competing consumers).
- **Fan-out.** Одно событие доставляется многим независимым подписчикам.

## Две модели: очередь (queue) vs журнал (log)

Это ключевое различие, вокруг которого строятся все брокеры.

### Очередь (queue) — «работа»

Сообщение — это **задача**. Его читает **один** из консьюмеров, после подтверждения (ack) оно **удаляется**. Это модель «конкурирующих потребителей» (competing consumers): добавили консьюмеров — быстрее разгребли очередь.

```
                 ┌── consumer 1  (взял msg A)
[A][B][C] ---->  ├── consumer 2  (взял msg B)
  очередь        └── consumer 3  (взял msg C)
   каждое сообщение достаётся ровно одному консьюмеру, потом удаляется
```

Так работают RabbitMQ, классические SQS, ActiveMQ.

### Журнал (log) — «событие»

Сообщения дописываются в **упорядоченный, неизменяемый лог** (append-only). Консьюмеры **не удаляют** записи — они держат **оффсет** (позицию курсора) и читают лог как ленту. Одну и ту же запись могут независимо прочитать несколько потребителей; можно «перемотать» оффсет назад и перечитать историю.

```
offset:  0    1    2    3    4    5
log:    [A]  [B]  [C]  [D]  [E]  [F]  <- append-only, ничего не удаляется по чтению
                        ^
                  consumer group X читает с offset=3
              ^
        consumer group Y читает с offset=1 (независимо)
```

Так работает Kafka (и NATS JetStream, Redpanda, Pulsar в log-режиме).

| | Очередь (queue) | Журнал (log) |
|---|---|---|
| Что после чтения+ack | сообщение удаляется | остаётся, хранится по retention |
| Позиция чтения | у брокера | у консьюмера (оффсет) |
| Перечитать историю | нельзя | можно (сдвинуть оффсет) |
| Несколько независимых читателей | сложно (нужен fan-out/copy) | естественно |
| Типичный представитель | RabbitMQ, SQS | Kafka |

## Топики, партиции, оффсеты (модель лога)

- **Топик (topic)** — именованный поток сообщений («логическая тема»), например `orders`.
- **Партиция (partition)** — топик физически разбит на несколько партиций. Каждая партиция — **отдельный упорядоченный лог**. Партиции — единица параллелизма и масштабирования.
- **Оффсет (offset)** — порядковый номер сообщения **внутри партиции** (0, 1, 2, …). Консьюмер хранит «докуда дочитал».
- **Ключ (key)** — по нему брокер выбирает партицию (обычно `hash(key) % N`). Все сообщения с одним ключом попадают в одну партицию → **сохраняется порядок в пределах ключа**.

```
topic "orders", partitions = 3

  key=user-1 -> hash%3=0 -> partition 0: [o1][o4][o7]   (порядок для user-1 сохранён)
  key=user-2 -> hash%3=1 -> partition 1: [o2][o5]
  key=user-3 -> hash%3=2 -> partition 2: [o3][o6]
```

**Важно:** глобального порядка по всему топику нет — порядок гарантирован только **внутри одной партиции**. Хотите строгий порядок для сущности — кладите её события с одним ключом.

> ⚠️ Частый вопрос на собеседовании: в чём разница между очередью и логом? В очереди сообщение забирает один консьюмер и после ack оно удаляется, позицию хранит брокер. В логе сообщения неизменяемы и хранятся по retention, позицию (оффсет) хранит консьюмер, историю можно перечитать, а несколько групп читают независимо.

> ⚠️ Частый вопрос на собеседовании: гарантирует ли Kafka глобальный порядок сообщений? Нет, только в пределах партиции. Чтобы события одной сущности шли по порядку, отправляйте их с одинаковым ключом — они попадут в одну партицию.
