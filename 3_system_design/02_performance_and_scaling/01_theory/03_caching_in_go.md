# Кэширование в Go: конкурентный L1-кэш, `singleflight` и ловушки GC

## О чём эта тема (краткий контекст)

Кэширование позволяет отдавать часто запрашиваемые данные из быстрой памяти за
наносекунды или микросекунды вместо повторных походов в базу данных или внешний
сервис. В Go локальный in-process кэш (L1) разделяется сразу между всеми
горутинами одного процесса, что даёт колоссальный выигрыш по памяти и hit ratio,
но требует грамотной синхронизации, защиты от шторма запросов (cache stampede) и
учёта работы сборщика мусора на больших объёмах данных.

> - [Уровни кэширования, паттерны (Cache-Aside, Write-Through), вытеснение (LRU/LFU) и аномалии](../../../../5_devops_sre_knowledgebase/14_system_design/02_performance_caching_and_scaling/01_theory/02_caching_levels_and_patterns.md)
>

> библиотека и идиомы языка).

## 1. Потокобезопасный in-memory кэш в Go: три архитектурных подхода

Стандартный тип `map` в Go **не потокобезопасен**: одновременная запись и чтение
из разных горутин приводят к неперехватываемому `fatal error: concurrent map
read and map write` (аварийное завершение процесса, которое нельзя поймать через
`recover()`).

Выбор структуры для L1-кэша в Go зависит от профиля нагрузки и числа ядер CPU:

| Вариант | Как устроен | Когда выбирать |
| :--- | :--- | :--- |
| **`map[K]V` + `sync.RWMutex` (или `Mutex`)** | Единая мапа под общим мьютексом; для LRU добавляется двусвязный список `container/list` (внимание: `Get` в LRU двигает элемент в начало списка, поэтому требует эксклюзивного `Lock()`, а не `RLock()`!). | Небольшие и средние кэши (до десятков тысяч RPS), где простота кода важнее экстремальной конкурентности. |
| **Шардированная мапа (`[256]shard`)** | Массив из $N = 64..512$ независимых бакетов (степень двойки), в каждом свой `sync.RWMutex` и своя `map`. Номер шарда выбирается быстрым хешем ключа: `hash(key) & (N - 1)`. | **Стандарт для высоконагруженных L1-кэшей на многоядерных серверах.** Снижает конкуренцию за мьютекс (lock contention) в $N$ раз. |
| **`sync.Map`** | Специализированная структура из stdlib с двумя внутренними мапами (`read` atomic-only и `dirty` под мьютексом). | **Только для двух узких сценариев:** 1) ключи записываются один раз и почти никогда не перезаписываются/не удаляются; 2) разные горутины работают с непересекающимися наборами ключей. При частых вставках и вытеснении по TTL/LRU `sync.Map` медленнее шардированной мапы! |

### Эскиз шардированного кэша в Go

```go
type shard struct {
	mu    sync.RWMutex
	items map[string]cacheItem
}

type ShardedCache struct {
	shards [256]shard
}

func (c *ShardedCache) getShard(key string) *shard {
	// Вычисляем FNV-1a хеш без аллокаций и берём младшие 8 бит (& 255).
	var h uint32 = 2166136261
	for i := 0; i < len(key); i++ {
		h ^= uint32(key[i])
		h *= 16777619
	}
	return &c.shards[h&255]
}
```

## 2. Защита от Cache Stampede в Go: `golang.org/x/sync/singleflight`

Когда истекает TTL популярного ключа («горячая новость» или профиль популярного
продавца), тысячи горутин одновременно обнаруживают промах кэша (`cache miss`)
и лавиной бьют в базу данных одним и тем же тяжёлым запросом.

В экосистеме Go эта проблема решается пакетом `golang.org/x/sync/singleflight`
(или его простой реализацией на `sync.Mutex` + `map[string]*call`, показанной в
примере `02_examples/03_stampede_singleflight/main.go`):

- Первая горутина с ключом `"user:42"` вызывает `group.Do("user:42", fn)` и
  реально идёт в Redis или PostgreSQL.
- Все остальные 999 горутин, пришедшие с тем же ключом, пока `fn` ещё
  выполняется, **блокируются и ждут результата первой горутины**, после чего
  одновременно получают готовый ответ (`shared = true`). В базу уходит ровно
  **один** запрос вместо тысячи!

> ⚠️ **Критическая ловушка `singleflight.Do` и отмена контекста:**
> Если первая горутина передала внутрь `group.Do(key, func() { return
> db.Query(r.Context(), ...) })` свой клиентский `r.Context()`, и этот первый
> клиент отменил запрос через 10 мс, то запрос в БД оборвётся с `context
> canceled`, и ошибку получат **все 999 ожидающих горутин**! И наоборот: если
> база зависла, `Do` заблокирует все ожидающие горутины, игнорируя их
> индивидуальные дедлайны.
>
> **Решение для продакшена:** внутри `singleflight` используйте независимый
> контекст с собственным разумным таймаутом (`context.WithTimeout(
> context.WithoutCancel(ctx), 2*time.Second)`), а ожидание вызывающих горутин
> делайте через `ch := group.DoChan(key, fn)` + `select` с их личным
> `<-ctx.Done()`.

## 3. Ловушка сборщика мусора Go на больших кэшах (GC Pointer Scanning)

Представьте, что вы решили закэшировать в памяти Go-сервиса 20 миллионов записей
в обычной мапе `map[string]*UserProfile`. Даже если вы вообще ничего не пишете в
эту мапу, во время каждого цикла сборки мусора фаза конкурентной разметки (GC
Mark Phase) обязана **просканировать каждый из 20 миллионов ключей `string`
(так как `string` содержит указатель на массив байт!) и каждый указатель
`*UserProfile`**.

В результате паузы и нагрузка GC на CPU вырастают до сотен миллисекунд, хотя
объекты в кэше долгоживущие.

### Как устроены Zero-GC кэши в Go (`bigcache`, `freecache`, `fastcache`)

Если структура ключа и значения мапы **не содержит указателей** (например,
`map[uint64]uint32`), компилятор Go помечает бакеты такой мапы специальным
флагом `noscan`, и сборщик мусора **полностью пропускает её при обходе графа**!

На этом принципе строятся кэши гигабайтного объёма в Go:
1. Все значения сериализуются в байты и складываются подряд в один большой
   предаллоцированный кольцевой буфер `[]byte` (у всего слайса всего один
   заголовок!).
2. Индекс хранится как `map[uint64]uint32` (64-битный хеш ключа → смещение в
   буфере `[]byte`).
3. Сборщик мусора видит всего 1 слайс и 1 мапу без указателей и проходит фазу
   разметки за микросекунды независимо от того, хранится ли в кэше 10 тысяч или
   50 миллионов элементов.
