# Работа с сетью (`netpoll`, HTTP) и стили API (REST, gRPC) в Go

## О чём эта тема (краткий контекст)

Любой бэкенд-сервис общается с внешним миром и соседними сервисами по сети:
принимает соединения, разбирает протоколы (TCP, HTTP/1.1, HTTP/2, gRPC) и сам
ходит во внешние API. На высоких нагрузках именно неправильная работа с
сокетами, пулами соединений, таймаутами и сериализацией становится главной
причиной исчерпания файловых дескрипторов, утечек памяти и каскадных сбоев.

## 1. Секрет сетевой производительности Go: рантайм `netpoll`

В классических языках программист вынужден выбирать между двумя крайностями:
1. «Поток ОС на соединение» — простой синхронный код, но поток ОС весит ~1–8 МБ
   стека и дорог в переключении контекста ядром (проблема C10k).
2. Асинхронный event loop (`epoll`/`kqueue`) — мало памяти, но сложный код на
   колбэках или `async/await`, где одна случайная блокирующая функция вешает
   весь воркер.

Go объединяет лучшее из обоих миров с помощью встроенного в рантайм сетевого
поллера (**`netpoll`**):

- Под капотом все сетевые сокеты (`net.Conn`) в Go переводятся в неблокирующий
  режим (`O_NONBLOCK`) и регистрируются в системном мультиплексоре (`epoll` в
  Linux, `kqueue` в macOS/BSD, `IOCP` в Windows).
- Для программиста код выглядит полностью синхронным: `n, err := conn.Read(buf)`
  в отдельной горутине на каждое соединение (`go handleConn(conn)`).
- Когда данных в сокете ещё нет, рантайм Go **не блокирует поток ОС (`M`)**. Он
  паркует только лёгкую горутину (`G`, стек от 2 КБ) в очередь ожидания
  `netpoll`, а поток ОС тут же берёт следующую готовую к работе горутину.
- Когда ядро ОС сообщает через `epoll_wait`, что в сокет пришли байты, `netpoll`
  будит горутину и возвращает её в очередь планировщика.

Благодаря этому один Go-процесс легко держит **100 000+ одновременных
TCP/HTTP/WebSocket-соединений**, расходуя всего несколько сотен мегабайт RAM.

## 2. Промышленная настройка `http.Server`: защита от зависаний и Slowloris

⚠️ **Критическая ловушка стандартной библиотеки:** вызов
`http.ListenAndServe(":8080", handler)` или создание `&http.Server{}` без полей
таймаутов оставляет **все таймауты бесконечными (`0`)**. Один медленный клиент
или атака Slowloris (отправка по одному байту заголовка раз в 30 секунд)
навсегда удержит сокет и горутину до падения процесса по `ulimit -n` (`too many
open files`) или OOM.

Всегда задавайте явные таймауты в продакшене:

```go
srv := &http.Server{
	Addr:              ":8080",
	Handler:           mux,
	ReadHeaderTimeout: 5 * time.Second,  // Защита от Slowloris при чтении заголовков
	ReadTimeout:       10 * time.Second, // Полное время чтения заголовков + тела запроса
	WriteTimeout:      15 * time.Second, // Время на формирование и отправку ответа
	IdleTimeout:       60 * time.Second, // Время жизни keep-alive соединения без запросов
	MaxHeaderBytes:    1 << 20,          // 1 МБ максимум на заголовки
}
```

## 3. Тюнинг исходящего клиента `http.Client` и `http.Transport`

Не менее опасные дефолты скрыты на стороне исходящих HTTP-запросов:

1. **У `http.DefaultClient` поле `Timeout: 0` (бесконечность).** Если внешний
   сервис завис и не шлёт ответ, горутина заблокируется навсегда.
2. **У `http.DefaultTransport` лимит `MaxIdleConnsPerHost = 2`!** При общем
   пуле `MaxIdleConns = 100` стандартный транспорт держит в пуле keep-alive
   **всего 2 свободных соединения на один хост назначения**. Если ваш сервис
   в 50 горутин параллельно вызывает внутренний сервис биллинга, 48 соединений
   после каждого запроса будут закрываться, вызывая шторм новых TCP+TLS
   рукопожатий и исчерпание эфемерных портов в состоянии `TIME_WAIT`.
3. **Утечка сокетов при невычитанном `resp.Body`:** в HTTP/1.1 соединение
   возвращается в пул keep-alive только тогда, когда его тело дочитано до `EOF`
   **и** закрыто.

### Эталонная конфигурация HTTP-клиента в Go

```go
transport := &http.Transport{
	MaxIdleConns:        500,
	MaxIdleConnsPerHost: 100,              // Критично для микросервисных вызовов!
	MaxConnsPerHost:     200,              // Верхний предел активных соединений к хосту
	IdleConnTimeout:     90 * time.Second,
	TLSHandshakeTimeout: 5 * time.Second,
}

client := &http.Client{
	Transport: transport,
	Timeout:   10 * time.Second, // Страховочный общий таймаут
}
```

```go
// Правильное чтение ответа, гарантирующее возврат соединения в keep-alive пул:
req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
if err != nil {
	return err
}
resp, err := client.Do(req)
if err != nil {
	return err
}
defer func() {
	// Вычитываем остаток тела, чтобы сокет не закрылся, а вернулся в пул!
	_, _ = io.Copy(io.Discard, resp.Body)
	_ = resp.Body.Close()
}()
```

## 4. REST (`encoding/json`) против gRPC (`grpc-go` + Protobuf) в Go

В экосистеме Go разница между REST/JSON и gRPC/Protobuf особенно заметна из-за
устройства сериализации и сетевого транспорта:

| Критерий | REST + `encoding/json` | gRPC (`grpc-go`) + Protobuf |
| :--- | :--- | :--- |
| **Сериализация** | Работает через **рефлексию (`reflect`)** в рантайме, создаёт много мелких аллокаций в куче и нагружает GC. | **Кодогенерация (`protoc-gen-go`)**: статически типизированные методы `Marshal`/`Unmarshal` без рефлексии (в 3–10 раз быстрее и меньше аллокаций). |
| **Транспорт** | HTTP/1.1 (или HTTP/2), текстовый JSON. | HTTP/2: мультиплексирование тысяч вызовов в **одно долгоживущее TCP-соединение**, сжатие заголовков HPACK. |
| **Стриминг** | Только односторонний (SSE) или поверх WebSockets. | Нативный серверный, клиентский и двунаправленный (`bidi`) стриминг из коробки. |
| **Дедлайны и отмена** | Нужно вручную передавать заголовок `X-Request-Timeout` и парсить его на сервере. | Встроенная передача дедлайна `context.WithTimeout` по проводу (`grpc-timeout`): отмена контекста клиентом автоматически отменяет `ctx` на сервере! |

### Как ускорить JSON в Go, если нужен именно REST

- Использовать потоковые `json.NewDecoder(r.Body)` / `json.NewEncoder(w)` вместе
  с переиспользованием буферов `*bytes.Buffer` через `sync.Pool`, чтобы снизить
  давление на сборщик мусора (GC).
- Следить за выходом `encoding/json/v2` в новых версиях Go, где существенно
  сокращены аллокации.

> ⚠️ **Ловушка балансировки gRPC в Kubernetes:** так как `grpc-go`
> мультиплексирует
> все запросы через одно HTTP/2 TCP-соединение, обычный L4-балансировщик
> (`ClusterIP` Service в Kubernetes) привяжет все вызовы к одному поду
> назначения. Для gRPC необходим L7-прокси (Envoy / Istio / Ingress),
> клиентская балансировка в `grpc-go` (`round_robin` через headless service DNS)
> или настройка `MaxConnectionAge` на сервере.
