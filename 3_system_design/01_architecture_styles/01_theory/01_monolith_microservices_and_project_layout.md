# Монолит, микросервисы и структура проекта в Go

## О чём эта тема (краткий контекст)

Архитектурный стиль определяет, как система разбивается на части:
разворачивается
ли она как единый процесс (монолит), как строго изолированные модули внутри
одного бинарника (модульный монолит) или как набор сетевых сервисов
(микросервисы). Правильный выбор границ позволяет команде быстро развивать
продукт, не утонув в распределённых транзакциях и сетевых сбоях. В Go этот
выбор тесно связан с системой пакетов, компилятором и принципами 12-Factor App.

## 1. Модульный монолит и микросервисы в экосистеме Go

В языках с тяжёлым рантаймом или глобальной блокировкой интерпретатора переход к
микросервисам иногда вынужденно используют ради утилизации всех ядер CPU или
ускорения сборки. В Go обе эти причины отсутствуют:

- **Сборка и утилизация CPU:** компилятор Go собирает монолит из сотен тысяч
  строк за секунды, а планировщик `G-M-P` эффективно нагружает все ядра внутри
  одного процесса.
- **Статический бинарник:** с флагом `CGO_ENABLED=0` монолит или микросервис
  компилируется в один исполняемый файл без внешних зависимостей, который
  упаковывается в `scratch` или `distroless` образ размером 10–25 МБ и стартует
  за миллисекунды.

Поэтому в Go золотой стандарт старта проекта — **модульный монолит**. Вынос
модуля в отдельный микросервис оправдан только при разном профиле нагрузки
(например, CPU-интенсивная обработка медиа отдельно от I/O-шлюза), независимых
релизных циклах разных команд или жёстких требованиях к изоляции отказов.

## 2. Стандартная раскладка Go-проекта (`cmd/`, `internal/`, `pkg/`)

Инструментарий Go превращает структуру каталогов в архитектурный механизм:
директория `internal/` защищена **на уровне компилятора**. Пакет внутри
`.../a/internal/b` может импортироваться только кодом, лежащим внутри дерева
`.../a/`.

```text
myservice/
├── cmd/
│   ├── api/                 # Точка входа HTTP/gRPC сервера (package main)
│   │   └── main.go          # Только сборка зависимостей и запуск
│   └── worker/              # Точка входа фонового воркера из того же модуля
│       └── main.go
├── internal/                # Приватный код сервиса (защищён компилятором)
│   ├── billing/             # Доменный модуль 1 (в модульном монолите)
│   │   ├── internal/        # Детали БД биллинга скрыты даже от соседних модулей!
│   │   └── service.go       # Публичный Go-контракт модуля billing
│   ├── orders/              # Доменный модуль 2
│   └── platform/            # Общая инфраструктура (логгер, пул БД, конфиг)
└── go.mod
```

### Как компилятор Go защищает границы модульного монолита

Если внутри `internal/orders/` создать свою подпапку `internal/postgres/`, то
код из `internal/billing/` физически **не скомпилируется** при попытке
импортировать `internal/orders/internal/postgres`. Модули общаются только через
узкие экспортируемые Go-интерфейсы и DTO в корне `internal/orders/`. Когда
наступит момент распилить монолит на микросервисы, вы просто заменяете вызов
Go-интерфейса на gRPC/HTTP-клиент и переносите папку `internal/orders` в новый
сервис.

> ⚠️ **Антипаттерн `pkg/`:** не выносите код в `pkg/` «на всякий случай». Если
> репозиторий не является публичной библиотекой, которую импортируют внешние
> проекты через `go get`, держите весь код в `internal/`.

## 3. 12-Factor App по-гошному

Принципы облачного приложения (12-Factor) в Go реализуются напрямую средствами
стандартной библиотеки:

| Фактор | Идиоматичная реализация в Go |
| :--- | :--- |
| **Dependencies** | `go.mod` + `go.sum`, сборка с `-mod=readonly` в CI. |
| **Config** | Чтение из `os.Getenv` в типизированную структуру `Config` при старте в `main.go` с немедленной валидацией (fail-fast). Никаких глобальных `os.Getenv` посреди бизнес-логики. |
| **Build, Release, Run** | Многоступенчатый Dockerfile: `golang:1.22-alpine` (`CGO_ENABLED=0 go build -ldflags="-s -w"`) → `gcr.io/distroless/static:nonroot`. |
| **Processes** | Stateless-процесс: не хранить сессии в глобальных `map`; для in-memory кэша учитывать, что при рестарте или масштабировании реплик память у каждого пода своя. |
| **Port binding** | Встроенный `net/http` (`http.Server`) без внешнего веб-сервера приложений. |
| **Disposability** | Мгновенный старт бинарника + перехват `SIGTERM` через `signal.NotifyContext` и `srv.Shutdown(ctx)`. |
| **Logs** | Структурный JSON в `os.Stdout` через стандартный `log/slog` без записи и ротации файлов внутри приложения. |

```go
// Идиоматичная загрузка конфигурации при старте (fail-fast).
type Config struct {
	Port        string
	DatabaseDSN string
}

func LoadConfig() (Config, error) {
	port := os.Getenv("PORT")
	if port == "" {
		port = "8080"
	}
	dsn := os.Getenv("DATABASE_DSN")
	if dsn == "" {
		return Config{}, fmt.Errorf("DATABASE_DSN is required")
	}
	return Config{Port: port, DatabaseDSN: dsn}, nil
}
```

## 4. Миграция из монолита в микросервисы (Strangler Fig в Go)

При плавном выносе маршрутов из старого монолита (паттерн «Душитель» / Strangler
Fig) стандартная библиотека Go даёт готовый промышленный инструмент —
`net/http/httputil.ReverseProxy`. Монолит или лёгкий Go-шлюз может прозрачно
проксировать часть маршрутов (или процент трафика по заголовку/cookie) в новый
микросервис без внедрения тяжёлого внешнего сервис-меша на первом этапе.

> ⚠️ **Частый вопрос на собеседовании:** как организовать общий код между
> микросервисами на Go и не получить распределённый монолит?
> В общий репозиторий (или `pkg/`) можно выносить только чистую инфраструктуру
> (обёртки телеметрии, логгер, middleware аутентификации). Выносить в общую
> библиотеку бизнес-сущности и модели таблиц БД категорически нельзя: любая
> правка поля потребует синхронного релиза всех сервисов. Контракты между
> сервисами передаются через версионируемые `.proto`-схемы или OpenAPI.
