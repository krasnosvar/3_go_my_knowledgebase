# Rate Limiting (ограничение частоты запросов)

Rate limiting ограничивает, сколько запросов клиент (или система целиком) может сделать за интервал времени. Это защита от перегрузки, злоупотреблений и способ честно делить ресурс между потребителями.

## Зачем

- **Защита от перегрузки** — не дать всплеску трафика положить сервис (и его зависимости).
- **Справедливость** — один шумный клиент не должен съесть всю ёмкость.
- **Защита от abuse** — брутфорс, скрейпинг, DoS.
- **Контроль стоимости** — платные API, квоты на пользователя/тариф.

Превышение лимита обычно отвечает `429 Too Many Requests`, часто с заголовком `Retry-After`.

## Token bucket (корзина токенов)

Корзина ёмкостью `capacity` наполняется токенами со скоростью `rate` токенов/сек (но не выше `capacity`). Каждый запрос забирает токен; нет токена → отказ.

- **Разрешает всплески (burst)** — накопленные токены позволяют пропустить пачку запросов сразу, пока корзина не опустеет.
- **В среднем держит `rate`** — долгосрочная частота ограничена скоростью наполнения.

```
наполнение: +rate токенов/сек (макс capacity)
        ┌──────────────┐
рефилл ->│ ● ● ● ●      │ токены
        └──────────────┘
запрос забирает 1 токен: есть -> allow, пусто -> deny (429)
```

## Leaky bucket (дырявое ведро)

Запросы попадают в очередь (ведро) и «вытекают» с постоянной скоростью `rate`. Ведро переполнилось → запрос отбрасывается.

- **Сглаживает выход** — на выходе строго равномерный поток, всплески на входе поглощаются очередью (до её предела).
- **Отличие от token bucket** — token bucket допускает всплеск на выходе (пока есть токены), leaky bucket — нет, он всегда выпускает ровно `rate`.

```
вход (рывками) -> [ ведро/очередь ] -> вытекает ровно rate/сек
                  переполнилось -> drop
```

## Fixed window (фиксированное окно)

Считаем запросы в рамках календарного окна (например, «100 запросов в минуту»). Счётчик сбрасывается в начале каждого окна.

- **Просто и дёшево** — один счётчик на окно.
- **Проблема границы окна** — на стыке двух окон клиент может сделать до `2×limit` запросов: `limit` в конце первого окна и `limit` в начале второго за короткий промежуток.

```
окно1 [00:00–00:59]        окно2 [01:00–01:59]
............|100 req|  |100 req|............
                   ^стык: 200 req за ~несколько секунд
```

## Sliding window (скользящее окно)

Сглаживает проблему границы fixed window.

- **Sliding log** — храним временные метки всех запросов за последнее окно и считаем их точно. Точно, но дорого по памяти.
- **Sliding window counter** — аппроксимация: берём счётчик текущего окна плюс взвешенную долю предыдущего:

  `count ≈ curr + prev × (доля предыдущего окна, попавшая в скользящий интервал)`

  Дёшево (два счётчика) и почти устраняет всплеск на границе.

## Сравнение

| Алгоритм              | Всплески        | Память        | Точность на границе |
|-----------------------|-----------------|---------------|---------------------|
| Token bucket          | разрешает burst | O(1)          | —                   |
| Leaky bucket          | сглаживает      | O(размер очереди) | равномерный выход |
| Fixed window          | до 2×limit      | O(1)          | плохая              |
| Sliding log           | точно           | O(кол-во req) | идеальная           |
| Sliding window counter| сглаживает      | O(1)          | хорошая (аппрокс.)  |

## Где применять

- **Локальный (per-instance)** — простой in-memory лимитер на каждый инстанс; суммарный лимит = `N × локальный`.
- **Распределённый (глобальный)** — общий счётчик в Redis/valkey (атомарный `INCR` + TTL), чтобы лимит был единым на кластер.
- **По ключу** — лимит на IP, на API-ключ, на пользователя, на эндпоинт.

> ⚠️ Частый вопрос на собеседовании: чем token bucket отличается от leaky bucket? Token bucket допускает контролируемый всплеск (накопленные токены выпускаются сразу), удерживая среднюю скорость; leaky bucket выпускает запросы строго равномерно, поглощая всплеск в очереди. Token bucket — про среднюю скорость с burst, leaky bucket — про сглаживание выхода.

> ⚠️ Частый вопрос на собеседовании: в чём слабость fixed window и как её лечит sliding window? На стыке окон можно пропустить до двойного лимита за короткий промежуток. Sliding window (лог или взвешенный счётчик) учитывает часть предыдущего окна, поэтому равномерно держит лимит на любом отрезке.
