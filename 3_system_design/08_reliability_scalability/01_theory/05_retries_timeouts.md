# Retries и Timeouts (повторы и таймауты)

Повторы и таймауты — базовая пара приёмов работы с ненадёжной сетью. Таймаут не даёт вызову висеть вечно, а повтор пытается пережить временный сбой. Применённые бездумно, они превращаются из лекарства в усилитель отказа.

## Таймауты

Таймаут ограничивает время ожидания. Без него один зависший вызов удерживает горутину и соединение, пулы исчерпываются, отказ распространяется вверх.

- **Виды** — connect timeout (установка соединения), read/write timeout (передача), overall/request timeout (весь запрос целиком).
- **Правило** — таймаут должен стоять на **каждом** внешнем вызове. Значение — исходя из реального p99 задержки зависимости, а не «на глаз».
- **В Go** — `context.WithTimeout` для общего дедлайна, плюс настройки `http.Client{Timeout}`, `net.Dialer{Timeout}`, серверные `ReadTimeout`/`WriteTimeout`.

## Deadline propagation (распространение дедлайна)

Дедлайн запроса нужно передавать вниз по всей цепочке вызовов, а не задавать заново на каждом шаге.

- **Зачем** — если у внешнего запроса осталось 200 мс, нет смысла у вложенного вызова ждать целую секунду: ответ всё равно уже никому не нужен.
- **Как** — в Go дедлайн живёт в `context.Context` и передаётся первым аргументом во все вызовы (`func(ctx, ...)`), а также в HTTP/gRPC-заголовках между сервисами. Дочерний `context.WithTimeout` берёт минимум из своего таймаута и унаследованного дедлайна.

```
клиент (deadline=1000ms)
  └─ сервис A (осталось 950ms)
       └─ сервис B (осталось 900ms)
            └─ БД: ждать не дольше остатка, а не свежую 1с
дедлайн течёт вниз -> никто не работает «в стол»
```

## Retries (повторы)

Повтор пытается пережить транзиентный сбой (сетевой глюк, кратковременная перегрузка, `503/429`).

- **Что ретраить** — только транзиентные ошибки: таймауты, сброс соединения, `5xx`, `429`. **Не** ретраить `4xx` (кроме `429`) — это ошибка запроса, повтор не поможет.
- **Ограничение попыток** — фиксированный max (например, 3), иначе повторы усиливают перегрузку.
- **Retry storm / thundering herd** — если все клиенты синхронно повторяют разом, они добивают уже перегруженную зависимость. Лечится backoff + jitter и circuit breaker'ом.

## Exponential backoff + jitter

Между повторами нужно ждать, причём с растущей паузой.

- **Exponential backoff** — задержка растёт экспоненциально: `base × 2^attempt` (например, 100 мс, 200, 400, 800...), обычно с потолком `max`.
- **Jitter (случайный разброс)** — добавляет случайность, чтобы разнести повторы клиентов во времени и не создать синхронную волну. Популярен «full jitter»: `sleep = random(0, min(max, base × 2^attempt))`.

```
attempt:   0     1     2     3
backoff:  100   200   400   800  (мс, экспонента)
+jitter:  ~57  ~130  ~310  ~640  (случайно в [0, backoff])
цель: клиенты не бьют по зависимости в один и тот же момент
```

## Идемпотентность как условие ретраев

Повторять безопасно только идемпотентную операцию: её многократное выполнение даёт тот же эффект, что и однократное.

- **Проблема** — при таймауте клиент не знает, дошёл ли запрос. Первый вызов мог **выполниться**, а ответ — потеряться. Повтор неидемпотентной операции (`POST /charge`) → двойное списание.
- **Идемпотентные по природе** — `GET`, `PUT` (полная замена), `DELETE`. **Неидемпотентные** — `POST`, «увеличь счётчик на 1».
- **Idempotency key** — клиент присваивает операции уникальный ключ (`Idempotency-Key`); сервер, увидев повтор с тем же ключом, возвращает результат первого выполнения, не делая работу дважды. Так небезопасную операцию делают безопасной для повтора.

> ⚠️ Частый вопрос на собеседовании: зачем к backoff добавлять jitter? Чистый экспоненциальный backoff синхронизирует клиентов: все, кто получил ошибку в один момент, повторят одновременно и снова обрушатся волной (thundering herd). Jitter случайно разносит повторы во времени, сглаживая нагрузку.

> ⚠️ Частый вопрос на собеседовании: почему нельзя ретраить любой запрос? Повтор безопасен только для идемпотентных операций. Иначе при потерянном ответе на уже выполнившийся `POST` повтор выполнит операцию дважды (двойное списание). Решение — идемпотентные ключи или проектирование операций идемпотентными.

> ⚠️ Частый вопрос на собеседовании: что важнее — retry или timeout? Таймаут первичен: без него вызов может висеть вечно, а retry вообще не сработает (нечего повторять — предыдущая попытка не завершилась). Retry имеет смысл только поверх таймаута.
