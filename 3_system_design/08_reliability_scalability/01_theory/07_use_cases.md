# Reliability & Scalability: практические применения

Как приёмы раздела складываются в цельную стратегию устойчивого масштабируемого сервиса. По отдельности каждый паттерн полезен, но настоящая надёжность рождается из их сочетания.

## Масштабирование под рост

- **Начните stateless** — вынесите сессии и состояние в Redis/valkey и БД; тогда веб-слой масштабируется горизонтально одним изменением числа реплик.
- **Autoscaling** — масштабируйте по нагрузке (CPU/RPS/длина очереди), а не вручную. Требует stateless-инстансов и graceful shutdown, чтобы сжатие не рвало запросы.
- **Вертикально — то, что плохо шардируется** — primary реляционной БД проще усилить (RAM/CPU) до определённого предела, чем расщеплять.
- **Шардируйте, когда упёрлись в один узел** — выбирайте ключ без hotspot; для перемещаемых данных и кэшей — consistent hashing.

## Балансировка и трафик

- **L7 на краю** — ingress/ALB терминирует TLS, роутит по пути, делает канареечные выкатки.
- **Least-connections для разнородных запросов**, round-robin — для коротких однородных.
- **Health checks + readiness** — только живые и готовые инстансы в ротации; readiness обязателен для корректного деплоя и graceful shutdown.

## Защита от перегрузки (цепочка обороны)

Единого «серебряного» приёма нет — они выстраиваются слоями:

```
клиент
  │  timeout на каждый вызов        (не висеть вечно)
  │  retry + backoff + jitter       (пережить транзиентный сбой, без волны)
  │  circuit breaker                (fail fast, не добивать больную зависимость)
  ▼
сервис
  │  rate limiting                  (не дать себя перегрузить)
  │  bulkhead / пулы                (изолировать ресурсы по зависимостям)
  ▼
зависимость (БД, соседний сервис)
```

- **Rate limiting на входе** — token bucket на инстанс или распределённый счётчик в Redis на кластер; лимиты по IP/ключу/пользователю.
- **Timeout + retry + circuit breaker на исходящих вызовах** — вместе: timeout завершает зависший вызов, retry с backoff+jitter переживает временный сбой, breaker обрывает лавину повторов к явно упавшей зависимости.
- **Идемпотентность** — предусловие безопасных повторов: `Idempotency-Key` для небезопасных операций.

## Корректная эксплуатация

- **Graceful shutdown везде** — ловить SIGTERM, дренировать в пределах grace-периода; иначе каждый деплой/скейл роняет запросы.
- **Deadline propagation** — прокидывать `context` с дедлайном сквозь всю цепочку, чтобы никто не работал «в стол».
- **Backpressure** — при перегрузке лучше явно отказать (`429/503 + Retry-After`), чем копить неограниченные очереди и упасть целиком.

## Типичные антипаттерны

- **Retry без backoff/jitter и без ограничения** — усиливает перегрузку (retry storm).
- **Retry неидемпотентной операции** — двойные списания и дубли.
- **Отсутствие таймаутов** — исчерпание пулов и каскадный отказ.
- **Health check, дёргающий БД** — сами проверки убивают здоровые инстансы под нагрузкой.
- **Stateful-веб-слой** (локальные сессии) — ломает горизонтальное масштабирование и требует sticky-сессий.
- **Игнор SIGTERM** — оборванные соединения на каждом деплое.

> ⚠️ Частый вопрос на собеседовании: как защитить сервис от каскадного отказа зависимости? Комбинацией: таймаут на вызов (не висеть), circuit breaker (fail fast при серии сбоев, не добивать зависимость), bulkhead (изолировать пулы), fallback (кэш/деградация) и backpressure на входе (rate limiting). Ни один приём в одиночку проблему не закрывает.

> ⚠️ Частый вопрос на собеседовании: спроектируйте устойчивый к нагрузке API. Ожидаемый ответ склеивает подтемы: stateless-инстансы за L7-балансировщиком с health-check, autoscaling, rate limiting на входе, timeout+retry(backoff+jitter)+circuit breaker на исходящих вызовах, идемпотентные ключи и graceful shutdown для бесшовных выкаток.
