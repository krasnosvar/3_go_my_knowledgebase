# Масштабирование (Scaling)

Масштабирование — способность системы обрабатывать растущую нагрузку. Есть два принципиально разных пути: сделать одну машину мощнее или добавить машин.

## Вертикальное масштабирование (scale up)

Наращиваем ресурсы одного узла: больше CPU, RAM, быстрее диск.

- **Плюсы** — просто (кода менять почти не нужно), нет проблем распределённости, ниже сетевые задержки внутри одной машины.
- **Минусы** — есть физический потолок (самая большая машина конечна), дорого на верхнем краю, узел остаётся единой точкой отказа (SPOF), рестарт = полный простой.

## Горизонтальное масштабирование (scale out)

Добавляем узлы и распределяем нагрузку между ними (обычно за балансировщиком).

- **Плюсы** — практически без потолка, отказоустойчивость (падение узла ≠ падение системы), можно расти/сжиматься по спросу (autoscaling), дешевле на объёме (commodity-железо).
- **Минусы** — сложность распределённой системы: согласованность данных, координация, сетевые сбои, распределённое состояние.

```
Вертикальное (scale up)          Горизонтальное (scale out)
   ┌─────────┐                    ┌──┐ ┌──┐ ┌──┐ ┌──┐
   │  БОЛЬШЕ  │                    │n1│ │n2│ │n3│ │n4│
   │ CPU/RAM  │                    └──┘ └──┘ └──┘ └──┘
   └─────────┘                      \    |    |    /
   один узел растёт                    балансировщик
```

| Аспект            | Вертикальное           | Горизонтальное            |
|-------------------|------------------------|---------------------------|
| Способ            | мощнее узел            | больше узлов              |
| Потолок           | есть (жёсткий)         | почти нет                 |
| Отказоустойчивость| SPOF                   | резервирование            |
| Сложность         | низкая                 | высокая (распределёнка)   |
| Стоимость наверху | растёт нелинейно       | линейна на commodity      |

> ⚠️ Частый вопрос на собеседовании: когда выбирать вертикальное масштабирование? Как быстрое временное решение и для того, что плохо шардируется (например, primary реляционной БД): проще докинуть RAM/CPU, чем расщеплять данные. Для stateless-веб-слоя почти всегда предпочтительнее горизонтальное.

## Stateless-сервисы — ключ к горизонтальному масштабированию

Сервис *stateless*, если не хранит между запросами состояния, влияющего на следующие запросы. Любой инстанс может обработать любой запрос — значит их можно свободно добавлять, убирать и заменять.

- **Где хранить состояние** — выносить наружу: сессии → Redis/valkey, данные → БД, файлы → объектное хранилище (S3). Сам инстанс становится «одноразовым».
- **Почему это важно** — можно масштабировать без sticky-сессий, спокойно убивать инстансы при autoscaling и деплое, не бояться потери локальных данных.
- **Stateful-компоненты** (БД, брокеры, кэши) масштабируются сложнее — через репликацию и шардирование, с отдельными гарантиями согласованности.

> ⚠️ Частый вопрос на собеседовании: почему stateless-сервисы масштабируются проще? Раз локального состояния нет, балансировщик отправляет запрос на любой инстанс, а инстансы добавляются/удаляются без миграции данных и без привязки клиента к конкретному узлу.

## Шардирование нагрузки (sharding / partitioning)

Когда данные или нагрузка не влезают в один узел, их разбивают на шарды (партиции), и каждый узел отвечает за свою часть.

- **Range-шардирование** — по диапазонам ключа (A–M → шард 1, N–Z → шард 2). Просто, но склонно к перекосу (hotspot), если ключи распределены неравномерно.
- **Hash-шардирование** — шард = `hash(key) % N`. Равномернее, но `% N` при изменении числа узлов переносит почти все ключи.
- **Consistent hashing** — кольцо хэшей: добавление/удаление узла двигает лишь ~`1/N` ключей. Стандарт для распределённых кэшей и хранилищ.

```
Consistent hashing (кольцо):
        ключи -> ближайший по часовой узел
      0°        node A
       \        /
   node D ---- (ключ K) -> идёт к node A
       /        \
      node C   node B
   добавили node E -> переехали только ключи между C и E
```

- **Выбор ключа шардирования** критичен: плохой ключ → hotspot (весь трафик в один шард). Хороший ключ равномерно раскладывает и нагрузку, и данные.
- **Rebalancing** — при добавлении шардов нужно перераспределить данные; consistent hashing и виртуальные ноды минимизируют объём переезда.

> ⚠️ Частый вопрос на собеседовании: чем плохо `hash(key) % N` при добавлении узла? Меняется `N`, поэтому почти для всех ключей меняется остаток → почти все ключи переезжают (для кэша — массовый промах, «cache stampede»). Consistent hashing перемещает лишь малую долю.
