# Graceful Shutdown (корректное завершение)

Graceful shutdown — упорядоченное завершение процесса: перестать принимать новую работу, дать текущей завершиться и освободить ресурсы. Противоположность — hard kill, при котором соединения обрываются на полуслове, а данные теряются.

## Зачем

В облаке процессы завершаются постоянно: деплой, autoscaling, перепланировка пода, spot-прерывание. Без graceful shutdown это означает:

- оборванные запросы у клиентов (500-ки на каждом деплое);
- незакоммиченные транзакции, потерянные сообщения;
- утёкшие соединения и незакрытые файлы.

Правильно завершаясь, сервис делает выкатку и масштабирование невидимыми для пользователей.

## Порядок завершения

```
1. Получили сигнал (SIGTERM)
2. Перестали проходить readiness -> LB выводит инстанс из ротации
3. Перестали принимать новые соединения/запросы
4. Дренаж (drain): дали активным запросам доиграть до конца (в пределах таймаута)
5. Закрыли ресурсы: БД-пулы, брокеры, файлы, flush логов/метрик
6. Вышли с кодом 0
```

Обратите внимание на шаг 2: между «получили SIGTERM» и «остановили приём» нужен зазор, пока балансировщик заметит readiness-провал, иначе он ещё какое-то время шлёт трафик на закрывающийся инстанс.

## Сигналы

- **SIGTERM** — «вежливая» просьба завершиться. Оркестраторы (Kubernetes, systemd) шлют именно его и дают grace-период (по умолчанию 30 с у k8s), после чего добивают **SIGKILL**.
- **SIGINT** — Ctrl+C в терминале, обрабатывается так же.
- **SIGKILL** — нельзя перехватить; наступает, если не уложились в grace-период. Отсюда правило: **дренаж должен быть короче grace-периода**.

## Реализация в Go: context + signal

Идиома — превратить сигнал ОС в отмену `context`, затем вызвать `Server.Shutdown(ctx)`:

- `signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)` возвращает context, который отменяется по сигналу.
- `http.Server.Shutdown(ctx)` перестаёт принимать новые соединения и **ждёт завершения активных запросов**; аргумент `ctx` задаёт крайний срок дренажа. Возвращает ошибку, если дедлайн истёк раньше, чем всё дренировалось.
- Отдельный `context.WithTimeout` ограничивает сам дренаж, чтобы завершение не висело вечно.

```
signal.NotifyContext(SIGTERM) ──> ctx.Done()
        │
        └─> shutdownCtx = WithTimeout(background, 25s)
            srv.Shutdown(shutdownCtx):
              • стоп accept новых соединений
              • ждём активные запросы <= 25s
              • не успели -> вернуть ошибку, форсировать выход
```

## Дренаж соединений (connection draining)

Дренаж = «доиграть текущее, не начинать нового».

- **HTTP** — `Server.Shutdown` закрывает listener, ждёт завершения активных запросов и idle keep-alive соединений.
- **Фоновые воркеры** — прекратить забор новых задач, дождаться обработки взятых (или вернуть их в очередь), затем закрыть.
- **Долгоживущие соединения** (WebSocket, стримы, gRPC-стримы) сами по себе `Shutdown` не завершит — их нужно закрывать явно, иначе они удержат процесс до дедлайна.
- **Потребители очередей** — остановить чтение, дообработать полученные сообщения, аккуратно закоммитить/отклонить offset.

> ⚠️ Частый вопрос на собеседовании: что произойдёт, если проигнорировать SIGTERM? Оркестратор подождёт grace-период и пришлёт SIGKILL, который нельзя перехватить: активные запросы оборвутся, транзакции не докоммитятся, ресурсы не закроются. Поэтому SIGTERM надо ловить и укладывать дренаж в grace-период.

> ⚠️ Частый вопрос на собеседовании: зачем зазор между получением SIGTERM и остановкой приёма запросов? Балансировщик узнаёт о выводе инстанса не мгновенно (по readiness/health-check). Если оборвать приём сразу, часть трафика ещё прилетит на закрытый listener и получит ошибку. Короткая пауза (провалить readiness, подождать) даёт LB перестать слать трафик.
