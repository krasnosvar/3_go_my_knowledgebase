# Балансировка нагрузки (Load Balancing)

Балансировщик нагрузки (load balancer, LB) распределяет входящие запросы между несколькими бэкенд-инстансами. Это фундамент горизонтального масштабирования и отказоустойчивости: если один инстанс упал, трафик уходит на остальные.

## Зачем

- **Масштабирование** — размазать нагрузку по многим машинам вместо одной большой.
- **Отказоустойчивость** — вывести упавший инстанс из ротации без простоя.
- **Гибкость эксплуатации** — rolling-обновления, blue/green, канарейки без даунтайма.
- **Единая точка входа** — клиент знает один адрес (VIP), а не список бэкендов.

## Алгоритмы распределения

- **Round-robin** — по кругу: 1-й запрос → инстанс A, 2-й → B, 3-й → C, 4-й → A... Просто и честно при равных инстансах и одинаковой стоимости запросов.
- **Weighted round-robin** — то же, но с весами: более мощный инстанс получает больше запросов.
- **Least connections** — новый запрос уходит на инстанс с наименьшим числом активных соединений. Лучше round-robin, когда запросы разной длительности (долгие соединения не копятся на одном узле).
- **Least response time** — учитывает и число соединений, и измеренную задержку.
- **Hash (по ключу)** — детерминированный выбор инстанса по хэшу от ключа (IP клиента, session-id, user-id). Один и тот же ключ всегда попадает на один инстанс → полезно для sticky-сессий и локальных кэшей.
- **Consistent hashing** — вариант хэширования, при котором добавление/удаление инстанса перемещает лишь малую долю ключей (а не всю карту). Основа шардирования и распределённых кэшей.

```
Round-robin:            Least connections:        Hash(key):
req1 -> A               A: 5 conn                 hash("user42") % 3 = 1
req2 -> B               B: 2 conn  <- сюда        -> всегда инстанс B
req3 -> C               C: 8 conn
req4 -> A               (новый -> B)
```

> ⚠️ Частый вопрос на собеседовании: round-robin против least-connections — когда что? Round-robin честен при однородных коротких запросах. Как только длительность запросов разная (WebSocket, стриминг, тяжёлые вычисления), round-robin складывает долгие соединения неравномерно, и least-connections распределяет нагрузку точнее.

## L4 vs L7 балансировка

Ключевое различие — на каком уровне модели работает балансировщик и **что он видит**.

- **L4 (транспортный уровень)** — работает с TCP/UDP. Видит только IP и порты, не заглядывает в содержимое. Просто пробрасывает соединение на выбранный бэкенд (NAT/DSR). Очень быстрый, дёшев по CPU, но «глупый».
- **L7 (прикладной уровень)** — работает с HTTP(S)/gRPC. Видит URL, заголовки, cookie, метод. Умеет маршрутизировать по пути (`/api` → одни бэкенды, `/static` → другие), терминировать TLS, переписывать заголовки, делать sticky-сессии по cookie. Дороже по ресурсам.

| Аспект                | L4                          | L7                              |
|-----------------------|-----------------------------|---------------------------------|
| Уровень               | TCP/UDP                     | HTTP/gRPC                       |
| Что видит             | IP, порт                    | URL, заголовки, метод, cookie   |
| Маршрутизация по пути | нет                         | да                              |
| Терминация TLS        | нет (обычно passthrough)    | да                              |
| Накладные расходы     | минимальные                 | выше (парсинг запроса)          |
| Примеры               | AWS NLB, IPVS, MetalLB      | AWS ALB, nginx, Envoy, Ingress  |

> ⚠️ Частый вопрос на собеседовании: чем L7-балансировщик отличается от L4? L4 маршрутизирует по IP:порт, не видя содержимого; L7 разбирает прикладной протокол (HTTP), поэтому может роутить по URL/заголовкам, терминировать TLS и делать sticky-сессии — ценой более высоких затрат CPU.

## Health checks (проверки здоровья)

Балансировщик должен слать трафик только на живые инстансы. Для этого он периодически опрашивает бэкенды.

- **Active health check** — LB сам стучится по эндпоинту (`GET /healthz`) с интервалом; N успешных подряд → инстанс `healthy`, M провалов подряд → `unhealthy` и вывод из ротации.
- **Passive health check** — LB наблюдает за реальным трафиком: если бэкенд возвращает ошибки/таймауты, он временно исключается (outlier detection).
- **Liveness vs readiness** — *liveness* отвечает «процесс жив» (иначе рестарт), *readiness* — «готов принимать трафик» (иначе временно убрать из ротации, но не убивать). Разделять их важно: на прогреве/при потере зависимости инстанс жив, но ещё не готов.

```
         health check каждые N сек
LB  --GET /healthz-->  инстанс
    <--200 OK-------    (healthy: в ротации)
    <--503 / timeout    (после M провалов -> unhealthy, из ротации)
```

- **Порог и гистерезис** — не выводить/возвращать инстанс с одного ответа; требовать несколько подряд, чтобы не «мигать» из-за единичного сбоя (flapping).
- **Дешёвый эндпоинт** — health-проверка не должна дёргать БД на каждый опрос, иначе проверки сами создают нагрузку и каскадно «убивают» здоровые инстансы.

> ⚠️ Частый вопрос на собеседовании: зачем разделять liveness и readiness? Liveness-провал ведёт к перезапуску пода, readiness-провал — лишь к выводу из балансировки. Если смешать, то временная неготовность (прогрев кэша, недоступная зависимость) вызовет ненужные рестарты и усилит инцидент.
