# Типичные проблемы кэширования

Кэш добавляет вторую копию данных и промежуточный слой — вместе с ускорением приходят специфические проблемы.

## Cache stampede / thundering herd

Популярный ключ протухает (или ещё не прогрет) — и **множество параллельных запросов одновременно** промахиваются и разом идут в БД за одним и тем же значением. БД получает всплеск дублирующей нагрузки и может лечь.

```
TTL истёк для ключа K
   req1 miss ┐
   req2 miss ┤
   req3 miss ┼──→ все N разом грузят K из БД (шторм)
   ...       ┤
   reqN miss ┘
```

**Термины.** *Cache stampede* и *thundering herd* обычно означают одно и то же — толпу одновременных промахов на один ключ. Иногда *dogpile* — частный случай (много запросов пересчитывают одно дорогое значение).

**Решения:**

- **Single-flight / request coalescing.** На каждый ключ разрешаем **ровно одну** параллельную загрузку; остальные горутины ждут её результата. Именно это реализует пример `03_stampede_singleflight` (через `sync.Mutex` + карту in-flight запросов). В экосистеме Go — пакет `golang.org/x/sync/singleflight`.
- **Блокировка/лок на пересчёт.** Первый промахнувшийся берёт лок (напр. `SET NX` в Redis) и пересчитывает, остальные ждут или отдают старое значение.
- **Jitter в TTL.** Разброс сроков, чтобы ключи не протухали синхронно (см. `03_ttl_eviction.md`).
- **Early / probabilistic recomputation.** Обновлять значение чуть **до** истечения TTL, вероятностно, чтобы перезагрузка размазалась по времени и не совпала у всех.
- **Прогрев (cache warming).** Заранее заполнять кэш горячими ключами перед всплеском трафика.

## Инвалидация

Как вовремя убрать/обновить устаревшее значение — самая тонкая часть.

- **По TTL** — «протухнет само». Просто, но между изменением в БД и истечением TTL данные stale.
- **По событию (write path)** — на записи в БД удаляем/обновляем ключ (cache-aside). Точно, но легко забыть путь записи или получить гонку.
- **По версии/тегу** — хранить `version`/`generation`; менять его → старые ключи автоматически «невалидны» (часто через префикс/тег в ключе).

Проблема **широкой инвалидации**: одно изменение затрагивает много производных ключей (список, агрегаты, страницы). Точечно удалить всё сложно → используют версионирование или инвалидацию по тегам.

## Stale data (устаревшие данные)

Между изменением в источнике и обновлением кэша значение в кэше отстаёт. Это **неизбежная цена** eventual consistency.

- Осознанно решить, **какая устареваемость допустима** для конкретных данных (см. `01_why_cache.md`).
- Для критичных данных (деньги, остатки на складе в момент оплаты) — либо не кэшировать, либо читать первоисточник в критической точке.
- TTL ограничивает **максимальный лаг** устаревания.

## Negative caching (кэширование отрицательных результатов)

Кэшировать надо не только «нашлось», но и «**не нашлось**» / ошибку — иначе запросы к несуществующим ключам всегда промахиваются и бьют по БД.

```
без negative caching:            с negative caching:
req(нет такого id) → miss → DB   req(нет такого id) → hit ($ = "not found")
(и так на КАЖДЫЙ запрос)         (БД не трогаем до истечения короткого TTL)
```

- Кладём маркер «отсутствует» (напр. пустое значение / tombstone) с **коротким TTL** (значение может вскоре появиться).
- Защищает от **cache penetration**: поток запросов к заведомо отсутствующим ключам (часто — сканирование/атака), который иначе проходит кэш насквозь в БД.
- Альтернатива/дополнение — Bloom-фильтр: быстро отсекать заведомо отсутствующие ключи, не ходя в БД.

## Прочие подводные камни

- **Cache pollution** — разовый большой скан вымывает горячие данные (лечит LFU / сегментированный LRU).
- **Hot key** — один сверхпопулярный ключ перегружает узел кэша (лечит локальная реплика значения / шардирование / локальный кэш перед распределённым).
- **Согласованность локального и распределённого кэша** — многоуровневый кэш (L1 in-process + L2 Redis) требует протокола инвалидации между узлами (например, pub/sub).

> ⚠️ Частый вопрос на собеседовании: что такое cache stampede и как с ним бороться? Это одновременный промах множества запросов по одному протухшему ключу, которые разом грузят БД. Борются: single-flight (одна загрузка на ключ, остальные ждут), локом на пересчёт, jitter в TTL и вероятностным ранним обновлением.

> ⚠️ Частый вопрос на собеседовании: как защититься от потока запросов к несуществующим ключам? Negative caching — кэшировать сам факт отсутствия с коротким TTL; дополнительно Bloom-фильтр, чтобы отсекать заведомо отсутствующие ключи до обращения к БД.
