# Зачем нужен кэш

Кэш — это быстрое хранилище копий данных, которые дорого получать из первоисточника. Идея одна: **не считай/не тяни повторно то, что уже посчитано/вытянуто**.

## Что даёт кэш

- **Латентность.** Обращение к RAM — десятки-сотни наносекунд, к локальному in-memory кэшу — микросекунды, к Redis по сети — доли миллисекунды, к диску/БД — единицы-десятки миллисекунд, к внешнему API — сотни миллисекунд. Кэш сдвигает горячие данные на несколько порядков ближе.
- **Разгрузка первоисточника.** Каждое попадание в кэш (cache hit) — это запрос, который не дошёл до БД или внешнего сервиса. При hit ratio 90% нагрузка на БД падает в ~10 раз. Часто именно это, а не латентность, — главная причина ставить кэш.
- **Стоимость.** Читать из кэша дешевле, чем масштабировать БД под пиковый QPS. Реплики БД, вертикальный скейл, оплата запросов к платному API — всё это дороже, чем узел с памятью под кэш.
- **Сглаживание пиков.** Кэш поглощает всплески трафика на популярные ключи, не давая им дойти до backend.

### Порядки величин (запомнить)

```
L1 cache        ~1 нс
RAM             ~100 нс
in-memory map   ~микросекунды (с учётом хеширования/локов)
Redis по сети   ~0.2–1 мс
SSD             ~0.1 мс
запрос к БД     ~1–10 мс
HDD seek        ~10 мс
внешний API     ~50–500 мс
```

## Ключевая метрика: hit ratio

```
hit ratio = hits / (hits + misses)
```

Эффективность кэша определяется долей попаданий. Средняя латентность с кэшем:

```
avg = hit_ratio * t_cache + (1 - hit_ratio) * t_source
```

При `t_cache = 0.5 мс`, `t_source = 10 мс` и hit ratio 0.9 средняя латентность ≈ 1.45 мс вместо 10 мс. Разница между 90% и 99% попаданий огромна: «длинный хвост» промахов бьёт по p99.

## Когда кэш уместен

- Данные читаются **гораздо чаще, чем меняются** (read-heavy).
- Есть **горячие ключи** — небольшая доля данных даёт большую долю запросов (принцип 80/20, закон Ципфа).
- Допустима **некоторая устареваемость** (eventual consistency) — можно отдать данные «на секунду назад».
- Вычисление/получение значения **дорогое**: тяжёлый JOIN, агрегат, вызов внешнего API.

## Когда кэш вреден или бесполезен

- **Данные меняются почти на каждый запрос** — кэш всё время «холодный», hit ratio низкий, а на инвалидацию тратятся силы.
- **Строгая согласованность обязательна** (баланс счёта, остаток на складе в момент оплаты) — устаревшее значение недопустимо; кэш добавляет риск отдать stale data.
- **Равномерный доступ без горячих ключей** — кэш не помещает весь датасет, hit ratio низкий.
- **Данные уникальны на запрос** (персональный ответ, одноразовый токен) — переиспользовать нечего.

Кэш — это **оптимизация, а не источник истины**. Он всегда добавляет ещё одну копию данных → ещё одну проблему согласованности. Ставить его нужно, когда измеренная выгода перевешивает эту цену.

> ⚠️ Частый вопрос на собеседовании: почему кэш ускоряет систему не только за счёт латентности? Потому что снимает нагрузку с БД/внешних сервисов: попадание в кэш — это запрос, который вообще не дошёл до дорогого первоисточника, что и позволяет держать высокий QPS без масштабирования БД.

> ⚠️ Частый вопрос на собеседовании: две главные проблемы в computer science — инвалидация кэша и именование. Смысл шутки: положить данные в кэш легко, а вовремя и корректно их оттуда убрать/обновить — сложно.
