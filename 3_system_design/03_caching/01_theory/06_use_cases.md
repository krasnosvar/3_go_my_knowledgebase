# Практические применения

Сводка того, где и как реально применяют кэширование, и как это соотносится с паттернами и проблемами из предыдущих подтем.

## Уровни кэширования в системе

Кэш есть почти на каждом слое пути запроса:

```
Клиент → CDN → Reverse proxy → App (L1 in-process) → Redis (L2) → БД (buffer pool)
  │        │         │              │                    │            │
браузер  edge     nginx/varnish  локальный кэш      распределённый  кэш страниц
кэш      кэш      кэш ответов    (map+RWMutex)      кэш            БД в RAM
```

- **Клиент/браузер** — HTTP-кэш по заголовкам `Cache-Control`, `ETag` (см. раздел networking).
- **CDN** — кэш статики и кэшируемых ответов ближе к пользователю.
- **Reverse proxy** (nginx/Varnish) — кэш HTTP-ответов перед приложением.
- **Приложение** — L1 in-process кэш горячих данных (быстрее всего, но у каждого инстанса свой).
- **Распределённый кэш** (Redis/Memcached) — L2, общий для инстансов.
- **БД** — свой buffer pool держит горячие страницы в RAM.

## Типовые сценарии и выбор паттерна

| Сценарий | Что кэшируем | Паттерн | Особенности |
|----------|--------------|---------|-------------|
| Профиль пользователя, каталог | результат чтения из БД | cache-aside + TTL | read-heavy, редкие изменения |
| Сессии / токены | session id → данные | write-through/aside | TTL = время жизни сессии |
| Лента/агрегаты (счётчики, топы) | предпосчитанный результат | cache-aside, версия/тег | широкая инвалидация |
| Rate limiting | счётчик запросов на ключ | атомарные операции в Redis | TTL = окно лимита |
| Ответы дорогого внешнего API | тело ответа | cache-aside + negative caching | короткий TTL, кэшировать ошибки |
| Дорогой запрос/вычисление | результат | cache-aside + single-flight | защита от stampede |

## Мини-чеклист «ставить ли кэш»

1. Данные **читаются чаще, чем меняются**? Есть **горячие ключи**? — иначе кэш почти бесполезен.
2. Какая **устареваемость допустима**? — задаёт TTL и стратегию инвалидации.
3. Насколько **дорог первоисточник** (латентность, нагрузка, деньги)? — оправдывает ли выгода сложность.
4. Что при **промахе и при падении кэша**? — должен быть корректный fallback в источник.
5. Как **инвалидируем** на записи? — TTL как минимум, событийная инвалидация точнее.
6. Ждём **всплески на один ключ**? — нужен single-flight/лок и jitter в TTL.
7. Возможны запросы к **несуществующим ключам**? — negative caching / Bloom-фильтр.

## Что показывают примеры этого раздела

- `01_cache_aside` — базовый цикл cache-aside: промах → загрузка из «медленной БД» → запись в кэш → попадание, с наглядной разницей во времени.
- `02_lru_eviction` — ограничение размера кэша и вытеснение по LRU (`map` + `container/list`).
- `03_stampede_singleflight` — защита от cache stampede: N горутин на один ключ вызывают загрузку ровно один раз.

Упражнения (`03_exercises/`) закрепляют: TTL-протухание, LRU `Put/Get` с вытеснением, подсчёт hit ratio, инвалидацию по ключу.

## Итоговые принципы

- Кэш — **оптимизация, а не источник истины**; система обязана работать (медленнее) без него.
- Всегда ставить **TTL** как предохранитель, на записи **удалять** ключ, а не обновлять.
- Мерить **hit ratio** и латентность p99 — иначе непонятно, помогает ли кэш.
- Проектировать под **промах, падение кэша, всплеск на ключ и запросы к отсутствующим ключам**, а не только под «счастливый путь».

> ⚠️ Частый вопрос на собеседовании: где в типичном веб-стеке находятся кэши? На всём пути запроса: браузер (HTTP-кэш), CDN, reverse proxy, L1 in-process в приложении, L2 распределённый (Redis), buffer pool БД. Многоуровневость — норма, а не исключение.
