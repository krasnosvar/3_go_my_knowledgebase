# Redis как кэш

Redis — in-memory хранилище ключ-значение, самый распространённый распределённый кэш. В отличие от локального in-process кэша (одна память на процесс), Redis — **отдельный сетевой сервис**, общий для многих инстансов приложения.

> Фрагменты кода ниже — **иллюстрация паттернов**, а не рабочий клиент. Реального подключения к Redis здесь нет (по стандарту раздела — только stdlib). Runnable-примеры тех же идей на in-memory кэше — в `02_examples/`.

## Почему Redis, а не локальная map

| Свойство            | Локальный in-process (`map` + `sync.RWMutex`) | Redis |
|---------------------|-----------------------------------------------|-------|
| Скорость            | быстрее (без сети)                            | доля мс (сеть) |
| Общий на инстансы   | нет (у каждого свой)                          | да (единый) |
| Согласованность между инстансами | нет                              | есть |
| Переживает рестарт  | нет                                           | да (persistence) |
| TTL, eviction, атомарные операции | руками                          | из коробки |
| Объём               | ограничен памятью процесса                    | отдельный узел/кластер |

Часто используют **двухуровневый кэш**: L1 — локальный (супербыстрый), L2 — Redis (общий). L1 гасит hot key и сеть, L2 даёт согласованность между инстансами.

## Структуры данных под кэш

- **String** — простое значение по ключу (сериализованный JSON/protobuf, число). База для cache-aside.
- **Hash** — поля объекта под одним ключом (`user:42 → {name, email}`); можно читать/писать отдельные поля.
- **Set / Sorted Set** — множества и рейтинги/лидерборды, диапазонные выборки по score.
- **List** — очереди, последние N элементов.
- **Bitmap / HyperLogLog** — компактные счётчики уникальностей (например, приблизительный подсчёт уникальных посетителей).

Ключи именуют по конвенции с разделителем `:` — `entity:id:field`, например `user:42:profile`.

## TTL в Redis

TTL задают при записи (`SET key val EX <seconds>`) или отдельно (`EXPIRE key <seconds>`). Redis удаляет протухшие ключи лениво (при обращении) и активно (фоновая выборка ключей с TTL). При заполнении `maxmemory` вытесняет по политике (`allkeys-lru`, `allkeys-lfu`, …; см. `03_ttl_eviction.md`).

## Паттерн cache-aside в Go-сервисе (иллюстрация)

Псевдо-интерфейс кэша (что-то вроде go-redis), чтобы показать поток вызовов:

```go
// Иллюстрация: интерфейс распределённого кэша (не реальный клиент).
type Cache interface {
	Get(ctx context.Context, key string) (string, bool, error)
	Set(ctx context.Context, key, val string, ttl time.Duration) error
	Del(ctx context.Context, key string) error
}

// Чтение по паттерну cache-aside.
func (s *Service) GetUser(ctx context.Context, id string) (User, error) {
	key := "user:" + id

	// 1) пробуем кэш
	if raw, ok, err := s.cache.Get(ctx, key); err != nil {
		return User{}, err
	} else if ok {
		var u User
		if err := json.Unmarshal([]byte(raw), &u); err == nil {
			return u, nil // hit
		}
		// битое значение в кэше — трактуем как miss
	}

	// 2) miss -> идём в БД
	u, err := s.db.LoadUser(ctx, id)
	if err != nil {
		return User{}, err
	}

	// 3) кладём в кэш с TTL (+ jitter, чтобы ключи не протухали синхронно)
	if b, err := json.Marshal(u); err == nil {
		ttl := 5*time.Minute + time.Duration(rand.Intn(30))*time.Second
		_ = s.cache.Set(ctx, key, string(b), ttl)
	}
	return u, nil
}

// Запись: сперва БД, затем ИНВАЛИДАЦИЯ ключа (удаление, не обновление).
func (s *Service) UpdateUser(ctx context.Context, u User) error {
	if err := s.db.SaveUser(ctx, u); err != nil {
		return err
	}
	return s.cache.Del(ctx, "user:"+u.ID) // следующее чтение перезагрузит свежее
}
```

Ключевые решения в коде: **TTL с jitter**, на записи **удаляем** ключ (см. `02_patterns.md`), битое значение считаем промахом.

## Защита от stampede через Redis-лок (иллюстрация)

Первый промахнувшийся берёт короткий лок (`SET NX`) и пересчитывает; остальные ждут или отдают старое значение:

```go
// SET lockKey token NX EX 5  -> получить эксклюзив на пересчёт ключа.
ok, _ := s.cache.SetNX(ctx, "lock:"+key, token, 5*time.Second)
if ok {
	// мы единственные грузим значение и кладём в кэш
	val := loadFromDB()
	_ = s.cache.Set(ctx, key, val, ttl)
	_ = s.cache.Del(ctx, "lock:"+key)
} else {
	// кто-то уже грузит: подождать и перечитать кэш
}
```

Локальный (in-process) аналог того же — single-flight через `sync.Mutex` + карту in-flight, реализованный в `02_examples/03_stampede_singleflight`.

## Эксплуатационные заметки

- **Redis — обычно кэш, а не источник истины.** Даже с persistence его теряемость закладывают в дизайн: приложение должно переживать пустой/упавший Redis (промахи идут в БД).
- **Сериализация** стоит CPU и место — выбирают формат (JSON проще, protobuf/msgpack компактнее и быстрее).
- **Размер значения:** очень большие значения бьют по латентности и памяти; крупные объекты лучше хранить в Hash по полям.
- **Пул соединений и таймауты** обязательны: зависший Redis не должен вешать запросы приложения (fail-fast + fallback в БД).

> ⚠️ Частый вопрос на собеседовании: почему Redis, а не локальная map в приложении? Redis — общий для всех инстансов, даёт согласованность между ними, переживает рестарт процесса, имеет встроенные TTL/eviction/атомарные операции. Локальная map быстрее, но у каждого инстанса своя и теряется при рестарте; их часто комбинируют (L1 локальный + L2 Redis).

> ⚠️ Частый вопрос на собеседовании: что произойдёт с сервисом, если Redis упадёт? При корректном дизайне (cache-aside + таймауты) запросы просто пойдут промахами в БД — медленнее, но работает. Redis — оптимизация, а не источник истины; на его отказ закладывают fallback и защиту БД от резкого всплеска нагрузки.
