# HTTP/3 и QUIC

HTTP/3 (RFC 9114) — третья версия HTTP, которая работает не поверх TCP, а поверх **QUIC** (RFC 9000) — транспортного протокола, построенного на **UDP**.

## Зачем понадобился новый транспорт

HTTP/2 решил прикладной head-of-line blocking, но упёрся в ограничение TCP: одно соединение + гарантия порядка байтов означает, что **потеря одного TCP-сегмента останавливает все мультиплексированные потоки** до его переотправки. Чтобы избавиться от этого, транспорт пришлось менять — но менять TCP в ядрах ОС и в железе крайне тяжело. Поэтому QUIC построили поверх UDP (который передаётся везде) и реализовали в user-space.

## Что такое QUIC

QUIC — надёжный транспорт поверх ненадёжного UDP, вобравший функции TCP + TLS:

```
        HTTP/1.1 / HTTP/2            HTTP/3
        +----------------+          +----------------+
        |     HTTP       |          |     HTTP/3     |
        +----------------+          +----------------+
        |      TLS       |          |      QUIC      |  (TLS 1.3 встроен)
        +----------------+          +----------------+
        |      TCP       |          |      UDP       |
        +----------------+          +----------------+
        |      IP        |          |      IP        |
        +----------------+          +----------------+
```

## Что решает QUIC / HTTP/3

- **Устраняет TCP head-of-line blocking** — потоки в QUIC действительно независимы: потеря пакета в одном потоке не тормозит остальные (каждый поток управляет своим порядком отдельно).
- **Быстрое установление соединения** — транспортное и криптографическое рукопожатие объединены. Первое подключение — 1-RTT, повторное — **0-RTT** (данные летят вместе с первым пакетом), тогда как TCP + TLS 1.3 требуют минимум 2 RTT.
- **Встроенный TLS 1.3** — шифрование не опция, а часть протокола.
- **Connection migration** — соединение привязано к Connection ID, а не к паре IP:port. При смене сети (Wi-Fi → LTE) соединение не рвётся.

## Компромиссы

- UDP-трафик иногда блокируется корпоративными фаерволами → клиенты умеют откатываться на HTTP/2 поверх TCP.
- Обработка в user-space нагружает CPU сильнее, чем аппаратно оптимизированный TCP (нивелируется offload'ом).

## Итоговая эволюция

| Версия   | Транспорт | HOL-блокировка         | Рукопожатие              |
|----------|-----------|------------------------|--------------------------|
| HTTP/1.1 | TCP       | на уровне приложения   | TCP (+TLS отдельно)      |
| HTTP/2   | TCP       | только на уровне TCP   | TCP + TLS                |
| HTTP/3   | QUIC/UDP  | отсутствует            | 1-RTT / 0-RTT, TLS 1.3 встроен |

> ⚠️ Частый вопрос на собеседовании: почему HTTP/3 поверх UDP, если UDP ненадёжен? QUIC реализует надёжность, переотправку и контроль перегрузки сам, в user-space поверх UDP. UDP выбран потому, что он проходит через существующую сетевую инфраструктуру, а менять/заменять TCP в ядрах ОС и промежуточном оборудовании практически невозможно.
