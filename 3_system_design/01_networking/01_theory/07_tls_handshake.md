# TLS-хендшейк

TLS (Transport Layer Security, преемник SSL) обеспечивает защищённый канал поверх TCP (или встроен в QUIC). Даёт три вещи: **конфиденциальность** (шифрование), **целостность** (защита от подмены) и **аутентификацию сервера** (сертификат).

## Что даёт TLS

- Симметричное шифрование трафика после установки канала (быстрое).
- Асимметричная криптография и подписи — только на этапе рукопожатия (обмен ключами, проверка сертификата).
- Проверка сертификата — цепочка доверия до корневого CA.

## Сертификаты и цепочка доверия

Сервер предъявляет **X.509-сертификат**, подписанный удостоверяющим центром (CA). Клиент проверяет:

1. Подпись сертификата ведёт по цепочке к **корневому CA**, которому клиент доверяет (root store в ОС/браузере).
2. Сертификат не истёк и не отозван (CRL / OCSP).
3. Имя в сертификате (SAN) совпадает с запрашиваемым доменом.

```
Root CA  ──подписал──▶  Intermediate CA  ──подписал──▶  Сертификат example.com
(в доверенном                                            (предъявляет сервер)
 хранилище клиента)
```

## TLS 1.3 handshake (1-RTT) по шагам

TLS 1.3 упростил и ускорил рукопожатие — одно RTT до передачи данных:

```
Клиент                                             Сервер
  |                                                   |
  |-- ClientHello ----------------------------------->|
  |   (версии, cipher suites, key_share:              |
  |    временный публичный ключ клиента)              |
  |                                                   |
  |<------------------------------- ServerHello ------|
  |   (выбранный cipher, key_share сервера),          |
  |   {Certificate},                                  |
  |   {CertificateVerify}  — подпись, доказывающая    |
  |                          владение приватным ключом|
  |   {Finished}                                      |
  |                                                   |
  |  теперь обе стороны вычислили общий               |
  |  сессионный ключ (ECDHE) и проверили сертификат   |
  |                                                   |
  |-- {Finished} ------------------------------------>|
  |== зашифрованные данные приложения ===============>|
  |<=================================================>|
```

Ключевые моменты:

- **ECDHE (Диффи-Хеллман на эллиптических кривых)** — стороны обмениваются публичными частями и независимо вычисляют один и тот же общий секрет. Приватные части не передаются никогда.
- **Forward secrecy** — временные (ephemeral) ключи ECDHE уникальны для каждой сессии, поэтому компрометация долгоживущего ключа сервера не расшифрует ранее записанный трафик.
- **CertificateVerify** — сервер подписывает хендшейк своим приватным ключом, доказывая, что сертификат действительно его.

## TLS 1.2 vs 1.3 (кратко)

- **1.2** — рукопожатие занимало 2 RTT, допускало устаревшие/небезопасные наборы шифров, RSA-обмен ключами без forward secrecy.
- **1.3** — 1 RTT (и 0-RTT для возобновления сессии), только современные AEAD-шифры, обязательный forward secrecy, меньше «ручек» для ошибок конфигурации.

## После рукопожатия

Дальше весь HTTP-трафик передаётся симметрично зашифрованным сессионным ключом — это быстро. Асимметрика используется только один раз, при установке.

> ⚠️ Частый вопрос на собеседовании: зачем в TLS и асимметричная, и симметричная криптография? Асимметричная нужна для безопасного согласования общего секрета и аутентификации сервера, но она медленная. Поэтому её применяют один раз в хендшейке, а весь дальнейший трафик шифруют быстрым симметричным ключом.

> ⚠️ Частый вопрос на собеседовании: что такое forward secrecy и зачем он? Использование временных ключей ECDHE на каждую сессию: даже если приватный ключ сервера позже утечёт, ранее перехваченный и записанный трафик расшифровать не получится.
