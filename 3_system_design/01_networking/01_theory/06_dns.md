# DNS

DNS (Domain Name System) — распределённая иерархическая система, которая переводит человекочитаемые имена (`api.example.com`) в IP-адреса (`93.184.216.34`). Работает в основном поверх UDP на порту 53 (при больших ответах — поверх TCP).

## Иерархия имён

Имя читается справа налево, от корня к листу:

```
                      . (root)
                      |
             +--------+--------+
            com      org      ru      <- TLD (top-level domain)
             |
         example.com               <- authoritative (второй уровень)
             |
   api.example.com  www.example.com <- поддомены
```

## Как происходит резолвинг (рекурсивный)

```
Приложение                Recursive Resolver           DNS-серверы
    |  api.example.com ------->|
    |                          |-- "?" ------------> Root server  (. )
    |                          |<-- "спроси .com" ---|
    |                          |-- "?" ------------> TLD server (.com)
    |                          |<-- "спроси example.com NS" --|
    |                          |-- "?" ------------> Authoritative (example.com)
    |                          |<-- A: 93.184.216.34 ----------|
    |<-- 93.184.216.34 --------|
```

1. Приложение спрашивает **рекурсивный резолвер** (обычно резолвер провайдера или `8.8.8.8`).
2. Резолвер идёт по иерархии: root → TLD (`.com`) → authoritative-сервер зоны.
3. Authoritative-сервер даёт финальный ответ (A-запись).
4. Резолвер кэширует ответ и возвращает клиенту.

## Основные типы записей

| Тип     | Назначение                                            |
|---------|-------------------------------------------------------|
| **A**   | имя → IPv4-адрес                                       |
| **AAAA**| имя → IPv6-адрес                                       |
| **CNAME**| псевдоним: имя → другое имя (канонический alias)      |
| **MX**  | почтовый сервер домена (с приоритетом)                |
| **NS**  | authoritative name-серверы зоны                       |
| **TXT** | произвольный текст (SPF, DKIM, верификация владения)  |
| **SOA** | параметры зоны (serial, TTL, ответственный сервер)    |
| **PTR** | обратный резолвинг: IP → имя                          |
| **SRV** | адрес+порт сервиса                                    |

## Кэширование и TTL

Каждая запись имеет **TTL (Time To Live)** — сколько секунд её можно держать в кэше. Кэширование происходит на нескольких уровнях: ОС, рекурсивный резолвер, иногда само приложение.

- **Большой TTL** — меньше нагрузка на DNS, но изменения (новый IP при переезде) распространяются медленно.
- **Маленький TTL** — быстрое переключение (нужно для failover, blue-green), но больше запросов.

Типовой приём перед миграцией: заранее снизить TTL (например, до 60 сек), переключить запись, дождаться распространения, затем вернуть большой TTL.

## Почему UDP, а при необходимости TCP

Запрос и ответ обычно умещаются в одну датаграмму → UDP даёт минимальную задержку без накладных расходов на соединение. Если ответ не помещается (флаг truncated, TC=1) или для zone transfer (AXFR) — клиент повторяет запрос по TCP. Современные расширения: **EDNS0** (большие UDP-ответы), **DoT/DoH** (DNS over TLS/HTTPS для приватности).

> ⚠️ Частый вопрос на собеседовании: почему после смены IP старый адрес ещё какое-то время резолвится? Из-за кэширования по TTL на резолверах и в ОС: пока TTL старой записи не истёк, отдаётся старый закэшированный IP.

> ⚠️ Частый вопрос на собеседовании: в чём разница CNAME и A? A указывает прямо на IP; CNAME указывает на другое имя, которое затем резолвится отдельно. На корне зоны (apex) CNAME использовать нельзя.
