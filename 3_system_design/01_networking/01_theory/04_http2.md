# HTTP/2

HTTP/2 (RFC 7540) — эволюция HTTP/1.1, сохраняющая ту же семантику (методы, статусы, заголовки), но полностью меняющая формат передачи по проводу. Работает поверх того же TCP (в браузерах — почти всегда поверх TLS).

## Главная проблема, которую решает

В HTTP/1.1 по одному TCP-соединению запросы идут строго последовательно — **head-of-line blocking на уровне приложения**. Медленный ответ блокирует все последующие. Браузеры открывали 6+ соединений на домен как обходной путь.

## Ключевые особенности

### 1. Бинарный формат и фреймы

HTTP/2 разбивает обмен на бинарные **фреймы** (HEADERS, DATA и др.) вместо текстовых строк. Это компактнее и надёжнее парсится.

### 2. Мультиплексирование (multiplexing)

Внутри **одного** TCP-соединения одновременно живёт множество независимых **потоков (streams)**, каждый со своим ID. Фреймы разных потоков перемежаются:

```
HTTP/1.1: [req1][resp1][req2][resp2]  — по очереди, одно соединение

HTTP/2 (одно соединение):
  stream 1: HEADERS ---- DATA ------------ DATA
  stream 3:      HEADERS ---- DATA
  stream 5:          HEADERS -------- DATA
  (фреймы разных потоков идут вперемешку и собираются на приёмнике)
```

Это устраняет прикладной head-of-line blocking: медленный ответ в потоке 1 не мешает потоку 3.

### 3. Сжатие заголовков (HPACK)

Заголовки в HTTP/1.1 повторялись в каждом запросе (Host, User-Agent, Cookie) и передавались текстом. HTTP/2 применяет **HPACK** — сжатие с общей таблицей ранее переданных заголовков, так что повторяющиеся передаются как ссылка на индекс.

### 4. Server Push (кратко)

Сервер мог **упреждающе** отправить ресурсы, которые клиент ещё не запросил (например, CSS вместе с HTML). На практике оказался малоэффективным и **признан устаревшим / отключается** в большинстве браузеров — вместо него используют `<link rel="preload">` и заголовок `103 Early Hints`.

### 5. Приоритизация потоков

Клиент может указать относительную важность потоков, чтобы критичные ресурсы (например, CSS) грузились раньше.

## Оставшееся ограничение: TCP head-of-line blocking

Мультиплексирование убирает HOL-блокировку на уровне HTTP, но не на уровне TCP: HTTP/2 живёт в **одном** TCP-соединении, а TCP гарантирует порядок байтов. Если потерялся один TCP-сегмент, все потоки ждут его переотправки. Эту проблему решает уже HTTP/3 поверх QUIC (см. `05_http3_quic.md`).

> ⚠️ Частый вопрос на собеседовании: почему HTTP/2 не полностью снимает head-of-line blocking? Он снимает её на уровне приложения (мультиплексирование потоков), но остаётся HOL на уровне TCP: потеря одного сегмента тормозит все потоки, потому что все они делят одно TCP-соединение с гарантией порядка.
