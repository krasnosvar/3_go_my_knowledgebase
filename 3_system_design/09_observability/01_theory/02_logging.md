# Логирование

Лог — поток записей о событиях. Ключевой вопрос — как сделать эти записи пригодными для машинной обработки, а не только для чтения глазами.

## Неструктурные vs структурные логи

**Неструктурный лог** — свободный текст:

```
2026-07-09 12:00:01 user alice failed login from 10.0.0.5
```

Читается человеком, но плохо парсится и агрегируется: чтобы посчитать неудачные логины по пользователю, нужен regexp, который сломается при любом изменении формата.

**Структурный лог** — запись с явными полями, обычно в JSON:

```json
{"time":"2026-07-09T12:00:01Z","level":"WARN","msg":"failed login","user":"alice","src_ip":"10.0.0.5"}
```

Такую запись легко фильтровать, агрегировать и индексировать в системах сбора логов (Loki, Elasticsearch и т.п.): `level="WARN" AND user="alice"`.

**Правило:** в проде логируем структурно. Сообщение (`msg`) должно быть постоянной строкой, а всё переменное — в полях, а не в тексте (иначе теряется группировка одинаковых событий).

## Уровни логирования

Стандартная шкала по возрастанию важности:

- **DEBUG** — подробности для отладки; в проде обычно выключены.
- **INFO** — штатные значимые события (запуск, обработан запрос).
- **WARN** — что-то подозрительное, но система работает (ретрай, деградация).
- **ERROR** — операция не удалась, требуется внимание.

Уровень задаёт **порог**: при уровне INFO записи DEBUG отбрасываются. Это управляет объёмом и стоимостью логов. Избегайте логирования на ERROR того, что не является реальной проблемой, — иначе алерты по ERROR превращаются в шум.

## Корреляция запросов

Чтобы собрать все записи, относящиеся к одному запросу или пользователю, в лог добавляют **идентификатор корреляции**:

- `request_id` / `correlation_id` — генерируется на входе (или берётся из заголовка `X-Request-Id`) и прокидывается через весь обработчик запроса.
- `trace_id` — связывает логи с распределённым трейсом (см. подтему про трейсинг).

В Go идентификатор удобно прокидывать через `context.Context`, а логгер обогащать этими полями один раз на запрос, чтобы каждая запись их наследовала.

## log/slog в Go (stdlib)

С Go 1.21 в стандартной библиотеке есть `log/slog` — структурное логирование без внешних зависимостей.

Ключевые понятия:

- **`slog.Logger`** — фронтенд, у которого вызывают `Info`, `Warn`, `Error`, `Debug`.
- **`slog.Handler`** — бэкенд, определяющий формат и назначение вывода. Встроены `slog.NewTextHandler` (человекочитаемый) и `slog.NewJSONHandler` (структурный JSON).
- **Атрибуты (attrs)** — пары ключ-значение, передаются в вызов или прикрепляются к логгеру.

```go
logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
    Level: slog.LevelInfo,
}))

logger.Info("failed login", "user", "alice", "src_ip", "10.0.0.5")
// {"time":"...","level":"INFO","msg":"failed login","user":"alice","src_ip":"10.0.0.5"}
```

**Дочерний логгер** через `With` — все последующие записи наследуют указанные поля. Это и есть механизм корреляции:

```go
reqLogger := logger.With("request_id", "req-42")
reqLogger.Info("handling request")   // добавит request_id=req-42
reqLogger.Warn("slow dependency")    // тоже с request_id=req-42
```

Есть и контекст-ориентированные методы (`InfoContext` и т.п.) — они передают `context.Context` в handler, что позволяет, например, извлечь `trace_id` из контекста.

> ⚠️ Частый вопрос на собеседовании: почему переменные данные кладут в поля, а не в текст сообщения? Постоянный `msg` позволяет группировать одинаковые события и строить по ним счётчики; если вклеивать значения прямо в строку (`"user alice failed"`), каждая запись становится уникальной и не агрегируется.

> ⚠️ Частый вопрос на собеседовании: как связать несколько лог-записей одного запроса? Сгенерировать `request_id`/`trace_id` на входе, положить в контекст и в дочерний логгер (`logger.With(...)`), чтобы каждая запись обработчика несла этот идентификатор.
