# Метрики

**Метрика** — числовое измерение, снимаемое во времени и хранимое как временной ряд (time series). В отличие от логов, метрики — это агрегаты: дёшево хранить, легко строить графики и алерты.

## Типы метрик

### Counter (счётчик)

Монотонно возрастающее значение — только увеличивается (или сбрасывается в 0 при рестарте). Примеры: общее число запросов, число ошибок, отправленные байты.

Абсолютное значение счётчика само по себе малоинформативно; полезна **скорость его роста** — `rate(http_requests_total[5m])` даёт запросов в секунду.

### Gauge (измеритель)

Значение, которое может расти и падать. Примеры: текущее использование памяти, число активных соединений, длина очереди, температура.

С gauge смотрят текущее значение и его динамику (min/max/avg), а не rate.

### Histogram (гистограмма)

Распределение значений по заранее заданным интервалам (buckets). Классический случай — задержка запросов. Гистограмма хранит счётчики «сколько наблюдений попало в bucket ≤ границы» плюс сумму и общее количество.

По гистограмме на стороне сервера мониторинга вычисляют **квантили** (перцентили): p50, p90, p99 задержки. Именно перцентили, а не среднее, показывают «хвост» — как плохо худшим пользователям.

> Есть и summary — квантили считаются на стороне клиента. Histogram обычно предпочтительнее, потому что гистограммы разных инстансов можно складывать (агрегировать), а клиентские квантили — нет.

## Методики: RED и USE

Две дополняющие друг друга методологии — что именно измерять.

### RED — для сервисов (request-driven)

Смотрим на сервис глазами запроса:

- **Rate** — запросов в секунду.
- **Errors** — доля (или число) ошибочных запросов.
- **Duration** — распределение задержек (гистограмма → перцентили).

RED хорошо ложится на HTTP/RPC-сервисы и близка к «симптомам», которые чувствует пользователь.

### USE — для ресурсов

Смотрим на ресурс (CPU, память, диск, сеть, пул соединений):

- **Utilization** — насколько ресурс занят (% времени/ёмкости).
- **Saturation** — сколько работы стоит в очереди сверх того, что ресурс успевает (длина очереди, load).
- **Errors** — число ошибок ресурса.

USE помогает найти **причину**: сервис тормозит (RED: выросла Duration), потому что диск насыщен (USE: Saturation).

## Модель Prometheus: pull

Prometheus — распространённая система метрик. Её ключевая особенность — **pull-модель**:

1. Сервис держит HTTP-эндпоинт (обычно `/metrics`), отдающий текущие значения метрик в текстовом формате.
2. Prometheus по расписанию (scrape interval) **сам ходит** и опрашивает эти эндпоинты.

Плюсы pull: Prometheus знает список целей (service discovery) и сам решает, кого опрашивать; недоступность цели — сама по себе сигнал (`up == 0`); нет риска, что клиент «завалит» коллектор.

Формат экспозиции — простой текст «имя{метки} значение»:

```
# HELP http_requests_total Total HTTP requests.
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200"} 1027
http_requests_total{method="GET",status="500"} 3
```

- **Имя метрики** + опциональные **метки (labels)** в фигурных скобках задают конкретный временной ряд.
- Строки `# HELP` и `# TYPE` — метаданные.

**Кардинальность.** Каждая уникальная комбинация меток — отдельный ряд. Метки с неограниченным множеством значений (user_id, request_id, полный URL) взрывают число рядов и убивают Prometheus. Правило: метки — только для значений с ограниченным набором (method, status, endpoint-шаблон).

Для push-сценариев (короткоживущие джобы) есть Pushgateway и отдельный push-протокол, но базовая модель — pull.

> ⚠️ Частый вопрос на собеседовании: почему для задержки берут histogram и p99, а не average? Среднее маскирует хвост: если 1% запросов отвечает за 10 секунд, среднее почти не сдвинется, но этим пользователям очень плохо. Гистограмма позволяет считать перцентили и агрегировать их по инстансам.

> ⚠️ Частый вопрос на собеседовании: чем опасна высокая кардинальность меток? Каждая комбинация меток — отдельный временной ряд в памяти и на диске. Метки с неограниченными значениями (user_id, request_id) порождают миллионы рядов и роняют систему метрик. Такие идентификаторы — в логи/трейсы, не в метки.
