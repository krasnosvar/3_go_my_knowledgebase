# Observability: практические применения

Краткий обзор того, как наблюдаемость всплывает в реальной эксплуатации и в задачах System Design.

## Разбор инцидента по трём столпам

Типовой поток дежурного:

1. **Алерт на симптом** (метрика): выросла доля 5xx или p99-задержка сверх SLO.
2. **Дашборд по RED**: смотрим rate/errors/duration сервиса — насколько всё плохо и с какого момента.
3. **Трейсы медленных/ошибочных запросов**: находим, в каком шаге/сервисе теряется время или ломается запрос.
4. **Логи виновного сервиса** (по `trace_id`/`request_id`): детали конкретных упавших запросов.
5. **USE-метрики ресурса** (CPU/диск/пул): проверяем, не в насыщении ли причина.

Ключ к скорости разбора — **корреляция**: общий `trace_id` в логах, метриках-exemplar’ах и трейсах позволяет переходить между столпами в один клик.

## Что и как логировать

- Структурно (JSON), постоянный `msg`, переменное — в поля.
- На каждый запрос — `request_id`/`trace_id` в дочернем логгере (`slog.With`).
- Уровни осмысленно: ERROR только для реальных проблем (иначе алерты по ERROR шумят).
- Не логировать секреты и PII; следить за объёмом (дорого хранить).

## Что измерять метриками

- **RED** на каждый сервис/эндпоинт: rate, errors, duration (гистограмма → p50/p90/p99).
- **USE** на ресурсы: utilization, saturation, errors.
- Метки — только с ограниченным множеством значений (method, status, endpoint-шаблон), никаких user_id/request_id в метках (кардинальность).
- Задержку — гистограммой и по перцентилям, не по среднему.

## Пробы в оркестраторе

- **liveness** — только то, что чинится рестартом; без внешних зависимостей.
- **readiness** — учитывает прогрев и зависимости; на старте false, при graceful shutdown false.
- Не путать: неправильный liveness, зависящий от БД, устраивает каскадные рестарты всего флота при недоступности БД.

## SLO-ориентированный алертинг

- Алерты — на симптомы, привязанные к SLO (например, burn-rate error budget), а не на каждую причинную метрику.
- Пороги с окном/`for`, чтобы не флапать; каждый page-alert — actionable, со ссылкой на раннбук.
- Причинные метрики (CPU, диск, GC) — на дашбордах и во вторичных предупреждениях.

## Стоимость и объём

- Метрики дёшевы (ряды чисел) — можно держать много и долго; враг — кардинальность.
- Логи дороги — управляйте уровнем, сэмплированием и retention.
- Трейсы — сэмплируйте (head/tail); tail-based позволяет гарантированно сохранять ошибочные/медленные.

## Диагностика: от симптома к причине

```
пользователю плохо?  -> RED-метрики (errors, p99)      (симптом)
где именно тормозит? -> трейс запроса, критический путь  (локализация)
что конкретно упало? -> логи по trace_id                 (детали)
почему ресурс не тянет? -> USE-метрики (saturation)      (причина)
жив/готов ли инстанс?  -> liveness / readiness пробы     (состояние)
```

> ⚠️ Частый вопрос на собеседовании: как вы будете разбирать рост 5xx в проде? Алерт на симптом (метрика) → RED-дашборд, чтобы оценить масштаб → трейсы ошибочных запросов, чтобы локализовать сервис/шаг → логи этого сервиса по `trace_id` для деталей → USE-метрики ресурса, чтобы понять причину. Три столпа связаны общим trace_id.
