# Распределённый трейсинг

В микросервисах один пользовательский запрос проходит через несколько сервисов. Метрики покажут, что где-то медленно, но не где именно. **Распределённый трейсинг** реконструирует полный путь запроса через все компоненты.

## Trace и span

- **Trace (трейс)** — вся история одного запроса в системе. У трейса есть общий `trace_id`.
- **Span (спан)** — одна операция внутри трейса: HTTP-хэндлер, вызов БД, RPC к другому сервису. У спана есть:
  - `span_id` — идентификатор спана;
  - `parent_span_id` — ссылка на родительский спан (у корневого его нет);
  - время начала и длительность;
  - имя операции;
  - **атрибуты** (теги) — например `http.method`, `db.statement`, `http.status_code`;
  - статус (ok/error) и события/логи внутри спана.

Спаны образуют дерево (по parent-ссылкам), а `trace_id` склеивает их в один трейс:

```
trace_id = abc123

[span: GET /order]                                (root, сервис api)
   ├── [span: rpc GetUser]      -> сервис users
   ├── [span: rpc GetCart]      -> сервис cart
   │       └── [span: query SELECT ...]  -> БД
   └── [span: rpc Charge]       -> сервис billing
```

По такому дереву сразу видно, какой шаг занял больше всего времени (критический путь) и где возникла ошибка.

## Context propagation (проброс контекста)

Чтобы спаны из разных сервисов попали в один трейс, `trace_id` и `span_id` родителя нужно **передавать вместе с запросом** через границы сервисов. Это и есть propagation:

- Сервис A создаёт спан, сериализует контекст трейса в **заголовки** исходящего запроса.
- Сервис B читает эти заголовки, продолжает тот же трейс, создавая дочерний спан.

Стандарт заголовков — **W3C Trace Context**: заголовок `traceparent` вида
`00-<trace_id>-<parent_span_id>-<flags>`, например:

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

`flags` содержит бит сэмплирования (записывать этот трейс или нет). Внутри процесса контекст трейса переносится через `context.Context` (в Go), между процессами — через заголовки (HTTP) или метаданные (gRPC).

## OpenTelemetry (концептуально)

**OpenTelemetry (OTel)** — стандарт и набор SDK для генерации телеметрии (трейсы, метрики, логи), не привязанный к конкретному бэкенду. Ключевые части модели:

- **API/SDK** — код инструментируется через общий API (`Tracer.Start(ctx, "op")` создаёт спан); SDK управляет сэмплированием и экспортом.
- **Propagators** — реализуют чтение/запись `traceparent` (W3C Trace Context) на границах.
- **Exporter** — отправляет собранную телеметрию по протоколу **OTLP** в коллектор/бэкенд (Jaeger, Tempo и т.п.).
- **Collector** — опциональный промежуточный процесс: принимает, обрабатывает (сэмплирует, обогащает) и рассылает телеметрию.

Идея OTel — инструментировать код один раз через вендор-независимый API, а куда слать данные, решать конфигурацией.

## Сэмплирование

Хранить трейс каждого запроса дорого. Поэтому применяют **сэмплирование**:

- **Head-based** — решение «записывать или нет» принимается в начале трейса (например, 1% запросов) и распространяется через флаг в `traceparent`. Просто, но можно пропустить редкую ошибку.
- **Tail-based** — решение принимается после завершения трейса (в коллекторе): сохранять все ошибочные и медленные трейсы, а из «нормальных» — выборку. Дороже, но не теряет интересные случаи.

> ⚠️ Частый вопрос на собеседовании: как спаны из разных сервисов оказываются в одном трейсе? Через propagation: `trace_id` и id родительского спана передаются в заголовке `traceparent` (W3C Trace Context) исходящего запроса; принимающий сервис продолжает тот же трейс, создавая дочерний спан.

> ⚠️ Частый вопрос на собеседовании: зачем сэмплировать трейсы и в чём разница head- и tail-based? Полное сохранение всех трейсов слишком дорого. Head-based решает в начале (дёшево, но может пропустить ошибку); tail-based решает после завершения трейса и позволяет гарантированно сохранять ошибочные и медленные запросы.
