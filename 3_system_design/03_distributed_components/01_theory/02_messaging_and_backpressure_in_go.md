# Очереди сообщений, Outbox, Worker Pools и Backpressure в Go

## О чём эта тема (краткий контекст)

Асинхронный обмен сообщениями через брокеры (Kafka, RabbitMQ, NATS) развязывает
микросервисы во времени и сглаживает пики нагрузки. Однако сама по себе очередь
не защищает от потери событий при сбое между коммитом в БД и отправкой в брокер,
от дубликатов доставки (`at-least-once`) и от переполнения памяти воркера, если
консьюмер считывает сообщения быстрее, чем успевает их обрабатывать.

> **Базовая теория и инфраструктурный фундамент (DevOps / SRE):**
> Полный разбор концепции, базовые определения, схемы, алгоритмы и
> платформенные компромиссы вынесены в канонический раздел:
> - [Брокеры сообщений (Kafka, RabbitMQ, NATS), гарантии доставки, Outbox и Backpressure](../../../../5_devops_sre_knowledgebase/14_system_design/03_distributed_components_and_data/01_theory/02_messaging_and_async_patterns.md)
>
> **Фокус этого урока:** здесь мы не дублируем общую теорию, а разбираем
> исключительно особенности реализации и эксплуатации в экосистеме
> **Go** (планировщик G-M-P, сборщик мусора, netpoll, стандартная
> библиотека и идиомы языка).

## 1. Transactional Outbox и идемпотентный консьюмер в Go

Нельзя просто сделать `tx.Commit()` в PostgreSQL и следующей строчкой вызвать
`kafkaWriter.WriteMessages(...)`: если процесс упадёт между этими двумя
строчками (или сеть до Kafka моргнёт), заказ в БД сохранится, а событие навсегда
пропадёт.

### Реализация Outbox в Go

1. В рамках **одной SQL-транзакции** (`*sql.Tx`) бизнес-метод вставляет строку в
   таблицу `orders` и тут же вставляет событие в таблицу `outbox_events`.
2. Фоновая горутина-релей (`OutboxRelay`) периодически (по `time.Ticker` или
   триггеру `LISTEN/NOTIFY`) выбирает пачку неотправленных записей запросом
   `SELECT ... FROM outbox_events WHERE sent_at IS NULL ORDER BY id LIMIT 100
   FOR UPDATE SKIP LOCKED`, публикует их в Kafka и помечает `sent_at = NOW()`.

Так как релей может отправить сообщение в Kafka и упасть до `UPDATE sent_at`,
брокер обеспечит доставку **at-least-once** (минимум один раз). Поэтому каждый
консьюмер на Go обязан быть **идемпотентным**: проверять `event_id` по таблице
обработанных ключей (`INSERT INTO processed_events (event_id) VALUES ($1) ON
CONFLICT DO NOTHING`) в одной транзакции с бизнес-эффектом. См. рабочий пример
`02_examples/05_at_least_once_idempotent/main.go`.

## 2. Естественный Backpressure и Worker Pools на каналах Go

⚠️ **Классическая ошибка в Go:** запускать новую горутину на каждое прочитанное
из брокера сообщение без ограничений:

```go
// АНТИПАТТЕРН: бесконтрольный спавн горутин!
for msg := range consumerChan {
	go handleMessage(msg) // При спайке в 500k сообщений -> OOMKill и DDoS своей БД!
}
```

В Go естественный механизм **обратного давления (Backpressure)** — это
ограниченный буферизованный канал (`jobs := make(chan Message, queueSize)`) в
связке с фиксированным пулом воркеров (**Worker Pool**) или семафором:

- Запускается ровно $N$ воркер-горутин (по пропускной способности целевой БД
  или внешнего API).
- Пока все $N$ воркеров заняты и буфер канала `jobs` заполнен, операция записи
  `jobs <- msg` **блокирует горутину чтения из брокера**, автоматически замедляя
  вычитку из TCP-сокета Kafka/RabbitMQ без расхода памяти!
- Если вместо блокировки нужно быстро отбросить лишнюю нагрузку (**Load
  Shedding**), используется неблокирующий `select` с веткой `default:` (см.
  пример `02_examples/06_backpressure/main.go`).

```go
// Неблокирующая постановка в очередь с Load Shedding при перегрузке:
select {
case jobs <- msg:
	// Принято в буфер обработки
default:
	// Очередь полна — сразу возвращаем 429 Too Many Requests / NACK
	metrics.DroppedTotal.Inc()
}
```

## 3. Координация конкурентных задач через `errgroup.WithContext`

Когда при обработке сообщения или агрегации ответа в API-шлюзе нужно параллельно
опросить 3 сервиса и отменить оставшиеся запросы при первой же ошибке,
используйте стандартный пакет `golang.org/x/sync/errgroup`:

```go
g, ctx := errgroup.WithContext(parentCtx)
g.SetLimit(10) // Встроенный семафор: не более 10 активных горутин одновременно!

for _, item := range batch {
	item := item
	g.Go(func() error {
		// Если любая горутина вернёт ошибку, ctx автоматически отменится для всех остальных!
		return processItem(ctx, item)
	})
}

if err := g.Wait(); err != nil {
	return err // Возвращает первую не-nil ошибку после завершения всех горутин
}
```

> ⚠️ **Ловушка утечки горутин при отправке в канал:** если читатель канала
> вышел раньше времени по ошибке, а писатель пытается сделать `ch <- result` в
> небуферизованный канал без `select` с `<-ctx.Done()`, горутина-писатель
> зависнет навсегда (goroutine leak). Всегда оборачивайте отправку и чтение из
> каналов в долгоживущих пайплайнах в `select` с проверкой `<-ctx.Done()`.
