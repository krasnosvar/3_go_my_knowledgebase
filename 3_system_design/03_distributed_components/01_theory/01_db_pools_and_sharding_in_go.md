# Пул соединений `database/sql`, репликация и шардирование в Go

## О чём эта тема (краткий контекст)

При росте нагрузки одна база данных перестаёт справляться с потоком чтения,
записи или объёмом диска. Архитектурно проблема решается пулингом соединений,
репликацией (разделением чтения и записи) и шардированием (горизонтальным
разбиением ключей по независимым узлам). В Go работа с базой данных строится
вокруг встроенного в `database/sql` конкурентного пула соединений, неправильная
настройка которого способна положить PostgreSQL даже при скромном трафике.

## 1. Устройство пула `database/sql` (и `pgxpool`) в Go

Объект `*sql.DB` в стандартной библиотеке Go — это **не одно соединение**, а
потокобезопасный пул соединений, создаваемый один раз при старте сервиса и
разделяемый всеми горутинами.

### Почему дефолтные настройки `*sql.DB` опасны под нагрузкой

По умолчанию в `database/sql` выставлены два коварных значения:
1. **`MaxOpenConns = 0` (без лимита):** при внезапном спайке трафика или
   медленном SQL-запросе 1000 горутин откроют 1000 параллельных соединений к
   PostgreSQL, исчерпают `max_connections` СУБД и уронят базу для всех сервисов.
2. **`MaxIdleConns = 2` (всего 2 свободных соединения в пуле!):** если `MaxOpen`
   равен 50, а `MaxIdle` оставлен по умолчанию равным `2`, то при конкурентной
   нагрузке в 50 горутин 48 соединений будут **открываться заново (TCP + TLS +
   аутентификация Postgres) и тут же закрываться** после каждого запроса!

### Промышленная настройка `*sql.DB`

```go
db, err := sql.Open("pgx", dsn)
if err != nil {
	return err
}

// 1. Жёсткий потолок открытых соединений от ОДНОГО пода.
// Учитывайте число реплик пода: 10 подов * 25 = 250 соединений к БД (или PgBouncer).
db.SetMaxOpenConns(25)

// 2. Держим пул прогретым: MaxIdleConns должен быть равен или близок к MaxOpenConns,
// чтобы под нагрузкой не пересоздавать TCP-соединения на каждый запрос.
db.SetMaxIdleConns(25)

// 3. Ротация соединений для балансировки по репликам и защиты от утечек памяти в backend-процессе БД.
db.SetConnMaxLifetime(30 * time.Minute)
db.SetConnMaxIdleTime(5 * time.Minute)
```

## 2. Контексты, транзакции и утечки соединений из пула

В продакшене на Go действуют три нерушимых правила работы с запросами к БД:

1. **Всегда используйте `*Context`-методы** (`QueryContext`, `QueryRowContext`,
   `ExecContext`, `BeginTx(ctx, nil)`). Если HTTP-клиент отменил запрос или
   сработал таймаут `ctx`, драйвер (`pgx` / `lib/pq`) отправит в PostgreSQL
   сигнал отмены выполняющегося запроса и освободит соединение в пуле.
2. **Всегда закрывайте `rows.Close()`:** пока `*sql.Rows` не дочитан до конца и
   не закрыт, физическое TCP-соединение остаётся **захваченным вне пула**. Если
   забыть `defer rows.Close()`, через 25 таких запросов пул `MaxOpenConns=25`
   навсегда зависнет в ожидании свободного коннекта.
3. **Гарантируйте откат транзакции через `defer tx.Rollback()`:** вызов
   `tx.Rollback()` после успешного `tx.Commit()` безопасен (возвращает
   `sql.ErrTxDone`), но спасает от незакрытой транзакции при раннем `return` или
   панике.

```go
func Transfer(ctx context.Context, db *sql.DB, fromID, toID int64, amount int64) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer func() { _ = tx.Rollback() }() // Безопасный no-op после успешного Commit()

	if _, err := tx.ExecContext(ctx,
		`UPDATE accounts SET balance = balance - $1 WHERE id = $2`, amount, fromID); err != nil {
		return err
	}
	if _, err := tx.ExecContext(ctx,
		`UPDATE accounts SET balance = balance + $1 WHERE id = $2`, amount, toID); err != nil {
		return err
	}
	return tx.Commit()
}
```

## 3. Роутинг чтения и записи (Read/Write Splitting) в Go

При наличии лидера (Primary) и нескольких синхронных/асинхронных реплик чтения
(Read Replicas) в Go создаётся тонкая обёртка `DBCluster`, содержащая пул
`primary *sql.DB` и срез `replicas []*sql.DB`:

- Все пишущие операции (`ExecContext`, `BeginTx`) идут строго в `primary`.
- Операции чтения (`QueryContext`) балансируются по `replicas` через атомарный
  Round-Robin (`atomic.Uint64`).
- Для обеспечения гарантии **Read-Your-Own-Writes** (когда пользователь только
  что обновил профиль и тут же перезагружает страницу) в `context.Context` или
  по флагу передаётся признак чтения с мастера (`WithPrimary(ctx)`).

## 4. Прикладное шардирование и Consistent Hashing в Go

Когда данные горизонтально разбиты на $N$ шардов (независимых кластеров БД или
кэш-узлов), маршрутизатор шардов (`ShardRouter`) на Go реализуется прямо в слое
репозитория:

- **Modulo Sharding (`hash(key) % N`):** работает быстро, если число шардов
  фиксировано. См. пример `02_examples/02_shard_router/main.go`.
- **Consistent Hashing с виртуальными нодами (`vnodes`):** чтобы при добавлении
  нового узла переезжало только $pprox 1/N$ ключей, в Go строится
  отсортированный слайс хеш-точек кольца `ring []uint32` (`crc32.ChecksumIEEE`
  или `xxhash`), а поиск узла за $O(\log M)$ выполняется стандартным бинарным
  поиском `sort.Search`. Полная реализация — в примере
  `02_examples/01_consistent_hashing/main.go`.
