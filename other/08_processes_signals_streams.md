# Процессы, сигналы и потоки ввода-вывода (Unix)

Программа не живёт в вакууме — она запускается как процесс внутри ОС, получает
аргументы и окружение, общается через стандартные потоки и слушает сигналы.
Разберём эти основы (на примере Unix/Linux) и как к ним подступиться из Go.

---

## Процесс vs поток

- **Процесс** — исполняемая программа со своим изолированным адресным
  пространством (памятью), файловыми дескрипторами и т.д. У каждого свой
  **PID** (Process ID).
- **Поток (thread)** — единица выполнения **внутри** процесса. Потоки одного
  процесса делят память, поэтому переключение между ними дешевле, чем между
  процессами.

В Go вы обычно работаете не с потоками ОС напрямую, а с **горутинами** —
лёгкими «зелёными» потоками, которые рантайм сам раскладывает по потокам ОС.
Подробно — см. `1_golang/3_concurrency`.

## Аргументы, коды возврата, окружение

**Аргументы командной строки** — то, что передали при запуске:
`myapp --port 8080 file.txt`.

**Код возврата (exit code)** — число, которое процесс возвращает ОС при
завершении:
- `0` — **успех**;
- ненулевой (1, 2, ...) — ошибка (конкретный смысл определяет программа).

Этим кодом пользуются shell-скрипты и CI: `command && echo ok || echo fail`.

**Переменные окружения (environment variables)** — пары ключ-значение, которые
процесс наследует от родителя. Классика для конфигурации: `PATH`, `HOME`,
`DATABASE_URL`.

```go
import (
    "fmt"
    "os"
)

func main() {
    fmt.Println(os.Args)          // [/path/to/app --port 8080] — [0] это сам путь
    fmt.Println(os.Getenv("PORT")) // значение переменной окружения PORT

    if os.Getenv("PORT") == "" {
        fmt.Fprintln(os.Stderr, "PORT is required")
        os.Exit(1) // завершиться с кодом ошибки
    }
}
```

## Стандартные потоки, пайпы, перенаправление

У каждого процесса есть три стандартных потока:

| Поток  | Дескриптор | Назначение                         |
|--------|------------|------------------------------------|
| stdin  | 0          | Ввод (данные в программу)          |
| stdout | 1          | Обычный вывод (результат работы)   |
| stderr | 2          | Вывод ошибок и диагностики         |

Зачем разделять stdout и stderr: полезный результат можно направить в файл, а
ошибки продолжать видеть в терминале.

**Пайп (`|`)** соединяет stdout одной программы со stdin другой:

```bash
cat access.log | grep 500 | wc -l     # цепочка: вывод → ввод → вывод
```

**Перенаправление:**

```bash
myapp > out.txt        # stdout в файл
myapp 2> err.txt       # stderr в файл
myapp > out.txt 2>&1   # и stdout, и stderr в один файл
myapp < in.txt         # stdin из файла
```

В Go это `os.Stdin`, `os.Stdout`, `os.Stderr` — обычные `*os.File`,
реализующие `io.Reader`/`io.Writer`. Диагностику пишите в `os.Stderr`, чтобы
не мешать полезному выводу в `os.Stdout`.

## Unix-сигналы

**Сигнал** — асинхронное уведомление процессу от ОС или другого процесса.
Самые важные:

| Сигнал   | Типичный источник      | Смысл                                   | Можно перехватить? |
|----------|------------------------|-----------------------------------------|--------------------|
| SIGINT   | Ctrl+C в терминале     | Прерывание пользователем                | Да                 |
| SIGTERM  | `kill`, оркестратор    | Вежливая просьба завершиться            | Да                 |
| SIGKILL  | `kill -9`              | Немедленное убийство                    | **Нет**            |
| SIGHUP   | Закрытие терминала     | Часто используют как «перечитай конфиг» | Да                 |

**SIGKILL** нельзя перехватить или проигнорировать — процесс убивается
мгновенно, без шанса на уборку. Поэтому вся «вежливая» логика завершения
строится вокруг **SIGTERM** (и SIGINT).

### Graceful shutdown

Оркестраторы (например, Kubernetes) при остановке пода сначала шлют
**SIGTERM** и дают время, а уже потом добивают **SIGKILL**. Поэтому сервис
должен ловить SIGTERM и корректно завершаться: перестать принимать новые
запросы, дать дообработать текущие, закрыть соединения с БД, сбросить буферы.
Подробнее про надёжность и graceful shutdown — см.
`3_system_design/03_distributed_components`.

```go
import (
    "context"
    "fmt"
    "os"
    "os/signal"
    "syscall"
)

func main() {
    ctx, stop := signal.NotifyContext(context.Background(),
        syscall.SIGINT, syscall.SIGTERM)
    defer stop()

    fmt.Println("running... (Ctrl+C to stop)")

    <-ctx.Done() // ждём SIGINT или SIGTERM

    fmt.Println("shutting down gracefully...")
    // здесь: server.Shutdown(ctx), db.Close(), flush логов и т.п.
}
```

`signal.NotifyContext` — удобный современный способ: при получении сигнала он
отменяет context, а вся остановка сервисов уже завязана на `ctx`. Более
низкоуровневый вариант — `signal.Notify(ch, ...)` с каналом.
