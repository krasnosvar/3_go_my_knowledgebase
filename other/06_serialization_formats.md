# Сериализация и форматы данных

## Что такое сериализация

**Сериализация** (serialization / marshaling) — превращение объекта из оперативной памяти в поток байт или текст, пригодный для **хранения** (файл, БД) или **передачи** (по сети). Обратная операция — **десериализация** (deserialization / unmarshaling) — восстановление объекта из этого потока.

```
объект в памяти  ──[сериализация]──►  байты/текст  ──► файл / сеть
файл / сеть  ──► байты/текст  ──[десериализация]──►  объект в памяти
```

Зачем это нужно: структура в памяти (со ссылками, указателями, раскладкой под конкретную машину) не может «как есть» лететь по сети или лежать в файле. Её нужно привести к плоскому, самодостаточному представлению.

Форматы делятся на две большие группы: **текстовые** и **бинарные**.

---

## Текстовые форматы

Человекочитаемы, легко дебажить глазами, но крупнее и медленнее в разборе.

- **JSON** — де-факто стандарт для web-API. Простой, поддержан везде.
- **XML** — многословный, но с богатыми возможностями (схемы, namespaces); много legacy.
- **YAML** — удобен для конфигов (читаемый, отступы вместо скобок), но капризен к пробелам.
- **CSV** — простые табличные данные; никакой вложенности и типов.

```json
{ "id": 1, "name": "Alice", "active": true }
```

---

## Бинарные форматы

Компактнее и быстрее, но глазами не прочитать — нужен декодер/схема.

- **Protobuf** (Protocol Buffers) — требует заранее описанную **схему** (`.proto`), кросс-язычный, очень компактный. Основа gRPC.
- **MessagePack** — «бинарный JSON», схема не обязательна, компактнее JSON.
- **gob** — родной бинарный формат Go; удобен между Go-сервисами, но **не кросс-язычный**.

## Таблица сравнения

| Формат      | Читаемость | Размер   | Нужна схема | Скорость | Кросс-язычность |
|-------------|------------|----------|-------------|----------|-----------------|
| JSON        | Высокая    | Средний  | Нет         | Средняя  | Отличная        |
| XML         | Средняя    | Большой  | Опц.        | Низкая   | Отличная        |
| YAML        | Высокая    | Средний  | Нет         | Низкая   | Хорошая         |
| CSV         | Высокая    | Малый*   | Нет         | Высокая  | Хорошая         |
| Protobuf    | Нет        | Малый    | Да          | Высокая  | Отличная        |
| MessagePack | Нет        | Малый    | Нет         | Высокая  | Хорошая         |
| gob         | Нет        | Малый    | Нет         | Высокая  | Только Go       |

\* CSV мал только для плоских таблиц; вложенные данные им нормально не выразить.

## Когда что выбирать

- **Публичный web-API, интеграция с фронтендом** → JSON (читаемость, вездесущность).
- **Конфиги** → YAML (или JSON/TOML), где человек правит руками.
- **Высоконагруженный внутренний RPC между сервисами** → Protobuf/gRPC (компактность, скорость, строгая схема).
- **Обмен только между Go-сервисами, без внешних потребителей** → gob (проще, чем тянуть Protobuf).
- **Экспорт/импорт таблиц, выгрузки** → CSV.

Подробнее про стили API (REST/JSON vs gRPC/Protobuf) — см. `3_system_design/02_api_styles`.

## Связь с Go

Go даёт кодеки в стандартной библиотеке:

```go
import (
    "encoding/json"
    "encoding/gob"
    "bytes"
    "fmt"
)

type User struct {
    ID   int    `json:"id"`
    Name string `json:"name"`
}

// JSON: текстовый, кросс-язычный
b, _ := json.Marshal(User{ID: 1, Name: "Alice"})
fmt.Println(string(b)) // {"id":1,"name":"Alice"}

var u User
_ = json.Unmarshal(b, &u)

// gob: бинарный, для Go↔Go
var buf bytes.Buffer
_ = gob.NewEncoder(&buf).Encode(User{ID: 2, Name: "Bob"})
```

Теги вроде `json:"id"` управляют именами полей при сериализации. Protobuf в стандартную библиотеку не входит — используется codegen из `.proto` (пакет `google.golang.org/protobuf`).

## Эволюция схемы и обратная совместимость

Сериализованные данные живут долго: старый сервис читает то, что записал новый, и наоборот. Поэтому важно менять формат **совместимо**:

- **Backward compatibility** — новый код читает старые данные.
- **Forward compatibility** — старый код читает новые данные (игнорирует незнакомые поля).

Правила «мягкой» эволюции:
- Добавляй **новые поля опциональными** (со значением по умолчанию), не ломай старые.
- **Не переиспользуй** номера/имена удалённых полей под новый смысл. В Protobuf у полей есть постоянные номера — их резервируют (`reserved`), а не переприсваивают.
- Удаляй поля осторожно: сначала перестань использовать, потом убирай, когда все стороны обновлены.

JSON прощает лишние/недостающие поля по умолчанию, Protobuf делает совместимость частью дизайна через номера полей.
