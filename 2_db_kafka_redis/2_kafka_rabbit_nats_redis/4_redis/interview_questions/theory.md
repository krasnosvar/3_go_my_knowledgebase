## Что такое Redis?

**Redis** = **RE**mote **DI**ctionary **S**erver

```
┌─────────────────────────────────────────────────────────┐
│              Redis — In-Memory база данных              │
└─────────────────────────────────────────────────────────┘

Ключевые особенности:
┌────────────────────────────────────────────────────────┐
│ • Хранит данные в RAM (оперативной памяти)             │
│ • Невероятно быстро (100,000+ ops/sec на 1 ядре)       │
│ • Key-Value хранилище                                  │
│ • Богатые типы данных (не только строки!)              │
│ • Single-threaded (один поток на команды)              │
│ • Опциональная персистентность на диск                 │
└────────────────────────────────────────────────────────┘
```

### Традиционная БД vs Redis

```
┌─────────────────────────────────────────────────────────┐
│          Традиционная БД (PostgreSQL, MySQL)            │
├─────────────────────────────────────────────────────────┤
│ Данные на диске (HDD/SSD)                               │
│                                                         │
│ Application                                             │
│      ↓ запрос                                           │
│   Database                                              │
│      ↓ читает с диска                                   │
│    HDD/SSD  ← 1-10ms задержка                           │
│                                                         │
│ Скорость: ~1,000 операций/сек                           │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│                        Redis                            │
├─────────────────────────────────────────────────────────┤
│ Данные в RAM (оперативной памяти)                       │
│                                                         │
│ Application                                             │
│      ↓ запрос                                           │
│    Redis                                                │
│      ↓ читает из RAM                                    │
│     RAM  ← 0.0001ms задержка (в 10,000 раз быстрее!)   │
│                                                         │
│ Скорость: ~100,000+ операций/сек                        │
└─────────────────────────────────────────────────────────┘
```

### Когда использовать Redis?

```
✅ ИСПОЛЬЗУЙТЕ Redis для:
┌─────────────────────────────────────────────┐
│ • Кеширование (самый популярный use case)   │
│ • Сессии пользователей                      │
│ • Rate limiting (ограничение запросов)      │
│ • Leaderboards (таблицы лидеров)            │
│ • Real-time analytics                       │
│ • Очереди сообщений (Queue)                 │
│ • Pub/Sub для real-time уведомлений         │
│ • Distributed locks (распределенные блокировки) │
│ • Счетчики и метрики                        │
└─────────────────────────────────────────────┘

❌ НЕ ИСПОЛЬЗУЙТЕ Redis для:
┌─────────────────────────────────────────────┐
│ • Основного хранилища (primary database)    │
│ • Больших объемов данных (> RAM)            │
│ • Сложных запросов с JOIN                   │
│ • Данных, которые нельзя потерять           │
│ • Полнотекстового поиска (используйте ES)   │
└─────────────────────────────────────────────┘
```

## Типы данных в Redis

Redis — это не просто key-value хранилище. У него богатые типы данных!

### 1. String (Строка)

**Самый простой тип — строка байтов (до 512 MB)**

```
Визуализация:
┌──────────────────────────────────────┐
│ Key          →      Value            │
├──────────────────────────────────────┤
│ "user:100"   →   "Alice"             │
│ "counter"    →   "42"                │
│ "logo.png"   →   [binary data...]    │
└──────────────────────────────────────┘
```

**Операции:**
```go
// Установить значение
rdb.Set(ctx, "user:100", "Alice", 0)

// Получить значение
val, err := rdb.Get(ctx, "user:100").Result()  // "Alice"

// Инкремент (атомарная операция!)
rdb.Incr(ctx, "counter")           // 1
rdb.Incr(ctx, "counter")           // 2
rdb.IncrBy(ctx, "counter", 10)     // 12

// Множественные операции
rdb.MSet(ctx, "key1", "val1", "key2", "val2")
vals, _ := rdb.MGet(ctx, "key1", "key2").Result()

// Битовые операции
rdb.SetBit(ctx, "bitmap", 7, 1)
rdb.GetBit(ctx, "bitmap", 7)       // 1
```

**Use cases для String:**
- Кеширование HTML страниц, JSON
- Счетчики (views, likes)
- Флаги (feature flags)
- Сессии пользователей

### 2. Hash (Хеш-таблица)

**Коллекция пар field-value (как Map в Go)**

```
Визуализация:
┌───────────────────────────────────────────────────┐
│ Key: "user:100"                                   │
│ ┌───────────────────────────────────────────────┐ │
│ │ field       →     value                       │ │
│ ├───────────────────────────────────────────────┤ │
│ │ "name"      →     "Alice"                     │ │
│ │ "email"     →     "alice@example.com"         │ │
│ │ "age"       →     "25"                        │ │
│ │ "city"      →     "Moscow"                    │ │
│ └───────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────┘

Аналог в Go:
map[string]string{
    "name":  "Alice",
    "email": "alice@example.com",
    "age":   "25",
    "city":  "Moscow",
}
```

**Операции:**
```go
// Установить поля
rdb.HSet(ctx, "user:100", "name", "Alice", "age", "25")

// Получить одно поле
name, _ := rdb.HGet(ctx, "user:100", "name").Result()  // "Alice"

// Получить все поля
user, _ := rdb.HGetAll(ctx, "user:100").Result()
// map[string]string{"name": "Alice", "age": "25", ...}

// Проверить существование поля
exists, _ := rdb.HExists(ctx, "user:100", "name").Result()  // true

// Инкремент поля
rdb.HIncrBy(ctx, "user:100", "login_count", 1)

// Получить только значения
vals, _ := rdb.HVals(ctx, "user:100").Result()
```

**Use cases для Hash:**
- Хранение объектов (пользователь, продукт)
- Настройки/конфигурация
- Счетчики по категориям
- Кеширование структурированных данных

**Почему Hash вместо JSON в String?**
```
String (JSON):                    Hash:
┌──────────────────────────┐     ┌──────────────────────────┐
│ Обновить один field:     │     │ Обновить один field:     │
│ 1. GET весь JSON         │     │ HSET user:100 age 26     │
│ 2. Parse JSON            │     │                          │
│ 3. Изменить значение     │     │ ✅ Одна операция!        │
│ 4. Serialize JSON        │     │ ✅ Атомарно!             │
│ 5. SET обратно           │     │                          │
│ ❌ Много операций        │     │                          │
└──────────────────────────┘     └──────────────────────────┘
```

### 3. List (Список)

**Связный список строк (двусторонняя очередь)**

```
Визуализация:
┌───────────────────────────────────────────────────┐
│ Key: "queue:tasks"                                │
│                                                   │
│  HEAD                                       TAIL  │
│   ↓                                           ↓   │
│ ┌────┐  ┌────┐  ┌────┐  ┌────┐  ┌────┐  ┌────┐  │
│ │task│←→│task│←→│task│←→│task│←→│task│←→│task│  │
│ │ 1  │  │ 2  │  │ 3  │  │ 4  │  │ 5  │  │ 6  │  │
│ └────┘  └────┘  └────┘  └────┘  └────┘  └────┘  │
│   ↑                                           ↑   │
│ LPUSH/LPOP                            RPUSH/RPOP  │
└───────────────────────────────────────────────────┘
```

**Операции:**
```go
// Добавить в начало (LEFT)
rdb.LPush(ctx, "queue:tasks", "task1", "task2")

// Добавить в конец (RIGHT)
rdb.RPush(ctx, "queue:tasks", "task3", "task4")

// Получить и удалить с начала
task, _ := rdb.LPop(ctx, "queue:tasks").Result()

// Получить и удалить с конца
task, _ := rdb.RPop(ctx, "queue:tasks").Result()

// Получить диапазон (без удаления)
tasks, _ := rdb.LRange(ctx, "queue:tasks", 0, -1).Result()
// 0, -1 означает "все элементы"

// Получить длину
length, _ := rdb.LLen(ctx, "queue:tasks").Result()

// Блокирующий pop (ждет пока появится элемент)
task, _ := rdb.BLPop(ctx, 5*time.Second, "queue:tasks").Result()
//                        ↑ timeout
```

**Use cases для List:**
```
1. Queue (FIFO очередь):
   RPUSH для добавления
   LPOP для извлечения
   ┌────┐  ┌────┐  ┌────┐
   │ 1  │←─│ 2  │←─│ 3  │
   └────┘  └────┘  └────┘
     ↑              PUSH
    POP

2. Stack (LIFO стек):
   LPUSH для добавления
   LPOP для извлечения
   
3. Timeline (лента новостей):
   LPUSH новые посты
   LRANGE для получения последних N

4. Recent items (последние действия):
   LPUSH + LTRIM для ограничения размера
```

### 4. Set (Множество)

**Неупорядоченная коллекция уникальных строк**

```
Визуализация:
┌─────────────────────────────────────┐
│ Key: "tags:article:100"             │
│                                     │
│  ┌────────────────────────────┐    │
│  │  "mongodb"                 │    │
│  │  "database"                │    │  ← Порядок
│  │  "nosql"                   │    │    не гарантирован
│  │  "tutorial"                │    │
│  └────────────────────────────┘    │
│                                     │
│  ✅ Только уникальные значения      │
│  ❌ Дубликаты игнорируются          │
└─────────────────────────────────────┘
```

**Операции:**
```go
// Добавить элементы
rdb.SAdd(ctx, "tags:article:100", "mongodb", "database", "nosql")
rdb.SAdd(ctx, "tags:article:100", "mongodb")  // Игнорируется (уже есть)

// Получить все элементы
tags, _ := rdb.SMembers(ctx, "tags:article:100").Result()

// Проверить существование
exists, _ := rdb.SIsMember(ctx, "tags:article:100", "mongodb").Result()  // true

// Удалить элемент
rdb.SRem(ctx, "tags:article:100", "mongodb")

// Получить количество
count, _ := rdb.SCard(ctx, "tags:article:100").Result()

// Случайный элемент
random, _ := rdb.SRandMember(ctx, "tags:article:100").Result()

// Извлечь случайный элемент (с удалением)
popped, _ := rdb.SPop(ctx, "tags:article:100").Result()
```

**Операции над множествами:**
```go
// Подготовка
rdb.SAdd(ctx, "set1", "a", "b", "c")
rdb.SAdd(ctx, "set2", "b", "c", "d")

// Пересечение (INTERSECTION)
inter, _ := rdb.SInter(ctx, "set1", "set2").Result()  // ["b", "c"]

// Объединение (UNION)
union, _ := rdb.SUnion(ctx, "set1", "set2").Result()  // ["a", "b", "c", "d"]

// Разность (DIFFERENCE)
diff, _ := rdb.SDiff(ctx, "set1", "set2").Result()    // ["a"]

Визуализация:
     set1             set2
   ┌──────┐         ┌──────┐
   │  a   │         │      │
   ├──────┤         ├──────┤
   │  b   │◄───────►│  b   │  ← Пересечение (SInter)
   ├──────┤         ├──────┤
   │  c   │◄───────►│  c   │  ← Пересечение (SInter)
   └──────┘         ├──────┤
                    │  d   │
                    └──────┘
```

**Use cases для Set:**
- Теги статей/продуктов
- Уникальные посетители (unique visitors)
- Друзья пользователя
- Подписчики
- Blacklist/Whitelist
- Поиск общих интересов (пересечение множеств)

### 5. Sorted Set (Упорядоченное множество)

**Множество с весом (score) для каждого элемента**

```
Визуализация:
┌──────────────────────────────────────────────┐
│ Key: "leaderboard"                           │
│                                              │
│  Score     Member                            │
│  ┌─────────────────┐                         │
│  │ 1000  →  Alice  │  ← Highest score        │
│  │  950  →  Bob    │                         │
│  │  920  →  Charlie│                         │
│  │  850  →  Diana  │                         │
│  │  800  →  Eve    │  ← Lowest score         │
│  └─────────────────┘                         │
│                                              │
│  ✅ Автоматическая сортировка по score       │
│  ✅ Уникальные members                       │
└──────────────────────────────────────────────┘
```

**Операции:**
```go
// Добавить элементы (score, member)
rdb.ZAdd(ctx, "leaderboard",
    redis.Z{Score: 1000, Member: "Alice"},
    redis.Z{Score: 950, Member: "Bob"},
    redis.Z{Score: 920, Member: "Charlie"},
)

// Обновить score (просто добавить с новым score)
rdb.ZAdd(ctx, "leaderboard", redis.Z{Score: 1100, Member: "Alice"})

// Получить топ-N (по возрастанию score)
top3, _ := rdb.ZRange(ctx, "leaderboard", 0, 2).Result()

// Получить топ-N (по убыванию score)
top3, _ := rdb.ZRevRange(ctx, "leaderboard", 0, 2).Result()
// ["Alice", "Bob", "Charlie"]

// Получить с scores
top3WithScores, _ := rdb.ZRevRangeWithScores(ctx, "leaderboard", 0, 2).Result()
// [{Member: "Alice", Score: 1100}, {Member: "Bob", Score: 950}, ...]

// Получить rank (позицию)
rank, _ := rdb.ZRevRank(ctx, "leaderboard", "Alice").Result()  // 0 (первое место)

// Получить score конкретного member
score, _ := rdb.ZScore(ctx, "leaderboard", "Alice").Result()  // 1100

// Диапазон по score
rdb.ZRangeByScore(ctx, "leaderboard", &redis.ZRangeBy{
    Min: "900",
    Max: "1000",
}).Result()

// Инкремент score
rdb.ZIncrBy(ctx, "leaderboard", 50, "Bob")  // Bob получил +50 очков

// Количество элементов
count, _ := rdb.ZCard(ctx, "leaderboard").Result()
```

**Use cases для Sorted Set:**
```
1. Leaderboards (таблицы лидеров):
   score = очки игрока
   
2. Priority Queue (приоритетная очередь):
   score = приоритет задачи
   
3. Time-series данные:
   score = timestamp
   member = event_id
   
4. Autocomplete (автодополнение):
   score = частота использования
   
5. Rate limiting:
   score = timestamp запроса
   Удалять запросы старше N секунд
```

### 6. Stream (Поток событий)

**Лог добавочных записей (append-only log) — похож на Kafka**

```
Визуализация:
┌──────────────────────────────────────────────────────┐
│ Key: "events:clicks"                                 │
│                                                      │
│  ID              Fields                              │
│  ┌────────────────────────────────────────────────┐ │
│  │ 1609459200000-0  {user: "alice", url: "/home"} │ │
│  │ 1609459201000-0  {user: "bob", url: "/about"}  │ │
│  │ 1609459202000-0  {user: "alice", url: "/shop"} │ │
│  │      ...                  ...                  │ │
│  └────────────────────────────────────────────────┘ │
│        ↑                                             │
│   timestamp-sequence                                 │
│                                                      │
│  ✅ Автоматическая генерация ID                     │
│  ✅ Consumer Groups для распределенной обработки     │
└──────────────────────────────────────────────────────┘
```

**Операции:**
```go
// Добавить событие
id, _ := rdb.XAdd(ctx, &redis.XAddArgs{
    Stream: "events:clicks",
    Values: map[string]interface{}{
        "user": "alice",
        "url":  "/home",
    },
}).Result()
// ID = "1609459200000-0" (timestamp-sequence)

// Читать последние N событий
events, _ := rdb.XRevRange(ctx, "events:clicks", "+", "-").Result()

// Читать с определенного ID
events, _ := rdb.XRead(ctx, &redis.XReadArgs{
    Streams: []string{"events:clicks", "0"},  // ["stream", "start_id"]
    Count:   10,
}).Result()

// Consumer Group (распределенная обработка)
// 1. Создать группу
rdb.XGroupCreate(ctx, "events:clicks", "workers", "0")

// 2. Читать из группы
messages, _ := rdb.XReadGroup(ctx, &redis.XReadGroupArgs{
    Group:    "workers",
    Consumer: "worker-1",
    Streams:  []string{"events:clicks", ">"},
    Count:    10,
}).Result()

// 3. Подтвердить обработку
rdb.XAck(ctx, "events:clicks", "workers", message.ID)
```

**Use cases для Stream:**
- Event sourcing
- Activity feeds
- Логирование
- Очередь сообщений с гарантиями доставки
- Real-time аналитика

## TTL и Expiration

### Что такое TTL?

**TTL** = Time To Live (время жизни ключа)

```
Визуализация:
┌────────────────────────────────────────────────┐
│ Ключ создан в 10:00:00                         │
│ TTL = 300 секунд (5 минут)                     │
│                                                │
│ 10:00:00  ────────────────────►  10:05:00      │
│ CREATE                           EXPIRE        │
│   │                                 │          │
│   ▼                                 ▼          │
│ ┌──────────────────────────────────┐           │
│ │ Key существует                   │ Key удален│
│ └──────────────────────────────────┘           │
└────────────────────────────────────────────────┘
```

**Операции с TTL:**
```go
// Установить ключ с TTL
rdb.Set(ctx, "session:abc123", "user_data", 30*time.Minute)

// Установить TTL на существующий ключ
rdb.Expire(ctx, "key", 60*time.Second)

// Установить время истечения (абсолютное время)
rdb.ExpireAt(ctx, "key", time.Now().Add(1*time.Hour))

// Проверить оставшееся время
ttl, _ := rdb.TTL(ctx, "session:abc123").Result()
// ttl.Seconds() → 1789.5 (осталось секунд)

// Убрать TTL (сделать ключ вечным)
rdb.Persist(ctx, "key")

// Проверить существование ключа
exists, _ := rdb.Exists(ctx, "key").Result()  // 1 = существует, 0 = нет
```

### Как Redis удаляет ключи?

```
┌──────────────────────────────────────────────────────┐
│         Стратегии удаления истекших ключей           │
└──────────────────────────────────────────────────────┘

1. Lazy (ленивое) удаление:
   ┌─────────────────────────────────┐
   │ GET key → Проверка TTL          │
   │          → Истек? Удалить!      │
   │          → Не истек? Вернуть    │
   └─────────────────────────────────┘
   ✅ Не тратит CPU когда ключ не используется
   ❌ Память не освобождается сразу

2. Active (активное) удаление:
   ┌─────────────────────────────────┐
   │ Каждые 100ms Redis:             │
   │ • Выбирает 20 случайных ключей  │
   │ • Проверяет TTL                 │
   │ • Удаляет истекшие              │
   │ • Если >25% истекло → повтор    │
   └─────────────────────────────────┘
   ✅ Постепенная очистка памяти
   ⚠️ Не гарантирует немедленное удаление
```

## Redis как кеш

### Cache Pattern

```
Типичная архитектура с кешем:

┌──────────────┐
│ Application  │
└──────┬───────┘
       │
       ▼
┌──────────────────────────────────────┐
│ 1. Проверить кеш (Redis)             │
│    ┌────────────────┐                │
│    │ GET user:100   │                │
│    └────────────────┘                │
└──────┬───────────────────────────────┘
       │
   ┌───┴────┐
   │ Есть?  │
   └───┬────┘
       │
   ┌───▼───────────────────────────┐
   │ ДА → Вернуть из кеша          │ ✅ Cache HIT
   │      (0.1ms)                  │
   └───────────────────────────────┘
       │
   ┌───▼───────────────────────────┐
   │ НЕТ → Прочитать из БД         │ ❌ Cache MISS
   │       (10ms)                  │
   │    ↓                          │
   │ Записать в кеш (SET)          │
   │    ↓                          │
   │ Вернуть результат             │
   └───────────────────────────────┘
```

**Пример в Go:**
```go
func GetUser(ctx context.Context, userID int) (*User, error) {
    cacheKey := fmt.Sprintf("user:%d", userID)
    
    // 1. Проверить кеш
    cached, err := rdb.Get(ctx, cacheKey).Result()
    if err == nil {
        // Cache HIT
        var user User
        json.Unmarshal([]byte(cached), &user)
        return &user, nil
    }
    
    // 2. Cache MISS - читаем из БД
    user, err := db.GetUser(userID)
    if err != nil {
        return nil, err
    }
    
    // 3. Сохраняем в кеш на 1 час
    userData, _ := json.Marshal(user)
    rdb.Set(ctx, cacheKey, userData, 1*time.Hour)
    
    return user, nil
}
```

### Cache Eviction Policies (Политики вытеснения)

**Что делать когда память заполнена?**

```
Конфигурация Redis:
maxmemory 2gb                      ← Максимум памяти
maxmemory-policy allkeys-lru       ← Политика вытеснения

┌────────────────────────────────────────────────────┐
│              Политики вытеснения                   │
├────────────────────────────────────────────────────┤
│                                                    │
│ 1. noeviction (по умолчанию)                       │
│    Возвращать ошибку при нехватке памяти           │
│    ❌ Не подходит для кеша                         │
│                                                    │
│ 2. allkeys-lru (Least Recently Used)               │
│    Удалять наименее используемые ключи             │
│    ✅ Лучше всего для кеша                         │
│                                                    │
│ 3. allkeys-lfu (Least Frequently Used)             │
│    Удалять редко используемые ключи                │
│    ✅ Хорошо для популярных данных                 │
│                                                    │
│ 4. volatile-lru                                    │
│    Удалять только ключи с TTL (по LRU)             │
│    ⚠️ Если нет ключей с TTL → ошибка               │
│                                                    │
│ 5. allkeys-random                                  │
│    Удалять случайные ключи                         │
│    ⚠️ Непредсказуемо                               │
└────────────────────────────────────────────────────┘
```

**Визуализация LRU:**
```
Память заполнена, нужно освободить место:

 Последнее использование
 ─────────────────────────►
┌────┬────┬────┬────┬────┐
│key1│key2│key3│key4│key5│
└────┴────┴────┴────┴────┘
  ↑                    ↑
  │                    └─ Использовали недавно (оставить)
  └─ Давно не использовали (удалить!)

LRU удалит key1, потом key2, и т.д.
```

### Cache Invalidation (Инвалидация кеша)

```
Проблема: Данные в БД изменились, кеш устарел!

┌────────────────────────────────────────┐
│ Стратегии инвалидации:                 │
├────────────────────────────────────────┤
│                                        │
│ 1. TTL-based (на основе времени)       │
│    SET key value EX 3600  // 1 час    │
│    ✅ Просто                           │
│    ❌ Данные могут быть устаревшими    │
│                                        │
│ 2. Write-through (запись сквозь кеш)   │
│    UPDATE БД → UPDATE кеш              │
│    ✅ Всегда актуальные данные         │
│    ❌ Медленная запись                 │
│                                        │
│ 3. Cache-aside (ручная инвалидация)    │
│    UPDATE БД → DELETE кеш              │
│    ✅ Простая логика                   │
│    ⚠️ Следующий запрос будет медленным │
│                                        │
│ 4. Event-based (на основе событий)     │
│    UPDATE БД → Pub событие → UPDATE кеш│
│    ✅ Гибкость                         │
│    ❌ Сложная архитектура              │
└────────────────────────────────────────┘
```

**Пример Cache-aside в Go:**
```go
func UpdateUser(ctx context.Context, user *User) error {
    // 1. Обновить в БД
    err := db.UpdateUser(user)
    if err != nil {
        return err
    }
    
    // 2. Удалить из кеша
    cacheKey := fmt.Sprintf("user:%d", user.ID)
    rdb.Del(ctx, cacheKey)
    
    // Следующий GET прочитает из БД и обновит кеш
    return nil
}
```

## Pub/Sub (Публикация/Подписка)

### Что это такое?

**Pub/Sub** — механизм отправки сообщений между компонентами системы.

```
Визуализация:
┌─────────────┐
│ Publisher 1 │
└──────┬──────┘
       │ PUBLISH channel "message1"
       ▼
┌──────────────────────────┐
│      Redis (Broker)      │
│   Channel: "news"        │
└──────────┬───────────────┘
           │
    ┌──────┼──────┬──────┐
    │      │      │      │
    ▼      ▼      ▼      ▼
┌────────┐ │  ┌────────┐ │
│Sub 1   │ │  │Sub 2   │ │
│(Web)   │ │  │(Mobile)│ │
└────────┘ │  └────────┘ │
┌──────────▼──┐ ┌────────▼───┐
│Subscriber 3 │ │Subscriber 4│
│  (Email)    │ │   (SMS)    │
└─────────────┘ └────────────┘

✅ Fire-and-forget (отправил и забыл)
❌ Если подписчик оффлайн → сообщение потеряно!
```

**Пример в Go:**
```go
// Publisher (издатель)
func PublishNews(ctx context.Context, news string) {
    rdb.Publish(ctx, "news:updates", news)
}

// Subscriber (подписчик)
func SubscribeToNews(ctx context.Context) {
    pubsub := rdb.Subscribe(ctx, "news:updates")
    defer pubsub.Close()
    
    ch := pubsub.Channel()
    for msg := range ch {
        fmt.Printf("Получено: %s\n", msg.Payload)
        // Обработать сообщение
    }
}

// Запуск в горутине
go SubscribeToNews(ctx)

// Публикация
PublishNews(ctx, "Breaking news!")
```

### Pattern Matching

```go
// Подписка на несколько каналов по паттерну
pubsub := rdb.PSubscribe(ctx, "news:*")

// Будет получать сообщения из:
// • news:tech
// • news:sports
// • news:politics
// • и т.д.

ch := pubsub.Channel()
for msg := range ch {
    fmt.Printf("Channel: %s, Message: %s\n", msg.Channel, msg.Payload)
}
```

### Pub/Sub vs Streams

```
┌────────────────────────────────────────────────────┐
│                 Pub/Sub                            │
├────────────────────────────────────────────────────┤
│ ✅ Простота                                        │
│ ✅ Real-time уведомления                           │
│ ✅ Fan-out (один ко многим)                        │
│ ❌ Сообщения не сохраняются                        │
│ ❌ Если подписчик оффлайн → потеря данных          │
│ ❌ Нет гарантий доставки                           │
│                                                    │
│ Use cases:                                         │
│ • Live notifications                               │
│ • Chat приложения                                  │
│ • Real-time дашборды                               │
└────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────┐
│                   Streams                          │
├────────────────────────────────────────────────────┤
│ ✅ Сообщения сохраняются                           │
│ ✅ Consumer Groups                                 │
│ ✅ Можно читать историю                            │
│ ✅ Подтверждение обработки (ACK)                   │
│ ❌ Сложнее в использовании                         │
│                                                    │
│ Use cases:                                         │
│ • Event sourcing                                   │
│ • Task queues с гарантиями                         │
│ • Аудит лог                                        │
└────────────────────────────────────────────────────┘
```

## Persistence (Сохранение данных)

Redis хранит данные в RAM, но может сохранять на диск!

### RDB (Redis Database)

**Point-in-time snapshot (снимок в определенный момент)**

```
Визуализация:
┌────────────────────────────────────────────┐
│          RAM (текущие данные)              │
└────────────┬───────────────────────────────┘
             │
             ▼ Периодически (каждые 5 минут)
┌────────────────────────────────────────────┐
│         Disk: dump.rdb (снимок)            │
└────────────────────────────────────────────┘

Конфигурация:
save 900 1      # Сохранить если 1+ изменение за 15 минут
save 300 10     # Сохранить если 10+ изменений за 5 минут
save 60 10000   # Сохранить если 10000+ изменений за 1 минуту
```

**Процесс сохранения:**
```
1. Redis создает child процесс (fork)
2. Child процесс пишет данные в dump.rdb
3. Когда завершено → заменяет старый файл
4. Parent процесс продолжает обрабатывать запросы

┌─────────────┐
│Redis (parent)│ ← Продолжает работать
└─────┬───────┘
      │ fork()
      ▼
┌─────────────┐
│Child process│ → Пишет dump.rdb
└─────────────┘

✅ Компактный файл
✅ Быстрое восстановление
❌ Можно потерять данные между снимками
```

### AOF (Append Only File)

**Лог всех операций записи**

```
Визуализация:
┌────────────────────────────────────────────┐
│              RAM                           │
└────────────┬───────────────────────────────┘
             │
             ▼ Каждая write операция
┌────────────────────────────────────────────┐
│         Disk: appendonly.aof               │
│  SET key1 value1                           │
│  INCR counter                              │
│  HSET user:100 name Alice                  │
│  ...                                       │
└────────────────────────────────────────────┘

Конфигурация:
appendfsync always      # Синхронизация после каждой команды (медленно, безопасно)
appendfsync everysec    # Каждую секунду (по умолчанию, балансированно)
appendfsync no          # ОС решает (быстро, рискованно)
```

**AOF Rewrite:**
```
Проблема: AOF файл растет бесконечно!

До rewrite (appendonly.aof):
SET counter 1
INCR counter
INCR counter
INCR counter
DEL key1
SET key1 new_value
...
(1000+ строк)

После rewrite:
SET counter 4        ← Финальное состояние
SET key1 new_value   ← Финальное состояние

✅ Файл меньше
✅ Быстрее загружается
```

### RDB vs AOF

```
┌────────────────────────────────────────────────────┐
│                     RDB                            │
├────────────────────────────────────────────────────┤
│ ✅ Компактный файл                                 │
│ ✅ Быстрое восстановление                          │
│ ✅ Меньше нагрузка на диск                         │
│ ❌ Можно потерять данные (последние N минут)       │
│                                                    │
│ Когда использовать:                                │
│ • Кеш (данные не критичны)                         │
│ • Резервные копии                                  │
└────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────┐
│                     AOF                            │
├────────────────────────────────────────────────────┤
│ ✅ Минимальная потеря данных (~1 секунда)          │
│ ✅ Читаемый формат (можно редактировать)           │
│ ❌ Больше файл                                     │
│ ❌ Медленнее восстановление                        │
│ ❌ Больше нагрузка на диск                         │
│                                                    │
│ Когда использовать:                                │
│ • Критичные данные                                 │
│ • Сессии пользователей                             │
└────────────────────────────────────────────────────┘

💡 Рекомендация: Использовать оба!
   RDB для резервных копий
   AOF для минимальной потери данных
```

## Transactions и Pipelining

### Transactions (MULTI/EXEC)

```
Проблема: Нужно выполнить несколько команд атомарно

Решение: MULTI/EXEC
┌────────────────────────────────────────┐
│ MULTI                                  │
│   DECRBY balance:alice 100             │
│   INCRBY balance:bob 100               │
│ EXEC                                   │
│                                        │
│ ✅ Команды выполнятся подряд, без      │
│    вклинивания чужих команд            │
│ ❌ НЕ «всё или ничего»: отката нет —   │
│    ошибка выполнения одной команды     │
│    не отменяет остальные               │
└────────────────────────────────────────┘
```

**Пример в Go:**
```go
// Транзакция с WATCH (optimistic locking)
err := rdb.Watch(ctx, func(tx *redis.Tx) error {
    // Проверить баланс
    balance, err := tx.Get(ctx, "balance:alice").Int()
    if err != nil {
        return err
    }
    
    if balance < 100 {
        return errors.New("insufficient funds")
    }
    
    // Выполнить транзакцию
    _, err = tx.TxPipelined(ctx, func(pipe redis.Pipeliner) error {
        pipe.DecrBy(ctx, "balance:alice", 100)
        pipe.IncrBy(ctx, "balance:bob", 100)
        return nil
    })
    return err
}, "balance:alice")
```

**WATCH механизм:**
```
Оптимистичная блокировка:

Thread 1                    Thread 2
│                           │
├ WATCH balance:alice       │
├ GET balance:alice (100)   │
│                           ├ GET balance:alice (100)
│                           ├ SET balance:alice 50
├ MULTI                     │
├ DECRBY balance:alice 50   │
├ EXEC                      │
│                           │
└ ❌ ОШИБКА!                │
  (balance изменился)       │

Транзакция отменена, нужно повторить!
```

### Pipelining

**Отправка нескольких команд без ожидания ответа**

```
БЕЗ Pipelining:
Client                  Redis
│ SET key1 val1 ────────►│
│◄──── OK ───────────────│
│ SET key2 val2 ────────►│
│◄──── OK ───────────────│
│ SET key3 val3 ────────►│
│◄──── OK ───────────────│

3 round-trips = медленно! ❌

С Pipelining:
Client                  Redis
│ SET key1 val1 ────────►│
│ SET key2 val2 ────────►│
│ SET key3 val3 ────────►│
│◄──── OK ───────────────│
│◄──── OK ───────────────│
│◄──── OK ───────────────│

1 round-trip = быстро! ✅
```

**Пример в Go:**
```go
pipe := rdb.Pipeline()

// Добавить команды в pipeline
pipe.Set(ctx, "key1", "val1", 0)
pipe.Set(ctx, "key2", "val2", 0)
pipe.Incr(ctx, "counter")
pipe.HSet(ctx, "hash", "field", "value")

// Выполнить все команды
_, err := pipe.Exec(ctx)

// Ускорение в 5-10 раз!
```

## Replication

### Master-Slave репликация

```
Архитектура:
┌────────────────────────────────────────┐
│            MASTER                      │
│      (принимает запись)                │
└──────────┬─────────────────────────────┘
           │
    ┌──────┼──────┐
    │      │      │
    ▼      ▼      ▼
┌────────┐ │  ┌────────┐
│ SLAVE 1│ │  │ SLAVE 2│
│(replica)│ │  │(replica)│
└────────┘ │  └────────┘
┌──────────▼──┐
│   SLAVE 3   │
│  (replica)  │
└─────────────┘

Запись: Client → MASTER только
Чтение: Client → MASTER или SLAVE (настраиваемо)
```

**Как работает репликация:**
```
1. SLAVE подключается к MASTER
2. MASTER создает RDB snapshot
3. MASTER отправляет snapshot → SLAVE
4. SLAVE загружает snapshot в память
5. MASTER отправляет буфер изменений (команды)
6. Непрерывная репликация начинается

┌─────────┐                ┌───────┐
│ MASTER  │                │ SLAVE │
└────┬────┘                └───┬───┘
     │                         │
     │ 1. SYNC ───────────────►│
     │◄──── OK ────────────────│
     │                         │
     │ 2. RDB snapshot ───────►│
     │                         │ Загрузка...
     │ 3. Buffer commands ────►│
     │                         │
     │ 4. Реал-тайм команды ──►│
     │    SET key val ────────►│
     │    INCR counter ───────►│
```

**Пример конфигурации SLAVE:**
```
# redis.conf на slave сервере
replicaof 192.168.1.100 6379    # IP и порт мастера
masterauth password123           # Пароль мастера (если есть)
```

**Пример в Go:**
```go
// Подключение к master
masterClient := redis.NewClient(&redis.Options{
    Addr: "master:6379",
})

// Подключение к slave для чтения
slaveClient := redis.NewClient(&redis.Options{
    Addr: "slave:6379",
})

// Запись в master
masterClient.Set(ctx, "key", "value", 0)

// Чтение из slave (разгрузка мастера)
val, _ := slaveClient.Get(ctx, "key").Result()
```

### Sentinel (высокая доступность)

```
Redis Sentinel — автоматический failover

┌────────────────────────────────────────┐
│         Sentinel 1                     │
│         Sentinel 2                     │
│         Sentinel 3                     │
│    (кворум для принятия решений)       │
└──────────┬─────────────────────────────┘
           │ Мониторинг
           ▼
┌──────────────────┐      ┌──────────┐
│     MASTER       │─────►│ SLAVE 1  │
└──────────────────┘      └──────────┘
           │              ┌──────────┐
           └─────────────►│ SLAVE 2  │
                          └──────────┘

Если MASTER упал:
1. Sentinels обнаруживают (каждый проверяет)
2. Кворум (большинство) подтверждает
3. Один из SLAVE повышается до MASTER
4. Клиенты автоматически переключаются

Время переключения: ~30-60 секунд
```

## Redis Cluster

### Зачем нужен Cluster?

```
Проблема:
┌──────────────────────────────────────┐
│   Один Redis сервер                  │
│   • Вся RAM на одной машине          │
│   • Один CPU обрабатывает команды    │
│   • Ограничение масштабирования      │
└──────────────────────────────────────┘

Решение — Redis Cluster:
┌────────────────────────────────────────┐
│ Данные распределены между нодами       │
└────────────────────────────────────────┘
┌──────┐  ┌──────┐  ┌──────┐
│Node 1│  │Node 2│  │Node 3│
│0-5460│  │5461- │  │10923-│
│      │  │10922 │  │16383 │
└──────┘  └──────┘  └──────┘
```

### Hash Slots

```
Redis Cluster использует 16384 hash slots

┌────────────────────────────────────────┐
│ Key → Hash → Slot → Node               │
└────────────────────────────────────────┘

Пример:
SET user:100 "Alice"
    ↓
CRC16("user:100") % 16384 = 12345
    ↓
Slot 12345 → Node 3
    ↓
Данные хранятся на Node 3

┌──────────────┐
│   Node 1     │  Slots: 0-5460
└──────────────┘
┌──────────────┐
│   Node 2     │  Slots: 5461-10922
└──────────────┘
┌──────────────┐
│   Node 3     │  Slots: 10923-16383 ← user:100 здесь!
└──────────────┘
```

**Hash Tags для группировки:**
```
Проблема: Хотим хранить связанные ключи на одной ноде

user:100:profile  → Node 1
user:100:settings → Node 3  ❌ Разные ноды!

Решение: Hash tags {}
user:{100}:profile  → Node 2
user:{100}:settings → Node 2  ✅ Одна нода!

Хешируется только часть в {}
```

### Cluster архитектура

```
Production конфигурация: 3 master + 3 slaves

┌──────────┐        ┌──────────┐        ┌──────────┐
│ Master 1 │───────►│ Master 2 │───────►│ Master 3 │
│ 0-5460   │        │5461-10922│        │10923-16383│
└────┬─────┘        └────┬─────┘        └────┬─────┘
     │                   │                   │
     ↓                   ↓                   ↓
┌──────────┐        ┌──────────┐        ┌──────────┐
│ Slave 1  │        │ Slave 2  │        │ Slave 3  │
└──────────┘        └──────────┘        └──────────┘

Если Master 1 упадет:
• Slave 1 становится новым Master
• Автоматический failover
• Данные не теряются
```

**Пример подключения в Go:**
```go
import "github.com/redis/go-redis/v9"

// Cluster клиент
rdb := redis.NewClusterClient(&redis.ClusterOptions{
    Addrs: []string{
        "node1:6379",
        "node2:6379",
        "node3:6379",
    },
})

// Использование как обычно
rdb.Set(ctx, "key", "value", 0)
// Автоматически определяет правильную ноду!
```

### Ограничения Cluster

```
❌ Что НЕ работает в Cluster:

1. Multi-key операции на разных слотах:
   MSET user:1 alice user:2 bob  ❌
   (user:1 и user:2 могут быть на разных нодах)
   
   Решение: Hash tags
   MSET user:{group1}:1 alice user:{group1}:2 bob  ✅

2. Transactions на разных слотах:
   MULTI
   SET key1 val1    ← Slot 1000
   SET key2 val2    ← Slot 5000  ❌
   EXEC
   
3. SELECT database:
   В Cluster всегда используется database 0

4. Pub/Sub:
   Классический PUBLISH доставляется по всему кластеру (рассылка
   через все ноды); доставка в пределах шарда — sharded Pub/Sub
   (SPUBLISH/SSUBSCRIBE, Redis 7.0+)
```

## Практические паттерны

### 1. Rate Limiting (Ограничение запросов)

```
Задача: Максимум 100 запросов в минуту от одного IP

Решение с Sorted Set:
┌────────────────────────────────────────────┐
│ Key: rate_limit:192.168.1.100              │
│                                            │
│ Score (timestamp)    Member (request_id)   │
│ 1609459200.123  →    req_abc123            │
│ 1609459201.456  →    req_def456            │
│ 1609459202.789  →    req_ghi789            │
│ ...                                        │
└────────────────────────────────────────────┘
```

**Реализация:**
```go
func CheckRateLimit(ctx context.Context, ip string) (bool, error) {
    key := fmt.Sprintf("rate_limit:%s", ip)
    now := time.Now().Unix()
    oneMinuteAgo := now - 60
    
    pipe := rdb.Pipeline()
    
    // 1. Удалить старые запросы (>1 минуты)
    pipe.ZRemRangeByScore(ctx, key, "0", fmt.Sprintf("%d", oneMinuteAgo))
    
    // 2. Добавить текущий запрос
    pipe.ZAdd(ctx, key, redis.Z{
        Score:  float64(now),
        // member должен быть уникален: при "req_<секунды>" запросы одной секунды схлопнутся
        Member: fmt.Sprintf("req_%d_%d", time.Now().UnixNano(), rand.Int63()),
    })
    
    // 3. Получить количество запросов за последнюю минуту
    pipe.ZCard(ctx, key)
    
    // 4. Установить TTL на ключ
    pipe.Expire(ctx, key, 1*time.Minute)
    
    results, err := pipe.Exec(ctx)
    if err != nil {
        return false, err
    }
    
    count := results[2].(*redis.IntCmd).Val()
    return count <= 100, nil  // Максимум 100 запросов
}
```

func GetPlayersAround(ctx context.Context, playerID string) ([]redis.Z, error) {

    start := rank - 5
    if start < 0 {
        start = 0
    }
    end := rank + 5
    
    return rdb.ZRevRangeWithScores(ctx, "leaderboard:global", start, end).Result()

### 3. Distributed Lock (Распределенная блокировка)

```
Задача: Только один процесс может выполнять задачу

┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  Worker 1   │     │  Worker 2   │     │  Worker 3   │
└──────┬──────┘     └──────┬──────┘     └──────┬──────┘
       │                   │                   │
       ├ Попытка захватить │                   │
       │ блокировку        │                   │
       │                   │                   │
       ▼                   │                   │
┌──────────────────────────┼───────────────────┼────┐
│  SET lock:task1 token1   │                   │    │
│  NX (only if not exists) │                   │    │
│  EX 30 (expire in 30s)   │                   │    │
│  ✅ Успех!               │                   │    │
└──────────────────────────┼───────────────────┼────┘
       │                   │                   │
       │                   ├ Попытка захватить │
       │                   │ ❌ Уже занято     │
       │                   │                   │
       │                   │                   ├ Попытка
       │                   │                   │ ❌ Занято
       │                   │                   │
       ├ Выполнение задачи │                   │
       ├ ...               │                   │
       ├ DEL lock:task1    │                   │
       ▼                   │                   │
    Освобождено            │                   │
                           ├ Попытка захватить │
                           ✅ Успех!           │
```

**Реализация:**
```go
import "github.com/google/uuid"

type DistributedLock struct {
    rdb   *redis.Client
    key   string
    token string
    ttl   time.Duration
}

func NewLock(rdb *redis.Client, key string, ttl time.Duration) *DistributedLock {
    return &DistributedLock{
        rdb:   rdb,
        key:   key,
        token: uuid.New().String(),
        ttl:   ttl,
    }
}

// Захватить блокировку
func (l *DistributedLock) Acquire(ctx context.Context) (bool, error) {
    result, err := l.rdb.SetNX(ctx, l.key, l.token, l.ttl).Result()
    return result, err
}

// Освободить блокировку (только свою!)
func (l *DistributedLock) Release(ctx context.Context) error {
    // Lua script для атомарности
    script := `
        if redis.call("get", KEYS[1]) == ARGV[1] then
            return redis.call("del", KEYS[1])
        else
            return 0
        end
    `
    return l.rdb.Eval(ctx, script, []string{l.key}, l.token).Err()
}

// Использование:
lock := NewLock(rdb, "lock:process-payments", 30*time.Second)

acquired, _ := lock.Acquire(ctx)
if !acquired {
    return errors.New("не удалось захватить блокировку")
}
defer lock.Release(ctx)

// Выполнить критическую секцию
processPayments()
```

### 4. Session Store (Хранилище сессий)

```go
type Session struct {
    UserID    int       `json:"user_id"`
    Username  string    `json:"username"`
    ExpiresAt time.Time `json:"expires_at"`
}

// Создать сессию
func CreateSession(ctx context.Context, userID int, username string) (string, error) {
    sessionID := uuid.New().String()
    
    session := Session{
        UserID:    userID,
        Username:  username,
        ExpiresAt: time.Now().Add(24 * time.Hour),
    }
    
    data, _ := json.Marshal(session)
    
    // Сохранить на 24 часа
    err := rdb.Set(ctx, "session:"+sessionID, data, 24*time.Hour).Err()
    return sessionID, err
}

// Получить сессию
func GetSession(ctx context.Context, sessionID string) (*Session, error) {
    data, err := rdb.Get(ctx, "session:"+sessionID).Result()
    if err != nil {
        return nil, err
    }
    
    var session Session
    json.Unmarshal([]byte(data), &session)
    return &session, nil
}

// Удалить сессию (logout)
func DeleteSession(ctx context.Context, sessionID string) error {
    return rdb.Del(ctx, "session:"+sessionID).Err()
}

// Продлить сессию
func RefreshSession(ctx context.Context, sessionID string) error {
    return rdb.Expire(ctx, "session:"+sessionID, 24*time.Hour).Err()
}
```
