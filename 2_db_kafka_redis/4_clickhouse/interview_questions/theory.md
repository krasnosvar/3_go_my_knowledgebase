## Что такое ClickHouse?

**ClickHouse** — это колоночная СУБД для онлайн-аналитической обработки данных (OLAP).

### OLTP vs OLAP

```
┌─────────────────────────────────────────────────────────────┐
│                    OLTP (PostgreSQL, MySQL)                 │
│  ─────────────────────────────────────────────────────────  │
│  • Много мелких транзакций                                  │
│  • INSERT отдельных строк                                   │
│  • UPDATE и DELETE часто используются                       │
│  • Чтение небольшого количества строк                       │
│                                                             │
│  Пример: интернет-магазин                                   │
│  - Добавить товар в корзину                                 │
│  - Обновить статус заказа                                   │
│  - Получить информацию о пользователе                       │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                    OLAP (ClickHouse)                        │
│  ─────────────────────────────────────────────────────────  │
│  • Большие пакеты данных (batch inserts)                    │
│  • Редкие UPDATE/DELETE                                     │
│  • Чтение миллионов строк для агрегаций                     │
│  • Аналитические запросы                                    │
│                                                             │
│  Пример: аналитика интернет-магазина                        │
│  - Сколько заказов за последний месяц?                      │
│  - Какая средняя стоимость заказа по регионам?              │
│  - Топ-10 товаров по продажам                               │
└─────────────────────────────────────────────────────────────┘
```

## Колоночное хранение данных

### Как хранятся данные в строковых БД (PostgreSQL, MySQL)

Представим таблицу с пользователями:

```
Таблица: users
┌────┬──────────┬─────┬──────────┬────────┐
│ id │ name     │ age │ city     │ salary │
├────┼──────────┼─────┼──────────┼────────┤
│ 1  │ Alice    │ 25  │ Moscow   │ 50000  │
│ 2  │ Bob      │ 30  │ London   │ 60000  │
│ 3  │ Charlie  │ 35  │ Paris    │ 70000  │
│ 4  │ Diana    │ 28  │ Berlin   │ 55000  │
└────┴──────────┴─────┴──────────┴────────┘
```

**Строковое хранение** (традиционные БД):
```
На диске:
┌────────────────────────────────────────┐
│ [1, Alice, 25, Moscow, 50000]          │  ← Строка 1
│ [2, Bob, 30, London, 60000]            │  ← Строка 2
│ [3, Charlie, 35, Paris, 70000]         │  ← Строка 3
│ [4, Diana, 28, Berlin, 55000]          │  ← Строка 4
└────────────────────────────────────────┘

Для запроса "SELECT AVG(salary) FROM users"
Нужно прочитать ВСЕ строки целиком! ❌
```

**Колоночное хранение** (ClickHouse):
```
На диске:
┌─────────────────┐  ┌──────────────────────┐  ┌────────────┐  ┌─────────────────┐  ┌──────────────────────┐
│ id:             │  │ name:                │  │ age:       │  │ city:           │  │ salary:              │
│ [1, 2, 3, 4]    │  │ [Alice, Bob,         │  │ [25, 30,   │  │ [Moscow, London,│  │ [50000, 60000,       │
│                 │  │  Charlie, Diana]     │  │  35, 28]   │  │  Paris, Berlin] │  │  70000, 55000]       │
└─────────────────┘  └──────────────────────┘  └────────────┘  └─────────────────┘  └──────────────────────┘

Для запроса "SELECT AVG(salary) FROM users"
Читаем только колонку salary! ✅
```

### Преимущества колоночного хранения

#### 1. **Сжатие данных**
```
Колонка age (однотипные данные):
[25, 30, 35, 28, 25, 30, 35, 28, 25, 30, 35, 28...]

После сжатия (LZ4):
[25×3, 30×3, 35×3, 28×3...] 
↓
Размер уменьшается в 5-10 раз! 🎉
```

#### 2. **Скорость чтения**
```
Запрос: SELECT city, COUNT(*) FROM events GROUP BY city

Строковая БД:                      Колоночная БД:
┌───────────────────┐              ┌───────────────┐
│ Читаем 1 000 000  │              │ Читаем только │
│ ПОЛНЫХ строк      │              │ колонку city  │
│ ❌ Медленно       │              │ ✅ Быстро     │
└───────────────────┘              └───────────────┘
     ~10 секунд                         ~0.1 секунды
```

#### 3. **Эффективная агрегация**
```
Колонка salary: [50000, 60000, 70000, 55000, 50000, ...]

SUM(salary) — процессор обрабатывает последовательно:
50000 + 60000 + 70000 + 55000 + ... (SIMD оптимизация!)
```

## Батчевые вставки

### ❌ Плохо: Одиночные INSERT

```go
// МЕДЛЕННО! Не делайте так в ClickHouse
for i := 0; i < 10000; i++ {
    _, err := db.Exec("INSERT INTO events VALUES (?, ?, ?)", 
        time.Now(), "click", userID)
}
```

**Проблема:**
```
Каждый INSERT = отдельный запрос к серверу

Client                          ClickHouse Server
   │                                   │
   │──INSERT row 1─────────────────>  │  
   │<─────────OK────────────────────  │
   │──INSERT row 2─────────────────>  │
   │<─────────OK────────────────────  │
   │──INSERT row 3─────────────────>  │
   │<─────────OK────────────────────  │
   ...
   
10 000 запросов = 10 000 сетевых вызовов
Время: ~10-30 секунд ❌
```

### ✅ Хорошо: Батчевые INSERT

```go
// БЫСТРО! Правильный подход
batch, err := conn.PrepareBatch(ctx, "INSERT INTO events")

for i := 0; i < 10000; i++ {
    batch.Append(time.Now(), "click", userID)
}

batch.Send() // Одна отправка!
```

**Преимущество:**
```
Client                          ClickHouse Server
   │                                   │
   │──INSERT 10000 rows────────────>  │  
   │<─────────OK────────────────────  │
   
1 запрос = 1 сетевой вызов
Время: ~0.1-0.5 секунд ✅

Ускорение в 20-100 раз!
```

### Оптимальный размер батча

```
┌─────────────────────────────────────────────────┐
│ Рекомендации по размеру батча:                  │
├─────────────────────────────────────────────────┤
│ • 1 000 - 10 000 строк — хороший старт          │
│ • 10 000 - 100 000 строк — оптимально           │
│ • > 100 000 строк — может быть медленнее        │
│                                                 │
│ Также учитывайте:                               │
│ • Размер одной строки                           │
│ • Общий размер батча ~10-100 MB                 │
│ • Доступную память                              │
└─────────────────────────────────────────────────┘
```

## MergeTree и партиционирование

### MergeTree — основной движок таблиц

```sql
CREATE TABLE events (
    date Date,
    user_id UInt32,
    event_type String,
    url String
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(date)  -- Разбивка по месяцам
ORDER BY (user_id, date)      -- Сортировка внутри
```

### Что такое партиционирование?

**Визуализация:**
```
Без партиционирования:
┌───────────────────────────────────────────────────────┐
│  ВСЕ ДАННЫЕ В ОДНОЙ КУЧЕ                              │
│  2024-01, 2024-02, 2024-03, 2024-04, 2024-05...       │
└───────────────────────────────────────────────────────┘
Удалить старые данные = сканировать всю таблицу ❌

С партиционированием:
┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
│ 2024-01  │ │ 2024-02  │ │ 2024-03  │ │ 2024-04  │
└──────────┘ └──────────┘ └──────────┘ └──────────┘
Удалить старые данные = удалить партицию 2024-01 ✅
```

**Пример удаления старых данных:**
```sql
-- Удаление целой партиции (мгновенно!)
ALTER TABLE events DROP PARTITION '202401';

-- Вместо медленного DELETE:
DELETE FROM events WHERE date < '2024-02-01';  -- Медленно! ❌
```

### Выбор ключа партиционирования

```
┌─────────────────────────────────────────────────────┐
│ Типичные ключи партиционирования:                   │
├─────────────────────────────────────────────────────┤
│                                                     │
│ ✅ ХОРОШО:                                          │
│  • toYYYYMM(date) — по месяцам                      │
│  • toMonday(date) — по неделям                      │
│  • toDate(timestamp) — по дням                      │
│  • (region, toYYYYMM(date)) — комбинация            │
│                                                     │
│ ❌ ПЛОХО:                                           │
│  • user_id — слишком много партиций!                │
│  • rand() — бессмысленно                            │
│  • Без партиционирования для больших таблиц         │
└─────────────────────────────────────────────────────┘
```

## PRIMARY KEY в ClickHouse

### ⚠️ Важно: PRIMARY KEY в ClickHouse ≠ PRIMARY KEY в MySQL/PostgreSQL

**В традиционных БД:**
```sql
-- PostgreSQL / MySQL
PRIMARY KEY (id)
↓
• Гарантирует уникальность ✅
• Не может быть дубликатов
• Автоматический индекс
```

**В ClickHouse:**
```sql
-- ClickHouse
ORDER BY (user_id, date)  -- Это и есть PRIMARY KEY!
↓
• НЕ гарантирует уникальность! ⚠️
• Используется для сортировки и индексации
• Разреженный индекс (sparse index)
```

### Как работает разреженный индекс (Sparse Index)

```
Данные на диске (отсортированы по user_id, date):
┌────────┬────────────┬──────┐
│user_id │ date       │ ...  │
├────────┼────────────┼──────┤
│ 1      │ 2024-01-01 │      │
│ 1      │ 2024-01-02 │      │  ← Гранула 0 (8192 строк)
│ 1      │ 2024-01-03 │      │
│ ...    │ ...        │      │
│ 5      │ 2024-01-05 │      │
├────────┼────────────┼──────┤
│ 5      │ 2024-01-06 │      │
│ 6      │ 2024-01-01 │      │  ← Гранула 1 (8192 строк)
│ 6      │ 2024-01-02 │      │
│ ...    │ ...        │      │
└────────┴────────────┴──────┘

Индекс (хранит каждую 8192-ю строку):
┌─────────┬────────────┬─────────────┐
│ Гранула │ user_id    │ Offset      │
├─────────┼────────────┼─────────────┤
│ 0       │ 1          │ 0           │  ← Минимум в грануле
│ 1       │ 5          │ 8192        │
│ 2       │ 10         │ 16384       │
│ 3       │ 15         │ 24576       │
└─────────┴────────────┴─────────────┘

Запрос: SELECT * FROM users WHERE user_id = 5

1. Индекс: user_id=5 может быть в грануле 0 (диапазон 1…5)
   и в грануле 1 (диапазон 5…10)
2. Читаем только гранулы 0 и 1 (2 × 8192 строки)
3. Фильтруем user_id = 5

Вместо чтения всей таблицы читаем 16 384 строки! ✅
```

### Правила выбора ORDER BY

```
┌────────────────────────────────────────────────────┐
│ Правило: Наиболее фильтруемые поля — слева!        │
├────────────────────────────────────────────────────┤
│                                                    │
│ ✅ ХОРОШО:                                         │
│  ORDER BY (region, user_id, timestamp)             │
│                                                    │
│  Запрос: WHERE region = 'EU' AND user_id = 123     │
│  → Быстро! Используется индекс                     │
│                                                    │
│ ❌ ПЛОХО:                                          │
│  ORDER BY (timestamp, user_id, region)             │
│                                                    │
│  Запрос: WHERE region = 'EU' AND user_id = 123     │
│  → Медленно! Индекс не помогает                    │
│                                                    │
│ Порядок полей в ORDER BY:                          │
│  • Сначала поля, по которым фильтруют через =      │
│  • Среди них — от низкой кардинальности к высокой  │
│  • Время и диапазоны (>, <) — ближе к концу        │
│ (ESR — правило для индексов MongoDB, не ClickHouse)│
└────────────────────────────────────────────────────┘
```

## Parts и процесс Merge

### Что такое Parts (части)?

Когда вы вставляете данные в ClickHouse, они сохраняются как **иммутабельные части**.

```
INSERT batch 1 (10000 строк):
┌──────────┐
│ Part_1   │
└──────────┘

INSERT batch 2 (10000 строк):
┌──────────┐  ┌──────────┐
│ Part_1   │  │ Part_2   │
└──────────┘  └──────────┘

INSERT batch 3 (10000 строк):
┌──────────┐  ┌──────────┐  ┌──────────┐
│ Part_1   │  │ Part_2   │  │ Part_3   │
└──────────┘  └──────────┘  └──────────┘

Проблема: слишком много маленьких частей!
```

### Фоновое слияние (Background Merge)

```
ClickHouse автоматически объединяет части в фоне:

До merge:
┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐
│Part_1│ │Part_2│ │Part_3│ │Part_4│
│1000  │ │1000  │ │1000  │ │1000  │
└──────┘ └──────┘ └──────┘ └──────┘

После merge:
┌───────────────┐ ┌───────────────┐
│   Part_5      │ │   Part_6      │
│   2000 строк  │ │   2000 строк  │
└───────────────┘ └───────────────┘

После еще одного merge:
┌──────────────────────────┐
│       Part_7             │
│       4000 строк         │
└──────────────────────────┘
```

### Почему это важно?

```
┌────────────────────────────────────────────────────┐
│ SELECT запросы читают ВСЕ части!                   │
├────────────────────────────────────────────────────┤
│                                                    │
│ 100 маленьких частей:                              │
│  • 100 файлов открыть                              │
│  • 100 раз прочитать метаданные                    │
│  • Медленно! ❌                                    │
│                                                    │
│ 5 больших частей:                                  │
│  • 5 файлов открыть                                │
│  • 5 раз прочитать метаданные                      │
│  • Быстро! ✅                                      │
└────────────────────────────────────────────────────┘
```

### Проблема "Too many parts"

```
⚠️ ОШИБКА: "Too many parts (600). Maximum: 300"
(порог — настройка parts_to_throw_insert, на партицию;
значение по умолчанию зависит от версии ClickHouse)

Причины:
• Слишком частые INSERT маленьких батчей
• Merge не успевает за INSERT
• Много партиций

Решения:
✅ Увеличить размер батчей
✅ Уменьшить частоту вставок
✅ Пересмотреть партиционирование
✅ OPTIMIZE TABLE (ручное слияние)
```

## Materialized Views

### Что это такое?

**Materialized View** — это таблица, которая автоматически обновляется при вставке данных в исходную таблицу.

### Пример: подсчет событий по часам

```sql
-- Исходная таблица с событиями (миллионы строк)
CREATE TABLE events (
    timestamp DateTime,
    user_id UInt32,
    event_type String
) ENGINE = MergeTree()
ORDER BY (user_id, timestamp);

-- Materialized view — предвычисленная агрегация
CREATE MATERIALIZED VIEW events_hourly
ENGINE = SummingMergeTree()
ORDER BY (hour, event_type)
AS
SELECT
    toStartOfHour(timestamp) AS hour,
    event_type,
    count() AS event_count
FROM events
GROUP BY hour, event_type;
```

### Как это работает?

```
Вставка данных:
┌─────────────────────────────────────────────────┐
│ INSERT INTO events VALUES                       │
│   ('2024-01-15 10:23:45', 123, 'click'),        │
│   ('2024-01-15 10:45:12', 456, 'click'),        │
│   ('2024-01-15 11:12:34', 789, 'view')          │
└─────────────────────────────────────────────────┘
                    ↓
        ┌───────────────────────┐
        │ Триггер автоматически │
        └───────────────────────┘
                    ↓
┌─────────────────────────────────────────────────┐
│ Данные преобразуются и вставляются в            │
│ events_hourly:                                  │
│                                                 │
│ ('2024-01-15 10:00:00', 'click', 2)             │
│ ('2024-01-15 11:00:00', 'view', 1)              │
└─────────────────────────────────────────────────┘

Быстрый запрос:
SELECT hour, event_type, sum(event_count)
FROM events_hourly
WHERE hour >= '2024-01-15'
GROUP BY hour, event_type;

Вместо сканирования миллионов строк в events,
читаем только агрегированные данные! ✅
```

### Когда использовать Materialized Views?

```
✅ ИСПОЛЬЗУЙТЕ когда:
• Одни и те же агрегации запрашиваются постоянно
• Исходная таблица очень большая
• Запросы долго выполняются
• Нужно real-time обновление агрегаций

❌ НЕ ИСПОЛЬЗУЙТЕ когда:
• Нужны разные агрегации (лучше предвычислить заранее)
• Данные редко запрашиваются
• Исходная таблица маленькая

Примеры использования:
• Счетчики событий по времени
• Топ товаров по продажам
• Метрики по регионам
• Дашборды в реальном времени
```

## Репликация и Шардирование

### Репликация — копирование данных

**Зачем нужна репликация?**
- Отказоустойчивость (если один сервер упадет)
- Распределение нагрузки чтения

```
┌─────────────────────────────────────────────┐
│         ReplicatedMergeTree                 │
└─────────────────────────────────────────────┘

         ZooKeeper/ClickHouse Keeper
              (координация)
                    │
        ┌───────────┼───────────┐
        │           │           │
    ┌───▼───┐   ┌───▼───┐   ┌───▼───┐
    │Server1│   │Server2│   │Server3│
    │(main) │   │(копия)│   │(копия)│
    └───────┘   └───────┘   └───────┘
        │           │           │
        └───────────┴───────────┘
         Одинаковые данные!

INSERT на Server1 → автоматически реплицируется на Server2 и Server3
Если Server1 упадет → читаем с Server2 или Server3 ✅
```

**Пример создания реплицированной таблицы:**
```sql
CREATE TABLE events_replica (
    date Date,
    user_id UInt32,
    event_type String
)
ENGINE = ReplicatedMergeTree(
    '/clickhouse/tables/{shard}/events',  -- Путь в ZooKeeper
    '{replica}'                            -- Имя реплики
)
PARTITION BY toYYYYMM(date)
ORDER BY (user_id, date);
```

### Шардирование — разделение данных

**Зачем нужен шардинг?**
- Одна машина не может хранить все данные
- Распараллеливание запросов

```
┌─────────────────────────────────────────────┐
│           Distributed таблица               │
│    (виртуальная, данных не хранит)          │
└─────────────────────────────────────────────┘
                    │
        ┌───────────┼───────────┐
        │           │           │
    ┌───▼────┐  ┌───▼────┐  ┌───▼────┐
    │ Shard 1│  │ Shard 2│  │ Shard 3│
    │        │  │        │  │        │
    │user_id │  │user_id │  │user_id │
    │1-1000  │  │1001-   │  │2001-   │
    │        │  │2000    │  │3000    │
    └────────┘  └────────┘  └────────┘

SELECT count(*) FROM distributed_table
→ Запрос идет на все 3 шарда параллельно
→ Результаты объединяются
→ В 3 раза быстрее! ✅
```

**Пример Distributed таблицы:**
```sql
CREATE TABLE events_distributed AS events_local
ENGINE = Distributed(
    'my_cluster',      -- Имя кластера
    'default',         -- База данных
    'events_local',    -- Локальная таблица на шардах
    rand()             -- Функция шардирования (или user_id % 3)
);

-- Вставка в Distributed таблицу
INSERT INTO events_distributed VALUES (...);
→ Данные автоматически распределяются по шардам

-- Чтение из Distributed таблицы
SELECT * FROM events_distributed WHERE ...;
→ Запрос выполняется на всех шардах параллельно
```

### Репликация + Шардирование = ❤️


## 🎯 Резюме: Когда использовать ClickHouse?

```
✅ ИСПОЛЬЗУЙТЕ ClickHouse для:
┌─────────────────────────────────────────────┐
│ • Аналитика больших объемов данных          │
│ • Логи и метрики (веб, серверы, приложения) │
│ • Time-series данные                        │
│ • Агрегации и GROUP BY запросы              │
│ • Real-time дашборды                        │
│ • OLAP кубы                                 │
└─────────────────────────────────────────────┘

❌ НЕ ИСПОЛЬЗУЙТЕ ClickHouse для:
┌─────────────────────────────────────────────┐
│ • Транзакционные системы (OLTP)             │
│ • Частые UPDATE/DELETE                      │
│ • Хранение документов (используйте MongoDB) │
│ • Маленькие таблицы (<1M строк)             │
│ • Построчная вставка данных                 │
└─────────────────────────────────────────────┘
```

## 📚 Дополнительные материалы

**Официальная документация:**
- https://clickhouse.com/docs/

**Практические советы:**
1. Всегда используйте батчи для вставки (минимум 1000 строк)
2. Правильно выбирайте ORDER BY (частые фильтры первыми)
3. Используйте партиционирование для больших таблиц
4. Мониторьте количество parts (system.parts)
5. Создавайте materialized views для частых агрегаций
6. Настройте репликацию для production
7. Используйте шардирование для больших объемов данных (>1TB)

**Типичная архитектура:**
```
Application (Go)
      │
      ▼
 Kafka/Buffer  ← Батчирование данных
      │
      ▼
  ClickHouse
  (3 shards × 2 replicas)
      │
      ▼
  Grafana/Dashboards
```
