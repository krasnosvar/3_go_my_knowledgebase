# Индексы и оптимизация запросов

## Индексы
- **Что такое индексы? Какие бывают? Примеры из жизни!**
  Индекс — это вспомогательная структура данных, ускоряющая поиск и выборку строк в таблице.

  Основные виды индексов:
  1. **B-Tree** — самый ходовой вариант, тянет и сравнения, и диапазонные условия
  2. **Hash** — только равенство, но на точечном поиске обгоняет B-Tree
  3. **GiST (Generalized Search Tree)** — под сложные типы (геоданные, полнотекстовый поиск)
  4. **GIN (Generalized Inverted Index)** — под составные значения (массивы, JSON)
  5. **BRIN (Block Range Index)** — для гигантских таблиц с естественным порядком данных
  6. **SP-GiST (Space-Partitioned GiST)** — для неоднородно распределённых данных

  Аналогии из повседневности:
  - оглавление в книге — по сути тот же индекс
  - алфавитный указатель в конце энциклопедии
  - навигация по тегам в интернет-магазине

- **Как устроен B-Tree индекс и где он используется?**
  B-Tree (B-дерево) — это сбалансированное дерево поиска: в каждом узле лежат отсортированные ключи и ссылки на дочерние узлы.

  Из чего состоит индекс B-Tree:
  - корневой узел (root) — вершина дерева
  - внутренние узлы (internal nodes) — хранят диапазоны ключей
  - листовые узлы (leaf nodes) — содержат сами данные либо ссылки на них

  Чем хорош B-Tree:
  - работает с диапазонами (>, <, BETWEEN)
  - даёт стабильную сложность O(log n)
  - удобен для сортировки и группировки

  Где применяется:
  - индекс по умолчанию почти во всех СУБД
  - первичные и уникальные ключи
  - столбцы из условий WHERE, JOIN, ORDER BY

- **В чем разница между B-Tree и Hash индексами?**
  | Характеристика | B-Tree | Hash |
  |----------------|--------|------|
  | Поддержка операций | =, >, <, >=, <=, BETWEEN, LIKE | Только = |
  | Производительность | O(log n) | O(1) на точном совпадении |
  | Использование памяти | Умеренное | Высокое |
  | Поддержка сортировки | Да | Нет |
  | NULL значения | Поддерживаются | Зависит от СУБД |
  | Обновление | Средняя скорость | Быстрое |

  Пример создания Hash индекса:
  ```sql
  -- PostgreSQL
  CREATE INDEX idx_user_email ON users USING HASH(email);
  
  -- MySQL (InnoDB автоматически создает Hash индекс для индексов на строках)
  CREATE TABLE users (
      id INT PRIMARY KEY,
      username VARCHAR(50),
      email VARCHAR(100),
      INDEX idx_email (email) USING HASH
  );
  ```

- **Что такое составной индекс?**
  Составной (композитный) индекс охватывает сразу несколько столбцов таблицы.

  Что важно учитывать:
  - порядок перечисления столбцов имеет значение
  - индекс подхватывается для запросов, фильтрующих по левому префиксу столбцов
  - хорошо работает, когда в WHERE несколько условий сразу

  Пример:
  ```sql
  -- Создание составного индекса
  CREATE INDEX idx_name_age ON users(last_name, first_name, age);
  
  -- Индекс будет использоваться для:
  SELECT * FROM users WHERE last_name = 'Иванов';
  SELECT * FROM users WHERE last_name = 'Иванов' AND first_name = 'Иван';
  SELECT * FROM users WHERE last_name = 'Иванов' AND first_name = 'Иван' AND age > 30;
  
  -- НЕ будет использоваться для:
  SELECT * FROM users WHERE first_name = 'Иван';
  SELECT * FROM users WHERE age > 30;
  ```

- **Как работает селективность индекса?**
  Селективность показывает, насколько разнообразны значения в индексируемом столбце.

  Формула: `Селективность = Количество уникальных значений / Общее количество строк`

  Чем ближе показатель к 1, тем полезнее индекс:
  - высокая селективность (около 1): например, email или уникальный номер
  - низкая селективность (около 0): булевы флаги и поля с малым числом вариантов

  Пример:
  ```sql
  -- Низкая селективность (плохой кандидат для индекса)
  CREATE INDEX idx_gender ON users(gender);  -- 'M' или 'F'
  
  -- Высокая селективность (хороший кандидат)
  CREATE INDEX idx_email ON users(email);    -- Уникальные значения
  ```

- **Каковы накладные расходы индексации?**
  1. **Место на диске**
     - под каждый индекс уходит дополнительное пространство (ориентировочно 5-20% от размера таблицы)
     - составные индексы весят больше

  2. **Замедление записи**
     - при INSERT/UPDATE/DELETE приходится обновлять все индексы
     - чем их больше, тем медленнее модификация данных

  3. **Фрагментация**
     - частые правки фрагментируют индексы
     - нужно периодическое обслуживание (REINDEX, VACUUM)

  4. **Нагрузка на планировщик**
     - обилие индексов усложняет выбор плана
     - иногда планировщик может выбрать неоптимальный вариант

- **Как работают частичные (partial) индексы?**
  Частичный индекс строится не по всей таблице, а только по строкам, попадающим под заданное условие.

  Что это даёт:
  - индекс получается компактнее
  - выше скорость для частых запросов к этому подмножеству
  - меньше накладных расходов при обновлении

  Примеры:
  ```sql
  -- Индекс только для активных пользователей
  CREATE INDEX idx_active_users ON users(email) WHERE is_active = true;
  
  -- Индекс для заказов за последний месяц
  CREATE INDEX idx_recent_orders ON orders(order_date) 
  WHERE order_date > CURRENT_DATE - INTERVAL '1 month';
  
  -- Уникальный индекс для неудаленных записей
  CREATE UNIQUE INDEX idx_unique_active_email ON users(email) 
  WHERE deleted_at IS NULL;
  ```

- **В каких случаях индекс не будет использоваться?**
  1. **Низкая селективность**
     ```sql
     -- Индекс вряд ли будет использован
     SELECT * FROM users WHERE gender = 'M';
     ```

  2. **Функция поверх столбца в условии**
     ```sql
     -- Индекс не будет использован
     SELECT * FROM users WHERE LOWER(name) = 'иванов';
     
     -- Решение: функциональный индекс
     CREATE INDEX idx_lower_name ON users(LOWER(name));
     ```

  3. **Несовпадение типов**
     ```sql
     -- Индекс не будет использован, если user_id - строка
     SELECT * FROM orders WHERE user_id = 123;
     ```

  4. **Отрицание (NOT)**
     ```sql
     -- Индекс не будет использован
     SELECT * FROM products WHERE category_id NOT IN (1, 2, 3);
     ```

  5. **Слишком маленькая таблица**
     - если таблица укладывается в одну-две страницы, СУБД зачастую предпочтёт полный проход

- **Как проверить, используется ли индекс в запросе?**
  ```sql
  -- PostgreSQL
  EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'user@example.com';
  
  -- MySQL
  EXPLAIN FORMAT=JSON 
  SELECT * FROM users WHERE email = 'user@example.com';
  
  -- SQL Server
  SET SHOWPLAN_TEXT ON;
  GO
  SELECT * FROM users WHERE email = 'user@example.com';
  GO
  SET SHOWPLAN_TEXT OFF;
  
  -- Oracle
  EXPLAIN PLAN FOR 
  SELECT * FROM users WHERE email = 'user@example.com';
  SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
  ```

  По каким признакам видно, что индекс задействован:
  - в плане встречается `Index Scan` или `Index Seek` (а не `Seq Scan`/`Table Scan`)
  - запрос отрабатывает заметно быстрее полного сканирования
  - число прочитанных строк (rows) близко к размеру ожидаемого результата

## Оптимизация запросов
- **Как оптимизировать медленный запрос?**
  (Базовый разбор уже был в предыдущем файле, здесь — дополнительные приёмы.)

  Что ещё можно сделать:
  1. **Переписать запрос**
     - заменить подзапросы на JOIN, где это возможно
     - для проверки наличия использовать EXISTS вместо IN
     - отказаться от SELECT *

  2. **Поменять организацию данных**
     - денормализовать часто читаемые данные
     - применить материализованные представления
     - разбить большие таблицы на партиции

  3. **Подстроить СУБД**
     - настроить работу с памятью
     - подкрутить поведение планировщика
     - обновить статистику

- **Как использовать EXPLAIN и EXPLAIN ANALYZE для анализа запросов?**
  ```sql
  -- Базовый EXPLAIN (только план запроса)
  EXPLAIN SELECT * FROM users WHERE age > 30;
  
  -- Подробный анализ с фактическим временем выполнения
  EXPLAIN ANALYZE SELECT * FROM users WHERE age > 30;
  
  -- Форматированный вывод (PostgreSQL)
  EXPLAIN (FORMAT JSON) SELECT * FROM users WHERE age > 30;
  
  -- С буферами (полезно для анализа ввода-вывода)
  EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM large_table;
  ```

  На что обращать внимание при разборе:
  - способ сканирования (Seq Scan, Index Scan, Bitmap Scan)
  - расхождение оценочного и фактического числа строк
  - время каждого шага плана
  - появление временных файлов (если они есть)
  - количество обращений к диску

- **Что такое DeadTuple и как с ним бороться с помощью VACUUM?**
  **Dead Tuple (мёртвый кортеж)** — это устаревшая версия строки, которую уже не видит ни одна транзакция, но которая всё ещё занимает место на диске.

  Откуда они берутся:
  - UPDATE порождает новую версию строки, а прежняя превращается в мёртвый кортеж
  - DELETE лишь помечает строку удалённой, физически её не убирая

  Лечится командой VACUUM:
  ```sql
  -- Обычная очистка (не блокирует таблицу)
  VACUUM [VERBOSE] [ANALYZE] [table_name];
  
  -- Полная очистка (требует эксклюзивной блокировки)
  VACUUM FULL [VERBOSE] [ANALYZE] [table_name];
  
  -- Автоматическая очистка (настроена по умолчанию в PostgreSQL)
  ALTER TABLE table_name SET (autovacuum_enabled = on);
  ```

  Параметры autovacuum в postgresql.conf:
  ```
  autovacuum = on
  autovacuum_vacuum_threshold = 50
  autovacuum_analyze_threshold = 50
  autovacuum_vacuum_scale_factor = 0.2
  autovacuum_analyze_scale_factor = 0.1
  ```

- **Как работают материализованные представления?**
  Материализованное представление — это объект БД, который хранит уже посчитанный результат запроса и время от времени пересчитывается.

  Чем полезно:
  - заметно ускоряет тяжёлые запросы
  - снижает нагрузку на сервер БД
  - удобно для отчётов и аналитики

  Пример в PostgreSQL:
  ```sql
  -- Создание материализованного представления
  CREATE MATERIALIZED VIEW monthly_sales AS
  SELECT 
      date_trunc('month', order_date) AS month,
      product_id,
      SUM(quantity) AS total_quantity,
      SUM(amount) AS total_amount
  FROM orders
  GROUP BY date_trunc('month', order_date), product_id;
  
  -- Создание индекса для ускорения запросов
  CREATE UNIQUE INDEX idx_monthly_sales ON monthly_sales(month, product_id);
  
  -- Обновление данных (вручную)
  REFRESH MATERIALIZED VIEW [CONCURRENTLY] monthly_sales;
  
  -- Автоматическое обновление с помощью триггеров или заданий
  ```

- **Что такое реплика и как она помогает в оптимизации?**
  Реплика — это копия базы, которую постоянно синхронизируют с основным (первичным) сервером.

  Разновидности репликации:
  1. **Синхронная** — запись подтверждается лишь после сохранения на всех репликах
  2. **Асинхронная** — запись подтверждается сразу после сохранения на основном сервере
  3. **Логическая** — переносятся изменения данных, а не физические страницы

  Как это помогает производительности:
  - чтение раскидывается по нескольким серверам
  - аналитику можно гонять на репликах, не трогая основную базу
  - растёт отказоустойчивость

  Пример настройки в PostgreSQL:
  ```sql
  -- На основном сервере (postgresql.conf)
  wal_level = replica
  max_wal_senders = 3
  wal_keep_size = 512MB        -- PG 13+; до 13 был wal_keep_segments
  
  -- На реплике (PG 12+: postgresql.conf + пустой файл standby.signal в каталоге данных;
  -- recovery.conf и standby_mode удалены в PG 12)
  primary_conninfo = 'host=master port=5432 user=repl_user password=secret'
  restore_command = 'cp /path/to/archive/%f %p'
  ```

- **Как работает кэширование запросов?**
  Кэширование — это сохранение результатов запросов, чтобы потом отдавать их повторно, не пересчитывая заново.

  На каких уровнях кэшируют:
  1. **Уровень СУБД**
     - буферный пул (страницы данных лежат в памяти)
     - кэш планов запросов

  2. **Уровень приложения**
     - реализуется в коде (Redis, Memcached)
     - кэшируются результаты тяжёлых запросов

  3. **Уровень веб-сервера**
     - кэш HTTP-ответов
     - заголовки Cache-Control, ETag

  Пример кэширования на стороне приложения:
  ```go
  func GetUserProfile(userID int) (*UserProfile, error) {
      // Пробуем получить из кэша
      if cached, found := cache.Get(fmt.Sprintf("user:%d", userID)); found {
          return cached.(*UserProfile), nil
      }
      
      // Если нет в кэше, загружаем из БД
      var profile UserProfile
      err := db.QueryRow("SELECT * FROM user_profiles WHERE user_id = $1", userID).Scan(&profile)
      if err != nil {
          return nil, err
      }
      
      // Сохраняем в кэш на 5 минут
      cache.Set(fmt.Sprintf("user:%d", userID), &profile, 5*time.Minute)
      
      return &profile, nil
  }
  ```

- **Что такое планировщик запросов и как он принимает решения?**
  Планировщик (Query Planner/Optimizer) — это часть СУБД, которая подбирает наиболее выгодный способ выполнения SQL-запроса.

  Как он работает по шагам:
  1. **Парсинг** — превращение SQL в синтаксическое дерево
  2. **Преобразование** — применение правил переписывания запроса
  3. **Планирование** — построение возможных вариантов выполнения
  4. **Оценка стоимости** — расчёт «цены» каждого варианта
  5. **Выбор** — берётся план с наименьшей стоимостью

  Что влияет на его решение:
  - статистика по таблицам и индексам
  - наличие индексов
  - размеры таблиц
  - параметры СУБД (work_mem, random_page_cost и др.)
  - настройки планировщика (параметры enable_* в PostgreSQL)

  Пример работы со статистикой в PostgreSQL:
  ```sql
  -- Обновление статистики
  ANALYZE table_name;
  
  -- Просмотр статистики по таблице
  SELECT * FROM pg_stats WHERE tablename = 'table_name';
  
  -- Принудительное использование индекса (не рекомендуется без веской причины)
  SET enable_seqscan = off;
  EXPLAIN SELECT * FROM users WHERE email = 'user@example.com';
  SET enable_seqscan = on;
  ```
