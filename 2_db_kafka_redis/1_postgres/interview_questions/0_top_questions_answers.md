# Разбор ключевых вопросов по базам данных

## 1. Накладные расходы индексации

**Ответ:**
Индексы делают чтение быстрее, но за это приходится расплачиваться:

- **Дополнительное место на диске** — под каждый индекс хранится отдельная копия проиндексированных значений.
- **Более медленная запись** — любая вставка, обновление или удаление вынуждает синхронно править все существующие индексы.
- **Обслуживание** — при активных изменениях структура индекса деградирует и требует перестроения.
- **Бесполезность при плохом выборе** — если у столбца низкая селективность, индекс почти не даёт выигрыша.

**Пример:**
```sql
-- Создание индекса
CREATE INDEX idx_orders_customer_id ON orders(customer_id);

-- Запрос, который может использовать индекс
SELECT * FROM orders WHERE customer_id = 1001;
```

## 2. Медленный запрос, что делать?

**Порядок действий при разборе тормозящего запроса:**

1. **Посмотреть план через EXPLAIN**
   ```sql
   EXPLAIN ANALYZE 
   SELECT * FROM orders WHERE status = 'shipped' AND created_at > '2023-01-01';
   ```

2. **Разобраться с индексами**
   - создать те, которых не хватает;
   - убрать лишние, которые только тормозят запись.

3. **Переписать сам запрос**
   - упростить условия фильтрации;
   - выбирать только необходимые столбцы вместо `SELECT *`;
   - привести в порядок соединения таблиц.

4. **Пересмотреть схему таблиц**
   - убедиться, что типы данных выбраны разумно;
   - решить, что уместнее — нормализация или денормализация.

## 3. Что такое СУБД? Какие бывают типы?

**СУБД (система управления базами данных)** — это ПО, с помощью которого базы данных создают, ведут и администрируют.

**Основные категории СУБД:**

1. **Реляционные (RDBMS)**
   - представители: PostgreSQL, MySQL, Oracle, SQL Server;
   - данные лежат в таблицах с заранее заданной схемой;
   - язык запросов — SQL.

2. **Документные**
   - представители: MongoDB, CouchDB;
   - единица хранения — документ (JSON/BSON);
   - схема нежёсткая, легко меняется.

3. **Колоночные**
   - представители: ClickHouse, Cassandra;
   - заточены под аналитику;
   - хорошо сжимают данные.

4. **Ключ-значение**
   - представители: Redis, DynamoDB;
   - максимально простая модель данных;
   - очень высокая скорость.

5. **Графовые**
   - представители: Neo4j, ArangoDB;
   - удобны там, где важны связи между сущностями.

## 4. ACID

**ACID** — четыре свойства, которые обеспечивают надёжность работы с транзакциями:

- **Atomicity (атомарность)** — транзакция применяется целиком либо не применяется совсем.
- **Consistency (согласованность)** — после транзакции база остаётся в корректном, целостном состоянии.
- **Isolation (изолированность)** — одновременно идущие транзакции не мешают друг другу.
- **Durability (долговечность)** — то, что закоммичено, переживёт даже сбой сервера.

## 5. Уровни изоляции транзакций

1. **Read Uncommitted**
   - минимальная изоляция, максимальная скорость;
   - допускает грязные чтения.

2. **Read Committed (значение по умолчанию во многих СУБД)**
   - грязные чтения исключены;
   - но остаются неповторяющиеся чтения и фантомы.

3. **Repeatable Read**
   - защищает и от грязных, и от неповторяющихся чтений;
   - фантомные чтения всё ещё возможны.

4. **Serializable**
   - самый строгий уровень;
   - полная изоляция транзакций;
   - платой становится падение производительности.

## 6. Что делает команда GROUP BY?

**GROUP BY** собирает строки с одинаковыми значениями заданных столбцов в единые агрегированные группы.

**Пример:**
```sql
-- Группировка по категориям товаров
SELECT 
    category,
    COUNT(*) as product_count,
    AVG(price) as avg_price
FROM products
GROUP BY category
HAVING COUNT(*) > 5;
```

## 7. HAVING и WHERE в SQL

| WHERE | HAVING |
|-------|--------|
| Отсеивает строки ещё до группировки | Отсеивает уже сформированные группы |
| Агрегатные функции недопустимы | Агрегатные функции разрешены |
| Отрабатывает перед GROUP BY | Отрабатывает после GROUP BY |

**Пример:**
```sql
-- WHERE фильтрует до группировки
-- HAVING фильтрует после
SELECT 
    department_id,
    AVG(salary) as avg_salary
FROM employees
WHERE hire_date > '2020-01-01'  -- до группировки
GROUP BY department_id
HAVING AVG(salary) > 50000;     -- после группировки
```

## 8. Transaction race

**Состояние гонки (race condition)** — это когда итог операции определяется тем, в каком порядке успели отработать параллельные операции.

**Пример проблемы:**
```sql
-- Транзакция 1
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- Читает 1000
-- Транзакция 2 выполняет то же самое
-- Обе транзакции увеличивают баланс на 100
UPDATE accounts SET balance = 1100 WHERE id = 1;
-- Вместо 1200 получаем 1100
```

**Решение:**
```sql
-- Использование SELECT FOR UPDATE
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- Другие транзакции ждут
UPDATE accounts SET balance = balance + 100 WHERE id = 1;
COMMIT;
```

## 9. Индексы. Какие бывают? Примеры из жизни!

**Разновидности индексов:**

1. **B-Tree** — универсальный тип, отлично подходит для сравнений и диапазонов
   ```sql
   CREATE INDEX idx_users_email ON users(email);
   ```

2. **Hash** — исключительно для проверки на равенство, но на точечных запросах опережает B-Tree
   ```sql
   CREATE INDEX idx_users_phone ON users USING HASH(phone);
   ```

3. **GIN (Generalized Inverted Index)** — для составных значений (массивы, JSON)
   ```sql
   CREATE INDEX idx_products_tags ON products USING GIN(tags);
   ```

4. **GiST (Generalized Search Tree)** — для геоданных и полнотекстового поиска
   ```sql
   CREATE INDEX idx_places_location ON places USING GIST(location);
   ```

**Где это встречается на практике:**
- отбор товаров по категории — B-Tree;
- поиск по точному значению — Hash;
- фильтрация по тегам — GIN;
- нахождение ближайших точек на карте — GiST.

## 10. BTree index (как устроен, где используется)

**Как устроено B-Tree:**
- это сбалансированное дерево;
- в каждом узле хранятся отсортированные ключи и указатели на потомков;
- дерево остаётся невысоким (как правило, 3-4 уровня).

**Сильные стороны:**
- работает с диапазонными условиями (>, <, BETWEEN);
- помогает при сортировке (ORDER BY);
- хорош для поиска по префиксу.

**Пример использования:**
```sql
-- Создание индекса
CREATE INDEX idx_orders_date ON orders(order_date);

-- Запрос, использующий индекс
SELECT * FROM orders 
WHERE order_date BETWEEN '2023-01-01' AND '2023-01-31';
```

## 11. BTree vs Hash indexes

| Характеристика | B-Tree | Hash |
|----------------|--------|------|
| Точное совпадение | Да | Да |
| Диапазоны | Да | Нет |
| Сортировка | Да | Нет |
| NULL значения | Да | Нет |
| Производительность | Высокая | Очень высокая |
| Использование памяти | Умеренное | Высокое |

**Когда стоит выбрать Hash:**
- нужны только сравнения на равенство;
- преобладают операции чтения;
- сортировка по этому столбцу не требуется.

## 12. Составной индекс

**Составной индекс** объединяет сразу несколько столбцов.

**Что важно помнить:**
1. Последовательность столбцов имеет значение.
2. Индекс работает по левому префиксу набора столбцов.

**Пример:**
```sql
-- Создание составного индекса
CREATE INDEX idx_orders_status_date ON orders(status, order_date);

-- Используется индекс
SELECT * FROM orders 
WHERE status = 'shipped' AND order_date > '2023-01-01';

-- Используется только первая часть индекса (status)
SELECT * FROM orders WHERE status = 'shipped';

-- Не используется индекс (пропущен status)
SELECT * FROM orders WHERE order_date > '2023-01-01';
```

## 13. Explain и Explain ANALYZE

**EXPLAIN** выводит предполагаемый план выполнения запроса:
```sql
EXPLAIN SELECT * FROM users WHERE age > 25;
```

**EXPLAIN ANALYZE** реально прогоняет запрос и показывает фактические цифры:
```sql
EXPLAIN ANALYZE 
SELECT * FROM users WHERE age > 25;
```

**На что смотреть в выводе:**
- **Seq Scan** против **Index Scan**;
- **Rows** — прогноз числа строк;
- **Loops** — сколько раз повторялась операция;
- **Execution Time** — фактическое время работы.

## 14. SELECT FOR UPDATE

**SELECT FOR UPDATE** ставит блокировку на выбранные строки вплоть до завершения транзакции.

**Способы применения:**
```sql
-- Блокировка строки
BEGIN;
SELECT * FROM products WHERE id = 1 FOR UPDATE;
-- Другие транзакции не могут изменить эту строку
UPDATE products SET stock = stock - 1 WHERE id = 1;
COMMIT;

-- Блокировка с ожиданием (по умолчанию)
SELECT * FROM products FOR UPDATE NOWAIT;

-- Блокировка с таймаутом
SELECT * FROM products FOR UPDATE SKIP LOCKED;
```

## 15. Какой тип данных обычно делают PK?

**Варианты для первичного ключа:**

1. **SERIAL/BIGSERIAL (PostgreSQL)**
   ```sql
   CREATE TABLE users (
       id SERIAL PRIMARY KEY,
       name VARCHAR(100)
   );
   ```

2. **INT/BIGINT с AUTO_INCREMENT (MySQL)**
   ```sql
   CREATE TABLE users (
       id INT AUTO_INCREMENT PRIMARY KEY,
       name VARCHAR(100)
   );
   ```

3. **UUID**
   ```sql
   CREATE TABLE users (
       id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
       name VARCHAR(100)
   );
   ```

4. **Натуральные ключи** (используются нечасто)
   - например, email или номер паспорта.

**Практические рекомендации:**
- для большинства задач достаточно SERIAL/BIGSERIAL;
- в распределённых системах удобнее UUID;
- строковых ключей на крупных таблицах лучше избегать.
