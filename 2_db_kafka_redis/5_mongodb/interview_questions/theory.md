## Что такое MongoDB?

**MongoDB** — это NoSQL документо-ориентированная база данных.

### SQL vs NoSQL (MongoDB)

```
┌─────────────────────────────────────────────────────────┐
│                 SQL (PostgreSQL, MySQL)                 │
│  ─────────────────────────────────────────────────────  │
│  • Жесткая схема (нужно определить заранее)             │
│  • Таблицы с фиксированными колонками                   │
│  • Строки                                               │
│  • JOIN для связей между таблицами                      │
│  • Вертикальное масштабирование (мощнее сервер)         │
│                                                         │
│  Пример:                                                │
│  CREATE TABLE users (                                   │
│    id INT PRIMARY KEY,                                  │
│    name VARCHAR(100),                                   │
│    email VARCHAR(100)                                   │
│  );                                                     │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│                    NoSQL (MongoDB)                      │
│  ─────────────────────────────────────────────────────  │
│  • Гибкая схема (можно менять на лету)                  │
│  • Коллекции с документами                              │
│  • Документы (JSON-подобные объекты)                    │
│  • Встраивание или ссылки вместо JOIN                   │
│  • Горизонтальное масштабирование (больше серверов)     │
│                                                         │
│  Пример:                                                │
│  {                                                      │
│    "_id": ObjectId("..."),                              │
│    "name": "Alice",                                     │
│    "email": "alice@example.com",                        │
│    "hobbies": ["reading", "coding"]  ← массив!          │
│  }                                                      │
└─────────────────────────────────────────────────────────┘
```

### Когда использовать MongoDB?

```
✅ ИСПОЛЬЗУЙТЕ MongoDB для:
┌─────────────────────────────────────────────┐
│ • Гибкая схема данных (меняется часто)      │
│ • Иерархические данные (JSON-структуры)     │
│ • Каталоги продуктов (разные атрибуты)      │
│ • Контент-менеджмент (CMS)                  │
│ • Real-time приложения                      │
│ • Большие объемы неструктурированных данных │
│ • Необходимо горизонтальное масштабирование │
└─────────────────────────────────────────────┘

❌ НЕ ИСПОЛЬЗУЙТЕ MongoDB для:
┌─────────────────────────────────────────────┐
│ • Сложные транзакции между таблицами        │
│ • Строгая консистентность критична          │
│ • Много сложных JOIN операций               │
│ • Финансовые системы (используйте SQL)      │
│ • Данные с четкими отношениями              │
└─────────────────────────────────────────────┘
```

## Документы и Коллекции

### Основные понятия

```
MongoDB                   ≈  SQL
─────────────────────────────────────────
Database (база данных)    ≈  Database
Collection (коллекция)    ≈  Table (таблица)
Document (документ)       ≈  Row (строка)
Field (поле)              ≈  Column (колонка)
```

### Визуализация

```
┌─────────────────────────────────────────────────────────┐
│                    Database: shop                       │
└─────────────────────────────────────────────────────────┘
                            │
            ┌───────────────┼───────────────┐
            │               │               │
    ┌───────▼──────┐ ┌──────▼─────┐ ┌──────▼──────┐
    │ Collection:  │ │Collection: │ │ Collection: │
    │   users      │ │  products  │ │   orders    │
    └──────────────┘ └────────────┘ └─────────────┘
            │
    ┌───────┴───────┬───────────┬───────────┐
    │               │           │           │
┌───▼────┐  ┌───────▼──┐  ┌─────▼────┐  ┌──▼──────┐
│Document│  │ Document │  │ Document │  │Document │
│   #1   │  │    #2    │  │    #3    │  │   #4    │
└────────┘  └──────────┘  └──────────┘  └─────────┘
```

### Пример документа

**SQL таблица:**
```sql
-- Жесткая схема
CREATE TABLE users (
    id INT,
    name VARCHAR(100),
    email VARCHAR(100)
);

INSERT INTO users VALUES (1, 'Alice', 'alice@example.com');
```

**MongoDB документ:**
```javascript
// Гибкая схема — каждый документ может быть разным!
{
  "_id": ObjectId("507f1f77bcf86cd799439011"),
  "name": "Alice",
  "email": "alice@example.com",
  "age": 25,                           // ← новое поле
  "address": {                         // ← вложенный объект
    "city": "Moscow",
    "street": "Lenina 1"
  },
  "hobbies": ["reading", "coding"],    // ← массив
  "created_at": ISODate("2024-01-15")
}

// Другой документ в той же коллекции может иметь другую структуру:
{
  "_id": ObjectId("507f1f77bcf86cd799439012"),
  "name": "Bob",
  "email": "bob@example.com",
  "premium": true,                     // ← поле, которого нет у Alice
  "subscription": {                    // ← другая структура
    "plan": "gold",
    "expires": ISODate("2025-01-01")
  }
}
```

## BSON vs JSON

### Что такое BSON?

**BSON** = Binary JSON (бинарный формат хранения)

```
┌─────────────────────────────────────────────────────────┐
│                      JSON (текст)                       │
├─────────────────────────────────────────────────────────┤
│ {                                                       │
│   "name": "Alice",                                      │
│   "age": 25,                                            │
│   "active": true                                        │
│ }                                                       │
│                                                         │
│ Размер: ~50 байт                                        │
│ Читаемо человеком: ✅                                   │
│ Парсинг: медленный ❌                                   │
└─────────────────────────────────────────────────────────┘
                         ↓ Конвертация
┌─────────────────────────────────────────────────────────┐
│                    BSON (бинарный)                      │
├─────────────────────────────────────────────────────────┤
│ \x16\x00\x00\x00\x02name\x00\x06\x00\x00\x00Alice...   │
│                                                         │
│ Размер: ~30 байт                                        │
│ Читаемо человеком: ❌                                   │
│ Парсинг: быстрый ✅                                     │
│ Доп. типы: Date, ObjectID, Binary ✅                    │
└─────────────────────────────────────────────────────────┘
```

### Дополнительные типы BSON

```javascript
// JSON поддерживает:
{
  "string": "hello",
  "number": 42,
  "boolean": true,
  "null": null,
  "array": [1, 2, 3],
  "object": {"key": "value"}
}

// BSON дополнительно поддерживает:
{
  "objectId": ObjectId("507f1f77bcf86cd799439011"),  // Уникальный ID
  "date": ISODate("2024-01-15T10:30:00Z"),           // Дата/время
  "binary": BinData(0, "base64..."),                 // Бинарные данные
  "int32": NumberInt(42),                            // 32-битное целое
  "int64": NumberLong(1234567890),                   // 64-битное целое
  "decimal": NumberDecimal("123.45"),                // Точные числа
  "regex": /pattern/i,                               // Регулярные выражения
  "timestamp": Timestamp(1234567890, 1)              // Внутренний тип
}
```

### ObjectID структура

```
ObjectID("507f1f77bcf86cd799439011")
         │      │   │     │
         │      │   │     └─ 5 байт: случайное значение
         │      │   └─ 3 байта: счетчик
         │      └─ 2 байта: ID процесса
         └─ 4 байта: timestamp (секунды с 1970)

Преимущества:
✅ Глобально уникальный без центрального генератора
✅ Содержит время создания
✅ Сортируется по времени создания
✅ 12 байт (меньше UUID - 16 байт)
```

## Индексы в MongoDB

### Зачем нужны индексы?

```
БЕЗ индекса (Collection Scan):
┌────────────────────────────────────────┐
│ Ищем user_id = 12345                   │
│                                        │
│ Проверяем каждый документ:             │
│ Doc 1: user_id = 1      ❌             │
│ Doc 2: user_id = 2      ❌             │
│ Doc 3: user_id = 3      ❌             │
│ ...                                    │
│ Doc 12345: user_id = 12345  ✅         │
│                                        │
│ Время: O(n) — очень медленно! ❌       │
└────────────────────────────────────────┘

С индексом (Index Scan):
┌────────────────────────────────────────┐
│ Индекс (B-tree):                       │
│                                        │
│      user_id → Document Location       │
│         1    →  0x1234                 │
│         2    →  0x1235                 │
│         ...                            │
│      12345   →  0xABCD  ← Быстрый     │
│         ...             поиск!         │
│                                        │
│ Время: O(log n) — быстро! ✅           │
└────────────────────────────────────────┘
```

### Типы индексов

#### 1. Single Field Index (по одному полю)

```javascript
// Создание индекса
db.users.createIndex({ email: 1 })  // 1 = возрастание, -1 = убывание

// Ускоряет запросы:
db.users.find({ email: "alice@example.com" })  // ✅ Быстро
db.users.find({ email: { $gt: "a@example.com" } })  // ✅ Быстро
db.users.find({}).sort({ email: 1 })  // ✅ Быстро (индекс уже отсортирован)

// Не помогает:
db.users.find({ name: "Alice" })  // ❌ Индекса на name нет
```

#### 2. Compound Index (по нескольким полям)

```javascript
// Создание составного индекса
db.orders.createIndex({ user_id: 1, created_at: -1 })

Визуализация индекса:
┌──────────┬─────────────┬─────────────┐
│ user_id  │ created_at  │ Document    │
├──────────┼─────────────┼─────────────┤
│ 100      │ 2024-01-15  │ → Doc A     │
│ 100      │ 2024-01-14  │ → Doc B     │
│ 100      │ 2024-01-13  │ → Doc C     │
│ 101      │ 2024-01-15  │ → Doc D     │
│ 101      │ 2024-01-12  │ → Doc E     │
└──────────┴─────────────┴─────────────┘

// Эффективные запросы (ESR правило):
db.orders.find({ user_id: 100 })  // ✅ Использует индекс
db.orders.find({ user_id: 100 }).sort({ created_at: -1 })  // ✅ Идеально!
db.orders.find({ user_id: 100, created_at: { $gte: "2024-01-01" } })  // ✅

// Неэффективные запросы:
db.orders.find({ created_at: { $gte: "2024-01-01" } })  // ⚠️ Индекс не используется полностью
db.orders.find({ status: "pending" })  // ❌ Индекса нет
```

**ESR правило (Equality, Sort, Range):**
```
Порядок полей в составном индексе:
1. Equality (=) — точное совпадение
2. Sort — сортировка
3. Range (>, <, >=, <=) — диапазон

Пример: { user_id: 1, status: 1, created_at: -1 }
         └─ Equality  └─ Equality  └─ Sort/Range
```

#### 3. Multikey Index (для массивов)

```javascript
// Документ с массивом
{
  "_id": 1,
  "name": "Alice",
  "tags": ["mongodb", "database", "nosql"]
}

// Индекс на массиве
db.articles.createIndex({ tags: 1 })

// MongoDB создает индекс для КАЖДОГО элемента:
┌──────────┬─────────────┐
│ tags     │ Document    │
├──────────┼─────────────┤
│ mongodb  │ → Doc 1     │  ← Один документ создает
│ database │ → Doc 1     │  ← несколько записей
│ nosql    │ → Doc 1     │  ← в индексе
└──────────┴─────────────┘

// Быстрый поиск:
db.articles.find({ tags: "mongodb" })  // ✅ Использует индекс
db.articles.find({ tags: { $in: ["mongodb", "nosql"] } })  // ✅
```

#### 4. Text Index (полнотекстовый поиск)

```javascript
// Создание текстового индекса
db.articles.createIndex({ title: "text", content: "text" })

// Поиск по словам
db.articles.find({ $text: { $search: "mongodb tutorial" } })

// Фразовый поиск
db.articles.find({ $text: { $search: "\"exact phrase\"" } })

// С оценкой релевантности
db.articles.find(
  { $text: { $search: "mongodb" } },
  { score: { $meta: "textScore" } }
).sort({ score: { $meta: "textScore" } })
```

#### 5. Unique Index (уникальность)

```javascript
// Гарантирует уникальность
db.users.createIndex({ email: 1 }, { unique: true })

// Попытка вставить дубликат:
db.users.insert({ email: "alice@example.com" })  // ✅ OK
db.users.insert({ email: "alice@example.com" })  // ❌ Ошибка: duplicate key
```

### Покрывающие индексы (Covered Queries)

```javascript
// Индекс
db.users.createIndex({ name: 1, email: 1 })

// Покрывающий запрос — все данные берутся из индекса!
db.users.find(
  { name: "Alice" },
  { name: 1, email: 1, _id: 0 }  // Проекция только индексированных полей
)

┌─────────────────────────────────────┐
│ MongoDB НЕ читает документы!        │
│ Все данные уже в индексе            │
│ ⚡ Самый быстрый тип запроса        │
└─────────────────────────────────────┘

// Не покрывающий запрос
db.users.find(
  { name: "Alice" },
  { name: 1, email: 1, age: 1 }  // age не в индексе
)
// MongoDB должен прочитать документы ❌
```

## Aggregation Pipeline

### Что это такое?

**Aggregation Pipeline** — это последовательность стадий обработки данных.

```
Данные проходят через "конвейер" преобразований:

Исходные документы
      ↓
 ┌────────┐
 │ $match │  ← Фильтрация (WHERE в SQL)
 └────┬───┘
      ↓
 ┌────────┐
 │ $group │  ← Группировка (GROUP BY в SQL)
 └────┬───┘
      ↓
 ┌────────┐
 │ $sort  │  ← Сортировка (ORDER BY в SQL)
 └────┬───┘
      ↓
 ┌────────┐
 │ $limit │  ← Ограничение (LIMIT в SQL)
 └────┬───┘
      ↓
Результат
```

### Основные стадии

#### $match — Фильтрация

```javascript
// SQL: WHERE status = 'active'
db.orders.aggregate([
  { $match: { status: "active" } }
])

┌─────────────────┐
│ All Documents   │
│ (1,000,000)     │
└────────┬────────┘
         ↓ $match
┌─────────────────┐
│ Active Only     │
│ (50,000)        │
└─────────────────┘
```

#### $group — Группировка

```javascript
// SQL: SELECT category, SUM(amount) FROM orders GROUP BY category
db.orders.aggregate([
  {
    $group: {
      _id: "$category",               // Группировать по категории
      total: { $sum: "$amount" },     // Сумма
      count: { $sum: 1 },             // Количество
      avg_amount: { $avg: "$amount" } // Среднее
    }
  }
])

Было:
┌──────────┬────────┬────────┐
│ order_id │category│ amount │
├──────────┼────────┼────────┤
│ 1        │ books  │ 100    │
│ 2        │ books  │ 150    │
│ 3        │ games  │ 200    │
│ 4        │ books  │ 120    │
└──────────┴────────┴────────┘

Стало:
┌──────────┬───────┬───────┬────────────┐
│ category │ total │ count │ avg_amount │
├──────────┼───────┼───────┼────────────┤
│ books    │ 370   │ 3     │ 123.33     │
│ games    │ 200   │ 1     │ 200.00     │
└──────────┴───────┴───────┴────────────┘
```

#### $project — Выбор полей

```javascript
// SQL: SELECT name, email FROM users
db.users.aggregate([
  {
    $project: {
      name: 1,                        // Включить
      email: 1,                       // Включить
      _id: 0,                         // Исключить
      fullName: {                     // Вычисляемое поле
        $concat: ["$firstName", " ", "$lastName"]
      }
    }
  }
])
```

#### $lookup — JOIN

```javascript
// SQL: SELECT * FROM orders JOIN users ON orders.user_id = users._id

db.orders.aggregate([
  {
    $lookup: {
      from: "users",           // Правая таблица
      localField: "user_id",   // Поле в orders
      foreignField: "_id",     // Поле в users
      as: "user_info"          // Результат (массив)
    }
  }
])

Было:
// orders
{ _id: 1, user_id: 100, amount: 50 }

// users
{ _id: 100, name: "Alice" }

Стало:
{
  _id: 1,
  user_id: 100,
  amount: 50,
  user_info: [                    // ← JOIN результат
    { _id: 100, name: "Alice" }
  ]
}
```

### Полный пример: Топ-5 категорий по продажам

```javascript
db.orders.aggregate([
  // Шаг 1: Фильтруем только выполненные заказы
  {
    $match: {
      status: "completed",
      created_at: { $gte: new Date("2024-01-01") }
    }
  },
  
  // Шаг 2: Группируем по категориям
  {
    $group: {
      _id: "$category",
      total_sales: { $sum: "$amount" },
      order_count: { $sum: 1 },
      avg_order: { $avg: "$amount" }
    }
  },
  
  // Шаг 3: Сортируем по продажам
  {
    $sort: { total_sales: -1 }
  },
  
  // Шаг 4: Берем топ-5
  {
    $limit: 5
  },
  
  // Шаг 5: Форматируем результат
  {
    $project: {
      category: "$_id",
      total_sales: 1,
      order_count: 1,
      avg_order: { $round: ["$avg_order", 2] },
      _id: 0
    }
  }
])

Результат:
[
  { category: "Electronics", total_sales: 150000, order_count: 500, avg_order: 300 },
  { category: "Books", total_sales: 80000, order_count: 2000, avg_order: 40 },
  ...
]
```

## Embedding vs Referencing

### Главный вопрос проектирования MongoDB

**Встраивать данные или использовать ссылки?**

### Embedding (Встраивание)

```javascript
// Все данные в одном документе
{
  _id: ObjectId("..."),
  name: "Alice",
  email: "alice@example.com",
  address: {                    // ← Встроенный документ
    street: "Lenina 1",
    city: "Moscow",
    country: "Russia",
    zip: "123456"
  },
  orders: [                     // ← Встроенный массив
    {
      order_id: 1001,
      date: ISODate("2024-01-15"),
      total: 100,
      items: [
        { product: "Book", qty: 2, price: 50 }
      ]
    },
    {
      order_id: 1002,
      date: ISODate("2024-01-20"),
      total: 200
    }
  ]
}

✅ Преимущества:
• Один запрос — все данные
• Атомарность (изменения в одной транзакции)
• Лучшая производительность чтения

❌ Недостатки:
• Дублирование данных
• Ограничение 16MB на документ
• Сложно обновлять связанные данные
```

### Referencing (Ссылки)

```javascript
// users коллекция
{
  _id: ObjectId("user123"),
  name: "Alice",
  email: "alice@example.com"
}

// orders коллекция
{
  _id: ObjectId("order1001"),
  user_id: ObjectId("user123"),  // ← Ссылка на пользователя
  date: ISODate("2024-01-15"),
  total: 100
}

// Чтение требует двух запросов:
const user = db.users.findOne({ _id: ObjectId("user123") })
const orders = db.orders.find({ user_id: ObjectId("user123") })

// Или $lookup (JOIN):
db.users.aggregate([
  {
    $lookup: {
      from: "orders",
      localField: "_id",
      foreignField: "user_id",
      as: "orders"
    }
  }
])

✅ Преимущества:
• Нет дублирования
• Гибкость
• Нет ограничения на размер

❌ Недостатки:
• Несколько запросов или JOIN
• Медленнее чтение
• Нет атомарности между документами (до версии 4.0)
```

### Когда что использовать?

```
┌────────────────────────────────────────────────────────┐
│                  EMBEDDING (встраивание)               │
├────────────────────────────────────────────────────────┤
│ Используйте когда:                                     │
│ ✅ One-to-Few отношения (1 к немногим)                 │
│ ✅ Данные всегда читаются вместе                       │
│ ✅ Данные не растут бесконечно                         │
│ ✅ Не нужно обновлять встроенные данные отдельно       │
│                                                        │
│ Примеры:                                               │
│ • Адрес пользователя                                   │
│ • Комментарии к посту (если немного)                   │
│ • Атрибуты продукта                                    │
│ • История статусов заказа (ограниченная)               │
└────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────┐
│                  REFERENCING (ссылки)                  │
├────────────────────────────────────────────────────────┤
│ Используйте когда:                                     │
│ ✅ One-to-Many / Many-to-Many отношения                │
│ ✅ Данные могут расти неограниченно                    │
│ ✅ Данные часто обновляются независимо                 │
│ ✅ Нужен доступ к данным отдельно                      │
│                                                        │
│ Примеры:                                               │
│ • Заказы пользователя                                  │
│ • Комментарии к посту (если много)                     │
│ • Авторы книг (многие ко многим)                       │
│ • Категории продуктов                                  │
└────────────────────────────────────────────────────────┘
```

### Гибридный подход

```javascript
// Лучшее из обоих миров!
{
  _id: ObjectId("order123"),
  user_id: ObjectId("user123"),     // ← Ссылка
  user_snapshot: {                  // ← Копия нужных данных
    name: "Alice",
    email: "alice@example.com"
  },
  items: [                          // ← Встроенные товары
    {
      product_id: ObjectId("prod1"), // ← Ссылка
      product_name: "Book",          // ← Копия для истории
      price: 50,
      qty: 2
    }
  ],
  total: 100
}

Зачем?
• Быстрое чтение (не нужен JOIN для имени)
• История сохранена (если user изменит email, заказ не изменится)
• Гибкость (можем получить полные данные user по ссылке)
```

## Replica Set

### Что это такое?

**Replica Set** — группа MongoDB серверов, хранящих одинаковые данные.

```
┌──────────────────────────────────────────────┐
│           Replica Set (3 ноды)               │
└──────────────────────────────────────────────┘

      ┌─────────────────────────────┐
      │         PRIMARY             │
      │   (принимает записи)        │
      └─────┬──────────────┬────────┘
            │              │
    Репликация    Репликация
       oplog        oplog
            │              │
    ┌───────▼──────┐  ┌────▼───────┐
    │  SECONDARY   │  │ SECONDARY  │
    │  (копия)     │  │  (копия)   │
    └──────────────┘  └────────────┘

Запись:  Client → PRIMARY только
Чтение:  Client → PRIMARY или SECONDARY (настраиваемо)
```

### Как работает репликация?

```
1. Запись приходит на PRIMARY
   ┌─────────┐
   │ PRIMARY │ ← INSERT document
   └────┬────┘
        │
        ↓ Запись в oplog (operation log)
   ┌─────────────────────────────────┐
   │ oplog: [insert doc_id=123, ...]│
   └─────────────────────────────────┘

2. SECONDARY читают oplog и применяют операции
   ┌───────────┐     ┌───────────┐
   │SECONDARY 1│     │SECONDARY 2│
   └─────┬─────┘     └─────┬─────┘
         │                 │
    Читают oplog      Читают oplog
         │                 │
         ↓                 ↓
   Применяют         Применяют
   операции          операции
```

### Автоматический Failover

```
Нормальная работа:
┌─────────┐  ┌───────────┐  ┌───────────┐
│ PRIMARY │  │SECONDARY 1│  │SECONDARY 2│
└─────────┘  └───────────┘  └───────────┘
     ✅            ✅             ✅

PRIMARY упал:
┌─────────┐  ┌───────────┐  ┌───────────┐
│ PRIMARY │  │SECONDARY 1│  │SECONDARY 2│
└─────────┘  └───────────┘  └───────────┘
     ❌            ✅             ✅
                   │
              Голосование
                   │
                   ↓
┌─────────┐  ┌───────────┐  ┌───────────┐
│ (старый)│  │  PRIMARY  │  │SECONDARY 2│
└─────────┘  └───────────┘  └───────────┘
     ❌           ✅              ✅
              ← Новый PRIMARY!

Время переключения: ~10-30 секунд
Приложение автоматически переподключается ✅
```

### Read Preference (предпочтение чтения)

```javascript
// В Go драйвере:
import "go.mongodb.org/mongo-driver/mongo/readpref"

// 1. primary (по умолчанию)
// Читать только с PRIMARY
clientOpts := options.Client().
    SetReadPreference(readpref.Primary())
✅ Всегда актуальные данные
❌ Вся нагрузка на PRIMARY

// 2. primaryPreferred
// PRIMARY, но если недоступен — SECONDARY
SetReadPreference(readpref.PrimaryPreferred())
✅ Обычно актуальные данные
✅ Отказоустойчивость

// 3. secondary
// Только с SECONDARY
SetReadPreference(readpref.Secondary())
✅ Разгрузка PRIMARY
⚠️ Могут быть немного устаревшие данные

// 4. secondaryPreferred
// SECONDARY, но если недоступны — PRIMARY
SetReadPreference(readpref.SecondaryPreferred())
✅ Балансировка нагрузки
✅ Отказоустойчивость

// 5. nearest
// Ближайший сервер (по сетевой задержке)
SetReadPreference(readpref.Nearest())
✅ Минимальная задержка
```

### Write Concern (гарантии записи)

```javascript
import "go.mongodb.org/mongo-driver/mongo/writeconcern"

// majority (рекомендуется)
// Подтверждение от большинства нод
wc := writeconcern.Majority()

┌─────────┐  ┌───────────┐  ┌───────────┐
│ PRIMARY │  │SECONDARY 1│  │SECONDARY 2│
└────┬────┘  └─────┬─────┘  └─────┬─────┘
     │             │              │
  INSERT        Реплик.        Реплик.
     │             │              │
     OK ←──────── OK ←────────── OK
                   ↑
          Клиент получает OK только
          когда 2 из 3 нод подтвердили
          
✅ Данные не потеряются при падении PRIMARY
⚠️ Немного медленнее

// w: 1 (быстро, но рискованно)
wc := writeconcern.W1()
// Подтверждение только от PRIMARY
✅ Быстро
❌ Данные могут потеряться при падении PRIMARY
```

## Sharding

### Зачем нужен шардинг?

```
Проблема:
┌──────────────────────────────────────┐
│      Один сервер MongoDB             │
│                                      │
│  • 1TB данных                        │
│  • Не хватает RAM                    │
│  • Не хватает места на диске         │
│  • Медленные запросы                 │
└──────────────────────────────────────┘
        ❌ Вертикальное масштабирование
           становится дорогим

Решение — Шардирование:
┌────────────────────────────────────────────┐
│ Данные распределены между серверами       │
└────────────────────────────────────────────┘
   ┌──────────┐  ┌──────────┐  ┌──────────┐
   │ Shard 1  │  │ Shard 2  │  │ Shard 3  │
   │ 350GB    │  │ 350GB    │  │ 350GB    │
   └──────────┘  └──────────┘  └──────────┘
        ✅ Горизонтальное масштабирование
```

### Архитектура Sharded Cluster

```
┌─────────────────────────────────────────────────────┐
│                    Application                      │
└────────────────────┬────────────────────────────────┘
                     │
        ┌────────────┴────────────┐
        │                         │
   ┌────▼────┐              ┌─────▼───┐
   │ mongos  │              │ mongos  │  ← Роутеры (можно много)
   │(router) │              │(router) │
   └────┬────┘              └─────┬───┘
        │                         │
        └────────────┬────────────┘
                     │
      ┌──────────────┼──────────────┐
      │              │              │
  ┌───▼───┐      ┌───▼───┐      ┌───▼───┐
  │Shard 1│      │Shard 2│      │Shard 3│
  │(RS)   │      │(RS)   │      │(RS)   │  ← Каждый shard — это Replica Set
  └───────┘      └───────┘      └───────┘
      ↑              ↑              ↑
      │              │              │
      └──────────────┼──────────────┘
                     │
              ┌──────▼──────┐
              │Config Servers│  ← Хранят метаданные
              │  (RS)        │     (какие данные где)
              └──────────────┘
```

### Shard Key — самое важное решение!

```javascript
// Включение шардирования для БД
sh.enableSharding("mydb")

// Выбор shard key для коллекции
sh.shardCollection("mydb.users", { user_id: 1 })
                                   └─ Shard key
```

**Как работает распределение:**
```
Shard Key: user_id (hashed)

              ┌──────────────┐
              │   mongos     │
              └──────┬───────┘
                     │
        INSERT { user_id: 12345, name: "Alice" }
                     │
                hash(12345) = 0xABC123
                     │
       Какой chunk содержит 0xABC123?
                     │
           ┌─────────┴─────────┐
           │                   │
      0x000000          0x800000          0xFFFFFF
           │                   │              │
      ┌────▼────┐         ┌────▼────┐    ┌───▼─────┐
      │ Shard 1 │         │ Shard 2 │    │ Shard 3 │
      └─────────┘         └─────────┘    └─────────┘
                              ↑
                    Документ попадает сюда!
```

### Плохие и хорошие Shard Keys

```
❌ ПЛОХИЕ Shard Keys:

1. Монотонно растущие (timestamp, _id)
┌────────────────────────────────────────┐
│ Все новые данные → Shard 3             │
│                                        │
│ Shard 1: [старые данные]               │
│ Shard 2: [старые данные]               │
│ Shard 3: [ВСЕ НОВЫЕ]  ← Перегружен!   │
└────────────────────────────────────────┘

2. Низкая кардинальность (country: 200 значений)
┌────────────────────────────────────────┐
│ Только 200 уникальных значений         │
│ → Нельзя создать много chunks          │
│ → Плохая балансировка                  │
└────────────────────────────────────────┘

3. Редко используемые в запросах
┌────────────────────────────────────────┐
│ Shard key: random_id                   │
│ Запрос: WHERE user_id = 123            │
│ → mongos не знает на каком шарде       │
│ → Broadcast query на ВСЕ шарды ❌      │
└────────────────────────────────────────┘

✅ ХОРОШИЕ Shard Keys:

1. Высокая кардинальность
• user_id (миллионы значений)
• email (уникальные)

2. Равномерное распределение
• hashed(user_id)
• {region: 1, user_id: 1}

3. Поддерживает частые запросы
• Если запросы: WHERE user_id = X
• Shard key: {user_id: 1}
• → Целевой запрос на один шард ✅
```

### Range-based vs Hashed Sharding

```
Range-based sharding:
sh.shardCollection("mydb.users", { user_id: 1 })

┌──────────┐  ┌──────────┐  ┌──────────┐
│ Shard 1  │  │ Shard 2  │  │ Shard 3  │
│ 1-10000  │  │10001-    │  │20001-    │
│          │  │20000     │  │30000     │
└──────────┘  └──────────┘  └──────────┘

✅ Хорошо для range queries: user_id BETWEEN 5000 AND 15000
❌ Монотонный рост → hotspot

Hashed sharding:
sh.shardCollection("mydb.users", { user_id: "hashed" })

┌──────────┐  ┌──────────┐  ┌──────────┐
│ Shard 1  │  │ Shard 2  │  │ Shard 3  │
│ hash:    │  │ hash:    │  │ hash:    │
│ 0x0-0x5..│  │0x5-0xA.. │  │0xA-0xF.. │
└──────────┘  └──────────┘  └──────────┘

✅ Равномерное распределение
✅ Нет hotspots
❌ Range queries требуют broadcast
```

## Транзакции

### До MongoDB 4.0

```javascript
// НЕТ транзакций!
// Атомарность только в пределах одного документа

db.accounts.updateOne(
  { _id: "alice" },
  { $inc: { balance: -100 } }
)
// Если здесь произойдет ошибка...

db.accounts.updateOne(
  { _id: "bob" },
  { $inc: { balance: +100 } }
)
// ...деньги могут потеряться! ❌
```

### С MongoDB 4.0+ (Multi-Document Transactions)

```go
import "go.mongodb.org/mongo-driver/mongo"

// Перевод денег между счетами
session, err := client.StartSession()
defer session.EndSession(ctx)

err = mongo.WithSession(ctx, session, func(sc mongo.SessionContext) error {
    // Начать транзакцию
    if err := session.StartTransaction(); err != nil {
        return err
    }

    // Операция 1: Снять деньги с Alice
    _, err := accounts.UpdateOne(
        sc,
        bson.M{"_id": "alice"},
        bson.M{"$inc": bson.M{"balance": -100}},
    )
    if err != nil {
        session.AbortTransaction(sc)  // Откат
        return err
    }

    // Операция 2: Добавить деньги Bob
    _, err = accounts.UpdateOne(
        sc,
        bson.M{"_id": "bob"},
        bson.M{"$inc": bson.M{"balance": 100}},
    )
    if err != nil {
        session.AbortTransaction(sc)  // Откат
        return err
    }

    // Зафиксировать транзакцию
    return session.CommitTransaction(sc)
})
```

**Визуализация:**
```
┌────────────────────────────────────────┐
│          Start Transaction             │
└───────────────┬────────────────────────┘
                │
        ┌───────▼────────┐
        │ Alice: -100    │  ← Временное изменение
        └───────┬────────┘
                │
        ┌───────▼────────┐
        │ Bob: +100      │  ← Временное изменение
        └───────┬────────┘
                │
           Все OK?
         ┌──────┴──────┐
        ДА            НЕТ
         │              │
    ┌────▼────┐    ┌────▼────┐
    │ COMMIT  │    │ ABORT   │
    │ Данные  │    │ Откат   │
    │сохранены│    │ всего   │
    └─────────┘    └─────────┘
         ✅             ❌
```

### Ограничения транзакций

```
⚠️ Требования:
• MongoDB 4.0+ для replica set
• MongoDB 4.2+ для sharded cluster
• Все операции должны быть в одной сессии

⚠️ Производительность:
• Медленнее обычных операций
• Блокировки документов
• Ограничение времени (60 секунд по умолчанию)

💡 Совет:
Если возможно, проектируйте схему так,
чтобы избежать транзакций!
• Используйте embedding
• Денормализация
• Атомарные операции на уровне документа
```

## 🎯 Резюме: Ключевые концепции MongoDB

```
┌────────────────────────────────────────────────────┐
│ 1. Документы и Коллекции                           │
│    • Гибкая схема (каждый документ может отличаться)│
│    • BSON формат (бинарный JSON)                   │
│    • ObjectID — уникальный идентификатор           │
└────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────┐
│ 2. Индексы                                         │
│    • Создавайте индексы на часто используемые поля │
│    • ESR правило для составных индексов            │
│    • Покрывающие запросы — самые быстрые           │
└────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────┐
│ 3. Aggregation Pipeline                            │
│    • $match → $group → $sort → $limit              │
│    • $lookup для JOIN                              │
│    • Мощный инструмент для аналитики               │
└────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────┐
│ 4. Embedding vs Referencing                        │
│    • Embedding: one-to-few, читаем вместе          │
│    • Referencing: one-to-many, растет безгранично  │
│    • Гибридный подход часто лучше                  │
└────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────┐
│ 5. Replica Set                                     │
│    • 3+ ноды для отказоустойчивости                │
│    • Автоматический failover (~10-30 сек)          │
│    • Read preference для балансировки              │
└────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────┐
│ 6. Sharding                                        │
│    • Горизонтальное масштабирование                │
│    • Shard key — критически важный выбор!          │
│    • Высокая кардинальность + равномерность        │
└────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────┐
│ 7. Транзакции                                      │
│    • MongoDB 4.0+ поддерживает ACID                │
│    • Используйте только когда действительно нужно  │
│    • Лучше проектировать схему без транзакций      │
└────────────────────────────────────────────────────┘
```

## 📚 Практические рекомендации

### 1. Проектирование схемы

```
✅ ДЕЛАЙТЕ:
• Моделируйте данные под ваши запросы (query-driven design)
• Денормализуйте для производительности
• Используйте embedding для часто читаемых вместе данных
• Ограничивайте размер массивов

❌ НЕ ДЕЛАЙТЕ:
• Не переносите SQL схему 1:1
• Не делайте глубокую вложенность (>3-4 уровней)
• Не создавайте unbounded arrays
• Не игнорируйте ограничение 16MB на документ
```

### 2. Индексирование

```
✅ ДЕЛАЙТЕ:
• Создавайте индексы на поля в WHERE
• Используйте ESR правило для составных индексов
• Мониторьте использование индексов (explain())
• Удаляйте неиспользуемые индексы

❌ НЕ ДЕЛАЙТЕ:
• Не создавайте слишком много индексов (замедляет запись)
• Не игнорируйте покрывающие индексы
• Не забывайте про уникальные индексы
```

### 3. Production архитектура

```
Минимальная production конфигурация:

Application Layer:
┌──────────────┐  ┌──────────────┐
│ App Server 1 │  │ App Server 2 │
└──────┬───────┘  └──────┬───────┘
       │                 │
       └────────┬────────┘
                │
MongoDB Replica Set:
┌───────────────┼───────────────┐
│               │               │
┌───▼───┐  ┌────▼────┐  ┌───▼───┐
│PRIMARY│  │SECONDARY│  │SECONDARY│
└───────┘  └─────────┘  └────────┘

• 3 ноды MongoDB (PSS)
• Connection pooling
• Read from secondaries для аналитики
• Регулярные бэкапы
• Мониторинг (MongoDB Atlas, Ops Manager)
```
