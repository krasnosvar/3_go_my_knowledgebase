# Переопределение методов

Если у внешнего типа определён метод с тем же именем, что у встроенного, — он **перекрывает** встроенный для данного типа.

```go
type Animal struct{ Name string }

func (a Animal) Speak() { fmt.Println("какой-то звук") }

type Dog struct { Animal }

func (d Dog) Speak() { fmt.Println("гав!") }

dog := Dog{Animal: Animal{Name: "Бобик"}}
dog.Speak()        // "гав!" — метод Dog
dog.Animal.Speak() // "какой-то звук" — метод Animal
```

## Это не override из классического ООП

- Нет виртуального вызова через базовый тип.
- `var a Animal = dog.Animal` — это копия, а не полиморфный объект.
- В отличие от Java, нельзя вызвать «super.Speak()» — пишешь явно `dog.Animal.Speak()`.

## Как использовать

Чаще всего переопределение нужно, чтобы:

- «обернуть» поведение: сделать своё до/после + вызов встроенного;
- заменить поведение целиком;
- подстроить поведение под конкретный контекст.

Пример «обёртки»:

```go
type loggingRepo struct {
    UserRepo
    log *slog.Logger
}

func (r loggingRepo) Save(ctx context.Context, u User) error {
    r.log.Info("save user", "id", u.ID)
    return r.UserRepo.Save(ctx, u) // делегируем встроенному
}
```

## Конфликты и неоднозначность

Если тип встраивает `A` и `B`, и у обоих есть метод `Do()`, внешний тип его **не** продвигает — требуется явное обращение:

```go
type A struct{}
func (A) Do() {}
type B struct{}
func (B) Do() {}

type Both struct { A; B }

var b Both
// b.Do() // ошибка: ambiguous selector
b.A.Do() // OK
b.B.Do() // OK
```

Это не override, а неоднозначность — и компилятор её не разрешает автоматически.

## Правила хорошего тона

- Переопределение уместно — если оно соответствует контракту (не ломает ожиданий вызывающего).
- Не переопределяй, чтобы скрыть поведение. Лучше сделай отдельный метод с другим именем.
- Документируй, если внешний метод делает что-то нетривиальное.
