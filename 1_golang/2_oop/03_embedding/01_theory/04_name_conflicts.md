# Конфликты имён при embedding

Когда внешний тип встраивает несколько типов с одноимёнными полями или методами, Go не пытается угадать — требует явности.

## Конфликт на одном уровне

```go
type A struct { Name string }
type B struct { Name string }

type Both struct {
    A
    B
}

var v Both
// v.Name = "x" // ошибка: ambiguous selector
v.A.Name = "x" // OK
v.B.Name = "y" // OK
```

Если несколько встроенных типов на **одном уровне глубины** имеют одноимённое поле/метод — promotion не работает, нужен явный путь.

## Конфликт методов

```go
type A struct{}
func (A) Do() {}
type B struct{}
func (B) Do() {}

type Outer struct { A; B }

var o Outer
// o.Do() // ошибка компиляции: ambiguous selector
o.A.Do()
o.B.Do()
```

## Как разрешить

- Вручную: обращаешься через явное имя поля.
- Через оверрайд: определи одноимённый метод на внешней структуре, он перекроет конфликт:

```go
func (o Outer) Do() {
    o.A.Do()
    o.B.Do()
}

o.Do() // теперь работает
```

- Через разные имена: если контракт позволяет, переименуй методы.

## Приоритет глубины

Если конфликт на **разных уровнях**, побеждает ближайший к внешнему типу.

```go
type A struct{ Name string }
type B struct{ A; Name string }
type Outer struct{ B }

var o Outer
o.Name // это B.Name, поле A.Name скрыто

// чтобы добраться до A:
o.B.A.Name
```

Поле/метод на более близком уровне «затеняет» одноимённое на более глубоком. Это уже не ambiguous, а просто shadowing.

## Практические советы

- Избегай встраивания двух типов с пересечением API — трогать нужно только сознательно.
- Если переопределяешь метод через внешний тип, чтобы разрешить конфликт, явно в коментарии зафиксируй, почему именно так.
- Линтеры чаще всего не ловят такое — следи сам при проектировании структур.
