# Best practices методов

## 1. Короткое имя receiver

Receiver — «this» Go-мира. Имя должно быть коротким, обычно одна буква:

```go
func (u *User) Rename(name string) // хорошо
func (user *User) Rename(name string) // слишком длинно
```

Во всём типе имя receiver должно быть одинаковым.

## 2. Один стиль receiver

Все методы типа — либо все `T`, либо все `*T`. Не смешивать.

## 3. Метод должен делать одну вещь

Если метод `Save(ctx, db, tx, opts) error` содержит 150 строк — это уже не метод, а сервис. Дели на меньшие методы или выделяй функцию.

## 4. Публичный API в интерфейсы

Если тип нужен как зависимость другим модулям — опиши интерфейс с нужными методами. Это упрощает моки в тестах и замену реализации.

## 5. Ошибки как последний возврат

```go
func (r *Repo) Get(id int) (User, error) // хорошо
func (r *Repo) Get(id int) (error, User) // не идиоматично
```

## 6. Context первым аргументом

Если метод делает сетевые/IO операции:

```go
func (r *Repo) Get(ctx context.Context, id int) (User, error)
```

## 7. Не возвращай `*T` там, где хватает `T`

Маленькие value-объекты без идентичности возвращай по значению. `*T` имеет смысл, когда:

- тип большой;
- меняется;
- должен быть «тот же самый» объект.

## 8. Избегай мутаторов-getter'ов

```go
// плохо
func (u *User) Name() string { u.visited = true; return u.name }
```

Метод с именем геттера должен быть чистым, без побочных эффектов.

## 9. Stringer для хорошего логирования

Реализуй `String() string`, если тип должен «красиво» печататься в логах:

```go
func (s Status) String() string { /* ... */ }
fmt.Println(s) // человеко-читаемо
```

## 10. Документация

Первая строка doc-комментария начинается с имени метода:

```go
// Get loads a user by id. Returns ErrNotFound if absent.
func (r *Repo) Get(ctx context.Context, id int) (User, error) { ... }
```

Так работает `godoc`.
