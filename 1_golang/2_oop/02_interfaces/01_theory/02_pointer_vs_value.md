# Pointer vs Value и реализация интерфейсов

## Правило method set

- У типа `T` в method set — только методы с value receiver.
- У типа `*T` в method set — и value, и pointer receiver.

Значит: если хоть один метод интерфейса объявлен на указателе, то **только `*T` реализует интерфейс**.

```go
type Incr interface { Inc() }

type Counter struct{ v int }

func (c *Counter) Inc() { c.v++ }

var x Incr = &Counter{} // OK
// var x Incr = Counter{} // ошибка: Counter не реализует Incr
```

## Почему так

Метод с pointer receiver обычно модифицирует значение. Если бы value типа `T` мог бы «реализовывать» такой метод, это создавало бы иллюзию модификации, которая по факту ничего не меняет — пришлось бы работать с копией.

## Проверка реализации на compile-time

```go
var _ Incr = (*Counter)(nil)
```

Это выражение — идиоматическая проверка: «пусть не скомпилируется, если `*Counter` перестанет реализовывать Incr». Пишется под определением типа.

## Интерфейс, value receiver + pointer receiver

Если одни методы на `T`, другие на `*T` — `T` **не** реализует интерфейс, который требует методы с pointer receiver.

Совет: все методы типа — одного вида (все pointer или все value). Это сильно упрощает жизнь с интерфейсами.

## Addressability

Автоматическое взятие адреса работает только для addressable-значений:

```go
var c Counter
c.Inc() // OK: &c
```

Но не для значений в map и не для возвратов функций:

```go
m := map[string]Counter{"a": {}}
// m["a"].Inc() // ошибка
```

Для таких структур либо храни `*Counter`, либо заводи переменную.

## Когда это бьёт в бою

- Репозитории/сервисы передаются по указателю — поэтому их интерфейсы легко реализуют `*T`.
- Value objects (Money, Coord) обычно со всеми value receiver — к интерфейсам почти не подключают.
- Если тебе надо «тот же объект» в нескольких местах — всегда `*T` + интерфейс.
