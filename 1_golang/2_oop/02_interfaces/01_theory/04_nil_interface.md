# Nil interface — типовая ловушка

## Как устроен интерфейс внутри

Интерфейсное значение — это пара `(type, value)`:

- **dynamic type** — конкретный тип, лежащий внутри;
- **dynamic value** — указатель на данные (или само значение, если влезает).

Интерфейс **равен `nil` только тогда, когда оба поля равны `nil`**.

## Классическая ошибка

```go
func mightFail() error {
    var e *MyError // nil
    // ... условно мы ничего не присвоили
    return e // возвращаем nil-указатель типа *MyError
}

if err := mightFail(); err != nil {
    fmt.Println("ошибка!") // сработает, хотя *MyError == nil
}
```

Почему: `return e` упаковывает `(*MyError, nil)`. Интерфейс имеет известный тип `*MyError`, а значит он **не** равен nil-интерфейсу.

## Правильно

Если ошибки реально нет, возвращай **голый `nil`**:

```go
func mightFail() error {
    return nil
}
```

Или явно проверяй перед возвратом:

```go
if e == nil {
    return nil
}
return e
```

## Как это проявляется

- HTTP-хендлер всегда «возвращает ошибку» и статус 500 — смотри, как конструируется err.
- Тесты падают «ошибка не ожидалась» при корректной логике.
- `errors.Is/As` видят «какая-то ошибка есть», но «какая — непонятно».

## Проверка конкретного типа и nil

Иногда нужно различить «ошибок нет» и «ошибка есть, но *T-значение nil». Строго:

```go
var t *MyError
if errors.As(err, &t) && t != nil {
    /* честно есть MyError */
}
```

## Рекомендация

- Всегда возвращай `nil` как голый `nil`, если ошибки нет.
- Линтеры (`staticcheck`, `errcheck`) ловят самые очевидные случаи — включай.
- В сложных местах закладывай тест, который специально проверяет «ошибки нет».
