# any / interface{}

`any` — alias для `interface{}`, добавленный в Go 1.18. Технически они идентичны, разница только в читаемости.

## Зачем нужен

- Принимать значение любого типа.
- Работать с «динамическими» данными: JSON, конфиги, хранилища неизвестной формы.
- Collections до появления generics.

## Типичные места

```go
func Print(v any) { fmt.Println(v) }

var m map[string]any = json.Decode(data)

var cache map[string]any = make(map[string]any)
```

## С чем приходит

- Потеря типобезопасности — компилятор не знает, что внутри.
- Нужна type assertion/switch при работе с данными.
- Стоимость box'инга значений — пара байт и аллокация для многих случаев.

## any vs generics

Generics появились как раз, чтобы снять большую часть случаев `any`:

```go
// старое, теряем тип
func First(s []any) any { return s[0] }

// новое, сохраняем тип
func First[T any](s []T) T { return s[0] }
```

Generics предпочтительны, когда тип фиксирован на уровне вызова.

## Когда `any` оправдан

- Контейнер неизвестных на этапе компиляции типов (JSON, TOML, пользовательские аннотации).
- Decode → потом явный type switch или `errors.As`/конвертация по ключу.
- Универсальный логгер/принтер, работающий через reflection.

## Когда НЕ оправдан

- Простое «чтобы не писать тип». Это убивает подсказки IDE и отладку.
- Сигнатура типа в публичном API. Пользователь библиотеки должен понимать, что принимается.
- Слабо типизированные коллекции внутри одного модуля: почти всегда лучше конкретный тип или generic.

## Проверка типа после any

Чтобы безопасно вытащить значение:

```go
if v, ok := m["port"].(int); ok {
    _ = v
}
```

Никогда не делай `m["port"].(int)` без `ok` на внешних данных.

## Упрощённое правило

Если ты пишешь на современном Go — сначала думай в терминах generics и интерфейсов. `any` — это последнее средство, когда других способов действительно нет.
