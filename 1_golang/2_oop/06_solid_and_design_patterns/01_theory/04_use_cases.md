# 04. Практическое применение принципов и паттернов в Go

Как принципы SOLID, DRY/KISS/YAGNI и паттерны проектирования проявляются в
повседневной разработке на Go и на code review.

## Тестируемость через DIP

Самая частая практическая выгода SOLID — изолированные unit-тесты. Если
высокоуровневый код зависит от узкого интерфейса (DIP + ISP), объявленного у
потребителя, а не от конкретной БД или HTTP-клиента, в тесте подставляется
in-memory фейк — без сети и без реальной базы.

```go
type UserRepo interface{ FindName(id int) (string, error) }

type Greeter struct{ repo UserRepo }

func (g Greeter) Greet(id int) (string, error) {
	name, err := g.repo.FindName(id)
	if err != nil {
		return "", err
	}
	return "привет, " + name, nil
}
// В тесте подставляем fakeRepo, в проде — sqlRepo. Greeter не меняется.
```

## Middleware как цепочка декораторов

HTTP-middleware (логирование, аутентификация, метрики, `recover`) — это
Decorator + Chain of Responsibility поверх `http.Handler`. Добавление сквозной
функциональности не затрагивает бизнес-хендлеры (OCP).

```go
func WithLogging(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		log.Printf("%s %s", r.Method, r.URL.Path)
		next.ServeHTTP(w, r)
	})
}
// mux := WithLogging(WithAuth(businessHandler)) — стек обёрток.
```

## Strategy для сменных алгоритмов

Разные тарифы и скидки, способы сортировки, форматы экспорта, политики ретраев
— всё это стратегии. В Go подставляют func-значение или маленький интерфейс с
одним методом; `sort.Slice(s, less)` в стандартной библиотеке устроен именно
так.

## Functional options вместо разрастающихся конструкторов

Когда у конструктора появляется 4–5 необязательных параметров с разумными
значениями по умолчанию, functional options (`Option func(*Server)`) дают
расширяемое API без ломки сигнатуры и без «телескопических» конструкторов.

## Запахи кода на review (что искать)

- `switch` по типу, который дополняется при каждой новой сущности → просится
  интерфейс (OCP).
- Один тип делает всё (валидация + SQL + форматирование HTTP-ответа) →
  нарушение SRP.
- «Толстый» интерфейс с 15 методами, из которых потребитель вызывает два →
  нарушение ISP.
- Конкретная инфраструктурная зависимость (`*sql.DB`) прямо в бизнес-логике
  вместо узкого интерфейса → мешает unit-тестам (DIP).
- Абстракции, фабрики и плагины «на будущее» без текущего требования →
  нарушение YAGNI и KISS.

> ⚠️ Частый вопрос на собеседовании: как принципы SOLID связаны между собой?
> SRP даёт маленькие типы → из них естественно вырастают узкие интерфейсы
> (ISP) → потребитель зависит от абстракции (DIP) → новое поведение добавляется
> реализациями и декораторами без правок (OCP). А KISS/YAGNI не дают увлечься
> и наплодить абстракций сверх нужного.

> ⚠️ Частый вопрос на собеседовании: назовите практическую пользу DIP кроме
> «красоты». Тестируемость (подмена фейком без реальной БД), заменяемость
> реализации (сменить хранилище или провайдера без правки бизнес-логики) и
> разрыв компиляционных зависимостей между пакетами.
