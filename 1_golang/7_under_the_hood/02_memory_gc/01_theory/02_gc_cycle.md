# GC cycle

GC в Go — concurrent, mark-and-sweep, tri-color. Главные цели:

- Короткие STW-паузы (обычно < 1 ms).
- Предсказуемая нагрузка на CPU и память.
- Минимум работы для разработчика.

## Триколор-алгоритм (упрощённо)

Объекты делятся на три цвета:

- **white** — ещё не достигнутые, кандидаты на удаление;
- **grey** — достигнутые, дети ещё не сканированы;
- **black** — достигнутые, дети уже обработаны.

GC начинает с roots (стеки горутин, глобалы), красит их в grey. Берёт grey, помещает в black, грей-кает их детей. Когда нет grey — всё white собирается.

Конкурентно: программа работает параллельно. Барьеры (write barriers) гарантируют корректность, когда программа меняет ссылки во время сканирования.

## Фазы

1. **Sweep termination + mark setup** — короткая STW-пауза (~µs), включаются write barriers.
2. **Concurrent mark** — основная работа. Программа продолжает работать.
3. **Mark termination** — короткая STW (≤ 1 ms), завершение метки.
4. **Concurrent sweep** — освобождение white-объектов в фоне.

Фактических STW-пауз — две, и обе короткие.

## GOGC

`GOGC` — основной параметр настройки GC. По умолчанию 100.

- `GOGC=100` (default): следующий GC запускается, когда heap вырос на 100% от размера после прошлого. Баланс CPU и памяти.
- `GOGC=200`: реже GC, больше памяти, меньше CPU.
- `GOGC=off`: GC выключен. Только для специальных тестов.

## GOMEMLIMIT (Go 1.19+)

Мягкий лимит памяти процесса. GC становится агрессивнее по мере приближения к лимиту.

```
GOMEMLIMIT=4GiB ./app
```

Полезно в Kubernetes, чтобы не получить OOM, если pod лимитирован.

## Диагностика

```
GODEBUG=gctrace=1 ./app
```

Печатает каждую сборку:

```
gc 1 @0.012s 0%: 0.014+0.55+0.025 ms clock, ...
```

- `@0.012s` — момент запуска GC.
- `0%` — доля CPU, занятая GC.
- Тайминги: STW + concurrent mark + STW.

`runtime.ReadMemStats` дам ту же информацию из Go-кода.

## Что повышает нагрузку на GC

- Много мелких аллокаций (даже коротко-живущих).
- Большой heap — ему дольше делать mark.
- Сложные графы объектов с указателями.

## Что снижает нагрузку

- Stack-аллокации вместо heap (escape analysis).
- `sync.Pool` для коротко-живущих объектов.
- Использование value-типов вместо `*T` где можно.
- Аррайнг big slices без множества мелких объектов.

## Правило

GC в Go быстрый и обычно не нужен тюнинг. Если паузы заметны — снимай trace, смотри на размер heap и частоту GC. Чаще проблема в hot allocations, а не в самом GC.
