# Stack vs Heap

В Go ты редко выбираешь явно. Компилятор сам решает, где разместить значение. Но понимать решение полезно — это влияет на производительность.

## Stack

- Выделяется при входе в функцию, освобождается при выходе.
- Очень дёшево: фактически инкремент указателя.
- Ограничен размером стека goroutine (растёт динамически до 1 GB).
- Не нагружает GC.

## Heap

- Память живёт, пока есть ссылка.
- Аллокация дороже: нужно идти к аллокатору.
- За освобождение отвечает GC.
- Каждое значение в heap — потенциальный кандидат для GC-сканирования.

## Escape analysis

Компилятор анализирует, может ли значение «убежать» из своей области видимости. Если да — оно идёт в heap.

Типовые причины escape:

- возврат указателя на локальную переменную;
- передача указателя в функцию, которая «теряет» его (например, в горутину);
- помещение значения в interface (часто требует boxing'а);
- значение, чей размер компилятор не может определить статически.

Посмотреть результаты:

```
go build -gcflags="-m" ./...
```

Выведет, что куда «убежало».

```
./main.go:15:6: moved to heap: u
```

## Пример

```go
func newUser(name string) *User {
    u := User{Name: name}
    return &u // u escape'ит в heap
}

func processUser(name string) {
    u := User{Name: name}
    fmt.Println(u.Name) // u остаётся на stack
}
```

## Почему это важно

- Каждая heap-аллокация — нагрузка на GC.
- В hot path 1 alloc/op × 100k RPS = 100k аллокаций/сек.
- Перенос в stack — частая микро-оптимизация после профайла.

## Уменьшение escape

- Возвращай value, не pointer, если структура небольшая.
- Передавай большие данные через writer/buffer, а не возвращай большой slice.
- Используй `sync.Pool` для переиспользования.
- Избегай interface'ов в hot path — `any` всегда escape'ит.

## Когда heap нужен

- Объекты с временем жизни больше функции.
- Большие данные — на стек могут не поместиться.
- Связанные структуры (linked list, tree) — узлы по природе heap.

## Правило

В обычном коде escape analysis работает за тебя. Думать про stack/heap нужно только когда профайл (pprof) показал hot аллокации.
