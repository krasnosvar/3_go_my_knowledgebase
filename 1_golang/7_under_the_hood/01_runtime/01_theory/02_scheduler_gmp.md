# Scheduler: модель GMP

Go-планировщик — кооперативный многопоточный, реализован в user-space.

## Три сущности

- **G** (Goroutine) — единица работы. Структура с собственным стеком и состоянием.
- **M** (Machine) — OS-thread. Реальный системный поток, на котором runtime выполняет код.
- **P** (Processor) — логический «слот»/«token» для исполнения горутин. Number P задаётся через `GOMAXPROCS` (по умолчанию = NumCPU).

## Как они работают вместе

- Чтобы выполнить G, нужен M, который держит P.
- Каждый P имеет локальную очередь готовых G (run queue).
- Если у P пустая очередь — он ворует из очереди другого P (work stealing).
- Если M блокируется на syscall — runtime отдаёт его P другому M, чтобы не простаивал.

Это даёт хорошее использование CPU при смеси I/O и compute задач.

## Preemption

Раньше планировщик вытеснял горутину только в `function call`-точках. С Go 1.14 — асинхронное вытеснение (signal-based), что позволяет прерывать «жадные» вычислительные горутины.

Без preemption тысячи горутин могли бы простаивать, пока одна крутит CPU-bound цикл.

## Network poller

Сетевые операции не блокируют M. Внутренний поллер (`epoll`/`kqueue`/`IOCP`) подхватывает события и пробуждает соответствующие G.

Это позволяет одному M обслуживать тысячи сетевых горутин — основа высокой производительности Go-серверов.

## Идеальная нагрузка

Go хорошо себя чувствует, когда:

- горутин намного больше, чем M (тысячи, миллионы);
- работа смешанная: I/O + немного compute;
- нет глобальных блокировок, которые сериализуют всё.

## Когда планировщик становится узким местом

- Тысячи горутин, лезущих за один mutex — будет contention, не паралелизм.
- Один CPU-bound монстр на 8-ядерной машине без `runtime.Gosched()` или регулярных yield-точек.
- Системные вызовы, не пускающие M — длительный native call.

## Как смотреть

```
GODEBUG=schedtrace=1000,scheddetail=1 ./app
```

Печатает раз в секунду состояние планировщика: сколько P, M, G, какой статус каждой.

`go tool trace trace.out` — визуализация с временной шкалой.

## Правило

Планировщик «просто работает» в 99% случаев. Если кажется, что нет — снимай trace и смотри, реальная ли это проблема, или ожидание external-системы.
