🧩 1. Что такое runtime в Go

runtime — это часть стандартной библиотеки Go, написанная на Go и на C/ассемблере, которая реализует:
планировщик горутин (scheduler),
сборщик мусора (GC),
управление стеком (grow/shrink stack),
взаимодействие с ОС (системные вызовы, сигналы),
инициализацию программы (init, main),
управление памятью (аллокатор, арены и т.д.).

Иными словами, runtime — это мини-операционная система внутри Go.
Когда ты компилируешь Go-программу, runtime встраивается прямо в бинарник (в отличие, например, от Python или Java, где нужен внешний интерпретатор или JVM).

⚙️ 2. Что делает планировщик (scheduler)
Планировщик отвечает за то, какая горутина и где выполняется.

Go использует модель M:N, где:
M — потоки ОС (threads),
N — горутины (логические задачи),
G — горутина (Goroutine),
P — процессор (Processor) — логическая сущность, обеспечивающая связь между M и G.

🔹 Коротко про G, M, P:
Объект	Что это	Количество
G	Горутина — функция с собственным стеком и состоянием	Миллионы
M	Поток ОС, который реально выполняет код	Около числа ядер
P	Планировщик, который выдает горутины M	Обычно = GOMAXPROCS

🔹 Как это работает:
Ты создаёшь горутину (go func() { ... }).
Runtime создаёт объект G и кладёт его в очередь P.
M (поток ОС), у которого есть P, берёт G и выполняет.
Когда G делает блокирующую операцию (например, syscall, channel recv, sleep), M может взять другую G — то есть выполнение переключается быстро и эффективно.
📘 Таким образом, Go обеспечивает кооперативную многозадачность без накладных расходов на системные треды.

🧱 3. Что именно из runtime попадает в бинарник
Когда ты делаешь:

go build main.go
Go:
Компилирует твой код и весь используемый стандартный код (runtime, fmt, time, и т.д.) в машинный код.
Линкует всё в один статически связанный бинарник.
(Поэтому бинарники Go большие — 2–10 МБ даже для “Hello, world”.)
Внутри бинарника есть:
твой код;
куски пакета runtime;
код GC, планировщика, memory allocator;
немного syscall и обёртки под конкретную ОС.
🧠 Даже если ты не импортируешь runtime явно, Go-компилятор всегда подключает его — это обязательная часть экосистемы.

🚀 4. Почему Go-программы "самодостаточные"
В отличие от языков вроде C или Python:
C зависит от libc (динамически или статически),
Python требует интерпретатор,
Go встраивает runtime прямо в бинарник → поэтому всё работает без внешних зависимостей.
Можно скопировать бинарник Go на чистую систему — и он запустится без библиотек, компилятора, интерпретатора и даже без интернета.

🔍 5. Что происходит при запуске Go-программы
Пошагово:
ОС загружает бинарник в память.
Выполняется runtime.rt0_go (ассемблерный код) — точка входа.
runtime инициализирует планировщик, память, стеки, GC.
Запускается runtime.main, который:
вызывает все init() из импортированных пакетов,
вызывает main.main().
Когда main.main() возвращается, runtime сразу завершает процесс (exit code 0) — остальные горутины не дожидаются и просто обрываются. Поэтому их ждут явно: sync.WaitGroup, каналы, context.

🧠 1. Как работает Go-шедулер с сетевыми операциями
Go использует асинхронную модель для сетевых вызовов.
Когда ты делаешь, например:
conn.Read(buf)
— этот вызов не блокирует реальный системный поток (thread).
Go-runtime использует сетевой поллер (обычно основанный на epoll / kqueue / IOCP в зависимости от ОС):
Когда горутина вызывает Read, рантайм вызывает pollDesc.WaitRead().
Если сокет готов — чтение выполняется сразу.
Если нет — шедулер паркует горутину (ставит её в “спящий” список) и отдаёт контроль другому runnable goroutine.
Meanwhile, сетевой поллер в отдельном системном потоке (обычно 1–2 per runtime) ждёт событий от ядра.
Когда ядро сообщает “socket готов к чтению”, поллер “будит” ту самую горутину.
→ В итоге: системные потоки никогда не простаивают из-за сетевых операций.

💾 2. А что насчёт операций с диском?
Вот тут начинается самое интересное 😄
💡 Основное отличие:
Go не имеет асинхронного поллера для файловой системы.
Когда ты делаешь:
data, err := os.ReadFile("/big/file")
или даже:
f.Read(buf)
— этот вызов блокирует системный поток, потому что стандартные системные вызовы (read(2), write(2), open(2), и т.д.)
на большинстве ОС не поддерживают неблокирующий I/O для обычных файлов.

⚙️ 3. Что делает Go runtime, чтобы это работало “гладко”
Рантайм распознаёт, что операция может быть блокирующей, и использует специальный механизм обёртки вокруг syscalls.
Если Go делает системный вызов, который может блокировать, шедулер временно “отвязывает” горутину от потока (M) и создаёт новый поток для обслуживания других горутин.
Примерно так:
G (горутина) выполняет f.Read()
↓
runtime enters syscall
↓
M помечается как "syscall блокирует"
↓
новый M создаётся и прикрепляется к тому же P (processor)
↓
шедулер продолжает выполнять другие горутины
↓
Когда syscall завершается, старая M возвращается и пробуждает горутину

📊 4. Ключевые различия
Тип I/O	Асинхронен?	Кто “следит” за завершением?	Как шедулер реагирует
Сеть (TCP, UDP, сокеты)	✅ Да	сетевой поллер (epoll/kqueue/IOCP)	Горутину паркуют, поток не блокируется
Файловая система	❌ Нет	ядро ОС (через обычный системный вызов)	Поток (M) блокируется, но Go создаёт новый для других горутин
Таймеры, sleep и т.п.	✅ Да	таймерный поллер runtime	Горутину паркуют
📎 5. Почему Go не делает асинхронный дисковый I/O

Потому что:
Для обычных файлов на Linux (ext4, xfs и т.п.) асинхронный I/O (aio) почти не работает стабильно.
В новых ядрах появился io_uring, но Go пока не интегрировал его в рантайм (есть эксперименты, например, gvisor/io_uring).
Поэтому Go runtime просто использует “one syscall per thread” и масштабируется за счёт большого пула M (потоков).
