# Stack и preemption

## Стек горутины

Каждая goroutine имеет собственный стек:

- Начальный размер ~2 KB (раньше было 8 KB).
- Растёт автоматически до 1 GB по умолчанию (`runtime/debug.SetMaxStack`).
- При нехватке runtime копирует стек в новое, большее место памяти.

Это резко отличается от классических OS-thread'ов, где каждый поток получает мегабайты стека сразу.

## Почему это важно

- Можно запускать миллионы горутин, не убивая память.
- Большая глубина рекурсии — ок, runtime сам растянет стек.
- Расширение стека требует копирования — небесплатно, но обычно незаметно.

## Stack overflow

Бесконечная рекурсия в Go завершается panic, но через несколько секунд: runtime пытается расширять стек, пока не упрётся в `MaxStack`. Тогда — runtime fatal error (а не recoverable panic).

```go
func loop() { loop() }
loop() // через ~1ГБ стека — fatal: stack overflow
```

## Preemption

Планировщик прерывает горутину в нескольких ситуациях:

- При вызове функции — runtime может «врезаться» (cooperative preemption).
- Раз в ~10 ms — асинхронное вытеснение (Go 1.14+).
- При блокировке (chan, syscall, lock).

Раньше тяжёлый `for { }` без вызовов функций мог захватить P навсегда. Сейчас такого нет.

## runtime.Gosched

```go
runtime.Gosched()
```

Подсказка планировщику: «отдай слот другим». Используется крайне редко — в особых local-tight-loop случаях. В современных версиях preemption сам справляется.

## Async preemption и signals

Async preemption работает через сигналы (SIGURG). Это значит:

- Сигнал-обработчики в Go должны быть устроены так, чтобы не путать.
- В debug-инструментах (`gdb`, `dlv`) можно увидеть периодические SIGURG — это норма.

## Goroutine starvation

Можно ли «загнать в угол» горутину так, чтобы её не запускали? Теоретически — да, в определённых патологических нагрузках. На практике — почти нет.

Если у тебя ощущение «горутина не выполняется» — почти всегда это:

- блокировка на канале / mutex / syscall;
- забытый `<-ctx.Done()`;
- goroutine leak.

## Правило

Стек растущий, preemption работает, ты редко с ними работаешь напрямую. Понимать модель полезно для диагностики, не для повседневного кода.
