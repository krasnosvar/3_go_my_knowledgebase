# unsafe

Пакет `unsafe` — обходит систему типов и систему памяти Go. Используется в редких случаях: интероп с C, экстремальная оптимизация, специальные структуры данных.

## Главная идея

`unsafe.Pointer` — нетипизированный указатель. Можно конвертировать **между разными типами указателей** через него:

```go
import "unsafe"

var i int64 = 42
p := unsafe.Pointer(&i)
fp := (*float64)(p) // одни и те же 8 байт интерпретируются как float64
```

Программа продолжит работать, но семантика непредсказуема.

## Зачем это вообще

1. **C-интероп** через `cgo` — большая часть `unsafe` именно там.
2. **Преобразование `string` ↔ `[]byte` без копии** (опасно):

```go
func bytes2string(b []byte) string {
    return unsafe.String(&b[0], len(b))
}
```

Эконмит копию, но если кто-то изменит исходный `b`, неизменяемая string — уже не неизменяемая. Приводит к глубоким багам.

3. **Низкоуровневые структуры данных**: lock-free queues, ring buffers с CAS-операциями.

4. **Сериализация фиксированного формата** через приведение byte-slice к struct.

## Что предлагает пакет

- `unsafe.Pointer` — нетипизированный указатель.
- `unsafe.Sizeof(x)` — размер типа в байтах.
- `unsafe.Alignof(x)` — выравнивание.
- `unsafe.Offsetof(struct.field)` — смещение поля внутри struct.
- `unsafe.Slice(ptr, len)` — слайс из указателя (Go 1.17+).
- `unsafe.String(ptr, len)` — строка из указателя (Go 1.20+).
- `unsafe.StringData(s)` — указатель на байты строки.
- `unsafe.SliceData(s)` — указатель на массив слайса.

## Правила использования

Документация Go даёт **6 разрешённых сценариев** для `unsafe.Pointer`. Любой другой — UB:

1. Конвертация `*T1` → `unsafe.Pointer` → `*T2`, если `T1` и `T2` совместимы по layout.
2. Конвертация в `uintptr` для арифметики и обратно — в одной строке выражения.
3. Конвертация для системных вызовов через `syscall.Syscall`.
4. Конвертация `reflect.Value.Pointer()` или `UnsafePointer()` в `unsafe.Pointer`.
5. Конвертация `reflect.SliceHeader` или `StringHeader` (legacy, теперь предпочтительны `unsafe.Slice`/`unsafe.String`).
6. Использование с `Sizeof/Alignof/Offsetof`.

Любое другое — рискованно. GC может перемещать объекты, и сохранённый `uintptr` станет dangling.

## Опасности

- Утечки памяти: GC не следит за `unsafe.Pointer` правильно во всех случаях.
- UB при неправильном layout — может работать сейчас и упасть после изменения структуры.
- `go vet` ловит часть случаев, но не все.

## Альтернативы

- `cgo` для C-кода.
- `encoding/binary` для бинарной сериализации.
- `sync/atomic.Pointer[T]` для типизированных atomic-указателей.
- Generics с `comparable` — для большинства типизированных задач.

## Правило

`unsafe` — последнее средство. Если решения через обычные типы и `atomic` нет, и причина — реальное узкое место (доказанное профайлом), тогда осторожно.

В большинстве проектов `unsafe` встречаться не должен.
