# Частые ошибки с context

## 1. Забыть `defer cancel()`

```go
ctx, _ := context.WithTimeout(parent, time.Second)
```

Таймер висит до истечения, ресурсы не освобождены. Всегда `defer cancel()`.

## 2. Передать nil

```go
doWork(nil) // panic при ctx.Done()
```

Если нет подходящего контекста, используй `context.TODO()` или `context.Background()`.

## 3. Хранить context в struct

```go
type Service struct { ctx context.Context }
```

Анти-паттерн: контекст теряет смысл «области жизни». Передавай `ctx` в методы.

Исключение: `http.Request` хранит контекст внутри — этот API сделал Go рано и уже не изменит.

## 4. Игнорировать `ctx.Err()`

```go
for job := range jobs {
    process(job) // никак не реагирует на отмену
}
```

Проверяй `ctx.Done()` в долгих циклах и возвращай `ctx.Err()`.

## 5. Использовать context.WithValue для бизнес-параметров

```go
ctx = context.WithValue(ctx, "amount", 100)
```

Бизнес-данные передаются явно в аргументах функции, а не через контекст.

## 6. Дедлайн, больший чем у родителя

```go
ctx, _ := context.WithTimeout(parent, 10*time.Minute)
```

Если у `parent` дедлайн через 1 секунду — `ctx` не «расширит» его. Это физически невозможно.

## 7. cancel() вызывают в другой горутине без синхронизации

Сам `cancel()` идемпотентен, но держать его как «шарящее состояние» между горутинами без правил — плохо. Обычно `cancel` — это `defer` в той же функции, где создан контекст.

## 8. Забыть о `context.Canceled` как нормальной ошибке

```go
if err != nil {
    log.Error(err) // не отличаем отмену от сбоя
}
```

Отмена — штатное завершение. Логировать её как error заливает метрики.

```go
if errors.Is(err, context.Canceled) {
    return nil
}
```

## 9. Длинные цепочки `WithValue`

Каждый `WithValue` — новый узел. Десятки подряд ухудшают производительность lookup и читаемость. Один раз — в начале запроса.

## 10. Context в init / глобальных переменных

```go
var ctx = context.Background()
```

Обычно плохой сигнал. Контекст живёт в рамках запроса/операции, а не пакета.
