# Deadlock

**Deadlock** — ситуация, когда две или больше горутин блокируют друг друга и никто не может продвинуться.

## Классический пример

```go
var a, b sync.Mutex

go func() {
    a.Lock()
    time.Sleep(time.Millisecond)
    b.Lock() // ждёт b
    b.Unlock()
    a.Unlock()
}()

go func() {
    b.Lock()
    time.Sleep(time.Millisecond)
    a.Lock() // ждёт a
    a.Unlock()
    b.Unlock()
}()
```

Горутина 1 держит `a`, ждёт `b`. Горутина 2 держит `b`, ждёт `a`. Тупик.

## Go runtime deadlock

Если **все** горутины заблокированы и никто не может проснуться, Go рантайм обнаружит это и паникует:

```
fatal error: all goroutines are asleep - deadlock!
```

Но если хотя бы одна горутина жива (пусть даже ничего не делает полезного), этот детектор не сработает.

## Классические источники

### 1. Порядок захвата mutex'ов

Если разные места кода захватывают одни и те же замки в **разном порядке** — deadlock становится вопросом времени.

Правило: определи глобальный порядок захвата и соблюдай его. Пример: «сначала `userMu`, потом `orderMu`, никогда наоборот».

### 2. Канал без получателя/отправителя

```go
ch := make(chan int)
ch <- 1 // блок навсегда, если никто не читает
```

Или:

```go
<-ch // блок, если никто не пишет
```

В main без goroutine — runtime deadlock. Внутри горутины — leak, не паника.

### 3. Повторный Lock обычного Mutex

`sync.Mutex` не re-entrant. Повторный `Lock` в той же горутине — deadlock.

```go
mu.Lock()
mu.Lock() // тупик
```

### 4. close закрытого канала

Не deadlock, а panic, но часто вызвано тем же классом ошибок.

### 5. WaitGroup с забытым Done

`wg.Wait()` будет ждать вечно.

## Предупреждение

- Не держать mutex во время I/O, вызовов пользовательского кода, блокирующих операций.
- Копировать состояние под замком, потом работать с копией без замка.
- Избегать «lock inside lock» — если нельзя, строго фиксировать порядок.
- Использовать `context.WithTimeout` для всего, что может повиснуть.

## Диагностика

- `GODEBUG=schedtrace=1000` — видно, сколько горутин в ожидании.
- pprof goroutine профиль — стек каждой заблокированной.
- Тайм-ауты и liveness probes в мониторинге ловят deadlock быстрее людей.

## Правило

Deadlock — почти всегда следствие непродуманного порядка синхронизации. Меньше замков и чёткий порядок их захвата — лучшая профилактика.
