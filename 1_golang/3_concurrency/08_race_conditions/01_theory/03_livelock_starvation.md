# Livelock и starvation

Эти баги тоньше deadlock'а: горутины не блокированы, но полезная работа не продвигается.

## Livelock

Горутины активно что-то делают, но состояние не меняется. Часто — реакция на чужой «конфликт»:

```go
// Две горутины, пытаясь не конфликтовать, откатывают операцию
for {
    if tryAcquire() {
        work()
        return
    }
    backoff() // и так обе горутины, по очереди
}
```

Все в рантайме, CPU греется — прогресса нет.

### Как избежать

- Разные backoff для разных горутин (jitter).
- Ограничение количества попыток + fallback.
- Чёткий протокол приоритета (кто первый — тот и успел).

## Starvation

Горутина **никогда не получает** доступ к ресурсу, потому что другие постоянно им пользуются.

Классика: `sync.RWMutex` и постоянный поток читателей блокирует писателя:

```go
// много читателей = писатель почти никогда не захватит Lock()
```

Go в рантайме старается смягчать, но гарантий справедливости нет.

### Типовые источники

- Долгий критический участок у одного игрока при высокой нагрузке.
- Жадный worker забирает все задачи из канала (если logic не распределяет равномерно).
- Приоритеты, где «низкий» не получает слота вообще.

### Как смягчать

- Ограничить время удержания ресурса.
- Batch-и разбивать на равные части.
- Тайм-аут на ожидание + fallback.
- Использовать `golang.org/x/sync/semaphore` с acquire по весу, если операции разной «тяжести».

## Зависание внешней стороны

Часто «горутина жива, но прогресса нет» — это не Go-проблема, а downstream: БД лагает, API отвечает медленно. Решение:

- Timeout в каждом внешнем вызове.
- Ретраи с backoff.
- Circuit breaker.

## Диагностика

- Мониторить latency и QPS, не только ошибки.
- Метрика «сколько времени горутина висит в состоянии Wait» — pprof goroutine.
- Heartbeat/ticker в worker'ах.

## Правило

Deadlock видно сразу (рантайм падает), livelock/starvation — нет. Это баги, которые всплывают только под нагрузкой. Лучший способ — тесты с concurrency + мониторинг в проде.
