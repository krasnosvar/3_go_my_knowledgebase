# Race detector

Go приходит со встроенным **data race detector**. Он — первый инструмент, к которому ты идёшь с вопросом «а есть ли у меня гонка».

## Как запустить

```
go run -race ./cmd/app
go test -race ./...
go build -race -o app ./cmd/app
```

Флаг `-race` включает инструментирование рантайма: каждое обращение к памяти логируется и сравнивается с другими.

## Что видим

При обнаружении detector печатает отчёт:

```
WARNING: DATA RACE
Read at 0x00c0000140a0 by goroutine 7:
  main.readValue()
      /path/main.go:42 +0x34

Previous write at 0x00c0000140a0 by goroutine 6:
  main.writeValue()
      /path/main.go:30 +0x64
```

- Адрес переменной, где конфликт.
- Стек-трейс обоих горутин.
- Отчёт идёт в stderr, тест провалится.

## Стоимость

- CPU: 5–10× медленнее.
- Память: 5–10× больше.
- Бинарник больше.

Поэтому `-race` в проде не используется, но в CI — must-have.

## Ограничения

- **Не** находит все гонки: ловит только те, что реально произошли во время run'а. Неактивные code path останутся скрытыми.
- **Не** находит deadlock, livelock, или race condition, не связанные с data race.
- Некоторые тесты становятся флаки из-за race detector — это сигнал, что гонка там есть, только проявляется редко.

## Встраивание в CI

Типичные настройки:

```
go test -race -timeout 5m ./...
```

Если в CI хотя бы раз-другой зарепортовал race — надо чинить. Игнорировать — плохая идея.

## Отключить для отдельного теста

Иногда нужно — редко. Пример: тест, специально делающий гонку, чтобы проверить хак.

```go
//go:build !race
```

Держи таких ровно ноль, если возможно.

## Альтернативы и дополнения

- Linters (`staticcheck`, `golangci-lint`) ловят часть заранее (copylocks, loop variable capture).
- `-trace` + `go tool trace` — пошаговая картина шедулинга.
- Внутренние инварианты + defensive checks в горячих местах.

## Практика

- Всегда прогоняй `-race` локально перед PR.
- Если race всплыл в CI — не «перезапускай до зелёного», читай отчёт и фикси.
- Новый код с concurrency пишется сразу с мыслью «прогоню race в тестах».
