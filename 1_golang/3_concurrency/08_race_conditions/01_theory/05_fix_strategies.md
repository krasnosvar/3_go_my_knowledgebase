# Стратегии исправления гонок

## 1. Локализовать shared state

Первый вопрос: нужен ли вообще общий доступ?

- Можно ли переменную сделать **локальной** для одной горутины?
- Можно ли передать **копию** значения, а не ссылку?
- Можно ли разделить данные по «shard'ам», где каждая горутина работает со своим куском?

Идеальный фикс — убрать shared state, а не защищать его.

## 2. Использовать правильный примитив

Если shared state остаётся:

- **Счётчик / флаг**: `sync/atomic`. Самый быстрый.
- **Несколько полей одновременно**: `sync.Mutex`.
- **Read-heavy**: `sync.RWMutex`, но измерь.
- **Передача данных** между горутинами: каналы.
- **Один раз выполнить**: `sync.Once`.

## 3. Ownership через канал

Идиома: у данных один владелец в момент времени. Передача — через канал:

```go
jobs := make(chan *Task)
// только receiver работает с task, отправитель больше его не трогает
```

Это не требует mutex'а: пока task в канале, его никто не трогает; кто получил — тот и владеет.

## 4. Copy-on-write + atomic.Pointer

Read-heavy + редкие обновления:

```go
var snapshot atomic.Pointer[Data]

// на read
d := snapshot.Load()
use(d)

// на write
newD := buildNewSnapshot()
snapshot.Store(newD)
```

Читатели не блокируются вообще, писатели периодически подменяют указатель.

## 5. Fix loop variable capture

До Go 1.22 переменная цикла «одна на всё тело». Фикс — явный параметр в горутину или локальная копия. См. `01_goroutines/03_loop_capture.md`.

## 6. Защищённая ленивая инициализация

Классический паттерн «проверил nil → создал» — гонка. Фикс — `sync.Once` или `atomic.Pointer` + CAS.

## 7. Deadlock — унифицировать порядок

Если deadlock из-за mutex'ов, договорись о глобальном порядке захвата. Все участники должны знать это правило.

## 8. Добавить таймауты

Там, где операция может зависнуть — явный таймаут через `context`. Это не «фикс» гонки, но предотвращает бесконечное ожидание, когда гонка случается.

## 9. Проверка тестами

После фикса — тесты с `-race` под нагрузкой. Обычные unit-тесты часто не триггерят race; нужен ещё stress-тест:

```go
for i := 0; i < 1000; i++ {
    go do()
}
```

и `t.Parallel()` в нужных тестах.

## 10. Документировать инварианты

Если структура потокобезопасна — доку в комментарии: какие методы можно звать параллельно, какие только последовательно. Это спасает будущего автора от наступания на грабли.

## Общее правило

Сначала — проектирование: можно ли избежать shared state? Потом — правильный примитив. Последним — хаки в духе «у нас много контеншена, нужно что-то выдумывать».
