# Add / Load / Store

Три базовых атомарных операции.

## Add

Прибавляет значение и возвращает новое:

```go
var n atomic.Int64

new := n.Add(1)        // n == 1, new == 1
n.Add(-1)              // n == 0
```

- Атомарное «прочитать + прибавить + записать».
- Работает и с отрицательными значениями, делая вычитание.
- Для `Uint32/Uint64` есть особенности при отрицательных (используй `int` типы, если нужно вычитание).

### Типовой use-case

Счётчики метрик:

```go
var requests atomic.Int64

func handle(r *http.Request) {
    requests.Add(1)
    // ...
}
```

## Load

Читает текущее значение атомарно:

```go
v := n.Load()
```

- Без `Load` чтение из горячей переменной — **data race**, даже если пишем через `Add`. Race detector это ловит.
- `Load` — O(1), обычно почти бесплатно, но в hot loop миллиардов итераций заметно.

## Store

Записывает новое значение:

```go
n.Store(42)
```

- Полностью заменяет текущее значение.
- Полезно для «установки флага», «замены snapshot-а».

## Чтение/запись примитивом

```go
var n int64 = 0
n++               // НЕ атомарно
v := n            // НЕ атомарно (с точки зрения race detector)
```

Всегда через `Load/Store/Add` или соответствующие функции.

## Выравнивание на 32-bit

На 32-битных платформах `int64`/`uint64` должны быть выровнены по 8 байт. Если используешь процедурное API, переменная должна быть первой в struct или отдельной:

```go
type Stats struct {
    count int64 // должен быть первым на 32-bit!
    name  string
}
```

С типизированными `atomic.Int64` — это решается автоматически, структура выровнена.

## Производительность

Примерный порядок:

- `atomic.Load/Store` — ~1 ns.
- `atomic.Add/Swap` — ~5-15 ns.
- `mutex Lock/Unlock` — ~25-50 ns на незанятом, и заметно больше при contention.

Порядок разный от процессора и нагрузки — всегда бенчмарки, если критично.

## Ошибки

- «Я прочитаю, подумаю, запишу» — это не атомарно. Нужен CAS.
- «Load два раза подряд» — между чтениями значение могло измениться.
- «Смешивать Atomic и обычный доступ» — гарантии уходят.
