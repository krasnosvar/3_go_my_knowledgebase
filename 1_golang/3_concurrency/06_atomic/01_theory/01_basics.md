# sync/atomic: основы

Пакет `sync/atomic` даёт атомарные операции над целыми числами и указателями. Они быстрее mutex'а и не требуют критической секции.

## Что значит «атомарно»

Операция выполняется одним CPU-инструкцией (или их серией с гарантией отсутствия пересечений). Никакая другая горутина не увидит «полусостояния».

## API

С Go 1.19 рекомендуемый стиль — типизированные обёртки:

```go
var n atomic.Int64

n.Add(1)
v := n.Load()
n.Store(42)
old := n.Swap(100)
ok := n.CompareAndSwap(100, 200)
```

Есть варианты: `atomic.Int32`, `atomic.Uint32`, `atomic.Uint64`, `atomic.Bool`, `atomic.Pointer[T]`.

До 1.19 — процедурный стиль:

```go
var n int64
atomic.AddInt64(&n, 1)
atomic.LoadInt64(&n)
atomic.StoreInt64(&n, 42)
```

Работает, но нужно следить за выравниванием `int64` на 32-битных платформах. Типизированные обёртки это решают сами.

## Когда использовать

- Счётчики (успехов/ошибок, requests_total).
- Флаги (enabled/disabled, ready/not_ready).
- Указатели на неизменяемое состояние (config snapshot) с copy-on-write.

## Почему быстрее mutex

- Нет блокирующих системных вызовов.
- CPU-уровневые инструкции (`LOCK CMPXCHG` и аналоги).
- Отсутствует потеря времени на planner/scheduler.

## Когда НЕ использовать

- Нужно обновить несколько полей вместе — атомарность одной операции не даёт атомарности «транзакции». Возьми mutex.
- Нужно сложное условие: «увеличь, если не больше N» — делаем через CAS-loop, но часто проще mutex.
- Нужны операции над структурой — atomic работает только со словом (и теперь через `atomic.Pointer`/`atomic.Value`).

## Правила

- Переменная, с которой работает atomic, — **только атомарно**. Смешивание `atomic.Load` и обычного `=` делает код data race.
- Атомарность — на уровне слова. Мегаструктуру атомарно не подменишь без `Pointer[T]`/`Value`.
- Проверяй с `-race`.

## Типичная ошибка

```go
n := counter.Load() + 1
counter.Store(n) // НЕ атомарно: между Load и Store другая горутина могла изменить
```

Правильно:

```go
counter.Add(1)
```

или через CAS-loop для более сложной логики.
