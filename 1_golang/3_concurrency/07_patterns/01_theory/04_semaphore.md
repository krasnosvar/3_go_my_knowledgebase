# Semaphore

Семафор ограничивает число одновременных выполнений операции. В Go удобно реализуется через buffered-канал.

## Базовая идея

```go
sem := make(chan struct{}, n) // ёмкость = параллелизм

for _, job := range jobs {
    sem <- struct{}{}         // блок, если занято
    go func(j Job) {
        defer func() { <-sem }()
        process(j)
    }(job)
}
```

`sem` вмещает не больше `n` элементов → одновременно работает не больше `n` горутин.

## Почему `struct{}`

`struct{}` не занимает память — канал становится «минимальным сигналом». Вариант с `bool` работал бы, но бесплатно не бывает: 1 байт на каждый слот.

## Graceful acquire

Если ожидание захвата тоже должно уважать отмену:

```go
select {
case sem <- struct{}{}:
    // захватили
case <-ctx.Done():
    return ctx.Err()
}
```

Так горутина не залипает, если глобальная отмена пришла раньше, чем место в семафоре.

## Release

Всегда `defer func() { <-sem }()`. Без defer легко забыть release при panic или ранних return'ах — и семафор постепенно «затянется» до полной блокировки.

## Альтернатива: `golang.org/x/sync/semaphore`

Библиотека даёт:

- `Acquire(ctx, n)` — можно захватывать сразу несколько «слотов»;
- `TryAcquire(n)` — non-blocking;
- `Release(n)` — соответствующий возврат.

Удобно для случаев «взял 4 слота из 10», когда задача стоит не единицу, а больше.

## Где применяется

- Ограничение параллельных HTTP-запросов к внешнему API (чтобы не получить rate limit).
- Ограничение одновременных обращений к БД (не превышать connection pool).
- Квотирование ресурсов: «не больше M тяжёлых задач одновременно».
- Подавление burst'ов во время массовой обработки.

## Ошибки

- Ёмкость = 0 или 1 без реальной причины → последовательность, не параллелизм.
- Захватил, но не освободил на error-path → утечка слота.
- Семафор глобальный, но каждый модуль создаёт свой → конфликт контроля concurrency.

## Когда семафор НЕ нужен

- Когда правильный размер — worker pool: фиксированное число worker'ов само ограничивает параллелизм.
- Когда ограничение эффективнее делать через rate limiter (по RPS, а не по параллелизму).
