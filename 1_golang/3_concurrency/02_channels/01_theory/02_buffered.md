# Buffered channels

Буфер у канала позволяет отправителю не блокироваться, пока в канале есть свободное место.

## Поведение

```go
ch := make(chan int, 3)
ch <- 1 // не блок: буфер 1/3
ch <- 2 // не блок: буфер 2/3
ch <- 3 // не блок: буфер 3/3
ch <- 4 // блок, пока кто-то не прочитает
```

Приём с пустого буфера — блок до первой отправки.

## Когда использовать

### 1. Smoothing (сглаживание burst-ов)

Producer выдаёт значения пачками, consumer работает медленнее. Буфер сглаживает пики.

### 2. «Result buffer size 1»

Популярная идиома для защиты от утечек:

```go
result := make(chan Res, 1)
go func() { result <- slowOp() }()

select {
case r := <-result:
    use(r)
case <-ctx.Done():
    // slowOp завершится и положит в буфер, горутина не застрянет
}
```

### 3. Semaphore

Ограниченное количество одновременных операций:

```go
sem := make(chan struct{}, 5)
for _, job := range jobs {
    sem <- struct{}{}
    go func(j Job) {
        defer func() { <-sem }()
        process(j)
    }(job)
}
```

5 горутин в работе одновременно.

## Когда НЕ использовать

- «На всякий случай большой буфер» — это маскировка проблем.
- Backpressure: буфер откладывает сигнал «потребитель не успевает», но не решает его.
- Синхронизация точек встречи — тут нужен unbuffered.

## Семантика буфера

Буфер — FIFO. Сохраняется порядок отправки.

## Ёмкость и длина

```go
len(ch) // сколько сейчас в буфере
cap(ch) // полная ёмкость
```

Применимо только к буферизованным.

## Что важно помнить

- Закрытый буферизованный канал отдаст все накопленные значения, потом даст `zero, false`.
- `len()` на канале — значение на момент вызова; в следующий миг может измениться.
- Ёмкость выбирается намеренно, а не «от балды». Если не знаешь, зачем — берёшь unbuffered.
