# Направленные каналы

Канал можно ограничить одной стороной. Это документация и страховка от ошибок.

## Типы

```go
chan int    // обе стороны
chan<- int  // только отправка
<-chan int  // только получение
```

Двунаправленный канал неявно приводится к однонаправленному, но не наоборот.

## В сигнатурах функций

```go
func producer(out chan<- int) {
    for i := 0; i < 5; i++ {
        out <- i
    }
    close(out)
}

func consumer(in <-chan int) {
    for v := range in {
        fmt.Println(v)
    }
}

func main() {
    ch := make(chan int)
    go producer(ch)
    consumer(ch)
}
```

Внутри `producer` нельзя читать из `out`, внутри `consumer` нельзя писать в `in`. Компилятор не даст ошибиться.

## Почему это важно

- Публичный API функции, принимающей канал, становится ясным: либо «я что-то туда кладу», либо «я оттуда беру».
- Защита от случайных ошибок, когда одна функция и пишет, и читает в один и тот же канал — это почти всегда ошибка дизайна.

## Получить полный канал обратно нельзя

```go
var w chan<- int = ch
// var full chan int = w // ошибка
```

Это by design: один раз сделав «только отправка», ты зафиксировал контракт.

## Использование в pipeline

```go
func generate(nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums { out <- n }
    }()
    return out
}
```

Возвращаемый тип `<-chan int` — «снаружи это только для чтения, не пытайтесь туда писать или закрывать».

## Практика

- Для аргументов-каналов публичных функций всегда ставь направленность.
- Возвращай `<-chan T` из конструкторов, если хочешь скрыть сторону записи.
- Внутри одного пакета двунаправленный канал часто удобнее и не хуже.
