# Channels: основы

Канал — это типизированная очередь для передачи значений между горутинами. Основной механизм коммуникации в Go: «Don't communicate by sharing memory; share memory by communicating.»

## Создание

```go
ch := make(chan int)       // небуферизованный
ch := make(chan int, 10)   // буферизованный, ёмкость 10
```

Нулевое значение канала — `nil`. Операции с nil-каналом блокируются навсегда (иногда используется специально в `select`).

## Отправка и приём

```go
ch <- 42     // отправить
v := <-ch    // принять
v, ok := <-ch // ok=false если канал закрыт и пуст
```

На небуферизованном канале отправка блокирует до тех пор, пока кто-то не прочитает. На буферизованном — блокирует, когда буфер полон.

## Закрытие

```go
close(ch)
```

- Отправка в закрытый канал — **panic**.
- Приём из закрытого — возвращает нулевое значение + `ok=false`.
- Закрывает только отправитель (owner), получателям это не нужно.

## Range по каналу

```go
for v := range ch {
    use(v)
}
```

Цикл выходит, когда канал закрыт и пуст. Классический паттерн consumer.

## Направленные каналы

Можно ограничить канал на чтение или запись:

```go
func producer(out chan<- int) { out <- 1 }
func consumer(in <-chan int)  { _ = <-in }
```

Компилятор не даст перепутать. Хорошая практика для публичных сигнатур.

## Сравнение с mutex

| | Mutex | Channel |
|---|---|---|
| Что защищает | shared state | поток значений |
| Когда выбирать | защищаю данные | передаю владение/сигналы |
| Производительность | быстрее на коротких секциях | чуть медленнее, но выразительнее |

## Размер канала

- `ch := make(chan int)` — отличный «synchronous handshake» для точек синхронизации.
- Буфер > 0 — нужен, если producer быстрее consumer'а и нет желания блокироваться.
- Большой буфер не «решает» backpressure, а только откладывает проблему.

## Главное правило

Получатель не закрывает канал. Отправитель — тот, кто единственно знает, что больше значений не будет.
