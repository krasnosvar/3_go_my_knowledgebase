# sync.RWMutex

`RWMutex` — mutex с разделением «много читателей ИЛИ один писатель». Читатели могут держать его одновременно, писатель — эксклюзивно.

## API

```go
var mu sync.RWMutex

mu.RLock()
defer mu.RUnlock()
// read-only секция

mu.Lock()
defer mu.Unlock()
// write секция
```

- `RLock / RUnlock` — для читателей.
- `Lock / Unlock` — для писателей.

## Когда применять

Стандартная эвристика: **read:write >= 10:1** и критическая секция заметна по времени. Например:

- кэш, который читают часто, обновляют редко;
- таблицы конфигураций;
- маппинги.

## Пример

```go
type Cache struct {
    mu    sync.RWMutex
    items map[string]string
}

func (c *Cache) Get(k string) (string, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    v, ok := c.items[k]
    return v, ok
}

func (c *Cache) Set(k, v string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.items[k] = v
}
```

## Ловушки

- RLock **не** re-entrant. Вложенный RLock в той же горутине может привести к deadlock, если в этот момент ждёт писатель.
- Overhead RWMutex выше, чем у обычного Mutex. На коротких секциях выигрыша может не быть.
- Писатели могут «голодать», если читатели всё время в очереди. Go смягчает это, но ориентироваться только на RWMutex для «read-heavy» без профайла — риск.

## Когда НЕ использовать

- Короткая критсекция — `sync.Mutex` быстрее.
- Запись сравнима по частоте с чтением.
- Нужна атомарность операций типа «инкремент» — `sync/atomic`.
- Нужна lock-free структура данных — `sync.Map` или специализированные библиотеки.

## Проверка

Перед выбором RWMutex запусти бенчмарк с обоими вариантами (`Benchmark*` на твоих нагрузках). Часто разница скромная или даже в пользу обычного Mutex.

## Combos

- `sync.RWMutex` + функция-обновлятор: читатели берут RLock, один писатель делает Lock и пересобирает состояние.
- Copy-on-write: читатели работают с неизменяемым снимком, писатели меняют указатель атомарно.
