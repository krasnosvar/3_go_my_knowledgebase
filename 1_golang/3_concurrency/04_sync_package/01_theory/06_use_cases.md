# Use-cases sync

## 1. Защита shared state → Mutex

Основа: счётчик, структура состояния, кэш с простой логикой.

```go
type Counter struct {
    mu sync.Mutex
    n  int
}
```

## 2. Read-heavy state → RWMutex

Кэш, который читают часто, пишут редко:

```go
type ConfigStore struct {
    mu    sync.RWMutex
    cfg   *Config
}
```

Плюс: несколько читателей одновременно.

## 3. Ленивая инициализация → Once / OnceValue

Один раз создать тяжёлый ресурс (логгер, БД-клиент):

```go
var dbOnce sync.Once
var db *sql.DB

func DB() *sql.DB {
    dbOnce.Do(func() { db = openDB() })
    return db
}
```

В Go 1.21+ короче: `sync.OnceValue`.

## 4. Ожидание набора горутин → WaitGroup

Для групп одновременных операций без возвращаемых значений. Если нужны результаты/ошибки — бери `errgroup`.

## 5. Условное ожидание → Cond (редко)

Когда условие сложнее, чем «канал пришёл / закрыт». Обычно можно обойтись каналом и context.

## 6. Переиспользование буферов → Pool

```go
var bufPool = sync.Pool{
    New: func() any { return make([]byte, 4096) },
}
```

Типично для hot path: JSON-сериализация, парсинг запросов, логгеры.

## 7. `sync.Map`

Concurrent map для двух сценариев:
- много операций чтения и мало вставок (snapshot-style);
- каждая запись обновляется только своей горутиной.

В остальных случаях обычная `map[K]V` + `sync.Mutex` проще и часто быстрее.

## 8. Atomic вместо mutex

Для счётчика/флага → `sync/atomic` (см. соседний раздел). Быстрее mutex и проще читается.

## Что НЕ делать

- Защищать одно значение mutex, если atomic подходит.
- Копировать структуры с sync-полями (Mutex, WaitGroup, Pool) — ломает внутренний state.
- Держать mutex во время I/O и долгих вычислений.

## Правило выбора

1. Можно сделать атомарно? → `sync/atomic`.
2. Нужно защитить несколько полей вместе? → `sync.Mutex`.
3. Очень асимметрично чтение/запись? → `sync.RWMutex`.
4. Нужно координировать горутины? → каналы / context.
5. Нужен один раз? → `sync.Once`.
6. Переиспользование буферов в hot path? → `sync.Pool`.
