# sync.Mutex

Mutex — базовый примитив взаимного исключения для защиты shared state.

## API

```go
var mu sync.Mutex

mu.Lock()
defer mu.Unlock()
// критическая секция
```

- `Lock()` — захватить; если захвачен — блок до освобождения.
- `Unlock()` — освободить. Освобождать должен тот же писатель, что захватил.

## Классическое применение

```go
type Counter struct {
    mu sync.Mutex
    n  int
}

func (c *Counter) Inc() {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n++
}

func (c *Counter) Value() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.n
}
```

## Правила

- Mutex защищает **данные**, не код. Думай «под замком — эти поля».
- Всегда парой: `Lock` + `Unlock`, через `defer` — нет риска забыть при `return`/`panic`.
- Mutex нельзя копировать: он хранит внутренний state. Передавай `*T`, не `T`.
- Критическая секция — как можно короче. I/O под mutex — почти всегда ошибка.

## Ошибки

### 1. Unlock без Lock

```go
mu.Unlock() // panic: sync: unlock of unlocked mutex
```

### 2. Повторный Lock

Обычный `sync.Mutex` не re-entrant: повторный `Lock` в той же горутине — deadlock.

```go
mu.Lock()
mu.Lock() // зависание
```

### 3. Lock на маленькой структуре внутри большой + копирование

```go
type Service struct { mu sync.Mutex }
s := Service{}
s2 := s // copy lock - vet предупредит, но не всегда ловит
```

Исправление: передавай `*Service`.

### 4. Долгая работа в критической секции

```go
mu.Lock()
externalHTTPCall() // очень плохо
mu.Unlock()
```

Длительные операции под mutex делают систему последовательной. Подумай: копию данных сделать и разблокировать, а потом работать.

## Когда выбрать mutex, а не канал

- Защита структуры (карта, список, счётчик).
- Короткие секции, где нужен лишь взаимный запрет.
- Критичен overhead (mutex быстрее канала).

## Когда канал лучше

- Передача значений от producer к consumer.
- Синхронизация «жду готовности».
- Передача владения объектом.
