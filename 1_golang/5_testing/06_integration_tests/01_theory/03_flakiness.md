# Flakiness — борьба с нестабильными тестами

Flake-тест — тот, что иногда проходит, иногда нет. Это худшее, что может случиться с CI: команды учатся «перезапускать», доверие к тестам падает.

## Источники flake

### 1. Зависимость от времени

```go
if time.Now().Sub(start) > 100 * time.Millisecond { ... }
```

100 мс на CI могут быть 10 мс или 2 секунды. Используй большие запасы или мокай время.

### 2. Сетевые таймауты

`http.Get("http://example.com")` без mock — внешняя сеть, неконтролируемая. Используй `httptest.NewServer` для управляемого сервера.

### 3. Параллельный доступ к общему ресурсу

Файлы, БД, глобальные переменные. См. предыдущий файл — изоляция.

### 4. Sleep как синхронизация

```go
go work()
time.Sleep(50 * time.Millisecond)
checkResult() // надеемся, что work закончил
```

Никогда не работает надёжно. Используй каналы, WaitGroup, channels с timeout.

### 5. Случайные значения

Тест использует `rand.Intn(100)` без seed → разные запуски проверяют разное. Фиксируй seed или генерируй детерминированно.

### 6. Order-dependent

Если `TestB` падает, когда `TestA` запущен раньше — тест зависит от порядка. Это всегда баг теста.

## Диагностика

Запуск много раз подряд:

```
go test -count=100 -run TestFlaky ./...
```

Если падает не каждый раз — значит, гонка. С `-race` шансы найти проблему вырастают.

CI флаки часто стабильно воспроизводятся в Docker-контейнере с лимитом CPU.

## Пример: ожидание события

Плохо:

```go
go produce()
time.Sleep(100 * time.Millisecond)
if !consumer.received { t.Fatal("not received") }
```

Хорошо:

```go
done := make(chan struct{})
go func() {
    produce()
    close(done)
}()
select {
case <-done:
case <-time.After(2 * time.Second):
    t.Fatal("timeout")
}
```

## Eventually-проверки

Иногда нужно «дождаться состояния»:

```go
deadline := time.Now().Add(2 * time.Second)
for time.Now().Before(deadline) {
    if check() { return }
    time.Sleep(10 * time.Millisecond)
}
t.Fatal("condition not met within timeout")
```

Полезно для интеграционных тестов с consumer'ами.

## Не игнорировать

Если CI пометил тест flaky — НЕ исправляй «ретраем». Найди причину. Flake — это не «природа теста», это баг.

## Правило

- Никаких `time.Sleep` для синхронизации.
- Все зависимости от времени контролируемы (mock, фиксированный seed).
- Поломавшийся flake-тест — приоритет, а не «авось пройдёт».
