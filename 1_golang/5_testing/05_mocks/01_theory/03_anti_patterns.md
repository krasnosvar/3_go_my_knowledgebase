# Mocking: анти-паттерны

## 1. Mock everything

```go
type fakeFmtPrintf struct{}
func (fakeFmtPrintf) Printf(format string, args ...any) (int, error) { ... }
```

Не моки stdlib и тривиальные функции. Моки — только для **внешних зависимостей**: БД, HTTP, файлы, время.

## 2. Тестировать вызовы, а не поведение

```go
if mock.GetCalls() != 1 { t.Fatal("expected Get to be called once") }
```

Проверка «метод вызван N раз» иногда нужна, но часто — это проверка деталей реализации. Если сервис вернул правильный результат, не важно, сколько раз он сходил в репозиторий.

Прверь **наблюдаемое поведение**: возвращаемое значение, side-effect, эффект на mock state.

## 3. Mock-фреймворк ради красоты

```go
mock.On("Get", mock.Anything, 42).Return(User{}, nil).Once()
mock.On("Save", mock.Anything).Return(nil).Twice()
```

Это уже DSL внутри теста. Читать сложно, изменения болят. Hand-made fake часто проще.

## 4. Слишком жирный интерфейс

Если у `UserRepo` 12 методов, а сервис использует 2 — моки избыточно сложны. Сделай маленький интерфейс именно с теми 2 методами.

## 5. Mock как «копия реализации»

```go
type fakeRepo struct{}
func (fakeRepo) Get(id int) User {
    // имитируем точно ту же логику, что в постгресе
    return doSomeBusinessLogic(id)
}
```

Если fake повторяет бизнес-логику настоящей реализации — мы тестируем сами тесты, а не сервис. Лучше in-memory implementation с минимальной поддержкой нужных кейсов.

## 6. Моки время через интерфейс глобально

```go
type Clock interface { Now() time.Time }

func New(...clock Clock) *Service { ... }
```

Это работает, но добавляет шум во **все** конструкторы. Для одной точки в коде проще:

```go
var now = time.Now // в проде

func use() {
    t := now()
    // ...
}
```

В тесте — `now = func() time.Time { return fixed }`. Compromise между моками и глобалкой.

## 7. Моки для частной логики

Если функция приватная (`saveLocal`) — её не нужно мокать. Тестируй публичный метод, который её вызывает.

## 8. Моки без `Cleanup`

Mock устанавливает временную глобальную замену? Обязательно `t.Cleanup(...)` — иначе следующий тест получит твой mock.

## 9. Утверждение «строго N вызовов»

Часто хрупко: рефакторинг кода может изменить количество внутренних вызовов без изменения семантики. Мягче: «вызван хотя бы один раз», «вызван с такими аргументами».

## 10. Mock для тестов конкретной БД

Если хочется протестировать SQL-запросы — нужен **integration test** с настоящей БД (в контейнере). Mock SQL-драйвера тестирует мок, не запросы.

## Правило

- Моки — для границы наружу.
- Простой fake > mock framework.
- Тестируй поведение, а не вызовы.
