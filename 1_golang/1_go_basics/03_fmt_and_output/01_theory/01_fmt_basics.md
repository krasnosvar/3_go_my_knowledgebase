# Основы пакета fmt и вывод

Пакет `fmt` реализует форматированный ввод-вывод: печать в консоль, сборку строк, чтение ввода. Это первое, с чем сталкивается любая Go-программа. Здесь — базовые функции печати и куда попадает вывод. Детали вынесены в отдельные файлы (ссылки ниже).

---

## 1. Базовые функции вывода

- **`fmt.Print(...)`** — выводит аргументы в стандартный поток вывода (stdout). Пробелы между аргументами добавляются только если ни один из соседних не является строкой. Перенос строки в конце не добавляется.
- **`fmt.Println(...)`** — выводит аргументы, всегда разделяя их пробелами, и добавляет в конце перенос строки (`\n`).
- **`fmt.Printf(format, ...)`** — форматирует строку по шаблону с глаголами (`%v`, `%d`, `%s` и т.д.) и выводит её.

```go
fmt.Print("a", "b", 1, 2)   // ab1 2   (пробел только между 1 и 2 — оба не строки)
fmt.Println("a", "b", 1, 2) // a b 1 2\n
fmt.Printf("%s=%d\n", "n", 42) // n=42\n
```

Помимо печати в консоль есть родственные функции:

- **`fmt.Sprintf(format, ...)`** — то же, что `Printf`, но возвращает строку вместо печати. См. [03_sprintf_errorf.md](./03_sprintf_errorf.md).
- **`fmt.Errorf(format, ...)`** — форматирует строку и возвращает `error`; с `%w` оборачивает ошибку. См. [03_sprintf_errorf.md](./03_sprintf_errorf.md).
- **`fmt.Fprint/Fprintln/Fprintf(w, ...)`** — пишут в произвольный `io.Writer` (файл, сокет, `http.ResponseWriter`). См. [03_sprintf_errorf.md](./03_sprintf_errorf.md).
- **`fmt.Scan/Sscanf/Fscan(...)`** — чтение форматированного ввода. См. [04_scan.md](./04_scan.md).

---

## 2. Куда попадает вывод

```text
Print/Println/Printf  ──▶ os.Stdout
Fprint*(w, ...)        ──▶ любой io.Writer
Sprint*(...)           ──▶ возвращается как string
```

Важно различать потоки: **данные — в stdout, диагностику и ошибки — в stderr**. Это позволяет пайпить stdout в другую команду, не смешивая его с сообщениями об ошибках.

```go
fmt.Println(result)                       // данные → stdout
fmt.Fprintln(os.Stderr, "warn:", warning) // диагностика → stderr
```

## 4. О производительности

> ⚠️ Частый вопрос на собеседовании: почему не стоит вызывать `fmt.Sprintf`/`fmt.Printf` в горячих циклах (hot paths)?

Есть две причины:

- **Аллокации в куче (boxing).** Все функции `fmt` принимают аргументы как `...any`:

  ```go
  func Printf(format string, a ...any) (n int, err error)
  ```

  Значение базового типа при передаче в `any` упаковывается в интерфейс. Escape Analysis не может гарантировать, что оно не «убежит» за пределы стека, поэтому данные аллоцируются в куче.
- **Рефлексия.** Под капотом `fmt` использует пакет `reflect` для разбора типов аргументов в рантайме, что затратно по CPU.

Альтернативы для критичных участков:

1. Простая склейка — обычное `str1 + str2`.
2. Сборка строки из многих частей — `strings.Builder`.
3. Быстрое логирование — специализированные логеры без рефлексии (`uber-go/zap`, `rs/zerolog`).

В обычном CRUD это несущественно; принципиально только в hot path.
