# Defer, Panic и Recover

## 1. Defer: отложенный вызов

Вызовы `defer` откладывают выполнение функции до выхода из функции-родителя. Они добавляются в стек и выполняются в порядке LIFO (Last-In, First-Out).

### Три золотых правила defer

1. **Аргументы вычисляются немедленно**. Аргументы отложенной функции вычисляются в строке объявления `defer`, а не в момент фактического вызова.

   ```go
   i := 0
   defer fmt.Println(i) // выведет 0, а не 1!
   i++
   ```

2. **Порядок LIFO**. Несколько `defer` выполняются в обратном порядке объявления.

   ```go
   defer fmt.Println("1")
   defer fmt.Println("2")
   defer fmt.Println("3")
   // вывод: 3, 2, 1
   ```

3. **Доступ к именованному возврату**. Отложенная функция может читать и изменять именованные возвращаемые значения функции-родителя:

   ```go
   func getNumber() (result int) {
       defer func() {
           result++ // меняем именованное возвращаемое значение
       }()
       return 1 // вернёт 2!
   }
   ```

## 2. Panic и Recover

`panic` — это исключительная ситуация, прерывающая обычный ход выполнения программы.

### Разворачивание стека (Stack Unwinding)

Когда происходит `panic`, выполнение текущей функции прерывается, но **все её отложенные `defer`-функции выполняются**. Затем паника поднимается вверх по цепочке вызовов, выполняя `defer` на каждом уровне, вплоть до `main`, после чего программа аварийно завершается.

### recover()

`recover` восстанавливает работу программы после паники. Он работает **только** внутри функций, вызванных через `defer`. В обычном коде `recover` всегда возвращает `nil`.

```go
func safeRun() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("Восстановились после паники:", r)
        }
    }()

    panic("критическая ошибка воркера")
}
```

> ⚠️ **Частый вопрос на собеседовании**: почему `recover()` вызывают только внутри `defer`? Потому что после `panic` обычный код функции уже не выполняется — успевают отработать только отложенные вызовы. Именно в них есть шанс перехватить панику.

## 3. Когда defer НЕ выполнится

Существует несколько сценариев, при которых отложенные через `defer` вызовы не будут выполнены.

### os.Exit()
```go
func main() {
    defer fmt.Println("не выполнится")
    os.Exit(0) // defer игнорируется
}
```

### Паника без recover (программа аварийно завершается)

Это не исключение из правила: `defer` уже объявленных функций отработают при разворачивании стека, но необработанная паника затем доводит программу до аварийного завершения. Не выполнятся только `defer`, до которых выполнение не дошло, а также код после `panic`.
```go
func main() {
    defer fmt.Println("выполнится") // напечатается перед сообщением о панике
    panic("fatal error")
    // программа завершится аварийно (exit status 2)
}
```

### Бесконечный цикл
```go
func main() {
    defer fmt.Println("не выполнится")
    for {
        // бесконечный цикл, функция никогда не завершится
    }
}
```

### Deadlock
```go
func main() {
    defer fmt.Println("не выполнится")
    ch := make(chan int)
    <-ch // deadlock, программа зависнет
}
```

### Сигнал SIGKILL
```go
func main() {
    defer fmt.Println("не выполнится")
    // kill -9 <pid> убьёт процесс мгновенно
    time.Sleep(time.Hour)
}
```

### log.Fatal() / log.Panic()
```go
func main() {
    defer fmt.Println("не выполнится")
    log.Fatal("error") // вызывает os.Exit(1)
}
```

### Важно
- `defer` выполняется только при **нормальном выходе** из функции (в т.ч. при разворачивании стека паникой).
- `os.Exit()`, `log.Fatal()` обходят механизм `defer`.
- Системные сигналы типа SIGKILL не дают времени на cleanup.
