# panic / recover: границы применения

В Go бизнес-ошибки — это `error`, не исключения. `panic` и `recover` — это отдельный механизм для **действительно невосстановимых** ситуаций.

⚠️ Частый вопрос на собеседовании: когда использовать `panic`, а когда `error`.

- **`error`** — для ожидаемых и восстановимых сбоев: ошибка сети, неверный ввод пользователя, отсутствие файла при наличии дефолтов.
- **`panic`** — для критических ошибок программирования или инфраструктуры на старте: неверный синтаксис регулярки, заданной константой; невозможность занять порт при запуске сервера.

## Когда panic уместна

- Инварианты программы нарушены (например, «этот случай не должен случиться»).
- Инициализация не удалась и без неё процесс не имеет смысла (`log.Fatal` тоже допустим).
- Внутри библиотеки, чтобы индикатор был однозначным, но **на границе** её снова перевести в `error`.

## Когда panic НЕ уместна

- Валидация ввода — это `error`.
- Сетевые сбои, ошибки БД, файловая система — это `error`.
- «Чтобы не писать `if err != nil`» — это лень, не инженерия.

## recover

`recover()` работает только внутри `defer`. Типовая идиома — поймать panic на границе и превратить в `error`:

```go
func safeCall() (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("panic: %v", r)
        }
    }()
    doWork()
    return nil
}
```

## Где это нужно на практике

- HTTP-middleware `recovery`: если handler упал, не валим весь сервер — логируем и отдаём 500.
- Планировщик задач/воркер: одна задача не должна убить всю очередь.
- gRPC-interceptor с ту же идею.

Во всех случаях recover **локальный** и максимально узкий. Не ловим `panic` повсеместно, иначе теряем быстрые сигналы об ошибках.

## Сложная ошибка между горутинами

`recover` работает только в той же горутине. `panic` в одной горутине не ловится в другой. Каждая длительная горутина должна сама иметь `defer recover`, если её падение недопустимо.
