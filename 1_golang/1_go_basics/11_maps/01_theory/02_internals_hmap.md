# Внутреннее устройство мапы: Swiss tables (Go 1.24+) и `hmap` (до Go 1.24)

Мапа в Go — это указатель на служебную структуру из пакета `runtime`. Её реализация
менялась: **начиная с Go 1.24 мапы построены на Swiss tables**, а классическая
схема `hmap`/`bmap` с бакетами и overflow-бакетами — это устройство **до Go 1.24**.
На собеседованиях до сих пор часто спрашивают про старую схему, поэтому ниже разобраны обе.

Что не изменилось и важно для кода:

*   порядок обхода `for range` по-прежнему специально рандомизирован;
*   значения мапы по-прежнему неадресуемы (`&m[k]` не компилируется);
*   мапа по-прежнему небезопасна для конкурентной записи;
*   `delete` по-прежнему не уменьшает выделенную память (см. [04_memory_delete.md](./04_memory_delete.md)).

## Go 1.24+: Swiss tables

```
                map header
         +---------------------+
         | used   (count)      |
         | seed                |
         | directory  -------> | [table0][table1][table2]...   (extendible hashing)
         +---------------------+
                                     |
                                     v
                         table (до 1024 слотов)
         +-----------------------------------------------------+
         | group 0: [ctrl: 8 байт][slot0..slot7 (key+value)]   |
         | group 1: [ctrl: 8 байт][slot0..slot7 (key+value)]   |
         | ...                                                 |
         +-----------------------------------------------------+
```

*   **Group (группа)**: 8 слотов «ключ-значение» плюс **control word** — 8 байт, по одному на слот.
    Каждый control-байт хранит состояние слота (пусто / удалён / занят) и 7 младших бит хэша (`h2`).
*   **Поиск**: хэш делится на `h1` (старшие 57 бит — выбирают стартовую группу) и `h2` (младшие 7 бит).
    Внутри группы сравниваются сразу все 8 control-байтов с `h2` (SIMD-подобная битовая операция),
    и только у совпавших слотов сравниваются сами ключи. Если ключ не найден и в группе нет пустых
    слотов — проверяется следующая группа (квадратичное пробирование). Цепочек overflow-бакетов больше нет.
*   **Таблицы и рост**: мапа разбита на несколько независимых таблиц (directory, extendible hashing).
    Таблица растёт при заполнении > 7/8: удваивается до 1024 слотов, а дальше **делится на две**.
    Рост затрагивает только одну таблицу и происходит целиком во время вставки — глобальной
    постепенной «эвакуации» всей мапы, как до Go 1.24, больше нет.
*   **Маленькие мапы** (до 8 элементов) хранятся в одной группе без таблиц и directory.

В Go 1.24 старую реализацию можно было временно вернуть через `GOEXPERIMENT=noswissmap`.

## До Go 1.24: структура `hmap` и бакеты `bmap`

```
              hmap struct
         +-------------------+
         | count  (int)      |
         | flags  (uint8)    |
         | B      (uint8)    | ---> Количество бакетов = 2^B
         | buckets (pointer) | -+
         | oldbuckets        |  |  (старый массив во время роста)
         +-------------------+  |
                                |
                                v
                       Массив Buckets (bmap)
         +-------------------------------------------------+
         | Bucket 0: [tophash0..7][key0..7][val0..7][next] |
         | Bucket 1: [tophash0..7][key0..7][val0..7][next] |
         | ...                                             |
         +-------------------------------------------------+
```

### Основные элементы

*   **Buckets (Бакеты)**: массив структур `bmap`. Номер бакета для ключа — младшие `B` бит хэша.
    Каждый бакет вмещает ровно **8 пар ключ-значение**.
*   **Tophash**: массив из 8 байт (старшие 8 бит хэша каждого ключа) для быстрого пред-поиска ключей внутри бакета.
*   **Overflow Buckets**: если в бакет, уже заполненный 8 ключами, попадает 9-й ключ (хэш другой,
    но младшие `B` бит совпадают — то есть ключ относится к тому же бакету), аллоцируется
    дополнительный связанный бакет (overflow bucket), указатель на который записывается в конец текущего бакета.
*   **Эвакуация (Rehashing)**: когда среднее заполнение бакетов превышает 6.5 элементов (load factor > 6.5),
    Go аллоцирует новый массив бакетов в 2 раза большего размера (старый остаётся в `oldbuckets`)
    и переносит данные постепенно — по одному-двум бакетам **при каждой операции записи или удаления**.
    Чтение ничего не переносит: если нужный бакет ещё не эвакуирован, поиск идёт в `oldbuckets`.
    При слишком большом числе overflow-бакетов выполняется рост «того же размера» (same-size grow) — для уплотнения.

## Рандомизация обхода (Map Iteration Order)

Go специально рандомизирует порядок обхода элементов в цикле `for range`.
При каждом запуске итератора выбирается случайная стартовая точка (в старой схеме — случайный бакет
и смещение внутри него; в Swiss tables — случайные таблица и слот).

**Зачем это сделано?**
1. Физический порядок элементов в памяти меняется во время роста мапы.
2. Чтобы разработчики не закладывались на порядок элементов в мапе (как это часто происходило в языках, где обход детерминирован).

> ⚠️ Частый вопрос на собеседовании: сколько пар ключ-значение вмещает один бакет и что происходит при переполнении?
> Ответ для реализации до Go 1.24 — 8 пар, далее аллоцируется overflow bucket. В Go 1.24+ (Swiss tables)
> overflow-бакетов нет: группа тоже на 8 слотов, но при её заполнении ключ ищет место в следующей группе (пробирование).
