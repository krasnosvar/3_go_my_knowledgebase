# Service layer: pitfalls

## 1. God-service

```go
type Service struct{ /* 50 методов */ }
```

Один service на всё приложение → нечитаемо, трудно тестировать. Дели по domain'у: `UserService`, `OrderService`, `BillingService`.

## 2. Бизнес-логика в handler или repo

Если валидация переезжает в handler (потому что «удобнее»), а агрегаты считаются в repo (через хитрый JOIN) — service становится пустым. Это плохой знак: изменения логики начнут расползаться.

## 3. Service зависит от конкретной реализации

```go
type Service struct{ db *sql.DB }
```

Это ломает тесты (нужен реальный postgres) и делает код негибким. Service зависит от **интерфейсов**.

## 4. Нет интерфейсов вообще

Если все слои конкретные — каждый слой не отделим. Любое изменение в repo требует пересборки тестов сервиса. Тонкие интерфейсы решают.

## 5. Циркулярные зависимости

Service A → Service B → Service A. Признак плохого деления. Решения:

- Объединить в один service, если это правда одна область.
- Вынести общий код в отдельный пакет (без обращений вверх).
- Event-driven: service A эмитит event, service B слушает.

## 6. Игнорирование context

```go
func (s *Service) Heavy() {
    // долгая работа без ctx
}
```

Сервис не отменяется → утечки горутин при shutdown, ресурсы держатся после клиентского отключения. Всегда `ctx context.Context` первым параметром.

## 7. Возврат интерфейсов вместо структур

```go
func (s *Service) Get(id int) (UserDTO, error) // хорошо
func (s *Service) Get(id int) (interface{}, error) // плохо
```

Возврат `interface{}` теряет тип, ломает IDE-помощь, заставляет получателя ассертить.

## 8. Транзакции внутри repo

```go
func (r *Repo) UpdateAndAudit(...) {
    tx, _ := db.Begin()
    // 200 строк
}
```

Транзакция — это бизнес-операция. Её границы определяет service, не repo. Repo предоставляет методы, которые можно собрать в транзакцию (через `TxRunner`-абстракцию).

## 9. Service знает про HTTP-статусы

```go
func (s *Service) Get(id int) (User, int, error) {
    return User{}, http.StatusNotFound, ErrNotFound
}
```

Маппинг ошибки → статус живёт в handler. Service возвращает только `error`.

## 10. Side effects без логирования

Service отправил email, списал деньги, запустил job — но этого не видно в логах/метриках. Под нагрузкой искать «почему пользователь получил два welcome» становится квестом.

Используй `slog` с request_id из контекста, метрики через Prometheus, traces через OpenTelemetry. Это инструменты диагностики, без них service — чёрный ящик.

## Правило

Service — это **бизнес-логика на чистых интерфейсах**. Если что-то в нём пахнет HTTP, SQL или конкретными внешними системами — рефактори.
